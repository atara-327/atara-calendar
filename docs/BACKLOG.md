# バックログ（後でやること）

最初のバージョン（MVP）には入れないが、忘れずにやることのメモ。

## Claude 連携（MCP サーバー）

- 出典: 1次ヒアリング I3、2次ヒアリング M1〜M3
- 優先度: W（本体ができてから追加）
- 内容:
  - Claude から予定の確認・追加・編集・削除・サマリができる MCP サーバーを作る
  - 使う Claude: Claude Code / Claude Desktop（PC）。ローカルで動く MCP サーバーを想定
  - 許可する操作: 確認・サマリ・追加・編集・削除のすべて
  - 参考: Googleカレンダーの MCP（ツールの分け方・引数の設計）
  - 認証: Cloudflare Access のサービストークン（`CF-Access-Client-Id` / `CF-Access-Client-Secret` ヘッダー）で API を呼ぶ（3次ヒアリング K2）
  - MCP（サービストークン）から API を呼ぶときは `Sec-Fetch-Site` が付かないので、そのときの扱いを決める（今の API は same-origin だけを通す。[設計書 10.3](design/design.md#103-その他の対策)）
- 移行: MCP ができたら、今の Googleカレンダーの予定を Claude に移してもらう（Googleカレンダーの MCP で読み、こちらの MCP で書き込む）（3次ヒアリング E14）
- MVP の時点で気をつけること:
  - 後から MCP サーバーを付けやすいように、データの読み書きは API として整理しておく

## 技術的な改善

実装中に見つかった、MVP の後でよい改善。

- 時刻の 15 分刻みと色の `#RRGGBB` の確認を、書き込み用のスキーマ（`entrySchema`・`workspaceSchema`）から、入力用のスキーマへ移す
  - 出典: PR #10 のレビュー
  - Why: 入力のルールを書き込み用のスキーマに入れない理由と同じ（[設計書 4.2](design/design.md#42-テーブル定義)）。ルールを変えたときや、手での修正（[設計書 付録 A.3](design/design.md#a3-壊れた行が見つかったとき)）で、書き直せない行ができないようにするため。
  - ルールを厳しくする前に行う。
- 入力の長さの上限を「UTF-16 の単位で数える」とした文書（[設計書 4.2](design/design.md#42-テーブル定義)）と `src/shared/schema.ts` のコメントを、実際の数え方に合わせるか、サーバーも UTF-16 で数えるようにする
  - 出典: 実装 #10（PR のブラウザでの確認中に見つかった）
  - 今の動き: Zod 4 の `z.string().max(n)` は UTF-16 の単位で数えない（`z.string().max(1)` が、UTF-16 で 2 単位の絵文字を通す）。画面の入力欄（`maxLength`）とフォームの確認は UTF-16 で数えるので、サーバーより厳しく、フォームを通った入力をサーバーが断ることはない。逆に、API から入れた、文字の数では上限以内だが、UTF-16 では上限を超える名前（例: 絵文字 26 個のワークスペース名。上限は 50）のワークスペースは、画面の確認で断られ、色だけの変更もできない（ワークスペースの編集。[設計書 11.5](design/design.md#115-サイドメニューws-14)）。
  - Why 今は直さない: 利用者に見える不具合は、API から入れたとき（上の絵文字の名前）だけで、画面から入力したときには起きず、#10 の目的（サイドメニュー）と別の変更のため。文書とコメントが実際と違うままだと、後でこの決まりを信じて作業すると間違えるので、記録しておく。どちらに合わせるかは、そのときユーザーに確認する。
- 端末の「やり直し」が写している、サーバーの書き込みの判定を、`src/shared/` に移して 1 つにする
  - 出典: 実装 #6
  - Why: 端末（`src/client/sync/replay.ts`）は、サーバーの `commitEntries`・`applyWrite` の判定（新しい行の id のぶつかり・削除済みのワークスペースを指す行・編集時刻の比較）を、同じ決め方で写している。2 か所に同じ規則があると、片方だけを直して食い違う。今は、本物の Worker に同じ依頼を当てて、結果の全行が一致することを確かめるテスト（`replay.equivalence.test.ts`）で、食い違いに気づける。
- タブの錠を奪われた直後の隙間を埋める（古いタブの保存が、新しいタブの読み込みの後に入ると、次に開くまで送られない）
  - 出典: 実装 #6 のレビュー
  - Why: 古いタブが錠を失う直前に、編集を IndexedDB に書き始め、その書き込みが、新しいタブの送信待ちの読み込みより後に終わると、新しいタブは、その依頼を知らないまま動く。消えはしない（IndexedDB に残り、次に開いたときに送られる）が、それまで送られない。
  - 対策案: 動いているタブが、きっかけのたびに（受け取りと一緒に）、IndexedDB の、列に入っていないキーを読み足す。
- 書き込みに 200 の HTML（Access の案内ページなど）が返り続けても、利用者に知らせない
  - 出典: 実装 #6 のレビュー
  - Why: 応答の形が合わないときは、外さずに再び試す（[設計書 6.2](design/design.md#62-送る端末--サーバー)）ので、データは失われない。しかし、「未送信 N件」が減らないだけで、原因は分からない。続けて失敗したときの知らせ（[ロードマップ](ROADMAP.md)の、リリース前の持ち越し）と一緒に決める。
- keepalive の本文の上限（64KB）を超える依頼は、タブが裏に回っている間は送れない
  - 出典: 実装 #6 のレビュー
  - Why: keepalive を付けた fetch は、本文が 64KB を超えると失敗する。通信の失敗と同じに扱い、外さずに再び試すので、消えはしない（前面に戻ったときに送られる）。メモが最大の予定（10000 文字。数十 KB）でも、通常は収まる。
- 繰り返す予定の 1 回の長さ（何日にわたるか）に上限を設けるかを決める
  - 出典: PR #10 のレビュー
  - Why: 展開は、系列ごとに「1 回がかかる日数」だけ手前から探すので、何年にもわたる回は、画面と Worker の両方で CPU 時間を使い、回が重なって出るため。
- フォームを遅れて読み込む（lazy import）か、手で分割の境目を決める。画面のバンドルが、Vite の警告の 500kB を超えた
  - 出典: PR #20 のレビュー（実装 8a。494.54 kB → 515.38 kB）、PR #21 のレビュー（実装 8b。515.38 kB → 527.46 kB。レビュー指摘の修正の前は 524.93 kB）、実装 #9（527.46 kB → 536.73 kB）
  - Why: 最初の表示を軽くするため。今は、ビルドの警告が出るだけで、表示が遅くなったわけではない。ただし、画面の JavaScript は、起動時に全部読み込む方針（[設計書 6.5](design/design.md#65-電波がない間の動き)。電波がない間に、後から読み込めないため）なので、遅れて読み込む場合は、この方針との兼ね合いを先に決める。

### 削除済みのワークスペースを指して残った予定を、利用者が直せない

- 出典: 実装 #6 の確認 Q10（ユーザーの回答。恒久的な対策はしない）。元は、[ロードマップ](ROADMAP.md)の #6 の持ち越し
- 起きる条件: 2 台でほぼ同時に操作したとき。一方がワークスペースを削除し、もう一方が、そのワークスペースの予定を作る・変更する（書き込みが割り込まれたとき。[設計書 6.4](design/design.md#64-食い違ったときsy-3)）。
- 影響: 残った予定は、画面（`isInLiveWorkspace`）にも `GET /api/occurrences` にも出ず、通知もしない。その系列への「すべて」の変更と、その回の「この予定のみ」の削除は、毎回 `not_found` で捨てられるので、利用者は直せない。データは壊れない（見えないだけ）。
- 直す案の候補（やるなら）:
  1. 端末が、画面に出さない行（削除済みのワークスペースを指す、削除されていない行）を見つけたら、「すべて」の削除の依頼を、自動で作って送る。「すべて」の削除は、ワークスペースを確かめずに書ける（[設計書 4.2](design/design.md#42-テーブル定義)の、削除する行には確認を当てない）。
  2. サーバーの定期実行（実装 11b）で、そういう行を論理削除する。
  3. ワークスペースの削除の書き込みの後に、そのワークスペースを指す行を、もう一度読んで確かめる。

### 2 台でほぼ同時にワークスペースを削除すると、最後の 1 つまで消せる

- 出典: [ロードマップ](ROADMAP.md)の #10 の持ち越し（実装 #6 の確認 Q10 の方針で、ロードマップから移した）
- 起きる条件: 2 台でほぼ同時に、別々のワークスペースを削除する。最後の 1 つを守る確認（API の `last_workspace`。[設計書 4.2](design/design.md#42-テーブル定義)）は、書く前に、残りの数を読むので、2 台の確認が、お互いの書き込みの前に重なると、どちらも通る（[設計書 6.4](design/design.md#64-食い違ったときsy-3)の割り込み）。
- 影響: 利用者のワークスペースが 0 個になり、予定を作れなくなる（予定はワークスペースに属するため。EV-2）。データは壊れない。
- 復旧: ワークスペースの編集（[設計書 11.5](design/design.md#115-サイドメニューws-14)）で、新しいワークスペースを作る。0 個でも、編集のダイアログは開け、［＋ ワークスペースを追加］で作れる（実際のブラウザで確かめた）。
- 決めないこと: 利用者のワークスペースが 0 個のときの、画面の表示。

### 系列に壊れた行があると、ワークスペースの削除が 500 になる場合がある

- 出典: PR #25 のレビュー（実装 11a）
- 起きる条件: 別のワークスペースの系列に、構造が壊れた行（`CorruptRowError`。[設計書 6.3](design/design.md#63-受け取るサーバー--端末)）があり、その系列の例外が、削除するワークスペースを指している。ワークスペースの削除は、そういう例外を、その回を削除した形（`cancelled`）にして書く（[設計書 5.1](design/design.md#51-エンドポイント)）。11a から、書く行の系列の全行を、通知の時刻の計算（[設計書 9.2](design/design.md#92-保存したときの計算実装-11a)）のために読むので、その系列の、ほかの壊れた行も読まれる。
- 影響: 削除の依頼が 500 になり、端末の送信待ちの列が止まる（5xx は再送する。[設計書 6.2](design/design.md#62-送る端末--サーバー)）。データは壊れない。
- 復旧: 付録 A.3 の手順で、壊れた行を直す。
- **Why 対処しないのか**: 壊れた行は、`GET /api/changes` も 500 にする（付録 A.3）ので、この状況は、全端末の同期が止まって、すでに気づく状態にある。A.3 の手順で直せば、削除も通る。壊れた行を飛ばして書く仕組みを足すより、壊れた行を黙って通さない方針（[設計書 6.3](design/design.md#63-受け取るサーバー--端末)）と、コードの単純さを優先する。

### 範囲を聞く段を開いている間に、ほかの端末が系列の開始日を変えると、段の「保存後: …」と結果がずれる

- 出典: PR #21 の再レビュー（実装 8b）
- 起きる条件: 繰り返しの予定の範囲を聞く段（[設計書 11.4](design/design.md#114-フォームev-14tb-12)）を開いている間に、ほかの端末が、同じ系列の開始日を変え、それが受け取りで届く。送る前の確かめ直しは、選んだ範囲を「まだ選べるか」だけを見るので、範囲は選べたまま送られる。
- 影響: 段に出ていた「保存後: 毎月 5 日」と、実際に保存された結果が違う。結果は月表示で見えるので、気づいて直せる。データは壊れない。
