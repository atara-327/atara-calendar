## 1. 設計

- 追加の設計書は作りません。確定した設計書をもとに実装に入ります。
  - **Why**: 間違えると直しにくい部分（データの形・同期・繰り返し・祝日・認証）は、もう設計書で決めてあります。残っているのは、画面の細かい見た目や操作感です。これは文書で詰めるよりも、実際の画面を触りながら決めた方が早くて確実です。
- 実装の途中で、設計書にないことを決める必要が出たら、その都度確認して設計書に追記します。

- **持ち越しの確認（本番の CPU 時間で確かめる。祝日の計算は今すぐ、残りは #8 で予定を入れられるようになってから）**: 次の 4 つが、本番の CPU 時間（Cloudflare のダッシュボード）で収まっているかを確かめる。
  - 祝日の計算の CPU 時間（起動直後で約3〜5ms。Node での実測）。`GET /api/occurrences`（#4c）と、#11（通知）で次の通知時刻を計算するときに使う。**今すぐ測れる。**
  - 初回の全件読み込みの CPU 時間（Node の実測で、5000件の検証が約8ms ＋ JSON 化が約5ms）。#8 の後に測る。
  - 書き込みの CPU 時間（Node の実測で、3000行の検証と JSON 化が、初回 約33ms・温まった後 約6〜11ms）。大きなワークスペースの削除（中の予定をすべて書く）が CPU 時間の上限を超えると、遅いだけでなく、5xx になる。同じ依頼は何度送っても同じ時間がかかるので、再送しても直らず、端末の送信待ちの列が止まる。#8 の後に測る。
  - `GET /api/occurrences` 全体の CPU 時間（全行の読み込みと検証、祝日の計算、展開の合計。部品ごとの実測はあるが、合計は測っていない）。#8 の後に測る。
  - **Why**: 無料プランの Worker は CPU 時間が1回10ms までで（[設計書 付録A.2](design/design.md#a2-無料枠の見積もりnf-1)）、Node での実測だけでは、Worker で収まるかがわからないため。ローカルの workerd で測らないのは、Workers が安全のため、処理中の時刻の進み方を止めるので、ローカルでも CPU 時間を正確に測れないため。
  - **Why 時期が分かれるのか**: 祝日の計算は、データがなくても `GET /api/occurrences` が毎回行うので、今すぐ測れる。残りの 3 つは、本番にデータがないと測れない。予定を入れられるようになるのは #8（入力フォーム）からで、#6（同期）と #7（月表示）では入れられない。
  - 実測に足りる件数（数千件）が溜まらないときに、本番に試験データを入れるかは、そのときユーザーに確認する。**Why**: 本番のデータを書く操作で、後で消す手順も要るため。
- **解決済み（#4c）**: 繰り返しの展開の CPU 時間。`GET /api/occurrences` の期間を、最大31日にした（実測値は[設計書 5.1](design/design.md#51-エンドポイント)）。
  - **Why**: 無料プランの Worker は CPU 時間が1回10ms までなので、1年分の展開は収まらない。長い期間が必要な MCP は、区切って呼ぶ。
- **解決済み（#6）**: 同じ行を続けて編集するとき、`editedAt` を必ず増やす。端末で `max(今の時刻, 前に決めた値 + 1)` にした（[設計書 6.4](design/design.md#64-食い違ったときsy-3)。ユーザーの回答。実装 #6 の確認 Q1）。
  - **Why**: サーバーは `edited_at` が同じ依頼を「2 回目の送信」として捨てるので、同じミリ秒の 2 回目が、黙って消えるため。
- **#6 の持ち越し（結果）**: 次の 5 点を考えた。決めたものは「解決済み」、残すものは「残す」「バックログへ」と書いた。
  - **解決済み（#6）**: 4xx は、別の端末の新しい編集との組み合わせでも起きる（例: 別の端末がルールを変えた後に、変えていないルールを含む「この予定のみ」が届くと `invalid_change`）。端末は 4xx の依頼を捨てるので、画面の下に「保存できなかった変更が N 件あります」と知らせる（[設計書 6.5](design/design.md#65-電波がない間の動き)。ユーザーの回答。実装 #6 の確認 Q2）。200 の `applied: false`（別の端末の新しい編集に負けた・対象がもうない）は、知らせない。
  - **解決済み（#6）**: `edited_at_in_future` で捨てた編集は戻らない。時計が進んだ端末では、「端末の時計がずれています。時計を合わせてから、ページを開き直してください」と、上の知らせに添える（実装 #6 の確認 Q2・Q11）。
  - **解決済み（#6・#7）**: 書き込みが重なって、削除済みのワークスペースを指す予定が残ることがある。`GET /api/occurrences` と同じく、画面でも除く。除く判定 `isInLiveWorkspace`（`src/shared/workspace.ts`）を用意し、Worker も同じ関数を使う形にした（#6）。画面への適用は、期間の回の一覧を作る月表示で行った（#7。一覧を作る関数は、下の「解決済み（#7 の前）」で shared にした）。
    - **バックログへ**: そうなると、その系列への「すべて」の変更と、その回の「この予定のみ」の削除が、毎回 `not_found` で捨てられ、その回は画面で除かれるので、利用者も直せない。恒久的な対策はしない（ユーザーの方針。実装 #6 の確認 Q10）。[バックログ](BACKLOG.md#恒久的な対策をしないもの)に記録した。起きるのが、2 台でほぼ同時に操作したときだけで、データは壊れないため。
  - 捨てた理由（`reason`）が、意味の上では `stale` のときに、`not_found` になる場合がある。例: 「この予定のみ」の変更の 2 回目が、その回をなくした後の編集（ワークスペースの削除で `cancelled` にした行、別の端末の「この予定のみ」の削除）の後に届くと、`dropped` が系列の行の `edited_at` と比べるので、`not_found` になる（その回の編集は、例外の行に記録されている）。端末の扱い（列から外す）は同じなので、`reason` を利用者への知らせに使うときに考える。
    - **残す**: #6 の知らせは、件数と時計のずれだけで、`reason` を使っていない（200 の捨ては知らせない）。
  - **解決済み（#6）**: 応答を実行時に確かめるなら、行の部分は、構造だけを見るスキーマにする。構造だけのスキーマを `src/shared/structure.ts` に置き、端末の受け取りの確認に使った（[設計書 6.3](design/design.md#63-受け取るサーバー--端末)）。Worker の `rows.ts` の読み込みの確認とは、部品（id・日付・時刻・時刻の数）を共有した。バックログの移し替えは、#6 より前に行わなかった。元の問い: または、バックログの[「15 分刻みと色の確認を入力用のスキーマへ移す」](BACKLOG.md#技術的な改善)を、#6 より前に行う。**Why**: `src/shared/api.ts` の応答のスキーマは、行の部分が書き込み用のスキーマ（入力のルールを含む）なので、ルールを満たさない行が 1 つあるだけで、全端末の受け取りが止まるため（[設計書 6.3](design/design.md#63-受け取るサーバー--端末)）。
- **解決済み（#7 の前）**: 期間の回の一覧（繰り返しの展開と、削除済みのワークスペースの予定を除く処理）を `src/shared/period.ts` の `occurrencesInPeriod` に、期間の祝日・記念日の一覧を `src/shared/holidays.ts` の `namedDatesBetween` に移した。Worker の `GET /api/occurrences` は、この 2 つを呼ぶ形にした（[設計書 5.1](design/design.md#51-エンドポイント)）。月表示（#7）が、同じ関数を呼ぶ（`src/client/month/weekViewCache.ts`。[設計書 11.2](design/design.md#112-月表示mv-110)）。
  - **Why**: 画面と Worker で、回の一覧が食い違うと、「API には出ないのに画面には出る」ことが起きる。除く判定そのものは、#6 で `src/shared/workspace.ts` に移した。
- **持ち越しの確認**: 「予定」の色を、8 色のピーコックに合わせる（決め方は[設計書 4.2](design/design.md#42-テーブル定義)）。8 色は、月表示の画面を見て、案B に決まり（ユーザーの回答。実装 #7 の確認 Q1。2026-10-22）、値は #7 で[設計書 11.1](design/design.md#111-共通) に書いた。色を合わせるマイグレーションは、#7 の次に、別の PR で行う。
  - **Why 別の PR にするのか**: 月表示は、各ワークスペースに保存された色を出すだけで、8 色の値を使わないため。また、本番のデータを書き換える変更を、その PR だけで戻せるようにするため。
  - **Why**: 「予定」の色は、8 色が決まるまでの仮の値のため。
  - 「予定」の色を合わせるマイグレーションは、本番のデータを書き換えるので、ユーザーに確認してからマージする（[CLAUDE.md](../CLAUDE.md) の「PR とコミット」）。ユーザーは、「予定」が未編集のときだけ色を変え、`rev` を進める中身で、レビューが通ったらマージしてよいと許可した（2026-10-22）。
- **解決済み（マイグレーション 0002）**: 最初に開いたときに作るワークスペース「予定」が、2台で同時に初めて開くと二重にできる問題。マイグレーションで、固定の id の行として最初から入れる形にした（[設計書 4.2](design/design.md#42-テーブル定義)）。
  - **Why**: 固定の id なら、全端末で同じ 1 行になる。画面の「最初に作る」処理も要らなくなる。
- **持ち越しの確認（実機。#8 の後）**: 月表示の速く動かしたときの重さを、スマホで確かめる（[設計書 11.2](design/design.md#112-月表示mv-110)の「スクロールの重さ」。要件 NF-6）。実際のブラウザ（Chromium。CPU を遅くした）では、系列 120 件・単発 3000 件（実際の想定より重い）で、速くスクロールし続けて（約 7,500px/秒を 3 秒）、CPU を 4 倍遅くしても、フレームが 50ms を超えたのは 1 回で、6 倍では数回だった。重ければ、先読み（スクロールの向きの先のまとまりを、空き時間に計算する）か、系列の展開を速くすることを考える。
  - **Why**: ブラウザの CPU の絞り方は、実機のスマホとは同じではなく、実機の描画の重さは、測れていないため。
- **持ち越しの確認（実機。#8 の後）**: スマホの幅では、祝日名・記念日名が数文字で「…」に省かれる（マスが約 55px のため。時間指定の予定の時刻と、1 月 1 日の年は、幅に入らないので省いた。設計書 11.2）。実機で見て、名前の出し方（日表示で全文を見る、1 行目に出す、など）を決める。
  - **Why**: 要件 HD-1 は、祝日名も表示するとしているが、スマホの幅で、どこまで出せるかは、実機の画面で見ないと決められないため。
- **持ち越しの確認**: #8 で、削除の「元に戻す」のボタンの見た目を作る（画面の下に、5 秒間出す。[設計書 6.6](design/design.md#66-削除の元に戻すot-1)）。
  - **Why**: #6 では、仕組み（`engine.undo`）とテストだけを作り、ボタンは作っていないため。
- **持ち越しの確認**: #9 で、日から日への移動（DV-5）で履歴を積むと、日表示の「月表示に戻る」が、前の日に戻ってしまう。`goToMonth`（`src/client/navigation.ts`）は、この画面で積んだ履歴なら `history.back()` にしているため。#9 で、日から日への移動を `replaceState` にするか、`goToMonth` を直す。
  - **Why**: #7 の日表示は仮の画面で、月表示 → 日表示の 1 回の移動しかなく、`history.back()` で月表示に戻る。#9 で日から日への移動ができると、この前提が崩れるため。
- **持ち越しの確認**: #10 で、ワークスペースの削除でも、予定の削除と同じ「元に戻す」を出す（[設計書 6.6](design/design.md#66-削除の元に戻すot-1)。実装 #6 の確認 Q8）。
  - **Why**: #6 で、仕組み（`deleteWorkspace` の待ちと `undo`）は、ワークスペースの削除にも付けたが、ボタンの見た目は、ワークスペースの編集を作る #10 で作るため。
- **持ち越しの確認（実機。#8 の後）**: やり直しの計算量を、スマホで確かめる。画面に出すデータは、状態が更新されるたびに、すべての送信待ちの依頼を、全行の上でやり直して作り直す（依頼 1 つにつき、全行を走査する）。電波がない間に、編集を長く溜めたとき（依頼が数十〜数百件）に、編集のたびに引っかからないかを、実際の端末で確かめる。重ければ、作り直しを間引くか、行を系列ごとの索引で引く。
  - **Why**: テストは数件の依頼しか使っておらず、行が数千件のときの、依頼の数 × 全行の走査の重さを、実測していないため。
- **持ち越しの確認（リリース前。「試用・受け入れ確認」の前に決める）**: 画面を開いた後、受け取りが 5xx で失敗し続けても、利用者に知らせない。続けて失敗したときの知らせを、いつ・どう出すかを決める。あわせて、書き込みが再試行を続けて止まっているとき（5xx・API のエラーの形でない 4xx・200 の HTML）も、一緒に決める。
  - **Why**: 電波がないときと区別せずに、黙って再び試すので、壊れた行で `GET /api/changes` が 500 を返し続ける（[設計書 付録 A.3](design/design.md#a3-壊れた行が見つかったとき)）と、他の端末の編集が届かないまま、気づけないため。書き込みも同じで、「未送信 N件」が減らないだけで、原因が分からない（[バックログ](BACKLOG.md#技術的な改善)の、書き込みに 200 の HTML が返り続ける項目と同じ）。
- **持ち越しの確認**: #11 で、定期実行のクエリにも `deleted_at IS NULL` を付ける（部分索引を使うため）。削除済みのワークスペースの予定は通知しない。

## 4. 試用・受け入れ確認

- 要件定義書の要件 ID ごとに、満たしているかを確かめるチェックリストを作り、1つずつ確認します。
- 特に、次の点は実際の環境で確かめます。
  - iPhone・Android での月表示のスクロール（NF-6）
  - 電車の中を想定した、機内モードでの編集と、電波が戻ったときの同期（SY-2）
  - 通知が1分以内に届くか（NT-5）
  - ログインが1か月続くか（AU-2）
- 見つかった問題を直し終えたら、リリースします。
