## 1. 設計

- 追加の設計書は作りません。確定した設計書をもとに実装に入ります。
  - **Why**: 間違えると直しにくい部分（データの形・同期・繰り返し・祝日・認証）は、もう設計書で決めてあります。残っているのは、画面の細かい見た目や操作感です。これは文書で詰めるよりも、実際の画面を触りながら決めた方が早くて確実です。
- 実装の途中で、設計書にないことを決める必要が出たら、その都度確認して設計書に追記します。

- **持ち越しの確認（本番の CPU 時間で確かめる。祝日の計算は今すぐ、残りは 8a で予定を入れられるようになってから）**: 次の 6 つが、本番の CPU 時間（Cloudflare のダッシュボード）で収まっているかを確かめる。
  - 祝日の計算の CPU 時間（起動直後で約3〜5ms。Node での実測）。`GET /api/occurrences`（#4c）と、11a（保存したときの、次の通知時刻の計算）で使う。**今すぐ測れる。**
  - 初回の全件読み込みの CPU 時間（Node の実測で、5000件の検証が約8ms ＋ JSON 化が約5ms）。8a の後に測る。
  - 書き込みの CPU 時間（Node の実測で、3000行の検証と JSON 化が、初回 約33ms・温まった後 約6〜11ms）。大きなワークスペースの削除（中の予定をすべて書く）が CPU 時間の上限を超えると、遅いだけでなく、5xx になる。同じ依頼は何度送っても同じ時間がかかるので、再送しても直らず、端末の送信待ちの列が止まる。8a の後に測る。
  - `GET /api/occurrences` 全体の CPU 時間（全行の読み込みと検証、祝日の計算、展開の合計。部品ごとの実測はあるが、合計は測っていない）。8a の後に測る。
  - 保存したときの、次の通知時刻の計算の CPU 時間（11a。Node の実測は[設計書 9.2](design/design.md#92-保存したときの計算実装-11a)）。上の「書き込みの CPU 時間」に足される。本番で、PUT・PATCH の CPU 時間を、あわせて見る。
  - 定期実行の CPU 時間（11b。1 回の実行で、時刻が来た行を最大 10 行処理する。1 行の Node の実測は[設計書 9.3](design/design.md#93-定期実行で送る実装-11b)）。毎分動くので、本番のデータで、1 回の実行の CPU 時間（Workers の Cron Triggers の実行ごとの CPU 時間）を、数日見る。10ms を超える実行があれば、行数の上限（`MAX_DUE_ENTRIES_PER_RUN`）を下げる。1 回の実行の D1 の呼び出しが、無料プランのサブリクエストの上限（50 回）に収まっていること（設計書 9.3 の見積もりは最大 42 回）も、あわせて見る。
  - **Why**: 無料プランの Worker は CPU 時間が1回10ms までで（[設計書 付録A.2](design/design.md#a2-無料枠の見積もりnf-1)）、Node での実測だけでは、Worker で収まるかがわからないため。ローカルの workerd で測らないのは、Workers が安全のため、処理中の時刻の進み方を止めるので、ローカルでも CPU 時間を正確に測れないため。
  - **Why 時期が分かれるのか**: 祝日の計算は、データがなくても `GET /api/occurrences` が毎回行うので、今すぐ測れる。残りの 5 つは、本番にデータがないと測れない。予定を入れられるようになるのは 8a（入力フォーム）からで、#6（同期）と #7（月表示）では入れられない。
  - 実測に足りる件数（数千件）が溜まらないときに、本番に試験データを入れるかは、そのときユーザーに確認する。**Why**: 本番のデータを書く操作で、後で消す手順も要るため。
- **解決済み（#4c）**: 繰り返しの展開の CPU 時間。`GET /api/occurrences` の期間を、最大31日にした（実測値は[設計書 5.1](design/design.md#51-エンドポイント)）。
  - **Why**: 無料プランの Worker は CPU 時間が1回10ms までなので、1年分の展開は収まらない。長い期間が必要な MCP は、区切って呼ぶ。
- **解決済み（#6）**: 同じ行を続けて編集するとき、`editedAt` を必ず増やす。端末で `max(今の時刻, 前に決めた値 + 1)` にした（[設計書 6.4](design/design.md#64-食い違ったときsy-3)。ユーザーの回答。実装 #6 の確認 Q1）。
  - **Why**: サーバーは `edited_at` が同じ依頼を「2 回目の送信」として捨てるので、同じミリ秒の 2 回目が、黙って消えるため。
- **#6 の持ち越し（結果）**: 次の 5 点を考えた。決めたものは「解決済み」、残すものは「残す」「バックログへ」と書いた。
  - **解決済み（#6）**: 4xx は、別の端末の新しい編集との組み合わせでも起きる（例: 別の端末がルールを変えた後に、変えていないルールを含む「この予定のみ」が届くと `invalid_change`）。端末は 4xx の依頼を捨てるので、画面の下に「保存できなかった変更が N 件あります」と知らせる（[設計書 6.5](design/design.md#65-電波がない間の動き)。ユーザーの回答。実装 #6 の確認 Q2）。200 の `applied: false`（別の端末の新しい編集に負けた・対象がもうない）は、知らせない。
  - **解決済み（#6）**: `edited_at_in_future` で捨てた編集は戻らない。時計が進んだ端末では、「端末の時計がずれています。時計を合わせてから、ページを開き直してください」と、上の知らせに添える（実装 #6 の確認 Q2・Q11）。
  - **解決済み（#6・#7）**: 書き込みが重なって、削除済みのワークスペースを指す予定が残ることがある。`GET /api/occurrences` と同じく、画面でも除く。除く判定 `isInLiveWorkspace`（`src/shared/workspace.ts`）を用意し、Worker も同じ関数を使う形にした（#6）。画面への適用は、期間の回の一覧を作る月表示で行った（#7。一覧を作る関数は、下の「解決済み（#7 の前）」で shared にした）。
    - **バックログへ**: そうなると、その系列への「すべて」の変更と、その回の「この予定のみ」の削除が、毎回 `not_found` で捨てられ、その回は画面で除かれるので、利用者も直せない。恒久的な対策はしない（ユーザーの方針。実装 #6 の確認 Q10）。[バックログ](BACKLOG.md#恒久的な対策をしないもの)に記録した。起きるのが、2 台でほぼ同時に操作したときだけで、データは壊れないため。
  - 捨てた理由（`reason`）が、意味の上では `stale` のときに、`not_found` になる場合がある。例: 「この予定のみ」の変更の 2 回目が、その回をなくした後の編集（ワークスペースの削除で `cancelled` にした行、別の端末の「この予定のみ」の削除）の後に届くと、`dropped` が系列の行の `edited_at` と比べるので、`not_found` になる（その回の編集は、例外の行に記録されている）。端末の扱い（列から外す）は同じなので、`reason` を利用者への知らせに使うときに考える。
    - **残す**: #6 の知らせは、件数と時計のずれだけで、`reason` を使っていない（200 の捨ては知らせない）。

- **解決済み（#9）**: 日表示で、日から日への移動（‹ ›・スワイプ・［今日］）は、履歴を積まず、置き換える（`replaceDay`）にした。`goToMonth`（`src/client/navigation.ts`）は、この画面で積んだ履歴なら `history.back()` のままで、何日動いたあとでも、月表示に戻る（[設計書 11.3](design/design.md#113-日表示dv-16)）。
  - **Why**: 日ごとに履歴を積むと、［月表示］のボタン（`goToMonth`）も、スマホの「戻る」も、月表示ではなく、前の日に戻ってしまうため。#7 の日表示は仮の画面で、月表示 → 日表示の 1 回の移動しかなく、`history.back()` で月表示に戻れたが、#9 で日から日へ移れるようになり、この前提が崩れるため。
- **持ち越しの確認（実機。#9 の後）**: スマホで、日表示の操作感を、実機で確かめる。左右のスワイプと縦のスクロールの区別、15 分（15px）の項目の押しやすさ、空いているところのタップで決まる時刻（15 分単位）、今の時刻の線、画面の左端からのスワイプと、スマホ（Android）の「戻る」の操作との取り合い。実際のブラウザ（Chromium。412×830。タッチの操作を送った）では、スワイプで日が動くこと、縦のスクロールでは動かないこと、スワイプのあとにフォームが開かないことを確かめた（[設計書 11.3](design/design.md#113-日表示dv-16)）。
  - **Why**: 動き始めの向きを決める距離（8px）と、スワイプとみなす距離（60px）、15px の項目の押しやすさは、実機の指で見ないと分からないため。Android のジェスチャー操作では、画面の端からのスワイプが「戻る」に使われるので、日表示の左右のスワイプが、画面の端から始まったときに、どちらが効くかも、実機で見ないと分からない。
- **解決済み（#10）**: ワークスペースの削除でも、予定の削除と同じ「元に戻す」を出す。削除したあと、5 秒の間、「削除しました［元に戻す］」を、編集のダイアログの中に出す（[設計書 6.6](design/design.md#66-削除の元に戻すot-1)・[11.5](design/design.md#115-サイドメニューws-14)。実装 #6 の確認 Q8）。削除の前の確認（「中の予定 N 件も削除されます」）も、そのまま残した。
  - **Why**: #6 で、仕組み（`deleteWorkspace` の待ちと `undo`）は、ワークスペースの削除にも付けたが、ボタンの見た目は、ワークスペースの編集を作る #10 で作ることにしていたため。ダイアログの中に出すのは、モーダルが開いている間、画面の下の列は押せないため。
- **持ち越しの確認（実機。#10 の後）**: スマホで、サイドメニューとワークスペースの編集の操作感を、実機で確かめる。左から出るメニューの開閉（背景を押す・「戻る」・画面の端からのスワイプとの取り合い）、色の見本（36px）と［↑］［↓］（40px）の押しやすさ、削除のあとの「元に戻す」。実際のブラウザ（Chromium。412×830。タッチの操作を送った）では、開閉と履歴、色の選択、並べ替え、削除と元に戻すが動くことを確かめた（[設計書 11.5](design/design.md#115-サイドメニューws-14)）。
  - **Why**: 押しやすさの大きさと、Android のジェスチャー操作（画面の端からのスワイプが「戻る」に使われる）との取り合いは、実機の指で見ないと分からないため。
- **持ち越しの確認（実機。8a の後）**: やり直しの計算量を、スマホで確かめる。画面に出すデータは、状態が更新されるたびに、すべての送信待ちの依頼を、全行の上でやり直して作り直す（依頼 1 つにつき、全行を走査する）。電波がない間に、編集を長く溜めたとき（依頼が数十〜数百件）に、編集のたびに引っかからないかを、実際の端末で確かめる。重ければ、作り直しを間引くか、行を系列ごとの索引で引く。
  - **Why**: テストは数件の依頼しか使っておらず、行が数千件のときの、依頼の数 × 全行の走査の重さを、実測していないため。
- **持ち越しの確認（リリース前。「試用・受け入れ確認」の前に決める）**: 画面を開いた後、受け取りが 5xx で失敗し続けても、利用者に知らせない。続けて失敗したときの知らせを、いつ・どう出すかを決める。あわせて、書き込みが再試行を続けて止まっているとき（5xx・API のエラーの形でない 4xx・200 の HTML）も、一緒に決める。あわせて、通知の定期実行の失敗（壊れた行で止まる・Discord への送信が続けて失敗する。どちらも、今はログに出るだけ。[設計書 9.3](design/design.md#93-定期実行で送る実装-11b)）も、一緒に決める。
  - **Why**: 電波がないときと区別せずに、黙って再び試すので、壊れた行で `GET /api/changes` が 500 を返し続ける（[設計書 付録 A.3](design/design.md#a3-壊れた行が見つかったとき)）と、他の端末の編集が届かないまま、気づけないため。書き込みも同じで、「未送信 N件」が減らないだけで、原因が分からない（[バックログ](BACKLOG.md#技術的な改善)の、書き込みに 200 の HTML が返り続ける項目と同じ）。

- **解決済み（11b）**: 定期実行のクエリにも `deleted_at IS NULL` を付けた（部分索引 `entries_notify` を使うため。テストで、`EXPLAIN QUERY PLAN` が索引を使うことを確かめている）。削除済みのワークスペースの予定は、送るときに、11b が確かめて、通知しない。11a の計算は、ワークスペースを見ないので（[設計書 9.2](design/design.md#92-保存したときの計算実装-11a)）。決まりと理由は[設計書 9.3](design/design.md#93-定期実行で送る実装-11b)。
- **解決済み（11b）**: 送る直前に、その系列を読み直し、送る回が、まだ「その行の回」かを確かめる（`occurrenceNotifiedAt`）。もうその行の回でないときは、送らずに、今の展開で計算し直した値にする（[設計書 9.3](design/design.md#93-定期実行で送る実装-11b)）。

    - 系列を削除する保存の途中で、同じ系列の例外が作られると、系列のない例外に値が残る。
    - 2 台で同時に「この予定のみ」を保存すると、系列の行の値が、片方の例外を知らない計算で上書きされる。
- **解決済み（11b。PR #25 の再レビューの申し送り）**: 次の 2 つを守った。

    - **Why**: 保存が同じ瞬間に決めた新しい値を、定期実行が古い計算で上書きしないため。
