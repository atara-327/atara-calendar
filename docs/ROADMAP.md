## 1. 設計

- 追加の設計書は作りません。確定した設計書をもとに実装に入ります。
  - **Why**: 間違えると直しにくい部分（データの形・同期・繰り返し・祝日・認証）は、もう設計書で決めてあります。残っているのは、画面の細かい見た目や操作感です。これは文書で詰めるよりも、実際の画面を触りながら決めた方が早くて確実です。
- 実装の途中で、設計書にないことを決める必要が出たら、その都度確認して設計書に追記します。

- **持ち越しの確認（本番の CPU 時間で確かめる。祝日の計算は今すぐ、残りは #8 で予定を入れられるようになってから）**: 次の 4 つが、本番の CPU 時間（Cloudflare のダッシュボード）で収まっているかを確かめる。
  - 祝日の計算の CPU 時間（起動直後で約3〜5ms。Node での実測）。`GET /api/occurrences`（#4c）と、#11（通知）で次の通知時刻を計算するときに使う。**今すぐ測れる。**
  - 初回の全件読み込みの CPU 時間（Node の実測で、5000件の検証が約8ms ＋ JSON 化が約5ms）。#8 の後に測る。
  - 書き込みの CPU 時間（Node の実測で、3000行の検証と JSON 化が、初回 約33ms・温まった後 約6〜11ms）。大きなワークスペースの削除（中の予定をすべて書く）が CPU 時間の上限を超えると、遅いだけでなく、5xx になる。同じ依頼は何度送っても同じ時間がかかるので、再送しても直らず、端末の送信待ちの列が止まる。#8 の後に測る。
  - `GET /api/occurrences` 全体の CPU 時間（全行の読み込みと検証、祝日の計算、展開の合計。部品ごとの実測はあるが、合計は測っていない）。#8 の後に測る。
  - **Why**: 無料プランの Worker は CPU 時間が1回10ms までで（[設計書 付録A.2](design/design.md#a2-無料枠の見積もりnf-1)）、Node での実測だけでは、Worker で収まるかがわからないため。ローカルの workerd で測らないのは、Workers が安全のため、処理中の時刻の進み方を止めるので、ローカルでも CPU 時間を正確に測れないため。
  - **Why 時期が分かれるのか**: 祝日の計算は、データがなくても `GET /api/occurrences` が毎回行うので、今すぐ測れる。残りの 3 つは、本番にデータがないと測れない。予定を入れられるようになるのは #8（入力フォーム）からで、#6（同期）と #7（月表示）では入れられない。
  - 実測に足りる件数（数千件）が溜まらないときに、本番に試験データを入れるかは、そのときユーザーに確認する。**Why**: 本番のデータを書く操作で、後で消す手順も要るため。
- **解決済み（#4c）**: 繰り返しの展開の CPU 時間。`GET /api/occurrences` の期間を、最大31日にした（実測値は[設計書 5.1](design/design.md#51-エンドポイント)）。
  - **Why**: 無料プランの Worker は CPU 時間が1回10ms までなので、1年分の展開は収まらない。長い期間が必要な MCP は、区切って呼ぶ。
- **持ち越しの確認**: #6 で、同じ行を続けて編集するとき、`editedAt` を必ず増やす（同じミリ秒の2回目が「反映済み」として捨てられないように）。ユーザーに確認してから決める。
- **持ち越しの確認**: #6 で、次の 5 点を考える。
  - 4xx は、別の端末の新しい編集との組み合わせでも起きる（例: 別の端末がルールを変えた後に、変えていないルールを含む「この予定のみ」が届くと `invalid_change`）。端末は 4xx の依頼を捨てるので、捨てたことを利用者に知らせるかを決めるときに考える。
  - `edited_at_in_future` で捨てた編集は戻らない。時計が進んだ端末では、利用者に知らせる必要がある。
  - 書き込みが重なって、削除済みのワークスペースを指す予定が残ることがある。`GET /api/occurrences` と同じく、画面でも除く。
    - そうなると、その系列への「すべて」の変更と、その回の「この予定のみ」の削除が、毎回 `not_found` で捨てられ、その回は画面で除かれるので、利用者も直せない。直すかどうかは #6 で決める。
  - 捨てた理由（`reason`）が、意味の上では `stale` のときに、`not_found` になる場合がある。例: 「この予定のみ」の変更の 2 回目が、その回をなくした後の編集（ワークスペースの削除で `cancelled` にした行、別の端末の「この予定のみ」の削除）の後に届くと、`dropped` が系列の行の `edited_at` と比べるので、`not_found` になる（その回の編集は、例外の行に記録されている）。端末の扱い（列から外す）は同じなので、`reason` を利用者への知らせに使うときに考える。
  - 応答を実行時に確かめるなら、行の部分は、構造だけを見るスキーマにする。または、バックログの[「15 分刻みと色の確認を入力用のスキーマへ移す」](BACKLOG.md#技術的な改善)を、#6 より前に行う。**Why**: `src/shared/api.ts` の応答のスキーマは、行の部分が書き込み用のスキーマ（入力のルールを含む）なので、ルールを満たさない行が 1 つあるだけで、全端末の受け取りが止まるため（[設計書 6.3](design/design.md#63-受け取るサーバー--端末)）。
- **持ち越しの確認**: #10 で、最初に開いたときに作るワークスペース「予定」が、2台で同時に初めて開くと二重にできる。固定の id にして、マイグレーションで入れる案を、ユーザーに確認する。
- **持ち越しの確認**: #10 で、2台で同時にワークスペースを削除すると、最後の 1 つまで消せる（割り込み。[設計書 6.4](design/design.md#64-食い違ったときsy-3)で許容）。利用者のワークスペースが 0 個のときの画面の扱いを、上の「予定」の固定 id の確認と一緒に決める。
- **持ち越しの確認**: #11 で、定期実行のクエリにも `deleted_at IS NULL` を付ける（部分索引を使うため）。削除済みのワークスペースの予定は通知しない。
- 各 PR の作り方とマージの条件は、[CLAUDE.md](../CLAUDE.md) の「PR とコミット」を参照してください。

## 4. 試用・受け入れ確認

- 要件定義書の要件 ID ごとに、満たしているかを確かめるチェックリストを作り、1つずつ確認します。
- 特に、次の点は実際の環境で確かめます。
  - iPhone・Android での月表示のスクロール（NF-6）
  - 電車の中を想定した、機内モードでの編集と、電波が戻ったときの同期（SY-2）
  - 通知が1分以内に届くか（NT-5）
  - ログインが1か月続くか（AU-2）
- 見つかった問題を直し終えたら、リリースします。
