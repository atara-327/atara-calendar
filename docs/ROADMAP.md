## 1. 設計

- 追加の設計書は作りません。確定した設計書をもとに実装に入ります。
  - **Why**: 間違えると直しにくい部分（データの形・同期・繰り返し・祝日・認証）は、もう設計書で決めてあります。残っているのは、画面の細かい見た目や操作感です。これは文書で詰めるよりも、実際の画面を触りながら決めた方が早くて確実です。
- 実装の途中で、設計書にないことを決める必要が出たら、その都度確認して設計書に追記します。

## 2. 下準備（ユーザーの作業）

Claude はユーザーの Cloudflare アカウントや Discord を操作できません。そのため、ここはユーザーの作業になります。手順は [docs/setup.md](setup.md) にまとめています。

## 3. 実装の順番

| # | PR | 主な要件 | 順番の理由 |
| --- | --- | --- | --- |
| 1 | 雛形（Vite + React + Worker + Hono、Lint・テスト・CI） | — | 以降のすべての土台 |
| 2 | 日付・祝日・記念日の計算 | HD-1〜5、RP-5 | 画面がなくてもテストで正しさを確かめられて、間違えやすい部分だから先に固める |
| 3 | 繰り返しの展開と、変更・削除の範囲の処理 | RP-1〜6 | 同上。#2 の平日・休日の判定を使う |
| 4a | 認証とセキュリティ（Access の JWT の検証・他サイトからの書き込みの拒否・セキュリティヘッダー） | AU-1、NF-2 | 1つの PR を小さくして、スマホでもレビューしやすくするため。4a と 4b は互いに依存しないので並行して作れる |
| 4b | DB（マイグレーション・行の読み書き・食い違いの判定） | SY-1、SY-3 | 4a と同じ理由で分けた。画面がデータを読み書きする先の土台 |
| 4c | API（エンドポイントと入力チェック） | NF-5 | 4a の認証と 4b の読み書きを使うので、この2つのあとに作る |
| 5 | 本番へのデプロイ（GitHub Actions・Access の確認） | ENV-4、AU-2 | 早めに本物の URL を用意して、以降の画面を**実際のスマホで**確かめながら作るため |
| 6 | 同期とオフライン（送信待ちの列・差分の受け取り） | SY-2、OT-1 | 画面はすべて、この手元のデータから表示するため |
| 7 | 月表示（無限スクロール・階段状の線・横棒） | MV-1〜10、NF-6 | アプリの中心で、スクロールの滑らかさがいちばん大きな技術的リスク |
| 8 | 予定・タイムブロックの入力フォーム | EV-1〜4、TB-1〜6、RP-4 | ここまでで、予定を入れて月表示で見られるようになる |
| 9 | 日表示（タイムライン・重なり・スワイプ） | DV-1〜6 | — |
| 10 | サイドメニュー・ワークスペースの編集 | WS-1〜4 | — |
| 11 | 通知（1分ごとの定期実行・Discord） | NT-1〜6 | 予定のデータと繰り返しの処理がそろってから作る |

- **持ち越しの確認**: 祝日の計算の CPU 時間（起動直後で約3〜5ms。Node での実測）を、Worker（workerd）で実測する。#4c（API）で年をまたぐ範囲を返すとき、#11（通知）で次の通知時刻を計算するときに確かめる。
  - **Why**: 無料プランの Worker は CPU 時間が1回10ms までで（[設計書 付録A.2](design/design.md#a2-無料枠の見積もりnf-1)）、Node での実測だけでは、Worker で収まるかがわからないため。
- **持ち越しの確認**: 繰り返しの展開の CPU 時間（Node の実測で、系列100件の1年分が約34ms）。#4c で `GET /api/occurrences` の期間に上限を設けるか、展開を速くするかを決める。
  - **Why**: 無料プランの Worker は CPU 時間が1回10ms までなので、Node の実測の時点で、収まらない恐れがあるため。
- **持ち越しの確認**: 初回の全件読み込みの CPU 時間（Node の実測で、5000件の検証が約8ms ＋ JSON 化が約5ms）を、#4c で Worker（workerd）で実測する。
  - **Why**: 無料プランの Worker は CPU 時間が1回10ms までなので（[設計書 付録A.2](design/design.md#a2-無料枠の見積もりnf-1)）、Node の実測の時点で、収まらない恐れがあるため。
- **持ち越しの確認**: 書き込みの CPU 時間（Node の実測で、3000行の検証と JSON 化が、初回 約33ms・温まった後 約6〜11ms）を、#4c で Worker（workerd）で実測する。
  - **Why**: 同じく、無料プランの Worker は CPU 時間が1回10ms までで、Node の実測でも、初回は 10ms を超えているため。
- **持ち越しの確認**: #6 で、同じ行を続けて編集するとき、`editedAt` を必ず増やす（同じミリ秒の2回目が「反映済み」として捨てられないように）。ユーザーに確認してから決める。
- **持ち越しの確認**: #10 で、最初に開いたときに作るワークスペース「予定」が、2台で同時に初めて開くと二重にできる。固定の id にして、マイグレーションで入れる案を、ユーザーに確認する。
- **持ち越しの確認**: #11 で、定期実行のクエリにも `deleted_at IS NULL` を付ける（部分索引を使うため）。削除済みのワークスペースの予定は通知しない。
- 各 PR の作り方とマージの条件は、[CLAUDE.md](../CLAUDE.md) の「PR とコミット」を参照してください。

## 4. 試用・受け入れ確認

- 要件定義書の要件 ID ごとに、満たしているかを確かめるチェックリストを作り、1つずつ確認します。
- 特に、次の点は実際の環境で確かめます。
  - iPhone・Android での月表示のスクロール（NF-6）
  - 電車の中を想定した、機内モードでの編集と、電波が戻ったときの同期（SY-2）
  - 通知が1分以内に届くか（NT-5）
  - ログインが1か月続くか（AU-2）
- 見つかった問題を直し終えたら、リリースします。
