**全体で繰り返し出てくる考え方**（各章では、ここを指すだけにします）:

- <a id="p1"></a>**P1 同じ決まりは、同じコードで**: 画面・Worker・MCP が同じ判断をするときは、`src/shared/` の同じ関数を使い、決まりを書き写しません。**Why**: 書き写すと、片方だけを直して食い違います（「画面には出ているのに通知が来ない」「フォームを通った入力をサーバーが断る」）。
- <a id="p2"></a>**P2 4xx になる依頼を、画面から送らない**: 端末は、4xx の依頼を「直らない」として捨てます（[6.2](#62-送る端末--サーバー)）。捨てると、保存したはずの変更が画面から消えるので、フォームは、サーバーと同じ確認を先に行い、通らない入力は保存させません。
- <a id="p3"></a>**P3 ほぼ同時の操作の食い違いは、データが壊れない限り、恒久的な対策をしない**（ユーザーの方針）: 自分 1 人の利用で、まず起きないので、直す仕組みよりコードの単純さを優先します。当たるものの記録は、[バックログ](../BACKLOG.md#恒久的な対策をしないもの)にあります。
- <a id="p4"></a>**P4 API から入った、画面では作れない値は、表示だけして、勝手に書き換えない**: 題名だけ直したいのに、開いて保存しただけで、ほかの値が変わるのを防ぐためです（終日の通知の時刻・8 色以外の色など）。

## 1. 全体構成

```
 ブラウザ（PC・スマホ）          Claude Desktop（MCP。13章）
   │  https://calendar.ataraman.com   │ サービストークン
   ▼                                  ▼
 Cloudflare Access ……… Google ログイン。自分のアカウントだけ通す（AU-1・AU-2）
   │
   ▼
 Cloudflare Worker（1個）
   ├─ 静的ファイル配信 … 画面（React で作った HTML/JS/CSS）
   ├─ /api/*  ………………… データの読み書き（画面と MCP が使う）
   └─ scheduled ………… 1分ごとの定期実行。通知を探して Discord に送る（NT-5）
         │                         │
         ▼                         ▼
   Cloudflare D1（DB）        Discord Webhook
```

- **Why Worker を1個にまとめるのか**: 画面・API・定期実行で同じコード（日付の計算、繰り返しの展開、祝日の計算）を使うからです。デプロイも設定も1回で済みます。

## 2. 技術の選定

| 役割 | 使うもの | Why |
| --- | --- | --- |
| 言語 | TypeScript（画面・Worker の両方） | 同じロジックを1つのコードで共有するため（[P1](#p1)）。型で、日付と時刻の取り違えを防げる |
| 画面 | React 19 + Vite | 使っている人が最も多く、仮想スクロールのライブラリが成熟している（[Q1](#q1-画面のフレームワーク)） |
| 仮想スクロール | TanStack Virtual | 見えている週だけを描画するため（数万週を全部描画すると、スマホでカクつく。NF-6） |
| 画面の状態管理 | Zustand | 小さく、React の外（同期処理）からも更新できるため。同期のエンジン（[6章](#6-同期オフライン)）が store を持ち、React は読むだけにする |
| 画面の切り替え | History API で手書きする。ルーターのライブラリは使わない | 2画面だけで、依存を増やすほどではないため。URL が変わるので、スマホの「戻る」がそのまま使える（[11.2](#112-月表示mv-110)） |
| API | Hono | Workers 向けの小さなフレームワークで、ルーティングと認証チェックを簡潔に書ける |
| 入力チェック | Zod | 画面と API で同じルールを共有でき、MCP からの不正な入力も API で止められる |
| 天文計算 | astronomia（MIT）＋ 間引いた VSOP87 データ | 春分・秋分・夏至・冬至・立春を求めるため（[8章](#8-祝日記念日の計算)）。自作すると係数の書き写し間違いを見つけにくい。astronomia のデータはバンドルが重いので、振幅の小さい項を捨てたデータを使い、精度はテストで確かめる（[`src/shared/data/README.md`](../../src/shared/data/README.md)） |
| ライセンスの表示 | Vite の `build.license`（`/third-party-licenses.md`） | 依存パッケージのライセンス全文を成果物に含めるため（ソースのコメントはバンドルで消える）。絵文字の画像（Apache 2.0）は、ここに載らないので、全文を画像と同じ場所に出す（[11.1](#111-共通)） |
| DB アクセス | SQL を直接書く（ORM は使わない） | テーブルが3つしかないため |
| DB の変更管理 | wrangler の D1 マイグレーション | 標準で、追加の道具がいらない |
| 認証の検証 | jose | Cloudflare 公式のサンプルが使っている。Access が付ける JWT を検証する（[10章](#10-認証セキュリティ)） |
| オフライン中の保存 | IndexedDB（idb-keyval） | 未送信の変更を、タブが閉じられても失わないため（[6章](#6-同期オフライン)） |
| スタイル | CSS Modules + CSS 変数 | 追加の道具がいらない。色は CSS 変数にまとめる |
| テスト | Vitest | Vite と同じ変換で動く。設定ファイルは `vite.config.ts` と分ける（Cloudflare の Vite プラグインがあると、起動時にエラーになるため）。D1 は Miniflare（wrangler が依存する版に固定）、IndexedDB は `fake-indexeddb` を使い、自作の偽物にしない（実物との食い違いに気づけなくなるため）。`@cloudflare/vitest-pool-workers` は Vitest 5 に対応していないので使わない。同期のテストは、端末のエンジンを Miniflare 上の本物の Worker につなぎ、時計・電波・タブの錠だけを偽物にする。React の画面のテストは置かない（判断は `.ts` のテストで確かめる。[3章](#3-ディレクトリ構成)） |
| フォント・絵文字 | Noto Sans JP（@fontsource。自分のドメインから配信）・Noto Color Emoji の SVG 画像（`@iconify-json/noto` から、ビルドのときに作る） | NF-7。詳細は [11.1](#111-共通) |
| 静的チェック | ESLint + Prettier | 型チェックでは見つからない書き方のミスを見つけ、書式を揃えるため。my-budget と同じ道具 |

### 日付・時刻の扱い（全体の方針）

- 日付は `"2026-10-19"`、時刻は `"15:00"` という**日本時間の文字列**で持ちます。内部の計算では、日付を「1970-01-01 から何日目か」の整数に直して扱います（`src/shared/date.ts`）。時刻は 1 分刻みです（DV-3）。`24:00` は使わず、終わりが翌日の 0:00 なら、終了日を翌日にして `00:00` と書きます。
- 「今」の日付は、端末のタイムゾーンを使わず、UTC に9時間足して求めます。
- **Why**: 要件で日本時間に固定しており（ENV-3）、日本には夏時間がないので、日付の足し算は整数の足し算で正しく計算できます。ブラウザの `Date` をそのまま使うと、海外に行ったときなどに、日付がずれるバグが起きます。

## 3. ディレクトリ構成

```
atara-calendar/
├─ src/
│  ├─ shared/        画面・Worker・MCP が共有するコード
│  ├─ worker/        Cloudflare Worker（api/・db/・notify/・cron.ts・認証）
│  ├─ sw/            Service Worker（14章）。rules.ts が判断、sw.ts がイベントの受け取り
│  └─ client/        画面（React。month/・day/・form/・sidebar/・sync/・emoji/）
├─ mcp/             Claude Desktop の MCP サーバー（13章）
├─ migrations/       D1 のテーブル定義と、最初から入れる行（4.2）
├─ public/           そのまま配信するファイル（静的ファイルのヘッダー `_headers`・マニフェスト・アイコン `icons/`）
├─ scripts/          開発用のスクリプト（天文計算のデータの生成・MCP のビルド・アイコンの PNG の生成）
├─ vite-plugins/     Vite のプラグイン（絵文字の画像の生成［11.1］・`sw.js` の生成［14.2］）
├─ third_party/      配布物に含める、第三者のライセンス全文
├─ test/fixtures/    テストの正解データ（内閣府の祝日一覧・国立天文台の暦要項）
├─ test/helpers/     テストで共通に使う道具（ローカル D1、同期の端末、偽の時計・電波・錠）
└─ wrangler.jsonc    Cloudflare の設定
```

何をどこに置くか:

- **2 つ以上（画面・Worker・MCP）が必要なロジックは、必ず `src/shared/` に置く**（[P1](#p1)）。片方だけが使うものは置かない（例: 通知の計算は Worker の `notify/`）。
- 複数の画面が使うものは、`client/` の直下に置く。
- `client/` では、判断を持つ部分（状態・計算・文言の決め方）を、React に依存しない `.ts` に置き、`.tsx` は描画とイベントの受け取りにとどめる。**Why**: React の画面のテストは置かないので、判断を画面なしで確かめられるようにするためです。
- ブラウザや外部の機能（fetch・IndexedDB・履歴・時計など）は、環境（env）として引数で受け取る。**Why**: テストで偽物に差し替えるためです。
- 大文字小文字だけが違うファイル名は作らない（`Timeline.tsx` に対して `timelineGeometry.ts`）。**Why**: 大文字小文字を区別しないファイルシステムで、`./Timeline` が取り違えられるからです。

## 4. データ設計

### 4.1 テーブル一覧

| テーブル | 中身 |
| --- | --- |
| `workspaces` | ワークスペース。組み込みの「祝日」「記念日」も行として持つ |
| `entries` | 予定とタイムブロック。両方を1つのテーブルに入れる |
| `meta` | 同期用の通し番号など、1行だけの管理情報 |

- **Why 予定とタイムブロックを1つのテーブルにするのか**: 違いは「ワークスペースがあるか」「終日にできるか」「通知の初期値」の3点だけで、繰り返し・通知・同期・削除の処理は同じだからです。
- 祝日と記念日は DB に入れず、コードで計算します（[8章](#8-祝日記念日の計算)）。

### 4.2 テーブル定義

```sql
-- ワークスペース
CREATE TABLE workspaces (
  id         TEXT PRIMARY KEY,         -- UUID（端末側で発行する）
  name       TEXT NOT NULL,
  color      TEXT NOT NULL,            -- '#RRGGBB'。画面は用意した8色から選ぶ。サーバーは形だけを確かめる（11.5）
  sort_order INTEGER NOT NULL,
  visible    INTEGER NOT NULL DEFAULT 1,   -- 表示 ON/OFF（WS-3, Q3）
  builtin    TEXT,                     -- 'holiday' / 'observance' / NULL（WS-4）
  edited_at  INTEGER NOT NULL,         -- 端末で編集した時刻（ms）。食い違いの判定用
  rev        INTEGER NOT NULL,         -- 保存したときの通し番号。差分同期用
  deleted_at INTEGER                   -- 削除した時刻（論理削除）
);

-- 予定とタイムブロック
CREATE TABLE entries (
  id            TEXT PRIMARY KEY,      -- UUID（端末側で発行する）
  kind          TEXT NOT NULL CHECK (kind IN ('event', 'block')),
  title         TEXT NOT NULL,
  workspace_id  TEXT REFERENCES workspaces(id),  -- block は NULL（TB-3）
  all_day       INTEGER NOT NULL DEFAULT 0,      -- block は常に 0
  start_date    TEXT NOT NULL,         -- 'YYYY-MM-DD'
  start_time    TEXT,                  -- 'HH:MM'。終日なら NULL
  end_date      TEXT NOT NULL,         -- 終日: 最終日（その日を含む）／時間指定: 終わる日
  end_time      TEXT,                  -- 'HH:MM'。終日なら NULL
  location      TEXT,                  -- 場所の名前（地図へのリンクは画面で作る）
  url           TEXT,
  memo          TEXT,
  rrule         TEXT,                  -- 繰り返しのルール（JSON）。繰り返さないなら NULL
  until_date    TEXT,                  -- 内部用。「これ以降すべて」で切った系列の最終日
  series_id     TEXT,                  -- 例外の行のとき、元の繰り返し予定の id
  original_date TEXT,                  -- 例外の行が置き換える回の日付
  cancelled     INTEGER NOT NULL DEFAULT 0,      -- 例外で「この回だけ削除」したら 1
  notify_enabled    INTEGER NOT NULL,  -- 通知 ON/OFF（NT-4）
  notify_offset_min INTEGER NOT NULL,  -- 開始の何分前に通知するか（4.3）
  next_notify_at    INTEGER,           -- 次に通知する時刻（UTC の ms）。サーバーが計算する
  edited_at     INTEGER NOT NULL,
  rev           INTEGER NOT NULL,
  deleted_at    INTEGER
);
CREATE INDEX entries_rev    ON entries(rev);
CREATE INDEX entries_series ON entries(series_id);
CREATE INDEX entries_notify ON entries(next_notify_at)
  WHERE next_notify_at IS NOT NULL AND deleted_at IS NULL;

-- 管理情報（1行だけ）
CREATE TABLE meta (
  id    INTEGER PRIMARY KEY CHECK (id = 1),
  rev   INTEGER NOT NULL,              -- 最後に払い出した通し番号
  epoch TEXT NOT NULL                  -- データを復元したら変える値（付録A.1）
);
```

**最初から入れる行**（マイグレーション。細部と Why は、各 SQL ファイルのコメント）

- `meta` の 1 行。
- 組み込みのワークスペース 2 行（固定の id `builtin-holiday`・`builtin-observance`。WS-4）。**Why**: 全端末で同じ id である必要があり、表示の ON/OFF も同期の対象だからです（[Q3](#q3-ワークスペースの表示-onoff-をどこに保存するか)）。`edited_at` は 0 にして、端末からの最初の編集が必ず勝つようにします。
- 利用者の最初のワークスペース「予定」（固定の id `default-workspace`）。**Why マイグレーションで入れるのか**: 画面が最初に開いたときに作る方式だと、2 台がほぼ同時に初めて開いたときに「予定」が 2 つできるからです。色は、0002 では仮の値で入れ、8 色（[11.1](#111-共通)）を画面で見て決めたあと、0003 でピーコックに直しました。0003 は、**利用者が編集していないとき（`edited_at` が 0）だけ**色を変え（利用者が選んだ色を上書きしないため）、**`rev` を進めます**（進めないと、`since` を覚えている端末が受け取れないため）。
- `wrangler.jsonc` の D1 の `database_id` は、秘密の値ではないので、リポジトリに入れます。

**型とスキーマ**（`src/shared/schema.ts`）

- TypeScript の型は、Zod のスキーマから導きます（camelCase。DB の snake_case との変換は `src/worker/db/rows.ts`）。`rev` と `next_notify_at` はサーバーの都合の列なので、型には入れません。
- スキーマは、役割で 3 つに分けます。
  - **読み書き用**（`entrySchema` など）: 行の形。DB への書き込み（`store.ts`）が、全行をこれで確かめてから書きます（「書けた行は、必ず読める」ため）。
  - **入力用**（`*InputSchema`）: API の入力の検証（長さ・形式・範囲）。**Why 分けるのか**: 読み書き用に入力のルールを足して後で厳しくすると、すでに DB にある行が、更新できなくなるからです。
  - **構造だけ**（`rows.ts` と `src/shared/structure.ts`）: DB から読んだ行と、端末が受け取った応答の確認（[6.3](#63-受け取るサーバー--端末)）。
- **項目をまたぐ確認**（下）は、スキーマに入れず、`src/shared/entryRules.ts` の `entryProblem` で行い、API と画面のフォームが同じものを使います（[P1](#p1)・[P2](#p2)）。**Why スキーマに入れないのか**: object に refine を付けると、下書きや変更のスキーマを `pick` / `omit` で導けなくなるためです。

**入力の検証（API）**

| 項目 | 上限・形式 |
| --- | --- |
| `title` | 1〜200 文字 |
| `location` | 200 文字まで |
| `memo` | 10000 文字まで |
| `url` | 2048 文字まで。`http://` か `https://` で始まり、URL として読める形（[10.3](#103-その他の対策)）。値は黙って整えない。空にするなら `null` |
| ワークスペースの `name` | 1〜50 文字 |
| `id`（URL の `:id`・`workspaceId`・`newId` を含む） | `^[A-Za-z0-9-]{1,64}$`。端末が作る UUID と、固定の id の両方が通る形 |
| 日付の年 | 1900〜2199 年（[Q2](#q2-スクロールできる範囲)） |
| `notifyOffsetMin` | -1440〜10080 の整数。終日は 0:00 からの分なので負の値もあり（[4.3](#43-各項目の決め方)）、最大は 1 週間前 |
| `editedAt` | 0 以上の整数。サーバーの今より 10 分より未来なら 400（[6.4](#64-食い違ったときsy-3)） |

- **Why 上限を決めるのか**: 1 行が D1 の値の上限（約 2MB）に収まるようにするためです。年の範囲は、展開（[7章](#7-繰り返しの展開)）が回を生成するのが 1900〜2199 年だけで、範囲外の日付が通ると、回が 1 つも出ない系列ができるからです。
- 本文・`changes` などのオブジェクトは、知らないキーがあれば 400 にします（黙って捨てると、変わったと思い込ませるため）。
- ワークスペースの PUT では、`deletedAt` は `null` だけを通します（削除は DELETE。PUT で論理削除できると、下の保護をすり抜けるため）。

**項目をまたぐ確認（API）**

- 終日なら開始・終了の時刻は `null`、時間指定ならどちらも時刻がある。終了は開始より後（終日は終了日が開始日以降、時間指定は同じ日時も不可）。
- タイムブロックは、終日にできず、`workspace_id` は `NULL`。予定は `workspace_id` が必要で、そのワークスペースが存在し、削除されていないこと（削除済みなら依頼を捨て、存在しなければ 409。[5.1](#51-エンドポイント)）。
- 組み込みのワークスペースは、名前・色・`builtin` の変更と削除ができず、変えてよいのは `visible` と `sort_order` だけです。`builtin` を付けた作成も、付け外しもできません。予定は、組み込みのワークスペースを指せません（WS-4。いずれも 400 `builtin_workspace`）。
- 最後の 1 つの（組み込みでない）ワークスペースは、削除できません（400。[11.5](#115-サイドメニューws-14)）。
- 繰り返しのルールと `until_date` がある行は、`until_date` が開始日以降であること。**Why**: ルールを変えて、ルールに合う最初の日が `until_date` より後にずれると、回が 1 つもない系列になり、画面に出ないので直せないからです。
- 確認は、**サーバーが計算した後の、書く行にも当てます**（年の範囲も）。**Why**: 「すべて」の変更などで、変えていない項目との組み合わせが合わなくなったり、日付をずらす途中で年の範囲を出たりするからです。
- 削除する行には、当てません（確認が厳しくなる前に保存された行を、削除できなくなるため）。

**DB への書き込みの決めごと**（`src/worker/db/store.ts`。SQL の書き方の Why は、そのコメント）

- 全行を読み書き用のスキーマで確かめ、合わない行が 1 つでもあれば、何も書きません。
- 1 回の依頼は、1 つの `batch()`（1 つのトランザクション）で書きます。行は JSON の配列にして 1 文にまとめ、D1 の値の上限に収まるよう、約 1MB ごとに分けます。**Why**: 1 行 1 文だと、ワークスペースの削除などで、D1 のクエリ数の上限に当たるおそれがあるためです。
- 同じ id の既存の行と `kind` が違う行、同じ id が 2 つ入った依頼は、何も書かずに例外にします（呼び出し側のバグなので、隠さない）。更新では、`kind` と `builtin` を書き換えません。
- 更新では `next_notify_at` を NULL に戻し、同じ batch の中で入れ直します（[9.2](#92-保存したときの計算実装-11a)）。**Why**: 古い値を残すと、時刻を変えた予定や削除した予定の通知が、変更前の時刻に送られるからです。

### 4.3 各項目の決め方

- **ID は端末側で発行する（UUID）**。**Why**: 電波がない間に作った予定にも、その場で ID が必要だからです（SY-2）。
- **通知のタイミングは「開始の何分前か」の1つの数で持つ**（`notify_offset_min`）。時間指定はそのまま（10分前なら `10`。NT-2）、終日は、開始を「その日の 0:00」とみなして、後なら負の数にします（朝6時なら `-360`。NT-3）。**Why**: 通知時刻の計算が「開始 − この数」の1つの式で済むからです。
  - **終日の通知の時刻は、画面では当日の朝6時（`-360`）に固定します**（NT-3）。データの形は変えないので、API や MCP からは別の値も入り、その行は、保存された値のとおりに通知します（[P4](#p4)）。**Why 形を変えないのか**: 固定は入力の画面だけの決まりで、形を変えると、通知の計算を分けることになるからです。
- **場所は名前だけを保存し、地図へのリンクは画面で作る**（Google マップの検索の URL）。**Why**: 地図の URL を保存すると、名前と URL の2つを入力することになるからです。
- **削除は「削除した時刻」を記録するだけにする（論理削除）**。**Why**: 削除したことを他の端末に伝えるには、削除の記録が DB に残っている必要があるからです。

### 4.4 繰り返しのルール（`rrule` 列）

| ルール | JSON | 補足 |
| --- | --- | --- |
| 毎日 | `{"freq":"daily"}` | |
| 毎週 | `{"freq":"weekly","days":[1,3,5]}` | 0=日〜6=土。複数選べる（RP-1） |
| 毎月 | `{"freq":"monthly"}` | 開始日の「日」と同じ日。その日がない月はスキップ（RP-2） |
| 毎年 | `{"freq":"yearly"}` | 開始日と同じ月日。2/29 はうるう年だけ（[Q9](#q9-毎年の繰り返しで229-を選んだとき)） |
| 平日 | `{"freq":"weekday"}` | 要件定義書3章の定義で判定（RP-5） |
| 休日 | `{"freq":"holiday"}` | 同上 |

- 1回目は `start_date` です。開始日がルールに合わない場合（例: 月曜を開始日にして「毎週 水・金」）は、保存するときに、**ルールに合う最初の日へ開始日をずらします**（`normalizeStart`）。**Why**: 合わない1回目があると、それを回として数えるかどうかで、処理が分かれるからです。
- 各回の長さ（終了 − 開始）は、1回目と同じにします。

### 4.5 繰り返し予定の変更・削除（RP-4）

Googleカレンダーと同じく、「元の予定（系列）」と「例外の行」で表します。処理は `src/shared/recurrence.ts`（`changeEntry`・`deleteEntry`）で、仕様の細部は、そのテスト（`recurrenceEdit.test.ts`）にあります。

| 操作 | 何をするか |
| --- | --- |
| **この予定のみ** 変更 | 例外の行を1つ作る（`series_id` = 元の予定、`original_date` = その回の日付、中身は変更後の内容） |
| **この予定のみ** 削除 | 例外の行を作り、`cancelled = 1` にする |
| **これ以降すべて** 変更 | 選んだ回の日付を D として、元の予定の `until_date` を **D の前の日**にして系列を切り、D 以降は変更後の内容で新しい系列を作る。`original_date` が D 以降の例外は消す |
| **これ以降すべて** 削除 | `until_date` を **D の前の日**にする。`original_date` が D 以降の例外は消す |
| **すべて** 変更 | 元の予定を書き換える。例外の扱いは下のとおり |
| **すべて** 削除 | 元の予定と、その例外を全部削除する |

- 最初の回の「これ以降すべて」は、系列を切らず、「すべて」と同じにします（切ると、1 回も残らない系列ができるため）。
- すでに切られた系列を切るときは、`until_date` の早い方を残します（延ばすと、切って消えた回が戻るため）。「これ以降すべて」の新しい系列は、元の `until_date` を引き継ぎます。
- 繰り返さない予定は、範囲を無視して、その行を書き換えます。ルールを付けると、繰り返す予定になります。
- `until_date` は内部だけで使い、画面に「終わりの指定」は出しません（RP-3）。

**変更の中身（`changes`）**

- 変えた項目だけを渡します。キーがない項目は「変えていない」、`null` は「空にした」です。**Why**: 「すべて」でタイトルだけ変えたとき、個別に決めた回の時刻まで上書きしないためです。
- 日付と時刻は、フォームに出ていた、その回の値に対する変更後の値です。
- **`kind` は、作成した後に変えられません**。**Why**: 列の組み合わせ（ワークスペース・終日・通知の初期値）が合わなくなるからです。
- **「この予定のみ」では、ルールを変えられません**（例外の行は 1 回だけの行で、ルールを持たないため）。ルールを変えたとは、現在と値が違うことです（曜日の並びだけの違いは、変えたことにしない。`isSameRrule`）。

**「すべて」変更のときの例外の扱い**

- 「この回だけ削除」した回は、削除した状態で残します。
- 個別に変えた回には、今回変えた項目だけを上書きします（日時と終日は除く）。**開いていた回が例外の行のときは、その例外だけ、日時・終日も含めて上書きします**（開いた回の時刻を変えたのに、その回だけ変わらないのは不自然なため）。
- 通知の分は、終日かどうかが系列と違う例外には上書きしません（分の意味が違うため。[4.3](#43-各項目の決め方)）。
- **ルールか開始日を変えた場合は、例外をすべて消します**。**Why**: どの例外がどの回に当たるかが変わるからです。それ以外（タイトルだけ、など）では消しません。

**日付を変えたときの系列のずらし方（「これ以降すべて」「すべて」で共通）**

- ずらす日数 **Δ** = 変更後の開始日 − その回の日付（例外の行なら `original_date`）。**Why 表示上の開始日から数えないのか**: 別の日に移した例外の回を開いて日付を変えたとき、利用者が選んだ日にならないからです。
- **ずらせるのは、weekly・monthly・yearly だけです**（daily・weekday・holiday で Δ ≠ 0 は `InvalidChangeError`。ルールを同時に変えたときは、変更後のルールで判定）。**Why**: これらのルールは、開始日が「どの日に回があるか」を決めないので、ずらしても回は動かず、最初の回や例外が黙って消えるだけだからです。日付を動かしたいときは、「この予定のみ」にします。
- 系列の開始日・終了日・`until_date` を Δ 日ずらします（回の数を変えないため）。weekly は、ルールを同時に変えていなければ、曜日も Δ だけずらします（水・金を 1 日後ろにしたら、木・土）。
- 1 回の長さは、変更後の終了日が渡されたときだけ変えます。**Why**: 表示中の回の長さから求めると、別の長さに変えた例外の回でタイトルだけを直したときに、系列全体の長さが変わるからです。

**ルールをなくす**: 「すべて」でルールを `null` にすると、繰り返さない予定になります（`until_date` は `NULL`、例外はすべて消す）。「これ以降すべて」なら、D 以降が、繰り返さない予定の行 1 つになります。

**エラーの種類**（API が、「依頼を捨てる」と「エラーを返す」を区別するため。[5.1](#51-エンドポイント)）

- `OccurrenceNotFoundError`: 対象の系列・回が存在しない・削除されている（ルールにも例外にも当たらない日付、削除した回への「この予定のみ」の変更を含む）。**Why**: 黙って受け付けると、存在しない回の予定を新しく作ってしまうからです。
- `InvalidChangeError`: 変更の中身が受け付けられない（上の 2 つの禁止）。

## 5. API 設計

画面も MCP サーバーも、同じ API を使います（NF-5）。

### 5.1 エンドポイント

すべて、[10章](#10-認証セキュリティ)の確認の後ろで動きます。本文と応答の形は `src/shared/api.ts`（Zod のスキーマ）で、JSON のキーは camelCase です。

| メソッドとパス | 本文（JSON）またはクエリ | 内容 |
| --- | --- | --- |
| `GET /api/changes?since=<rev>` | `since`（0 以上の整数。必須） | `since` より後に変わったワークスペース・予定を返す（削除も含む）。`since=0` なら全件（削除済みは除く） |
| `PUT /api/workspaces/:id` | `{ workspace }`（全項目） | ワークスペースの作成・更新 |
| `DELETE /api/workspaces/:id` | `{ editedAt }` | ワークスペースと、その中の予定をすべて論理削除する（[Q6](#q6-ワークスペースを削除したときの中の予定)） |
| `PUT /api/entries/:id` | `{ draft, editedAt }` | 予定・タイムブロックの作成 |
| `PATCH /api/entries/:id` | `{ occurrenceDate, scope, changes, newId, editedAt }` | 予定の変更。`:id` は系列の id（繰り返さない予定なら自分の id）。`scope` は `this` / `following` / `all`（繰り返さない予定は、`scope` と `occurrenceDate` を使わないが、形としては必要） |
| `DELETE /api/entries/:id` | `{ occurrenceDate, scope, newId, editedAt }` | 予定の削除 |
| `GET /api/occurrences?from=&to=` | `from`・`to`（両端を含む。最大 31 日） | 期間内の予定を、繰り返しを展開して返す（祝日・記念日も） |

- 書き込みは、サーバーが、DB から関係する行を読み、`shared/` の関数で書く行を計算し、`applyWrite`（[6.4](#64-食い違ったときsy-3)）で書きます（[5.2](#52-なぜ何をしたいかを送る形にするのか)）。
- 書き込みの API はすべて、`editedAt` を受け取ります。新しく作る行の id は、端末から送ります（PUT の `:id`、PATCH・DELETE の `newId`）。

**応答（200）**

| API | 応答 |
| --- | --- |
| `GET /api/changes` | `{ rev, epoch, workspaces, entries }` |
| 書き込み | `{ applied: true }` か、`{ applied: false, reason }`（`reason` は `stale` か `not_found`） |
| `GET /api/occurrences` | `{ occurrences, holidays, observances }` |

- 行ごとの `rev` と `next_notify_at` は返しません。書き込みの応答にも `rev` を返しません。**Why**: 端末が、書き込みの `rev` を受け取りの `rev` と取り違えて、他の端末の行を取りこぼさないようにするためです（[6.3](#63-受け取るサーバー--端末)）。

**依頼を捨てる（200 の `applied: false`）**

- **Why エラーにせず 200 で捨てるのか**: 途中で古くなって実行できなくなった依頼をエラーにすると、端末の送信待ちの列が先頭で止まるからです（[6.2](#62-送る端末--サーバー)）。
- `stale`: 依頼より新しい（または同じ）編集がある。**同じ依頼の 2 回目も、ここに入ります**。
- `not_found`: 対象の予定・回・ワークスペースがもうなく、その行が依頼より古い、または見つからない。
- 対象がもうないときは、対象の行（系列・ワークスペース）の `edited_at` が `editedAt` 以上なら `stale`、そうでなければ `not_found` です。**Why**: 同じ依頼の 2 回目を、削除でも変更でも `stale` にそろえるためです。
- 削除済みのワークスペースを指す予定の作成・変更と、削除済みのワークスペースの更新も、捨てます（生き返らせない）。**Why**: ワークスペースの削除は中の予定もまとめて消すので、更新で生き返ると、空のワークスペースだけが戻るからです。

**エラー**

本文は `{ error, message }` で、`message` は固定の短い文言です。Zod のエラー文や内部の情報は、Worker のログにだけ出します（攻撃者への手がかりにしないため）。

| 状態 | `error` | 起きるとき |
| --- | --- | --- |
| 400 | `invalid_request` | 本文・パラメータが不正（入力の検証・項目をまたぐ確認に合わない、`id` が URL と違う、`newId` が系列の id や書く他の行と重なる）。日付の計算や、計算した行の日付が、年の範囲を出る。期間が 31 日を超える |
| 400 | `invalid_change` | 変更の中身が受け付けられない（`InvalidChangeError`） |
| 400 | `builtin_workspace` | 組み込みのワークスペースの保護（[4.2](#42-テーブル定義)） |
| 400 | `last_workspace` | 最後の 1 つのワークスペースの削除 |
| 400 | `edited_at_in_future` | `editedAt` がサーバーの今より 10 分より未来 |
| 404 | `not_found` | `/api/*` の存在しないパスと、違うメソッド（認証の後ろで返すので、ログインしていない相手には 403 のまま） |
| 409 | `conflict` | 保存されているデータと合わず、再送しても直らない: 同じ id の行と `kind` が違う／存在しないワークスペースを指す／新しい行の id が、保存されている別の行とぶつかる |
| 500 | `internal_error` | 上のどれでもない例外。壊れた行（`CorruptRowError`）など |

- **依頼の値が原因の失敗は、5xx にしません**（日付の計算が年の範囲を出る場合も 400）。**Why**: 再送しても直らないのに、5xx だと端末が再送し続けるからです。
- **新しい行の id が、保存されている別の行とぶつかったときは、上書きしません**。保存されている行の `edited_at` が `editedAt` 以上なら `stale`、そうでなければ 409 です。同じ回の例外の行（`series_id` と `original_date` が同じ）は、ぶつかりとしません（「この予定のみ」の 2 回目）。**Why**: 上書きすると、例外の行を残したまま系列が繰り返さなくなる、削除した行が生き返る、などの、画面から直せない壊れ方をするからです。
- 存在しないワークスペースは、外部キー違反を待たず、書く前に確かめます。**Why**: 外部キー違反は D1 の例外の文言でしか判定できず、本番の文言が Miniflare と同じか確かめられないからです。

**ワークスペースの削除で、別のワークスペースの系列の例外が、このワークスペースを指しているとき**は、その例外を論理削除せず、その回を削除した形（`cancelled`）にして、`workspace_id` を系列のものに戻します（`src/shared/workspace.ts`）。**Why**: 例外を論理削除すると、例外が抑えていた元の回が、また現れます。移した先のワークスペースを削除すれば、そこに移していた回も消えるのが自然です。

**`GET /api/occurrences`**

- 画面からは呼びません。MCP が「今週の予定を教えて」に答えるためのものです。
- 中身は、`occurrencesInPeriod`（`shared/period.ts`）と `namedDatesBetween`（`shared/holidays.ts`）で作り、画面（月表示・日表示）も同じ関数を使います（[P1](#p1)）。
- **期間は最大 31 日**です（長い期間が必要なら、MCP は区切って呼ぶ）。**Why**: 系列 100 件の 1 年分の展開は約 34ms かかり、無料プランの CPU 時間（1 回 10ms）に収まらないからです。31 日なら約 3ms です。
- 削除済みのワークスペースの予定は、**展開の後で**除きます。表示の ON/OFF は、画面の都合なので、見ません。**Why 後なのか**: 展開の前に除くと、除いた例外の行が抑えていた、元の系列の回が現れるからです。
- DB からは、削除されていない予定の全行を読み、SQL では期間に絞りません（系列と例外がかかる条件が複雑で、間違えやすいため）。

### 5.2 なぜ「何をしたいか」を送る形にするのか

「これ以降すべて変更」は、行の書き換えとしては「元の系列を切る」「新しい系列を作る」「例外を消す」という3つの操作になります。画面が行を書き換える形にすると、MCP サーバーも同じ処理を自前で書く必要が出ます。そこで、API は「どの回を、どの範囲で、どう変えたいか」を受け取り、行の書き換えはサーバー側で行います。

- 画面も同じ処理（`shared/recurrence.ts`・`shared/workspace.ts`）を手元で実行して、すぐ表示に反映し、その後、同じ依頼をサーバーに送ります。同じコード・同じ入力なので、同じ結果になります。
- D1 の `batch()` で書き込むので、3つの操作のうち一部だけが保存されることはありません。

## 6. 同期・オフライン

同期のエンジンは `src/client/sync/engine.ts` です。細部は、そのコメントとテストにあります。

### 6.1 方針

- 画面は、起動時に**全データ**をサーバーから読み込んで手元（メモリ）に持ち、表示はすべて手元のデータから作ります。**Why**: 自分1人の予定なので、何年分あっても数千件・数MB程度です。手元に全部あれば、スクロールで通信せず速く（NF-6）、電波が切れても見られます（SY-2）。
- 変更はまず手元に反映し、その後サーバーに送ります（楽観的更新）。

### 6.2 送る（端末 → サーバー）

```
 編集 ──▶ 手元のデータを更新（すぐ表示に反映）
       └─▶ 送信待ちの列（IndexedDB に保存）──▶ 電波があれば先頭から順に送る
                                              失敗したら、電波が戻ってから再送
```

- 送信待ちの列は IndexedDB に保存します。**Why**: スマホのブラウザは裏のタブを勝手に閉じることがあり、メモリだけだと、電車の中での編集が電波の戻る前に消えます。
  - 依頼 1 つを、1 つのキーで保存します（列全体を配列で 1 つのキーに入れない）。**Why**: 書き込みが重なったとき（[6.7](#67-同じ端末の複数のタブ)）、配列を読んで書き戻すと、もう一方の依頼を消すからです。
  - 起動時に読み込んだ依頼は、サーバーと同じスキーマで確かめ、形の合わないもの（古い版の画面が保存したものなど）は、送らずに消して「保存できなかった変更」に数えます。
- 列は、先頭から 1 つずつ順番に送ります。**Why**: 順番が崩れると、対象がなくて捨てられる依頼が出る（作成より先にその変更が届くなど）からです。
- **同じ依頼を2回送っても結果は変わりません**（ID も編集時刻も端末で決めるため）。「送れたか分からない」ときは、気にせず再送します。サーバーは、今の行の `edited_at` が依頼と**同じ**なら、「反映済み」として捨てます。**Why**: 書き直すと、行は変わらないのに rev だけが進み、他の端末が差分をもう一度受け取るからです。
- `fetch` には `redirect: 'manual'` を付けます。**Why**: 付けないと、ログイン切れのときの Access のログイン画面への転送を追いかけて CORS で失敗し、通信の失敗と区別できません。
- **端末は、応答ごとに、次のように扱います**（`src/client/sync/http.ts`）。「次のきっかけ」は、[6.3](#63-受け取るサーバー--端末)の受け取るタイミングと、編集したときです。

  | 応答 | 扱い | Why |
  | --- | --- | --- |
  | 200（`applied` が true でも false でも） | 列から外して、次へ | 捨てられた依頼（[5.1](#51-エンドポイント)）で、列を止めないため |
  | 4xx で、本文が API のエラーの形（下の行を除く） | 列から外して（捨てて）次へ。「保存できなかった変更」として知らせる | 依頼の中身が原因で、何度送っても同じ結果になり、列が先頭で止まるため |
  | 401・403・Access のログイン画面への転送 | **捨てずに、送信を止める**。「ログインし直してください」と知らせる | 原因は依頼の中身ではなくログインで、捨てると送信待ちがすべて消えるため |
  | 5xx・通信の失敗・408・429・エラーの形でない 4xx・書き込みの応答の形でない 200 | 外さずに止めて、次のきっかけで再送する | 一時的か、経路が原因（Cloudflare の前段・ログイン前の案内ページの 200 など）で、捨てると編集が黙って消えるため |

  - 壊れた行（`CorruptRowError`）が原因の 500 は、サーバー側を直す（[付録 A.3](#a3-壊れた行が見つかったとき)）まで再送が続きます。

### 6.3 受け取る（サーバー → 端末）

- `GET /api/changes?since=<最後に受け取った rev>` で、差分だけを受け取ります。
- 受け取るタイミング: 起動したとき／送信が止まらずに終わったとき／電波が戻ったとき／タブが前面に戻ったとき／タブが前面にある間、60秒ごと。**Why 前面にある間だけなのか**: 裏にある間は、受け取っても見えないからです。
- **Why 通し番号（rev）を使うのか**: サーバーの時刻で「いつ以降」と区切ると、同じミリ秒の2件などを取りこぼす可能性があるからです。rev は保存のたびに1ずつ増える（`meta.rev`）ので、取りこぼしません。
- **覚えるのは、`GET /api/changes` が返す rev だけです**（書き込みは rev を返さない。[5.1](#51-エンドポイント)）。
- **読み込みは、行の構造だけを確かめます**（サーバーは `rows.ts`、端末は `src/shared/structure.ts`）。長さ・年の範囲のような入力のルールは、書き込むときに確かめます。**Why**: 入力のルールを後で厳しくしたとき、DB にある行が「壊れた行」になって、全端末の同期が止まるのを防ぐためです。
- **構造が壊れた行が 1 行でもあると、読み込み全体が失敗します**（`CorruptRowError`。直し方は [付録 A.3](#a3-壊れた行が見つかったとき)）。端末も、形が合わない応答は、当てずに知らせます。**Why 壊れた行だけを飛ばさないのか**: 飛ばすと、端末は「全部受け取った」と思い込み、その行が永久に届かないまま気づけないからです。
- **`epoch` が、覚えている値と違えば**、`since=0` で全データを読み込み直します（[付録 A.1](#a1-データの復元ot-2)）。送信待ちの列は消しません（まだサーバーにない編集のため）。
- 受け取りは、同時に 1 つだけです。**Why**: 古い応答が新しい応答の後に当たって、新しい内容を消すおそれがあるからです。受け取った行は、削除済みも持ちます（他の端末の削除を画面から消すため）。
- 起動時の全データの読み込みに失敗したら（SY-4）、「読み込めませんでした」と再試行のボタンを出します。
- **Why 即時通知（WebSocket）にしないのか**: 自分1人で、2台で同時に編集することはまずなく、前面に戻ったときに取りに行けば足りるからです。

### 6.4 食い違ったとき（SY-3）

- 行ごとに `edited_at`（端末で編集した時刻）を比べます。届いた依頼の方が新しければ保存し、**同じか古ければ**捨てます（[Q4](#q4-食い違ったときにどちらを正とするか)。判定は `src/shared/conflict.ts`）。
- 複数の行を書き換える依頼（「これ以降すべて」など）は、どれか1行でも、サーバー側の方が新しいか同じなら、**依頼全体を捨てます**。**Why**: 一部の行だけが保存されると、系列が二重になるなど、データの形が壊れるからです。
- **`editedAt` が、サーバーの今より 10 分より未来の依頼は、400（`edited_at_in_future`）で断ります**。**Why**: 時計が大きく進んだ端末の編集が、その後のすべての編集に勝ち続けるからです。10 分は、普通のずれは通し、大きく進んだ端末だけを止める値です。過去の方向には上限を設けません（電波がない間の編集は、何時間も前の時刻で届くため）。
- **`editedAt` は、`max(今の時刻, 前に決めた editedAt + 1)` にします**（`src/shared/editedAtClock.ts`。画面は、起動時に、送信待ちの最大値からも初期化する）。**Why**: サーバーは `edited_at` が同じ依頼を「2 回目の送信」として捨てるので、同じミリ秒の 2 回目の編集が消えるからです。
  - 時計が進んでいた端末は、時計を直しても、ページを開き直すまで、編集が断られ続けます。**Why 数え直す仕組みを入れないのか**: 時計のずれはまず起きないので、コードを複雑にしない方を、ユーザーが選びました（知らせで案内する。[6.5](#65-電波がない間の動き)）。
- サーバーの書き込み（`applyWrite`）は、(1) 今の行の `edited_at` を読む、(2) 上の判定をする、(3) `batch()` で `meta.rev` を1つ増やし、全行をその rev で保存する、の順です。(3) は、「依頼の `edited_at` が、今の行より大きいとき」だけ上書きします。
  - **Why 1〜3 を完全に1回の処理にしないのか**: 2台がほぼ同時に同じ行を書く確率が、ごく小さいからです（[P3](#p3)）。割り込まれると、一部の行だけが保存されることはありえますが、新しい行が古い行に上書きされることはありません。
- **画面に出すデータ**は、「サーバーから受け取った内容」の上に、「まだ受け取りで確かめていない依頼を、手元でやり直した結果」を重ねて作ります（`src/client/sync/replay.ts`）。**Why**: 手元の編集結果を持ち続けると、サーバーが捨てた依頼の結果が手元にだけ残って食い違い、気づけません。作り直せば、その結果は、依頼が列から外れた時点で画面からも消えます。
  - **やり直しは、サーバーと同じ計算にします**（同じ範囲の行から、`shared/` の関数で書く行を計算し、当てるかどうかも同じ決め方）。サーバーが 200 で「捨てた」にする場合も、当てません。本物の Worker と D1 に同じ依頼を当てて、全行が一致することを、テストで確かめています（`replay.equivalence.test.ts`）。
  - 例外（一時的な食い違い）: 起動時の全データの読み込みは、削除済みの行を含まないので、開き直した直後の端末は、削除済みの行と同じ id の作成と、削除済みのワークスペースの更新だけ、サーバーと結果が食い違います。送信が終われば、受け取りで直ります（[P3](#p3)）。
  - **サーバーの 400 の入力の検証は、真似ません**。**Why**: その依頼は、送ったときに 4xx で列から外れて画面からも消えるので、通る依頼だけを正しくやり直せばよく、検証まで真似ると、二重に保つ規則が増えて食い違うからです。
  - **200 を受け取った依頼は、次の受け取りが成功するまで、重ね続けます**。**Why**: 外した時点でやめると、編集した予定が、送信が終わった瞬間に消え、受け取りの後で現れる（ちらつく）からです。
  - 削除済みのワークスペースを指して残った予定（書き込みが重なったとき）は、画面でも除きます（`occurrencesInPeriod`。[5.1](#51-エンドポイント)）。

### 6.5 電波がない間の動き

- 画面の JavaScript は、起動時に**全部**読み込みます（後から読み込む方式にしない）。**Why**: 電波がない間に使えるのは、Service Worker が保存したファイルだけです（[14章](#14-pwaホーム画面への追加電波がなくても開く)）。後から読み込む方式は、保存の漏れがあると、電車の中で日表示を開いた瞬間に画面が壊れるため、作りを単純にしておきます。
- 画面の上部に「未送信 N件」を小さく表示します（置き場所は [11.2](#112-月表示mv-110)・[11.3](#113-日表示dv-16)）。
- **画面の下の知らせ**は、左下に 1 つの列にして縦に積みます（削除の「元に戻す」と共通。右は ( + ) ボタンのために空ける）。**Why**: 別々に固定すると、同じ場所に重なるからです。

  | 知らせ | 出るとき |
  | --- | --- |
  | 保存できなかった変更が N 件あります | サーバーが 4xx で断った依頼と、起動時に形が合わずに消した依頼があるとき。`edited_at_in_future` なら、時計を合わせて開き直す案内を添える |
  | ログインし直してください | 401・403・Access のログイン画面への転送のとき |
  | サーバーとのやり取りに失敗しています（HTTP 500） | 送信か受け取りで、最後に**返ってきた**応答が、失敗だったとき。同じ向きで、次に失敗でない応答が返れば消える |
  | サーバーのデータを読み取れませんでした | 受け取りの応答の形が合わないとき |
  | この端末では、未送信の変更を保存できません | IndexedDB が使えないとき（プライベートブラウズなど） |
  | 読み込めませんでした（再試行） | 起動時の全データの読み込みに失敗したとき |
  | 別のタブで開いたため、このタブは止めました | [6.7](#67-同じ端末の複数のタブ) |

  - **200 の `applied: false`（負けた・対象がもうない）は知らせません**。**Why**: 後から編集した方を正とする（SY-3）ので、負けた編集は、正常な動きの結果だからです。
  - **通信の失敗（応答がない）では、失敗の知らせを出しも消しもしません**。**Why**: 電波がないのは電車の中などで普通に起きるので、出すと邪魔です。サーバーの失敗は、電波では直らず、知らないと気づけません。
  - 失敗の知らせは、回数や時間を数えず、すぐ出します（次の成功で消えるので害が小さく、仕組みも単純なため）。送信と受け取りで分けて持ち、両方なら送信を出します（保存した編集が届いていない方が大事なため）。
  - 限界: 失敗で止まった先頭の依頼を「元に戻す」で取り消して列が空になると、送信の失敗の知らせが、次の編集か開き直しまで残ります（まず起きず、直すと取り消しの処理が増えるので、直さない）。

### 6.6 削除の「元に戻す」（OT-1）

- 削除すると、手元ではすぐに消えて、画面下に「元に戻す」が5秒間出ます（`DELETE_UNDO_MS`）。**サーバーへの送信は、その5秒が過ぎてから行い**、「元に戻す」を押したら送信しません。
- **Why 送信を遅らせるのか**: 先に送ると、「元に戻す」のために削除前の状態を再現する処理が必要になり、繰り返し予定の「これ以降すべて」削除などでは、かなり複雑になります。送信を遅らせれば、送らないだけで済みます。
- 予定の削除にも、ワークスペースの削除にも付けます。**Why**: ワークスペースの削除は、中の予定がすべて消えるので、間違えたときの被害がいちばん大きいからです。削除の前の確認（[Q6](#q6-ワークスペースを削除したときの中の予定)）も残します。
- 削除の依頼は、列に入れた時点で IndexedDB に保存し、「この時刻までは送らない」は、メモリにだけ持ちます。**Why**: タブが閉じられても削除を失わず、再読み込みで開いたとき（元に戻すボタンがもうない）は、待たずに送るためです。
- 先頭の依頼が待ち中なら、後ろの依頼も待ちます（順番を崩さないため）。
- タブが裏に回る・閉じるとき（`visibilitychange` の `hidden` と `pagehide`）は、待ちをやめて、`keepalive: true` ですぐ送ります。

### 6.7 同じ端末の複数のタブ

- **最後に開いたタブだけが動きます**。新しいタブが開くと、Web Locks API の錠を奪い（`steal`）、古いタブは止まって、「別のタブで開いたため、このタブは止めました」と表示します。新しいタブは、錠を取ってから、IndexedDB の送信待ちを読み込み、引き継いで送ります。
  - **Why**: 同じ端末の複数のタブはまれなので、タブ同士の調整の仕組みを増やすほど、不具合の余地が増えるからです。最後に開いたタブにするのは、スマホで裏に残った古いタブに邪魔されないためです。
- `navigator.locks` がないブラウザでは、調整せずに動かします。**Why**: 動かさないと、古いブラウザで予定が見られなくなります。同じ依頼を何度送っても結果が変わらないので、害は小さいからです。

## 7. 繰り返しの展開

- 展開とは、繰り返し予定から「その期間の何日に、何時から何時まで」という各回を作り出す処理です（`expandOccurrences`。`src/shared/recurrence.ts`）。
- 画面（月表示・日表示）・`GET /api/occurrences`・通知の計算（[9章](#9-通知)）が、同じ展開を使います（[P1](#p1)）。
- 手順（1つの系列について）:
  1. `start_date` から期間の終わり（`until_date` があればそこまで）について、ルールに合う日を求める
  2. 例外の行がある日は、例外の内容で置き換える（`cancelled` なら出さない）
  3. 例外の行のうち、日時を別の日に移したものは、移した先の日で出す（`original_date` が期間の外でも、移した先が期間にかかれば出す）

**回が「かかる日」の決め方**（`lastCoveredDate`）

- 終日: `start_date`〜`end_date`（両端を含む）。
- 時間指定: `start_date`〜`end_date`。終了が `00:00` のときは、`end_date` の前の日まで（開始日より前にはしない）。**Why**: 終わりの時刻は、その瞬間を含まないからです。そうしないと、毎日の 20:00〜翌 00:00 が、翌日にもかかって見えます。
- 複数日の回や、日付をまたぐ回（TB-6）は、期間の前から始まっていても、期間にかかっていれば出します。

**細部**

- 系列が削除されている、または見つからない例外の行は、出しません。
- 同じ回の例外の行が 2 行あるとき（同期の競合で起こりえます）は、`edited_at` が新しい方だけを使います（二重に出さないため）。
- **並び順**は、開始の日時の順で、同じ日なら終日が先、それでも同じなら id の順です（入力の並びに依存させないため）。
- `from` が `to` より後なら、空を返します。
- 系列が回を生成する日は、1900-01-01〜2199-12-31 に収めます。**Why**: 祝日の計算が対応するのは 1900〜2199 年だからです（[Q2](#q2-スクロールできる範囲)）。
- 展開した回には、繰り返しの系列の回かどうか（`recurring`）を付けます。**Why**: 画面のフォームが、範囲を選ぶ段を出すかどうかを決めるためです（[11.4](#114-フォームev-14tb-12)）。

## 8. 祝日・記念日の計算

### 8.1 方針

- 祝日は、ライブラリを使わず、**祝日法のルールを自前で実装**します（`src/shared/holidays.ts`）。**Why**: 既存のライブラリの多くは祝日の「一覧データ」を持つ方式で、数十年先までしか対応せず、HD-5 の「何年先でも」を満たせません。
- 春分・秋分・夏至・冬至・立春は、太陽の位置の**天文計算**で求めます（`src/shared/solarTerms.ts`。理由は[2章](#2-技術の選定)の表）。
- 計算できる年は 1900〜2199 年です（[Q2](#q2-スクロールできる範囲)）。範囲外の年は例外にします。
- 正式な発表と食い違ったときのために、コード内に「上書き一覧」を持ちます（[Q8](#q8-祝日の正式発表の反映方法)）。祝日と記念日の2つがあります。**Why 記念日にもあるのか**: 節分・夏至・冬至は、天文計算で決まる日で、国立天文台の発表と食い違うことがあるからです（HD-5）。

### 8.2 祝日の計算

1. 祝日法の各祝日を、「何年から何年まで、どのルールか」の表で持つ（例: 成人の日は「1月15日（1949〜1999年）」→「1月の第2月曜（2000年〜）」）。2020・2021年の五輪による移動も、年を限った行として入れる
2. 一度きりの祝日（結婚の儀・大喪の礼・即位礼正殿の儀・即位の日）を表で持つ。国民の休日の判定でも、祝日に数える
3. 振替休日: 1973年4月12日以降に、祝日が日曜にあたったとき。2006年までは翌日、2007年からは、その日より後で最も近い祝日でない日
4. 国民の休日: 1986年以降に、前の日と次の日がどちらも祝日（2 までの表の祝日）である日。2006年までは、その日が日曜・振替休日なら除く。2007年からは、その日が祝日でないとき
5. 春分の日・秋分の日: 太陽の黄経が0度・180度になる瞬間を含む日（日本時間）
6. 最後に祝日の上書き一覧を適用する。**上書きの後で、振替休日などを計算し直しません**。**Why**: 上書きは、内閣府が発表した結果をそのまま反映するためのもので、計算し直すと、発表と食い違う日が出るおそれがあるためです

**画面に出す祝日名**: 内閣府の一覧で「休日」と書かれている日は、「振替休日」か「国民の休日」に書き分けます。2019年の「休日（祝日扱い）」は、「即位の日」「即位礼正殿の儀」と表示します。

### 8.3 記念日の計算（HD-3）

| 記念日 | 計算 |
| --- | --- |
| 節分 | 立春（太陽の黄経が315度）の前の日 |
| 夏至・冬至 | 太陽の黄経が90度・270度になる日 |
| 母の日・父の日 | 5月の第2日曜・6月の第3日曜 |
| その他 | 固定の日付（2/14、3/3、3/14、7/7、10/31、12/24、12/25、12/31） |

- 記念日は、日付の決め方（固定日・第n曜日・節気）の表として持ちます（HD-4）。追加・削除は、表を直して行います。
- 同じ日に重なる記念日があるので（例: 2026年は夏至と父の日が 6/21）、「日付 → 名前」ではなく、日付順の一覧で扱います。
- 休日・平日の判定（RP-5）は、要件定義書3章の定義どおりです（`isDayOff`・`isWeekday`）。記念日は休日に含めません。

### 8.4 正しさの確認

- 内閣府の一覧にない夏至・冬至・立春は、国立天文台の暦要項と、日付が一致し、時刻も1分以内で一致することを確かめます。

## 9. 通知

### 9.1 仕組み

```
 予定を保存 ──▶ サーバーで「次に通知する時刻」を計算して next_notify_at に保存

 1分ごとの定期実行:
   next_notify_at が今以前の行を探す（索引を使うので、該当する行だけを読む）
   └─▶ その次の回の通知時刻を計算して next_notify_at を更新 ──▶ Discord に送る
```

- **Why 次の通知時刻を先に計算して保存しておくのか**: 毎分すべての繰り返し予定を展開すると、D1 の読み取り量と CPU 時間（無料プランは1回10ms）を毎分消費します。先に計算しておけば、毎分の処理は「時刻が来た行を探す」だけで済みます。

### 9.2 保存したときの計算（実装 11a）

計算は `src/worker/notify/nextNotifyAt.ts`、保存への組み込みは `notifyUpdates.ts` と `db/store.ts` です。数値（探す範囲など）と、その Why は、コードのコメントにあります。

- **1 回の通知の時刻は、`開始 − notifyOffsetMin 分`** です（[4.3](#43-各項目の決め方)）。日本時間から UTC への変換は、日数と分の足し算だけで行います。
- **次に通知する時刻は、削除されていない各行について、「その行が内容の元になっている回」のうち、通知の時刻が基準の時刻（`afterMs`）より後の、いちばん早いもの**です。なければ NULL です。
  - 繰り返さない予定は、その行の 1 回だけ。例外の行は、その行の開始から直接求めます（`cancelled` なら NULL）。系列の行は、展開した回のうち、例外でない回だけを見ます。
  - **画面に出ない回は、通知しません**。判定は書き写さず、展開（[7章](#7-繰り返しの展開)）をそのまま使います（[P1](#p1)）。
  - 系列の行は、期間を区切って先へ広げながら、**9 年後まで**探します。**Why**: 2/29 の毎年の繰り返しは、次の回が最大 8 年後になるからです。区切るのは、毎日の系列をいきなり 9 年ぶん展開すると、CPU 時間を使うからです。
- **保存した時点で、通知の時刻が過ぎている回は、通知しません**（基準は「今」）。**Why**: 作った直後に、過ぎた通知が来ても役に立たないためです。
- **ワークスペースは、この計算では見ません**。**Why**: ワークスペースを変えるたびに、中の全行を計算し直さずに済むためです。削除済みのワークスペースの予定は、送るときに除きます（[9.3](#93-定期実行で送る実装-11b)）。
- **表示 OFF のワークスペースの予定も、通知します**。**Why**: 通知は、予定ごとの ON/OFF（NT-4）で決めるもので、表示を消しただけで通知まで止まると、気づかないうちに予定を逃すおそれがあるからです。

**保存のとき**

- 書く行の系列（`series_id ?? id`）ごとに、「書いたあとの状態」を作って、その系列の、削除されていない全行の値を決めます。**書かない行も含めます**（「この予定のみ」で例外の行だけを書いたとき、系列の行の次の回も変わることがあるため）。
- **書かない行の、時刻が来て、まだ送っていない回は、飛ばしません**。**Why**: その回は、利用者が今回保存した回ではなく、定期実行が送るべきものだからです（例: 毎日 14:50 に通知する系列で、14:50:20 に明日の回だけを変えても、今日の通知は届く）。
- **決めた値は、書き込みと同じ `batch()` の中で入れます**。**Why**: 別の呼び出しにすると、その間に失敗したとき、`next_notify_at` が NULL のまま残り、予定が黙って通知されなくなるからです。
- **`rev` は変えません**。**Why**: `next_notify_at` はサーバーだけが使う列で、変えると、値だけが変わった行を他の端末へ送り直すことになるからです。
- この計算を入れる前に保存した行の値は、NULL のままで、**埋め直しは作りません**（ユーザーの回答。保存し直すと、その時点で計算される）。
- **計算が例外を投げたとき（バグ）は、その系列の値を NULL にして、書き込みは成功させます**（ログに、系列の id と例外を出す）。**Why**: 通知の計算のバグで保存が失敗すると、端末が再送し続けるか、4xx で捨てて、予定そのものを失うからです。

### 9.3 定期実行で送る（実装 11b）

実装は `src/worker/cron.ts`、Discord への送信は `src/worker/notify/discord.ts` です。数値（行数・秒数）の根拠と、SQL の書き方の Why は、コードのコメントにあります。

- **1 分ごとに動かします**（`wrangler.jsonc` の `triggers.crons`）。**Why**: 通知を、指定した時刻から 1 分以内に届けるため（NT-5）。無料プランの Cron Triggers は、アカウント全体で 5 個までで、これが 1 個目です（[要件定義書 7章](../requirements/requirements.md#7-システム構成前提)）。

**1 回の実行**

1. 時刻が来た行を、**時刻が新しい順に、10 行まで**取ります（残りは、次の分が拾う）。**Why 新しい順なのか**: 古い順だと、遅れた行や、壊れて値が進まない行が枠を占め、時刻どおりの新しい通知が遅れるためです。**Why 10 行なのか**: 無料プランの CPU 時間（1 回 10ms）と、サブリクエストの上限（1 回 50 回）に収めるためです。
2. 行ごとに、その系列を読み直し、送る回が、まだその行の回かを確かめます。**Why**: ほぼ同時の操作の割り込みで、もうない回の古い値が残ることがあるためです。もうその行の回でなければ、送らずに、値を計算し直します。
3. **先に `next_notify_at` を次の回に進めてから、送ります**。**Why**: 逆の順番だと、送った後で更新に失敗したときに、同じ通知が毎分届き続けます。この順番なら、最悪でも「1 回届かない」で済みます。
   - 更新は、読んだときの値のままの行にだけ行います。変わっていたら、別の実行か保存が先に変えたので、送りません（二重に送らないため）。
4. 次の条件を満たすときだけ、送ります（満たさなくても、値は進める。進めないと、毎分、同じ行が見つかり続けるため）。
   - **通知の時刻からの遅れが、10 分未満**（[Q10](#q10-大きく遅れた通知)）。
   - **その予定のワークスペースが、削除されていない**（画面と同じ判定。`shared/workspace.ts`）。表示の ON/OFF は見ません（[9.2](#92-保存したときの計算実装-11a)）。ワークスペースは、1 回の実行で 1 回だけ読みます（行ごとに読むと、サブリクエストの上限を超えるため。10 行で、D1 と Discord の呼び出しは最大 42 回）。
   - `notify_enabled` が true。

- **1 行で例外が起きても、ほかの行は続けます**（ログに、行の id と例外を出す。予定の題名などの中身は出さない）。
- **1 回の実行は、20 秒を過ぎたら、残りの行を次の分に回します**。**Why**: Discord の待ちが重なって、毎分の実行が重ならないようにするためです。
- **定期実行の失敗（壊れた行・Discord への送信が続けて失敗する）は、知らせる仕組みを作らず、ログだけにします**（ユーザーの回答）。**Why**: 壊れた行は、画面を開いたときの読み込みも 500 にするので、[6.5](#65-電波がない間の動き)の知らせで気づけます。Discord の失敗の主な原因は、Webhook の削除（自分の操作）か Discord の障害で、知らせても、届かなかった通知は戻りません。

**Discord への送信**

- Webhook の URL（Secret `DISCORD_WEBHOOK_URL`）に、`{ content, allowed_mentions: { parse: [] }, flags: 4 }` を送ります。
  - `allowed_mentions`: タイトルに `@everyone` と書いた予定があっても、全員への通知にしないため。
  - `flags: 4`（リンクのカードを付けない）: リンクの先は Access の後ろにあり、ログインの画面のカードが、毎回付くおそれがあるため。
- **失敗したら、その場で 1 回だけ再送します**。**Why 1 回だけなのか**: 何度も再送すると、Discord が落ちているときに、ほかの通知まで遅らせるためです。
- レート制限（429）は、ヘッダーの秒数だけ待ってから再送します。待つのは最大 5 秒、1 回の送信の待ちは最大 10 秒です（毎分の実行が重ならないようにするため）。
- **ログに、Webhook の URL を出しません**（例外のメッセージと応答の本文も出さない）。**Why**: URL を知っていれば、誰でも、そのチャンネルに投稿できるためです。
- **`DISCORD_WEBHOOK_URL` が設定されていないとき**は、送らず、値は進めて、ログで知らせます。

**残る限界**（いずれも、直すと作りが重くなり、起きても通知が 1 回多い・1 分遅いだけなので、直さない。[P3](#p3)）

- 保存が分の境目をまたぐと、同じ回が、1 分遅れで、もう一度届くことがある（保存が、定期実行の進めた値を、同じ回の値で上書きするため。直すには、最後に送った時刻を覚える列が要る）。
- Discord が投稿を受け付けたあとで、応答がタイムアウトすると、再送で同じ通知が 2 回届くことがある（届かないより害が小さい）。
- 止まっていたあとの最初の実行で、遅れた回を飛ばした先の回が、1 分、余計に遅れることがある。

### 9.4 通知の文面

```
🔔 10分後: 歯医者
10/19（月）15:00〜16:00
📍 ○○歯科
https://calendar.ataraman.com/day/2026-10-19
```

文面は `src/worker/notify/message.ts` が作ります（予定もタイムブロックも同じ）。言い回しの細部は、そのテストにあります。

- **1 行目は `🔔 {いつ}: {題名}`**。「いつ」は、時間指定なら、通知の分で決めます（0 は「今から」、10 は「10分後」、90 は「1時間30分後」）。終日なら、通知の日と開始日の差で決めます（「今日」「明日」「N日後」）。**Why 終日は「何分後」で言わないのか**: 終日の通知の分は、開始日の 0:00 からの分で、「朝 6 時」を「6時間後」と言っても伝わらないためです。複数日の終日は、題名のあとに期間を付けます。
- **2 行目は、時間指定だけ**（日時。日をまたぐときは、終わりにも日付を付ける）。
- **場所があれば `📍 場所`**。
- **最後の行は、その回の開始日の日表示へのリンク**です。**Why**: 通知から 1 タップで、その日の詳細を開けるようにするためです。URL の頭（`APP_ORIGIN`）は、`wrangler.jsonc` の `vars` に書きます（コードに書き込むと、ドメインを変えたときに直し忘れるため）。
- **Discord の上限（2000 文字）を超えるときは、題名と場所を切り詰めます**（日時とリンクは切らない）。**Why**: 超えると、Discord が 400 を返し、通知が届かないためです。

### 10.2 Worker 側の確認（二重の守り）

Access を通ったリクエストには、Access が署名した JWT（`Cf-Access-Jwt-Assertion` ヘッダー）が付きます。Worker は `/api/*` のすべてのリクエストで、API の処理をする前に、毎回これを確認します（`src/worker/auth.ts`）。

1. JWT の署名が、自分の Access の公開鍵で正しく検証できるか（RS256 だけ。期限のない JWT は受け付けない）
2. JWT の発行元（`iss`）と宛先（`aud`）が、このアプリのものか
3. JWT のメールアドレスが、許可したアドレスと同じか（大文字小文字は区別しない）。サービストークンの場合は、`common_name`（Client ID）が、許可した ID と同じか（サービストークンの JWT には `email` が付かないため。許可する ID が未設定なら、一切通さない）

どれか1つでも満たさなければ 403 を返します。

- **Why Access があるのに Worker でも確認するのか**: Cloudflare 公式が、「アプリを完全に守るには JWT を検証することが重要」としているからです。Access の設定ミスや、Access を通らない URL があっても、データは守れます。
- **本文には理由を入れず、理由は Worker のログにだけ残します**（どこで弾かれたかが、攻撃者への手がかりになるため）。ログには、食い違った項目の名前までを出し、値（JWT の中身・設定の値）は出しません。
- **設定（`ACCESS_TEAM_DOMAIN`・`ACCESS_AUD`・`ALLOWED_EMAIL`）が空・書式が違うときは、500 で拒否します**。**Why**: 設定漏れのまま、確認が素通りしないようにするためです。こちらの設定の問題なので、403 とは分けます。
- `workers.dev` の URL とプレビュー URL は、無効にします。入口は Custom Domain の1つだけにします。**Why**: これらは別の入口なので、Access の保護がかかりません。

### 10.3 その他の対策

| 対策 | 内容 | Why |
| --- | --- | --- |
| 入力チェック | API で Zod を使い、型・長さ・形式を確認する | MCP など画面以外から来る入力も、DB に入る前に止めるため |
| SQL | プレースホルダ（`?`）を使い、文字列をつなげて SQL を作らない | SQL インジェクションを防ぐため |
| URL 欄 | `http://` と `https://` で始まるものだけをリンクにする | `javascript:` で始まる URL を押したときに、スクリプトが実行されるのを防ぐため |
| 他サイトからのリクエスト | API は、すべてのメソッドで、`Sec-Fetch-Site` が `same-origin` でなければ（ないときも）403。`GET`・`HEAD` 以外は、本文の有無に関係なく `Content-Type: application/json` でなければ 415。サービストークン（MCP）だけは、`Sec-Fetch-Site` を確かめない（[13.2](#132-認証と他サイトからのリクエストの確認)） | 他のサイトから、ログイン状態を悪用して書き込まれたり、読み取られたりするのを防ぐため |
| API の応答のヘッダー | `X-Content-Type-Options: nosniff`、`Cache-Control: no-store`、`Referrer-Policy: no-referrer`（エラーにも付ける） | 応答を別の種類として解釈されたり、予定のデータがキャッシュや履歴に残ったりするのを防ぐため |
| CSP ヘッダー | 自分のドメインのスクリプト・スタイル・画像・フォント・通信だけを許す（`data:` の画像も許さない）。`object-src 'none'`、`frame-ancestors 'none'`、`base-uri` と `form-action` は自分のドメインだけ | 万一 XSS があっても、被害を広げないため |

- **`Sec-Fetch-Site` がないとき（ブラウザ以外）も 403 にします**。**Why**: 厳しい形なら判定も単純になり、今のブラウザは必ず付けるので、画面は通るからです。
- **`Content-Type` は、本文の有無に関係なく必須にします**。**Why**: 書き込みの API はすべて JSON の本文を持つので、正しいリクエストは必ず満たします。本文があるときだけ確かめる形は、環境で結果が変わります。
- **画面の zod は jitless にし、`'unsafe-eval'` は CSP に足しません**（`src/client/zodConfig.ts`。`main.tsx` の最初の import にする）。**Why**: zod は、スキーマを作るときに `new Function` を試し、CSP の違反が記録されます。`'unsafe-eval'` を足して黙らせると、XSS の被害を広げます。
- **CSP の下での書き方**: HTML の `style` 属性や `<style>` 要素は使いません。値が実行時に決まるもの（位置・高さ・ワークスペースの色）だけを、React の `style` プロパティ（CSP の対象外）で与えます。
- 画面（静的ファイル）のヘッダーは、`public/_headers` で付けます（画面は Worker のコードを通らないため）。**CSP は `vite dev` では付かないので、画面の PR では、`vite preview` で、CSP の違反がないことを確かめます**。

### 10.4 秘密情報（NF-3）

| 名前 | 中身 | 置き場所 |
| --- | --- | --- |
| `DISCORD_WEBHOOK_URL` | 通知先の Webhook URL（ログに出さない。未設定なら、通知は送らない） | Secrets |
| `ALLOWED_EMAIL` | ログインを許可するメールアドレス | Secrets（リポジトリにメールアドレスを残さないため） |
| `ALLOWED_SERVICE_TOKEN_ID` | 許可するサービストークンの Client ID | Secrets |
| `ACCESS_TEAM_DOMAIN` | Access のチーム名のドメイン（`<チーム名>.cloudflareaccess.com`。`https://` は付けない） | `wrangler.jsonc` の `vars`（秘密ではない） |
| `ACCESS_AUD` | Access アプリの宛先 ID | 同上 |
| `APP_ORIGIN` | 通知の文面の、リンクの頭（[9.4](#94-通知の文面)） | 同上 |

- 登録の手順は [docs/setup.md](../setup.md) です。
- 手元の開発環境には Access がないので、`.dev.vars`（Git に入れない。例は `.dev.vars.example`）で `AUTH_MODE=dev` を指定し、**かつリクエストのホスト名が `localhost` か `127.0.0.1` のときだけ**、JWT の確認を省略します。**Why**: 「指定しなければ厳しい側」なので、設定を忘れても危険になりません。ホスト名でも絞るのは、誤って本番に `AUTH_MODE` が入っても、効かないようにするためです。
- Secrets と `.dev.vars` の値の型は、`wrangler types` では作られないので、`src/worker/env.ts` に手で書きます。`npm run cf-typegen` は、`--strict-vars=false`（テストで値を差し替えても型エラーにしない）と `--env-file /dev/null`（手元の `.dev.vars` を型定義に混ぜない）を付けます。

| 記念日の横棒 | `#9AA0A6` | 控えめな灰色（HD-2） |
| 今の時刻の線 | `#F28B82` | 日表示で今の時刻を見分けるため |
| タイムブロック | `#3D4A5C` | 時間割は背景の予定なので、予定より目立たなくする（TB-5） |
| ワークスペースの色 | 8色から選ぶ（トマト `#E57373`・オレンジ `#FF8A65`・バナナ `#FFD54F`・バジル `#81C784`・ピーコック `#4FC3F7`・ブルーベリー `#7986CB`・ラベンダー `#B39DDB`・グラファイト `#BDBDBD`。`src/shared/workspaceColors.ts`） | 自由に選べると、暗い背景で読めない色を選ぶことがあるため。Google カレンダーの 8 色を明るくした値で、ユーザーが見本を見て選んだ |

- 祝日・記念日の横棒の色は、組み込みのワークスペースの行の色です（コードに既定値を持たない。色の決め場所を 1 か所にするため）。
- ブラウザが描く部品（プルダウンの一覧・日付の選択画面・スクロールバー）も、暗い配色で描かせます。
- **文字のフォント**（NF-7）: Noto Sans JP（太さ 400 と 700）を、自分のドメインから、文字の範囲ごとに分割したファイルで配信します。**Why**: Google Fonts だと、CSP で外部のサーバーを許可する必要があり、閲覧のたびに外部へ通信が発生するため。分割するのは、日本語のフォントが数MBあるためです。
- **絵文字**（NF-7）: 予定とワークスペースの名前の絵文字は、Noto Color Emoji の **SVG 画像に置き換えて**表示します（`src/client/emoji/`）。
  - **Why フォントではなく画像か**: ブラウザごとにカラー絵文字のフォント形式が違うため。画像なら、どのブラウザでも同じ見た目になります。
  - 画像は、npm の `@iconify-json/noto`（Apache 2.0）から、ビルドのときに作り（`vite-plugins/notoEmoji.ts`）、`/emoji/<パッケージの版>/<key>.svg` で配信します。リポジトリには入れません。**Why**: リポジトリが大きくならず、版が `package-lock.json` で固定され、ビルドで外部と通信しないため。URL に版を入れるのは、1 年間キャッシュさせつつ（電波がない間も出せる）、パッケージを上げたとき、古い画像が残らないようにするためです。
  - ライセンス（Apache 2.0）の全文は、画像と同じ場所（`/emoji/<版>/LICENSE.txt`）に出します。
  - `<img alt="元の絵文字">` にするので、コピーすると元の絵文字になります。画像がない・読み込めない絵文字は、端末の絵文字で出します（例外を投げて、アプリ全体を止めない）。
  - 入力欄の中・Discord の通知・国旗は、端末や Discord 側の絵文字で表示されます（ユーザーが了承）。
- **はみ出た予定名は、「…」ではなく、右端を薄くして切ります**（月表示・日表示。ユーザーの要望）。**Why**: 「…」が 1 文字ぶんの幅を取り、狭いマス（スマホで約 55px）では、見える文字がさらに減るため。
- **フォーム・サイドメニュー・ワークスペースの編集に共通の作り**:
  - **ネイティブの `<dialog>`（`showModal()`）**を使います。**Why**: フォーカスの閉じ込め・Esc で閉じる・背景を操作できなくする、が、追加の部品なしで手に入るため。
  - **開いたら、ブラウザの履歴を 1 つ積み、スマホの「戻る」で閉じます**（URL は変えない。`src/client/historyMark.ts`）。ほかの閉じ方でも、積んだ履歴を戻します。**Why**: 積まないと、開いたまま「戻る」を押したとき、月表示から出てしまうため。
  - **✕・Esc・背景を押す・スマホの「戻る」は、どの段にいても、全部を閉じます**（保存しない。確認も出さない）。段の中の［戻る］だけが、一つ前の段に戻ります。**Why**: 段ごとに履歴を積まず、ダイアログも入れ子にしないため（Esc や「戻る」の扱いが増える）。
  - 背景は、押し始めた位置も背景のときだけ閉じます（`src/client/backdropClose.ts`）。**Why**: 入力欄で文字を選ぶ途中に、指が背景にはみ出して離したとき、閉じて入力を失わないため。
  - **最初の読み込みが終わるまでは、( + )・チェックボックスなど、編集の入口を押せません**。**Why**: 選択肢がなく、エンジンも受け付けないので、入力してから失敗するより、先に押せなくするため。

### 11.2 月表示（MV-1〜10）

```
┌──────────────────────────────────┐
│ ≡   2026年10月           [今日]  │ ← 固定のヘッダー（MV-5・MV-7）
│ 日   月   火   水   木   金   土  │
├──────────────────────────────────┤
│ 27   28   29   30 ┃1 10月 2   3  │ ← 月の境目は階段状の線（MV-3）
│ [祝日名]          ┃[帰省━━━━━━━]  │ ← 祝日・記念日と複数日の予定は横棒（HD-1・MV-9）
│ 15:00 歯医者      ┃ 9:00 会議     │
│━━━━━━━━━━━━━━━━━━━┛ +2件          │ ← 入りきらない分は「+2件」（MV-6）
│ 4    5    6    7    8    9   10   │
└──────────────────────────────────┘
                              ( + )  ← 新規作成ボタン
```

- **仮想スクロール**: 表示できる範囲は1900年1月〜2199年12月です（[Q2](#q2-スクロールできる範囲)）。最初は、今日の週が画面の上から2行目に来るようにします（先週の予定も少し見えるように）。スクロールバーは隠します（数百年分の長さでは、つまみが位置の目安にならないため）。
- **行の高さ**: 「だいたい6週間が見える高さ」を画面の高さから計算し、すべての行で同じにします（MV-6）。**Why**: 高さが揃っていれば、画面上の距離が日数に比例するため（成功の基準）。
- **階段状の線**: マスごとに線を引いて、つなげます（`boundaries.ts`）。年の境目は、もっと太い線にします。
- **固定ヘッダー**: ≡（サイドメニュー）、年月、「今日」ボタン、曜日の見出し、「未送信 N件」です。年月は、いちばん上に見えている週の水曜日の年月です（その月が、その週の4日以上を占めるため）。日表示から戻ったときは、「今日」ではなく、出ていく前の位置を開きます。
- **1日のラベル**: 各月の1日のマスには「10月」、1月1日のマスには「2027年1月」と付けます（MV-5）。
- **予定の並べ方**（MV-9。Googleカレンダーと同じ。`layout.ts`）:
  - 上から、(1) 横棒（祝日 → 記念日 → 複数日の予定 → 1 日だけの終日の予定）、(2) 時間指定の予定（時刻順）です。**Why 祝日・記念日が上か**: 休みかどうかを先に知りたいため（ユーザーの回答）。
  - 複数日の予定と、時間指定でも**日付をまたぐ予定**は、横棒にします（時間指定の 1 行にすると、どの日にかかっているかが分からないため）。横棒の行は、かかる日のすべてで同じです（途中で動くと、1 本の棒に見えないため）。
  - 入りきらない日は、いちばん下の行を「+N件」にします。N は、その日にかかる予定のうち、出せなかった数です（祝日・記念日の横棒も数える）。
  - 横棒と終日の予定は、ワークスペースの色の背景で、文字は、コントラスト比が大きい方（白か `#1F1F1F`）にします。時間指定の予定は、色の小さな丸と、通常の文字色です。
- **祝日・記念日**は、終日の予定と同じ、その日 1 マスの横棒で出します（HD-1・HD-2。ユーザーの要望）。日付の横に名前は出しませんが、**日付の数字の色は残します**（横棒が「+N件」に隠れた日でも、休みだと分かるように）。表示の ON/OFF は、組み込みのワークスペースごとです（WS-3・WS-4）。
- **タイムブロックは出しません**（MV-10）。表示が OFF のワークスペースの予定（WS-3）は、**展開した回から**除きます（先に除くと、例外が抑えていた元の回が現れる。[5.1](#51-エンドポイント)）。
- **タップしたとき**: 日付・空いているところ・「+N件」・祝日と記念日の横棒 → その日の日表示へ（MV-8）。予定 → その回のフォーム。( + ) ボタン → 新しい予定のフォーム。
- **長押し**（MV-11）: 日のマスを 500ms 押し続けると、( + ) と同じフォームを、開始の日付を長押しした日にして開きます。10px 以上動いたら、やめます（スクロールの始まりと取り合わないため）。判定は `longPress.ts` です。
- **ドラッグで日付を移す**（EV-6）: 予定の横棒・時間指定の予定を 500ms 長押し（PC はマウスで掴んで）してから、別の日のマスへ動かして離すと、開始日と終了日を同じ日数だけずらします（時刻と長さは変えない）。繰り返しの予定は、日表示のドラッグ（11.3）と同じく、範囲を聞きます。祝日・記念日の横棒は動かせません。マスの長押し（予定を作る）とは、押す場所（マスか予定か）で分けます。
  - 始まり方（スマホは 500ms の長押しで、その前に 10px 動いたらスクロール。PC は 4px 動いたらドラッグ）と、ドラッグのあとの click を捨てることは、日表示と同じ判定（`dragTracker.ts`）です。動かしている間は、縦のスクロールを起こしません。
  - ずらす日数は、**押したマスと離したマスの差**です（`dragMove.ts`）。複数日の横棒は、押したマスの日ではなく、予定の開始日と終了日を、その日数だけずらします。週をまたいで分かれた横棒は、どの行を掴んでも同じ予定です。同じ日に離したら、何もしません。
  - 範囲（1900〜2199 年）の外へずれるときは、保存しません。範囲の外のマスは落ち先になりません。
  - 動かしている間は、指（マウス）の下のマスを強調します（`dropTarget.ts`）。**Why**: 離すとどの日に落ちるかが、分かるように。保存は日表示と同じ道（`form/move.ts`）です。
- **幅の狭い画面（約 640px 以下。スマホ）では、時間指定の予定の時刻と、1 月 1 日のラベルの年を省きます**（ユーザーの回答）。**Why**: マスが約 55px しかなく、題名が読めないため。**予定の文字は 10px** です（12・11・10px の見比べから、ユーザーが選んだ）。
- **範囲（1900〜2199 年）の外の日**（最初と最後の週にかかる日）は、リンクにせず、薄く出します。
- **読み上げ**: マスのリンクと予定のボタンに、日付を含む名前を付けます（画面ではマスの位置で日付が分かるが、読み上げでは分からないため）。祝日・記念日の横棒は、`<button>` にも `<Link>` にもせず、読み上げません（マスのリンクと重複するため）。
- **画面の切り替え（URL）**は、History API で手書きします（`src/client/navigation.ts`）。日付の形が正しくない・範囲の外・そのほかのパスは、月表示にします。日付のマスは普通のリンク（`<a href>`）です。日表示の［月表示］は、この画面から移ってきたなら、ブラウザの「戻る」と同じにします。
- **スクロールの重さ**（NF-6）:
  - 週ごとの情報は、描く週の分だけ、まとまりで計算して覚え、**行が変わったときだけ**捨てます（`weekViewCache.ts`・`stableRows.ts`）。**Why**: 同期のエンジンは、変更がなくても 60 秒ごとにデータの参照を作り直すので、そのたびに計算し直すと、1 分ごとにスクロールが引っかかるため。
  - `scrollTop` や `clientHeight` を、スクロールや描画のたびには読みません（強制リフローで、フレームの時間を食うため）。

### 11.3 日表示（DV-1〜6）

```
┌──────────────────────────────────┐
│ ≡ [月表示] ‹ 2026年10月19日（月） › [今日]│ ← 前後の日へ（DV-5）
│                         未送信 N件 │ ← 中身がなければ、この行は高さ 0
│ [文化の日                     ]  │ ← 祝日・記念日（押せない。DV-6）
│ [帰省 10/18〜10/21            ]  │ ← 終日・複数日の予定（DV-6）
├──────────────────────────────────┤
│  8:00 │                          │
│  9:00 │┌仕事──────────┐          │ ← タイムブロック（1色）
│ 10:00 ││              │┌会議───┐ │ ← 重なりは横に並べる（DV-4）
│ 11:00 ││              │└───────┘ │
└──────────────────────────────────┘
                              ( + )
```

- **ヘッダー**: ≡、［月表示］、‹ ›、日付（年も出す。範囲が 300 年あり、年が分からなくなるため。幅の狭い画面では省く）、［今日］。日付の文字の色は、月表示と同じです。
- **横の幅**: 上部の欄とタイムラインは、広い画面では中央に寄せ、左右に余白を空けます（PC で、予定が横に伸びすぎて見づらかったため。ユーザーの指示）。項目は、左右に 8px ずつ空けて、項目の外に正時の線が見えるようにします（どの時刻にかかっているか読めるように。ユーザーの指示）。
- **1時間の高さ**: 60px（1 分 = 1px）。項目の最小の高さは 15px（15 分ぶん）で、重なりの判定も、その長さで行います。**Why**: 短い予定でも、タイトルが1行読める高さを確保するため。
- **上部の欄**（DV-6）に出すのは、祝日・記念日と、終日の予定と、**長さが 24 時間以上**の時間指定の予定です（祝日 → 記念日 → 予定の順）。**Why**: タイムラインに入れると、画面全体がその予定で埋まるため（Googleカレンダーと同じ）。
  - **タイムブロックは、長さによらず、タイムラインに出します**（TB-6 が、日付をまたぐタイムブロックを、前の日と次の日に分けて表示するとしているため）。
  - 高さは約 3.5 行までで、超えたら、欄の中でスクロールします（スマホで、タイムラインが見えなくならないように。4 行目を半分見せて、続きがあることを示す）。
  - 祝日・記念日は、押せない項目です（ボタンにしない。Tab で止まるのに、何も起きないのを避ける）。
- **タイムライン**は、0:00〜24:00 を出します。24:00 の線と目盛りも出します（23 時台の項目の終わりが分かるように。ユーザーの要望）。スクロールバーは、細く出します（1 日の長さなので、位置の目安に使えるため）。
- **出す項目**は、月表示と同じ関数（`occurrencesInPeriod`）で求めます（`dayItems.ts`）。
  - **タイムブロックは、ワークスペースの表示 ON/OFF によらず、常に出します**（TB-3・TB-5・DV-2）。予定は、表示が ON のワークスペースのものだけです（WS-3）。
  - 日をまたぐものは、その日の範囲（0:00〜24:00）に切り取ります（TB-6）。時刻の表示は、切り取る前の、元の開始と終了です。
- **重なりの並べ方**（DV-4。`layout.ts`）: 時間が重なる項目をグループにまとめ、グループ内で左から順に空いている列に入れます。幅は「全体の幅 ÷ そのグループの列の数」です（Googleカレンダーと同じ）。**Why 列の数をグループごとに決めるか**: 全体を最大の重なりで割ると、離れた時間の項目まで細くなるため。
- **色**: 予定はワークスペースの色、タイムブロックは `#3D4A5C` です。
- **今の時刻の線**は、**今日の日表示にだけ**出します（ユーザーの回答）。分が変わる瞬間に合わせて更新します。
- **最初に表示する位置**: 今日なら「今の時刻の1時間前」、他の日なら「その日のタイムラインの最初の項目」（なければ 8:00）です。**Why**: 開いたときに、いちばん見たいところがすぐ見えるようにするため。同期でデータが変わっても、動かしません（見ている位置が、勝手に動くため）。
- **タップしたとき**:
  - 空いている時間 → その時刻（15分単位に切り下げ）から1時間の**タイムブロック**を作るフォーム。**Why タイムブロックか**: 日表示は時間割を立てる場所だから（TB-1。予定は月表示の ( + ) から作る）。
  - 予定・タイムブロック → その回のフォーム。
  - **( + ) ボタン** → タイムブロックのフォームを、**見ている日**の、今の時刻の次の正時から 1 時間で開きます（23 時台は 23:00）。
- **左右のスワイプ**（DV-5。`swipe.ts`）: 横に 60px 以上動かして指を離すと、前後の日に移ります。動き始めの向きで、横か縦かを決め、途中で変えません（斜めの指で、スクロールしながら日が動かないように）。**今は、アニメーションしません**（ユーザーの回答。[バックログ](../BACKLOG.md#画面の使い心地の改善)）。
- **日から日へ動くときは、履歴を積みません**（‹ ›・スワイプ・［今日］は、今の履歴を置き換える）。**Why**: 日ごとに履歴を積むと、［月表示］も、スマホの「戻る」も、月表示ではなく、前の日に戻ってしまうため。
- 「未送信 N件」と、読み込みの状態（再試行のボタン）は、日表示にも出します。**Why**: `/day/...` を直接開いて読み込みに失敗したとき、行き止まりになるため。
- **ドラッグで時刻を移す**（EV-6。ユーザーの回答。日表示を先に作り、月表示はあとから足した）:
  - スマホは、予定・タイムブロックを **500ms 長押し**してから動かします。PC は、マウスで掴んでそのまま動かします。**Why**: 押してすぐ動くと、縦のスクロールと見分けられないため。
  - 動かした量を **15 分刻み**にして、開始と終了を同じだけずらします（長さは変えない。10:07 を 15 分下げると 10:22）。**Why**: 1 分は 1px で、指では合わせられないため。細かい時刻はフォームで直します。
  - 離したときに保存します。繰り返しの予定は、離したあとに、フォームと同じ「範囲を聞く段」（この予定のみ／これ以降すべて／すべて）を出します（11.4）。**Why**: フォームで変えるときと同じ動きにして、迷わないようにするため。
  - 日付をまたいで、前後の日へは動かせません（その日の 0:00〜24:00 の中だけ）。**Why**: 日を変えるのは、月表示のドラッグとフォームで行うため。
  - 動かせるのは、その日の中だけに収まる時間指定の項目です（日をまたぐ項目と上部の欄は動かせない）。端では、15 分刻みのまま止まります。終了は、24:00 を書けないので 23:59 までです。
  - PC は、押して **4px** 以上動いたらドラッグです（それより小さい動きはクリック）。スマホは、500ms の前に **10px** 以上動いたら、スクロール・スワイプとして、長押しをやめます。動かしている間は、縦のスクロールと左右のスワイプを起こしません。
  - 動かしている間は、新しい時刻（「10:22〜11:22」）を項目に出します（15 分の短い項目は、題名の代わりに出す）。ずらす量が 0 なら、何もしません。ドラッグのあとの click は、フォームを開かずに捨てます（普通のタップとキーボードは、今どおり開く）。
  - **範囲を聞く段**は、フォームを開かず、その段だけのダイアログで出します（`MoveDialog`）。保存の道は、フォームと同じ（`decideScope` で範囲を決め、`changeEntry` で保存）。繰り返さない予定は、聞かずに保存します。保存できないとき（読み込み中・予定がもうない）は、理由をダイアログで知らせます。**Why not フォームを開く**: 入力の段が一瞬見えるため。やめる（✕・戻る）と、元の位置のままです。
  - 予定の長さを変える（端を引っ張る）操作は、作りません（バックログ）。

### 11.4 フォーム（EV-1〜4・TB-1〜2）

```
┌──────────────────────────────────┐
│ ✕                        [保存]  │
│ ( 予定 | タイムブロック )         │ ← 種類の切り替え（新しく作るときだけ）
│ タイトル ____________________    │
│ □ 終日                           │ ← 予定のときだけ
│ 開始 [2026/10/19] [15:00]        │
│ 終了 [2026/10/19] [16:00]        │
│ ワークスペース [仕事 ▼]          │ ← 予定のときだけ
│ 繰り返し [しない ▼]              │ ← 毎週のときは、下に曜日のトグル
│ 通知 [✓] [ 10 ] 分前             │ ← 終日は「当日 6:00」の表示だけ
│ 場所 ____________________        │
│ URL  ____________________        │
│ メモ ____________________        │
│                       [削除]     │
└──────────────────────────────────┘
```

判断は `src/client/form/` の `.ts`（`values.ts`・`validate.ts`・`build.ts`・`repeat.ts`・`scope.ts` など）に、文言は `messages.ts` にあります。共通の作り（`<dialog>`・履歴・閉じ方）は [11.1](#111-共通) です。

- スマホでは下から出てくるシート、PC では画面中央のダイアログで表示します。**Why**: スマホでは親指が届く下側に、PC では視線の中心に出すのが、操作しやすいため。
- **初期値**:
  - 種類は、月表示から開けば「予定」、日表示なら「タイムブロック」です（月表示は予定を並べる場所、日表示は時間割を立てる場所だから）。
  - 開始は、今日の次の正時、終了は 1 時間後です（Google カレンダーと同じ）。開始を変えたら、長さを保ったまま終了も動かします。
  - ワークスペースは、**新しく作った予定を保存したときに選んでいたもの**を、端末の `localStorage` に覚えて使います（EV-8）。**Why**: 編集で移しただけで次の初期値が変わると紛らわしく、入力の補助なので、端末ごとに違っても困らないため。
  - 通知は、予定は ON・タイムブロックは OFF（NT-4）。時間指定は 10 分前、終日は当日の朝 6 時（`src/shared/notifyDefaults.ts`）。
- **日付と時刻の入力**は、ブラウザ標準の入力欄（`<input type="date">`・`<input type="time">`）です。**Why**: 端末に慣れた選び方で、手早く入れられるため。
- **終日 ⇔ 時間指定を切り替えたら、通知のタイミングは、その形の初期値に戻します**（ON/OFF は変えない）。**Why**: 数の意味が違う（[4.3](#43-各項目の決め方)）ので、そのままだと、終日の「朝 6 時 = -360」が、時間指定の「開始の 360 分後」になるため。種類を切り替えたら、通知は、その種類の初期値に戻します（戻さないと、切り替える順番で、初期値が変わるため）。
- **通知のタイミング**: 時間指定は「[ 10 ] 分前」の入力欄（0〜10080 分）、終日は、入力欄を出さず「当日 6:00」と表示します（NT-3）。API から入った、画面では作れない値は、利用者が変えない限り、書き換えません（[P4](#p4)）。
- **繰り返しの欄**（RP-1・RP-3・RP-6）: 「しない／毎日／毎週／毎月／毎年／平日／休日」です。終わりの指定は出しません。
  - 毎週は、曜日をトグルで複数選びます。毎月・毎年・平日・休日には、決まりの説明（「毎月 31 日。その日がない月は飛ばします」など）を添えます。
  - 開始日がルールに合わないときは、**保存の前に**「最初の回は 10月21日（水）になります」と出します（[4.4](#44-繰り返しのルールrrule-列)。求めるのは shared の `normalizeStart`。[P1](#p1)）。
  - 開いた予定の欄には、系列のルールを出し、送るのは、値を変えたときだけです。**Why**: 変えていないルールまで送ると、別の端末が変えたルールを、上書きするため。
- **繰り返し予定を保存・削除するときは、「この予定のみ／これ以降すべて／すべて」を選ぶ段を出します**（RP-4）。フォームのダイアログの中身を差し替えて出します。
  - **選べる範囲は、shared の `changeEntry`・`deleteEntry` を、手元の行に、範囲ごとに実際に当てて決めます**（`scope.ts`。[P1](#p1)・[P2](#p2)）。サーバーも同じ関数で決めるので、選べた範囲が、サーバーで 4xx になることはありません。
  - 範囲が 1 つだけでも、聞きます（何が起きるかを、利用者が確かめられるように）。ルールか開始日を変えたときは、範囲ごとに、保存したあとの系列の説明（「保存後: 毎月 5 日」など）を、実際に当てた結果から作って出します。
  - どの範囲も選べないとき・開いている回がもうないときは、理由を出して、保存しません（行き止まりにしない）。
  - 範囲を選んで押したとき、もう一度、選べる範囲を確かめてから送ります（段を開いている間に、ほかの端末の変更が届くことがあるため）。
- **入力の確認**は、サーバーと同じ決まり（[4.2](#42-テーブル定義)）で、保存の前に行い、日本語の誤りを欄の近くに出します（[P2](#p2)）。開始・終了と通知の分の誤りは、入力の途中でも出し、ほかは、保存を押したあとに出します（開いた直後の空のタイトルに、誤りを出さないため）。空白だけのタイトルは、誤りにします。
- **保存**は、新しく作るときは下書きを、編集は、変えた項目だけを送ります（[4.5](#45-繰り返し予定の変更削除rp-4)）。何も変えていないなら、何も送らずに閉じます（送ると、編集時刻と rev だけが進むため）。
  - エンジンが受け付けないとき・想定外の例外が起きたときは、フォームを閉じずに、理由を出します（閉じると、保存したつもりで保存されないため）。
  - 場所・URL・メモは、空なら `null`、入力があれば、そのまま保存します。URL の欄は `type="url"` にしません（ブラウザが、前後の空白を黙って取り除くため）。
- **場所**があれば地図へのリンクを、**URL** が http(s) なら開くリンクを、横に出します（新しいタブで開く）。
- **削除**: 確認は出さず、フォームを閉じて、「削除しました［元に戻す］」を 5 秒出します（OT-1。[6.6](#66-削除の元に戻すot-1)）。続けて削除したときは、知らせを並べます（1 つに置き換えると、前の削除を戻せなくなるため）。

### 11.5 サイドメニュー（WS-1〜4）

```
┌──────────────┐
│ メニュー   ✕ │ ← 左から重ねて出す
│ ワークスペース│
│ ☑ ● 予定     │ ← チェックボックス（表示 ON/OFF）・色の丸・名前
│ ☑ ● 仕事     │
│ 祝日・記念日  │
│ ☑ ● 祝日     │
│ ☑ ● 記念日   │
│ [ワークスペースを編集] │
└──────────────┘
```

判断は `src/client/sidebar/` の `.ts`（`workspaceEdit.ts` など）にあります。共通の作りは [11.1](#111-共通) です。

- **サイドメニューは、PC もスマホも、≡ を押すと左から重ねて出します**（ユーザーの回答）。**Why**: PC だけ常に出すと、月表示のマスが狭くなり、画面の作りも 2 通りになるため。
- 中身は、利用者のワークスペース（並び順。予定のフォームの選択肢と同じ関数 `selectableWorkspaces`）と、祝日・記念日です。**表示の ON/OFF は、チェックを変えたら、すぐ保存します**（[Q3](#q3-ワークスペースの表示-onoff-をどこに保存するか)）。
- **ワークスペースの編集**は、予定のフォームと同じ形のダイアログで、3 つの段を、中身を差し替えて出します（ユーザーの回答）。
  - **段 1（一覧）**: 並び順を変える［↑］［↓］と、［＋ ワークスペースを追加］。**Why ドラッグにしないか**: 3 個くらいなら ↑↓ で足り、タッチの処理を作らずに済むため。並べ替えは、`sortOrder` を 0, 1, 2… に振り直して、変わった行だけを保存します。
  - **段 2（名前と色）**: 名前は必須です。同じ名前は作れます（色で見分ける。WS-2）。色は、[11.1](#111-共通) の 8 色からだけ選べます。サーバーは形だけを確かめるので、API から 8 色以外の色が入ったワークスペースは、その色を「今の色」として見本に足します（[P4](#p4)）。**Why サーバーで絞らないか**: 組み込みの「祝日」「記念日」が 8 色以外の色を持つので、絞ると例外が要るため。
    - 新しく作るときの色の初期値は、まだ使っていない最初の色です（`firstUnusedColor`）。
    - **既存の行の保存は、最新の行を土台にして、変えた項目（名前・色）だけを上書きして送ります**。**Why**: ワークスペースは行全体を送るので、開いたときの行を土台にすると、その間にほかの端末が変えた項目（表示の ON/OFF など）まで、戻してしまうため。
  - **段 3（削除の確認）**: 「『仕事』を削除します。中の予定 N 件も削除されます。」（[Q6](#q6-ワークスペースを削除したときの中の予定)）。N は、繰り返しを 1 件と数えます。削除したら、「元に戻す」を 5 秒、ダイアログの中に出します（画面の下の列は、モーダルが開いている間、押せないため）。
- **最後の 1 つは、削除できません**（［削除］を押せなくする）。**Why**: 予定はワークスペースに必ず属する（EV-2）ので、1つもないと予定を作れなくなるため。

## 12. 確認事項（すべて★推奨どおりで確定）

ドラフト（v0.1）で確認し、2026-10-19 に、**すべて★推奨どおり**で確定しました。選ばなかった案も、理由と一緒に残しています。

### Q1. 画面のフレームワーク

**React**（Vue・Svelte などにしない）。**Why**: 使っている人がいちばん多く、仮想スクロールのライブラリも、React 向けがいちばん成熟しているため。

### Q2. スクロールできる範囲

**1900年1月〜2199年12月（300年分）**（スクロールした分だけ行を足す方式にしない）。**Why**: 最初から全部の行がある前提にすると、スクロールが滑らかになり、作りも単純になります。後から行を足す方式は、足した瞬間に表示位置がずれやすいためです。MV-1 の「際限なく」とは厳密には違いますが、300年あれば困りません。

### Q3. ワークスペースの表示 ON/OFF を、どこに保存するか

**すべての端末で共通にする（DB に保存）**（端末ごとに別にしない）。**Why**: 「どの端末から見ても同じ内容」（SY-1）に合わせるため。

### Q4. 食い違ったときに、どちらを正とするか

**編集した時刻が後の方**（サーバーに届いたのが後の方にしない）。**Why**: 電車の中での古い編集が、後で電波が戻って届いたときに、その間にした新しい編集を上書きしてしまうのは不自然なため（SY-3）。

### Q5. 日曜・土曜の日付の色

**日曜は赤、土曜は青**（日曜だけ赤・色を付けない、にしない）。**Why**: 日本の紙のカレンダーで一般的な形で、休みの日がひと目でわかるため。

### Q6. ワークスペースを削除したときの、中の予定

**予定も一緒に削除する**（削除する前に「中の予定 N件も削除されます」と確認する。別のワークスペースに移す・削除できなくする、にしない）。**Why**: ワークスペースは3個くらいで、削除することはめったにないので、いちばん単純な形にします。間違えて消しても、過去7日間の時点に戻せます（OT-2）。

### Q7. デプロイ（本番への反映）の方法

**GitHub の main ブランチに取り込んだら、自動でデプロイする**（手動でコマンドを打たない）。**Why**: 手順を忘れたり、取り込んでいない古いコードをデプロイしたりする事故がないため。

### Q8. 祝日の正式発表の反映方法

**コード内の「上書き一覧」を、必要になったときに手で直す**（内閣府の CSV を毎日取りに行かない）。**Why**: 春分・秋分の天文計算は、過去数十年、正式発表と一致してきました。上書きが要るのは、五輪のような法律の特例のときだけです。CSV を取りに行く方式は、形式が変わると動かなくなり、作る量と壊れる可能性の割に、得るものが少ないためです。

### Q9. 毎年の繰り返しで、2/29 を選んだとき

**うるう年だけ表示する**（2/28 に表示しない）。**Why**: 毎月の繰り返しの「指定日がない月はスキップ」（RP-2）に揃えるため。

### Q10. 大きく遅れた通知

**10分以上遅れた通知は送らない**（どれだけ遅れても送る、にしない）。**Why**: 定期実行が止まると、復旧した瞬間に過去の通知がまとめて届き、役に立たず、うるさいだけのためです。遅れは、**通知を送る予定だった時刻**（`next_notify_at`）から数えます（予定の開始の時刻ではない。ユーザーの回答）。

### 前提（確定）

1. 予定は ( + ) ボタンから作り、日表示の空いている時間をタップするとタイムブロックを作る（11.3・11.4）
2. 24時間以上の時間指定の予定は、日表示ではタイムラインでなく上部の欄に出す（11.3）
3. 場所は名前だけを入力し、Googleマップの検索リンクを自動で作る（4.3）
4. ワークスペースは最低1つ必要で、最後の1つは削除できない（11.5）
5. 「これ以降すべて」で変更・削除すると、それより後で個別に変えた回は元に戻る（4.5。Googleカレンダーと同じ）

## 13. Claude 連携（MCP）

Claude Desktop（PC）から、予定の確認・追加・編集・削除をするための MCP サーバーです（要件 [5.12](../requirements/requirements.md#512-claude-連携mcp)）。決めたことは、ユーザーの回答（MCP Q1〜Q3。すべて推奨どおり）です。

### 13.1 構成

```
Claude Desktop ──(標準入出力)── MCP サーバー（PC の上で動く。.mcpb の拡張機能）
                                   │ HTTPS ＋ サービストークン
                                   ▼
                     Cloudflare Access ──(JWT)── Worker の API（5章）
```

- **Claude Desktop の拡張機能（`.mcpb`）にして配ります**。**Why**: Node.js を入れずに済み、トークンが OS の安全な保管場所に入り、ただの文字のファイルに残らないためです。`.mcpb` は、メインセッションが作って、チャットでユーザーに渡します（使うのは 1 人で、配る仕組みを作るより簡単なため）。
- コードは `mcp/` に置き、本文の形とスキーマは `src/shared/` を使います。
- **MCP サーバーは、API を呼ぶだけで、判定を持ちません**（[P1](#p1)）。食い違い・入力の検証・行の計算は、すべてサーバーの API が行います。

### 13.2 認証と、他サイトからのリクエストの確認

- MCP サーバーは、すべてのリクエストに、サービストークンのヘッダーを付けます。Worker は [10.2](#102-worker-側の確認二重の守り) の `common_name` の確認で通します。
- **サービストークンで入ってきたリクエストだけ、`Sec-Fetch-Site` がなくても通します**（[10.3](#103-その他の対策)）。**Why**: このヘッダーで防ぐのは、悪いサイトがブラウザのログイン状態を勝手に使う攻撃で、ブラウザ経由でしか起きません。サービストークンは、ブラウザのログイン状態とは別の鍵です。MCP がヘッダーを自分で付ける形にしないのは、ブラウザ以外は自由に付けられ、守りにならないからです。
- 接続先は `https://` だけを受け付け、`fetch` は転送を追いません（トークンを、平文や転送先に送らないため）。トークンは、ログに出しません。

### 13.3 ツール

| ツール | 内容 | 呼ぶ API |
| --- | --- | --- |
| `list_events` | 期間の予定・タイムブロックを、繰り返しを展開して返す。祝日・記念日も返す（期間は最大 366 日） | `GET /api/occurrences`（31 日ずつ）・`GET /api/changes?since=0` |
| `list_workspaces` | ワークスペースの一覧 | `GET /api/changes?since=0` |
| `create_event` | 予定・タイムブロックを作る（繰り返しも） | `PUT /api/entries/:id` |
| `update_event` | 予定・タイムブロックを変える（範囲 `this`・`following`・`all`） | `PATCH /api/entries/:id` |
| `delete_event` | 予定・タイムブロックを消す（範囲は同上） | `DELETE /api/entries/:id` |
| `create_workspace` | ワークスペースを作る。色は 8 色から名前で選ぶ | `PUT /api/workspaces/:id` |

- **ワークスペースは、一覧と追加だけ**です（名前・色の変更と削除は、画面でやる）。**Why**: 削除は中の予定もまとめて消えるので、勘違いで起きたときの被害が大きく、めったに使わないためです。
- **「サマリ」の専用のツールは作りません**（Claude が `list_events` の結果を、頼まれた形にまとめる）。
- ツールの入力は、`src/shared/` の入力用のスキーマで確かめます（通らない入力を送る前に、Claude に理由を返せる）。初期値（通知・色）も、画面と同じ shared の関数です。

### 13.4 書き込みの決まり

- `editedAt` は、画面と同じ時計です（[6.4](#64-食い違ったときsy-3)）。新しい行の id は、MCP サーバーが UUID で作ります。
- **通信の失敗と 5xx は、同じ依頼（同じ id・`newId`・`editedAt`）で 1 回だけ送り直します**。**Why**: 1 回目が保存されたのに応答だけが失われたとき、Claude が新しい依頼として作り直すと、予定が 2 つできるからです。同じ依頼なら、2 回目はサーバーが `stale` で捨てます。読み取りは送り直しません。
- 応答は、Claude が利用者に伝えられる短い日本語にします（`mcp/messages.ts`）。

### 13.5 実装の細部

- **ビルド**: `npm run build:mcp` が 1 つの JS ファイルにまとめ、`npm run pack:mcpb` が `.mcpb` を作ります。`npm run build` にも `build:mcp` を入れます（MCP のビルドが壊れたことに、CI で気づくため）。成果物はコミットしません。
- **設定**: 環境変数 `ATARA_CALENDAR_BASE_URL`・`CF_ACCESS_CLIENT_ID`・`CF_ACCESS_CLIENT_SECRET`（`manifest.json` の `user_config` から渡す）。
- **`create_event` は、省略した項目を初期値で補います**（Claude に、毎回すべての項目を渡させないため）。`update_event` で終日かどうかを変えて、通知の分を書かないときも、変更後の初期値を補います（画面と同じ。[11.4](#114-フォームev-14tb-12)）。

## 14. PWA（ホーム画面への追加・電波がなくても開く）

要件 [5.13](../requirements/requirements.md#513-ホーム画面への追加pwa)。決めたことは、ユーザーの回答（PWA Q1〜Q3。2026-11-11。すべて推奨どおり）と、それに沿ったメインセッションの判断です。アプリからの通知（Web Push）は作りません（通知は Discord に届くため。Q1）。

### 14.1 ホーム画面への追加

- `public/manifest.webmanifest` を置きます。開く画面は `/`、ブラウザのバーなし（`standalone`）、背景と上の帯の色は画面の背景色（`#1f1f1f`）です。
- **マニフェストは、Cookie を付けて取りに行かせます**（`<link rel="manifest" crossorigin="use-credentials">`）。**Why**: 画面全体が Cloudflare Access の後ろにあり、Cookie がないと、Access のログイン画面へ転送されて取れないため。
  - それでも実機で追加できないときは、Access に、`/manifest.webmanifest` と `/icons/*` だけを通す（Bypass）設定を足します（ユーザーの作業）。この 2 つはデータを含まないので、通しても予定は漏れません。
- **アイコン**は、暗い背景に、カレンダーの形を描いたものです（Q2）。元の SVG と、PNG（192・512px。丸く切られても欠けない maskable も）を `public/icons/` に置きます。差し替えるときは、この PNG を置き換えます。

### 14.2 Service Worker（電波がなくても開く）

- **自前で書きます**（ライブラリを使わない）。**Why**: 決まりが下の 4 つだけで少なく、Access の転送の扱いを自分で決める必要があるため。依存も増やしません。
- **ページ（`/` と `/day/...`）は、ネットワークを先に使います**。つながらないときだけ、保存したページを返します。Access のログイン画面への転送も、そのまま返します。**Why**: ログインが切れたときに、ログイン画面へ行けるようにするため（保存したページを先に返すと、ログインが切れたことに気づけず、API だけが失敗し続ける）。新しい版も、電波があれば、開いたときに入ります（PW-3）。
- **画面のファイル（`/assets/*`。名前に中身の hash が入る）は、ビルドで一覧を作り、Service Worker を入れたときに全部保存します**。次からは保存したものを使います。**Why**: 電波がない間に、保存していないファイルを要求して、画面が壊れないようにするため（[6.5](#65-電波がない間の動き)）。
- **絵文字の画像（`/emoji/*`）とフォントは、使ったときに保存します**。**Why**: 絵文字は数千個あり（[11.1](#111-共通)）、全部は保存しないため。
- **`/api/*` は扱いません**（そのまま通す）。**Why**: データは、同期の仕組み（6章。IndexedDB）が持っています。二重に持つと、食い違うため。
- **新しい版への切り替え**: `sw.js` はブラウザに覚えさせません（`Cache-Control: no-cache`）。新しい Service Worker は、入ったらすぐ切り替わり、古い保存を消します（Q3）。
- **壊れたとき**: ページはネットワークを先に使うので、直した `sw.js` を出せば、次に開いたときに戻ります。
- **作り方**: `vite-plugins/serviceWorker.ts` が、ビルドの出力から、保存するファイルの一覧と版（ファイル名の hash）を求め、`src/sw/sw.ts` に埋めて `sw.js` を作ります（版はキャッシュの名前に入る）。URL ごとの扱いの判断は `src/sw/rules.ts`。登録は、本番のビルドのときだけ（`src/client/registerServiceWorker.ts`）。**Why**: `vite dev` で登録すると、保存したファイルが開発中の変更を隠すため。
- **細部**: 保存するのは、ok で、転送されていない同じ origin の応答だけです（ログイン画面を「アプリ」として保存しないため）。install では、一覧のファイルに加えて `/` も保存します（古いキャッシュを消すとき、開いたばかりのページも消えるため）。フォント（`.woff2`）は数百個あるので、install では保存せず、使ったときに保存します。
- アイコンの PNG は、`npm run gen:icons`（Playwright）で `icon.svg` から作り、コミットします。**Why**: ビルドにブラウザを入れたくなく、めったに変わらないため。maskable も同じ絵です（絵が、最初から中心の安全な領域に収まっている）。

## 付録A. 運用

### A.1 データの復元（OT-2）

誤操作でデータを消したときは、D1 の Time Travel で過去7日間の任意の時点に戻します。画面は作らず、コマンドで行います。

```sh
# 1. 戻したい時刻を指定して復元する
npx wrangler d1 time-travel restore atara-calendar --timestamp=2026-10-19T12:00:00+09:00
# 2. 端末に全データの読み込み直しをさせるため、epoch を変える
npx wrangler d1 execute atara-calendar --remote --command "UPDATE meta SET epoch = lower(hex(randomblob(8)))"
```

- **Why 2の手順が必要なのか**: 復元すると、通し番号（rev）も過去に戻り、端末が覚えている rev より前の変更を受け取れなくなるため（[6.3](#63-受け取るサーバー--端末)）。

### A.2 無料枠の見積もり（NF-1）

| 項目 | 無料枠 | 見込み |
| --- | --- | --- |
| Worker のリクエスト | 1日10万回（[公式](https://developers.cloudflare.com/workers/platform/limits)） | 定期実行 1,440回 ＋ 同期・編集 数百回 ＝ 1日2,000回程度 |
| 静的ファイルの配信 | 無料・無制限（[公式](https://developers.cloudflare.com/workers/platform/pricing/)） | 画面の HTML・JS・CSS はここに入る |
| CPU 時間 | 1回10ms（DB の待ち時間は含まない） | 定期実行は、1 回に最大 10 行（[9.3](#93-定期実行で送る実装-11b)）。本番の値は[受け入れ確認の 3章](../acceptance.md#3-本番の-cpu-時間) |
| D1 の読み取り | 1日500万行 | 起動時の全件読み込み（数千行 × 1日10回程度）が中心で、数万行程度 |
| D1 の書き込み | 1日10万行 | 編集と通知の更新で、1日数百行程度 |

### A.3 壊れた行が見つかったとき

`GET /api/changes` が、行の構造が壊れていて失敗するときの直し方です（[6.3](#63-受け取るサーバー--端末)）。直すまで、全端末の同期が止まり、画面の下に知らせ（[6.5](#65-電波がない間の動き)）が出ます。定期実行も、その系列の通知を送れません。

1. Worker のログ（`npx wrangler tail`、または Cloudflare のダッシュボード）で、`CorruptRowError` の表名と id を探す。
2. `wrangler d1 execute` で、その行を見て、直すか消す。

```sh
npx wrangler d1 execute atara-calendar --remote --command "SELECT * FROM entries WHERE id = '<ログの id>'"
# 値を直すとき
npx wrangler d1 execute atara-calendar --remote --command "UPDATE entries SET start_date = '2026-10-19' WHERE id = '<ログの id>'"
# 消すとき
npx wrangler d1 execute atara-calendar --remote --command "DELETE FROM entries WHERE id = '<ログの id>'"
```

- 直す値は、`entrySchema`・`workspaceSchema` を満たすこと。**Why**: 満たさない値でも読めますが、その行を書き直す依頼が毎回 500 になり、端末の送信待ちが止まるためです。

### A.4 デプロイ（本番への反映）

main に取り込まれると、GitHub Actions（`.github/workflows/ci.yml` の `deploy`）が本番に反映します（[Q7](#q7-デプロイ本番への反映の方法)）。各ステップの Why は、ワークフローのコメントにあります。

1. 確認（`check`）が通ったときだけ動く。
2. main の最新のコミットでなければ、止める（古いコミットが、後から本番を上書きしないように）。
3. マイグレーションを先に当てる（新しいコードが、新しいテーブルの形を前提にできるように）。
4. `wrangler deploy` で、画面と Worker を入れ替える。

- リポジトリの変数 `DEPLOY_ENABLED` が `true` のときだけ動きます。
- 手で動かすときは、GitHub の **Actions → CI → Run workflow**（main を選ぶ）。main の最新の実行の `deploy` が cancelled か失敗になっていたときも、これで動かします。
- 本番のデータを元に戻せない形で変えるマイグレーションは、マージの前にユーザーに確認します（CLAUDE.md）。

#### 認証情報とログの扱い

このリポジトリは public で、Actions のログは誰でも読めます（手順は [docs/setup.md](../setup.md) の 4.2）。

- デプロイ用の Secret は、GitHub の環境 `production`（`main` だけが使える）に置きます。**Why**: リポジトリの Secret は、PR の側でワークフローを書き換えれば、レビュー前のコードが使えてしまうためです。
- Secret は、wrangler のステップにだけ渡します（`npm ci` や build に渡さず、依存パッケージが乗っ取られたときに盗まれる範囲を狭めるため）。
- ログのメールアドレスは、最初のステップで伏せ字にします（wrangler が、認証エラーのとき、トークンの持ち主のメールアドレスをログに出すため）。

#### マイグレーションの書き方と、戻し方

- マイグレーションは、**1つ前のコードでも動く形**にします。列を消す・名前を変えるときは、PR を2回に分けます。**Why**: マイグレーションを当ててからコードを入れ替えるまでの間と、デプロイが失敗したときは、古いコードが新しいテーブルで動くためです。
- 戻すときは、Squash したコミットを revert します（ふつうは、これだけでよい）。
- テーブルの変更そのものを戻す必要があるときだけ、Time Travel を使います。順番は、(1) revert をデプロイする、(2) Time Travel で戻す、(3) [A.1](#a1-データの復元ot-2) の手順を行う、です。**Why この順番なのか**: 新しいコードが動いたまま Time Travel をすると、古いテーブルで壊れ、Time Travel の後にデプロイすると、戻したはずのマイグレーションがもう一度当たるためです。

#### ログ

- Workers Logs を有効にしています（`wrangler.jsonc` の `observability`。[A.3](#a3-壊れた行が見つかったとき) で、ダッシュボードから探せるように）。
