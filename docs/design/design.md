## 1. 全体構成

```
 ブラウザ（PC・スマホ）
   │  https://calendar.ataraman.com
   ▼
 Cloudflare Access ……… Google ログイン。自分のアカウントだけ通す（AU-1・AU-2）
   │
   ▼
 Cloudflare Worker（1個）
   ├─ 静的ファイル配信 … 画面（React で作った HTML/JS/CSS）
   ├─ /api/*  ………………… データの読み書き（画面と、将来の MCP が使う）
   └─ scheduled ………… 1分ごとの定期実行。通知を探して Discord に送る（NT-5）
         │                         │
         ▼                         ▼
   Cloudflare D1（DB）        Discord Webhook
```

- **Why Worker を1個にまとめるのか**: 画面・API・定期実行で同じコード（日付の計算、繰り返しの展開、祝日の計算）を使うからです。1個にまとめると、デプロイも設定も1回で済みます。

## 2. 技術の選定

| 役割 | 使うもの | Why |
| --- | --- | --- |
| 言語 | TypeScript（画面・Worker の両方） | 画面と Worker で同じロジック（繰り返し・祝日）を1つのコードで共有するため。型があると、日付と時刻の取り違えのようなミスをコンパイル時に見つけられる |
| 画面 | React 19 + Vite | 使っている人がいちばん多く、資料やライブラリが揃っている。特に、無限スクロールに使う仮想スクロールのライブラリが成熟している（[Q1](#q1-画面のフレームワーク)） |
| 仮想スクロール | TanStack Virtual | 画面に見えている週だけを描画するため。数万週ぶんの行を全部描画すると、スマホでは確実にカクつく（NF-6） |
| 画面の状態管理 | Zustand | 小さく（約1KB）、React の外（同期処理）からもデータを更新できるため |
| 画面の切り替え | wouter | 月表示と日表示の2画面しかないので、小さなルーター（約2KB）で足りる。URL が変わるので、スマホの「戻る」操作がそのまま使える |
| API | Hono | Workers 向けに作られた小さなフレームワーク。ルーティングとミドルウェア（認証チェック）を簡潔に書ける |
| 入力チェック | Zod | 画面と API で同じチェックのルールを共有できる。将来の MCP からの不正な入力も API 側で止められる |
| 天文計算 | astronomia（MIT）＋ 間引いた VSOP87 データ | 春分・秋分・夏至・冬至・立春の日付を、太陽の位置から求めるため（[8章](#8-祝日記念日の計算)）。天文計算を自分で一から書くと、係数の書き写し間違いを見つけにくいので、広く使われているライブラリを使う。ただし、astronomia が持つ地球の軌道のデータ（VSOP87）は大きく、そのまま使うと画面のバンドルが重くなる。そこで、振幅の小さい項を捨てたデータを使う。日付の判定には十分な精度であることを、テストで確かめている。数字と作り方は [`src/shared/data/README.md`](../../src/shared/data/README.md) |
| ライセンスの表示 | Vite の `build.license`（`third-party-licenses.md` を出力） | 画面と Worker に組み込んだ依存パッケージ（astronomia・React・Hono など）のライセンス全文を、ビルドの成果物に含めるため。MIT などは、配布物に著作権表示と許諾文を含めることが条件で、ソースのコメントはバンドル時に消えてしまう。画面では `/third-party-licenses.md` で読める |
| DB アクセス | SQL を直接書く（ORM は使わない） | テーブルが3つしかないため。ORM を入れるほどの複雑さがない |
| DB の変更管理 | wrangler の D1 マイグレーション | Cloudflare 標準の仕組みで、追加の道具がいらない |
| 認証の検証 | jose | Cloudflare 公式のサンプルが使っているライブラリ。Access が付ける JWT を検証する（[10章](#10-認証セキュリティ)） |
| オフライン中の保存 | IndexedDB（idb-keyval） | 未送信の変更を、タブが閉じられても失わないように保存する（[6章](#6-同期オフライン)） |
| スタイル | CSS Modules + CSS 変数 | Vite に標準で入っていて、追加の道具がいらない。色は CSS 変数にまとめて、ダークモードの配色を1か所で管理する |
| テスト | Vitest | Vite と同じ仕組み（同じ TypeScript の変換）で動き、追加の設定がほとんどいらない。設定ファイルは `vite.config.ts` と分ける（Cloudflare の Vite プラグインを読み込んだままだと、Vitest が起動時にエラーになって動かないため）。祝日・繰り返し・レイアウトの計算を重点的にテストする。DB の読み書きは、Miniflare（wrangler が中で使っている、ローカルの D1）を Node のテストから起動して、本物の D1 で確かめる。miniflare は、wrangler が依存している版に固定しているので、wrangler を上げるときに合わせて上げる（版がずれると、テストの D1 が、本番の D1 を動かす wrangler と別の動きになりうるため）。`@cloudflare/vitest-pool-workers` は、今の Vitest 5 に対応していない（Vitest 4 が必要）ので使わない。D1 を自作の偽物にしないのは、upsert の条件や `batch()` の動きが本物と食い違うと、テストの意味がなくなるため |
| フォント | Noto Sans JP（@fontsource/noto-sans-jp。自分のドメインから配信） | NF-7。詳細は [11.1](#111-共通) |
| 絵文字 | Noto Color Emoji の SVG 画像（Google の noto-emoji。Apache 2.0） | NF-7。詳細は [11.1](#111-共通) |
| 静的チェック | ESLint + Prettier | 型チェックでは見つからない書き方のミスを見つけ、書式を自動で揃えるため。my-budget と同じ道具にして、プロジェクト間で迷わないようにする |

### 日付・時刻の扱い（全体の方針）

- 日付は `"2026-10-19"`、時刻は `"15:00"` という**日本時間の文字列**で持ちます。内部の計算では、日付を「1970-01-01 から何日目か」の整数に直して扱います。
- 「今」の日付は、端末のタイムゾーンを使わず、UTC に9時間足して求めます。
- **Why**: 要件で日本時間に固定しています（ENV-3）。そして日本には夏時間がありません。そのため、1日は必ず24時間で、日付の足し算は整数の足し算で正しく計算できます。逆に、ブラウザの `Date` をそのまま使うと、海外に行ったときなどに端末のタイムゾーンで日付がずれるバグが起きます。

## 3. ディレクトリ構成

```
atara-calendar/
├─ src/
│  ├─ shared/        画面と Worker の両方で使うコード
│  │  ├─ date.ts         日付の計算（日本時間固定）
│  │  ├─ holidays.ts     祝日・記念日の計算
│  │  ├─ solarTerms.ts   春分・秋分・夏至・冬至・立春の天文計算
│  │  ├─ astronomia.d.ts astronomia の型宣言（ライブラリに型定義が付いていないため）
│  │  ├─ data/           天文計算のデータ（間引いた VSOP87。作り方は README.md）
│  │  ├─ recurrence.ts   繰り返しの展開、「この予定のみ／これ以降／すべて」の処理
│  │  ├─ notify.ts       次の通知時刻の計算
│  │  └─ schema.ts       データの型と入力チェック（Zod）
│  ├─ worker/        Cloudflare Worker
│  │  ├─ index.ts        入口（fetch と scheduled）
│  │  ├─ auth.ts         Access の JWT の検証
│  │  ├─ api/            API の各エンドポイント
│  │  ├─ db/             D1 の読み書き
│  │  │  ├─ rows.ts          DB の行（snake_case）と型（camelCase）の変換と、読み込んだ行の構造の確認
│  │  │  └─ store.ts         差分の読み込みと、食い違いを判定する書き込み
│  │  └─ cron.ts         通知の送信
│  └─ client/        画面（React）
│     ├─ month/          月表示
│     ├─ day/            日表示
│     ├─ form/           予定・タイムブロックの入力フォーム
│     ├─ drawer/         ワークスペースの切り替え
│     └─ sync/           同期とオフライン対応
├─ migrations/       D1 のテーブル定義と、最初から入れる行（[4.2](#42-テーブル定義)）
├─ scripts/          開発用のスクリプト（天文計算のデータの生成）
├─ test/fixtures/    テストの正解データ（内閣府の祝日一覧・国立天文台の暦要項）
├─ test/helpers/     テストで共通に使う道具（テスト用の行の組み立て、Miniflare 上のローカル D1 など）
└─ wrangler.jsonc    Cloudflare の設定
```

- **Why `shared/` を分けるのか**: 繰り返しの展開と祝日の計算は、画面（表示）と Worker（通知）の両方が必要とするからです。同じコードを使わないと、「画面には出ているのに通知が来ない」という食い違いが起きます。

## 4. データ設計

### 4.1 テーブル一覧

| テーブル | 中身 |
| --- | --- |
| `workspaces` | ワークスペース。組み込みの「祝日」「記念日」も行として持つ |
| `entries` | 予定とタイムブロック。両方を1つのテーブルに入れる |
| `meta` | 同期用の通し番号など、1行だけの管理情報 |

- **Why 予定とタイムブロックを1つのテーブルにするのか**: 違いは「ワークスペースがあるか」「終日にできるか」「通知の初期値」の3点だけです。逆に、繰り返し・通知・同期・削除の処理は全部同じです。テーブルを分けると、同じ処理を2回書くことになります。
- 祝日と記念日は DB に入れず、コードで計算します（[8章](#8-祝日記念日の計算)）。

### 4.2 テーブル定義

```sql
-- ワークスペース
CREATE TABLE workspaces (
  id         TEXT PRIMARY KEY,         -- UUID（端末側で発行する）
  name       TEXT NOT NULL,
  color      TEXT NOT NULL,            -- '#RRGGBB'。用意した8色から選ぶ
  sort_order INTEGER NOT NULL,
  visible    INTEGER NOT NULL DEFAULT 1,   -- 表示 ON/OFF（WS-3, Q3）
  builtin    TEXT,                     -- 'holiday' / 'observance' / NULL（WS-4）
  edited_at  INTEGER NOT NULL,         -- 端末で編集した時刻（ms）。食い違いの判定用
  rev        INTEGER NOT NULL,         -- 保存したときの通し番号。差分同期用
  deleted_at INTEGER                   -- 削除した時刻（論理削除）
);

-- 予定とタイムブロック
CREATE TABLE entries (
  id            TEXT PRIMARY KEY,      -- UUID（端末側で発行する）
  kind          TEXT NOT NULL CHECK (kind IN ('event', 'block')),
  title         TEXT NOT NULL,
  workspace_id  TEXT REFERENCES workspaces(id),  -- block は NULL（TB-3）
  all_day       INTEGER NOT NULL DEFAULT 0,      -- block は常に 0
  start_date    TEXT NOT NULL,         -- 'YYYY-MM-DD'
  start_time    TEXT,                  -- 'HH:MM'。終日なら NULL
  end_date      TEXT NOT NULL,         -- 終日: 最終日（その日を含む）／時間指定: 終わる日
  end_time      TEXT,                  -- 'HH:MM'。終日なら NULL
  location      TEXT,                  -- 場所の名前（地図へのリンクは画面で作る）
  url           TEXT,
  memo          TEXT,
  rrule         TEXT,                  -- 繰り返しのルール（JSON）。繰り返さないなら NULL
  until_date    TEXT,                  -- 内部用。「これ以降すべて」で切った系列の最終日
  series_id     TEXT,                  -- 例外の行のとき、元の繰り返し予定の id
  original_date TEXT,                  -- 例外の行が置き換える回の日付
  cancelled     INTEGER NOT NULL DEFAULT 0,      -- 例外で「この回だけ削除」したら 1
  notify_enabled    INTEGER NOT NULL,  -- 通知 ON/OFF（NT-4）
  notify_offset_min INTEGER NOT NULL,  -- 開始の何分前に通知するか（下で説明）
  next_notify_at    INTEGER,           -- 次に通知する時刻（UTC の ms）。サーバーが計算する
  edited_at     INTEGER NOT NULL,
  rev           INTEGER NOT NULL,
  deleted_at    INTEGER
);
CREATE INDEX entries_rev    ON entries(rev);
CREATE INDEX entries_series ON entries(series_id);
CREATE INDEX entries_notify ON entries(next_notify_at)
  WHERE next_notify_at IS NOT NULL AND deleted_at IS NULL;

-- 管理情報（1行だけ）
CREATE TABLE meta (
  id    INTEGER PRIMARY KEY CHECK (id = 1),
  rev   INTEGER NOT NULL,              -- 最後に払い出した通し番号
  epoch TEXT NOT NULL                  -- データを復元したら変える値（付録A.1）
);
```

- マイグレーション（`migrations/0001_init.sql`）は、テーブルのほかに、次の行を最初から入れます。
  - `meta` の 1 行（`rev` = 0。`epoch` はランダムな値）。
  - 組み込みのワークスペース 2 行（WS-4）。固定の id は、祝日が `builtin-holiday`（`builtin` = `'holiday'`）、記念日が `builtin-observance`（`'observance'`）です。色は、[11.1](#111-共通) の祝日・記念日の色です。`sort_order` は大きな値にして、利用者のワークスペースの後ろに並べます。`edited_at` と `rev` は 0 です。
    - **Why 固定の id なのか**: 組み込みは全端末で同じ id である必要があり、表示の ON/OFF も同期の対象だからです（[12章](#12-確認事項すべて推奨どおりで確定)の Q3）。
    - **Why `edited_at` を 0 にするのか**: 端末からの最初の編集（表示の ON/OFF）が、必ず勝つようにするためです（[6.4](#64-食い違ったときsy-3)）。
- `wrangler.jsonc` の D1 の `database_id` は、本番の D1 を作るまで分からないので、仮の値（`00000000-0000-0000-0000-000000000000`）にしてあります。実装 #5（デプロイ）で、本物の値に差し替えます。
- TypeScript の型は、`src/shared/schema.ts` の Zod のスキーマから導きます。名前は camelCase（`start_date` → `startDate`）で、DB の snake_case との対応は、Worker の DB の層（`src/worker/db/rows.ts`）で行います。`rev` と `next_notify_at` はサーバーの都合の列なので、`schema.ts` の型には入れず、読み込み結果で別に持ちます。
  - DB から読んだ行の検証は、`schema.ts` のスキーマとは別に、`rows.ts` の読み込み用のスキーマで行います。確かめるのは行の構造だけです（[6.3](#63-受け取るサーバー--端末)）。
  - 時刻の分は 00・15・30・45 だけです（DV-3）。`24:00` は使わず、終わりが翌日の 0:00 なら、終了日を翌日にして `00:00` と書きます。
  - 項目をまたぐ確認（終日なら時刻が NULL、終了が開始より前でない、など）は、スキーマには入れません。object に refine を付けると、下書きや変更のスキーマを `pick` / `omit` で導けなくなるためです。確かめる場所は、API（実装 #4）を作るときに決めます。
  - 文字列の長さの上限（`title`・`memo`・`url`・`id`）と、日付の年の範囲（1900〜2199 年。[Q2](#q2-スクロールできる範囲)）も、#4 で決めます。スキーマは今、どちらも制限していません。
  - **Why 年の範囲を決めるのか**: 展開（[7章](#7-繰り返しの展開)）が回を生成するのは 1900〜2199 年の間だけなので、範囲外の年の日付が通ると、回が 1 つも出ない系列ができてしまうからです。
- DB への書き込み（`src/worker/db/store.ts`）には、次の決めごとがあります。
  - **書くときにも、すべての行を `entrySchema`・`workspaceSchema` で確かめます**。合わない行が 1 つでもあれば、何も書かずに例外にします。
    - **Why**: API の入力の検証を通らない行も、同じ書き込みで書くからです。サーバーが計算した行（`recurrence.ts` が返す、「これ以降すべて」で作る新しい系列など）がそうです。書き込みの入口で確かめれば、「書けた行は、必ず読める」が、呼び出し側によらず成り立ちます。
  - **書き込みは、表ごとに 1 文の upsert にします**（`INSERT ... SELECT ... FROM json_each(?) ... ON CONFLICT(id) DO UPDATE`）。1 回の書き込みは、`meta.rev` の UPDATE と合わせて、最大 3 文です。
    - **Why**: 1 行ごとに 1 文にすると、ワークスペースの削除（中の予定をすべて論理削除）や、例外の多い系列の削除で、1 回の依頼が数百文になります。D1 には、1 回の呼び出しあたりのクエリ数の上限（無料プランは少ない）があるので、そこに当たるおそれがあるからです。
  - **更新（upsert の DO UPDATE）では、`next_notify_at` を NULL に戻します**。新しい行の INSERT では書かないので NULL です。
    - **Why**: 更新で古い値を残すと、時刻を変えた予定や削除した予定の通知が、変更前の時刻に送られるからです。計算し直すのは、通知を作る実装 #11 です（[9章](#9-通知)）。
  - **更新では、`kind` を書き換えません**（`DO UPDATE SET` に入れません）。
    - **Why**: [4.5](#45-繰り返し予定の変更削除rp-4) の「`kind` は作成した後に変えられない」を、入力の検証だけでなく、DB への書き込みの形でも守るためです。

### 4.3 各項目の決め方

- **ID は端末側で発行する（UUID）**
  - **Why**: 電波がない間に作った予定にも、その場で ID が必要だからです（SY-2）。サーバーが ID を決める方式だと、オフライン中に作った予定を後から編集・削除したときに、どの予定のことか特定できません。
- **通知のタイミングは「開始の何分前か」の1つの数で持つ**
  - 時間指定の予定: そのまま「何分前か」。10分前なら `10`（NT-2）
  - 終日予定: 開始を「その日の 0:00」とみなし、それより後なら負の数にする。朝6時なら `-360`（NT-3）
  - **Why**: こうすると、時間指定と終日で別々の項目を持たずに済みます。通知時刻の計算も「開始 − この数」の1つの式で済みます。
- **場所は名前だけを保存し、地図へのリンクは画面で作る**（`https://www.google.com/maps/search/?api=1&query=場所の名前`）
  - **Why**: 地図の URL を保存すると、名前と URL の2つを入力することになるからです。名前から作れば、入力は1回で済みます。
- **削除は「削除した時刻」を記録するだけにする（論理削除）**
  - **Why**: 削除したことを他の端末に伝えるには、削除の記録が DB に残っている必要があるからです（[6章](#6-同期オフライン)）。データ量は小さいので、消した行を残し続けても問題ありません。

### 4.4 繰り返しのルール（`rrule` 列）

| ルール | JSON | 補足 |
| --- | --- | --- |
| 毎日 | `{"freq":"daily"}` | |
| 毎週 | `{"freq":"weekly","days":[1,3,5]}` | 0=日〜6=土。複数選べる（RP-1） |
| 毎月 | `{"freq":"monthly"}` | 開始日の「日」と同じ日。その日がない月はスキップ（RP-2） |
| 毎年 | `{"freq":"yearly"}` | 開始日と同じ月日。2/29 の扱いは [Q9](#q9-毎年の繰り返しで229-を選んだとき) |
| 平日 | `{"freq":"weekday"}` | 3章の定義で判定（RP-5） |
| 休日 | `{"freq":"holiday"}` | 同上 |

- 1回目は `start_date` です。開始日がルールに合わない場合（例: 月曜を開始日にして「毎週 水・金」を選んだ）は、保存するときに、ルールに合う最初の日へ開始日をずらします。
  - **Why**: 「開始日がルールに合わない1回目」があると、それを繰り返しの回として数えるのかどうかで、処理が分かれてしまうからです。
- 各回の長さ（終了 − 開始）は、1回目と同じにします。
- 毎月の指定日がない月や、2/29 のうるう年でない年は、その日付が存在しないので、数えなくてもスキップになります。

### 4.5 繰り返し予定の変更・削除（RP-4）

Googleカレンダーと同じく、「元の予定（系列）」と「例外の行」で表します。

| 操作 | 何をするか |
| --- | --- |
| **この予定のみ** 変更 | 例外の行を1つ作る（`series_id` = 元の予定、`original_date` = その回の日付、中身は変更後の内容） |
| **この予定のみ** 削除 | 例外の行を作り、`cancelled = 1` にする |
| **これ以降すべて** 変更 | 選んだ回の日付を D として、元の予定の `until_date` を **D の前の日**にして、系列を切る。D 以降は、変更後の内容で新しい系列を作る。`original_date` が D 以降の例外は消す |
| **これ以降すべて** 削除 | 元の予定の `until_date` を **D の前の日**にする。`original_date` が D 以降の例外は消す。1回目を選んだ場合は「すべて」削除と同じ |
| **すべて** 変更 | 元の予定を書き換える。例外の扱いは下のとおり |
| **すべて** 削除 | 元の予定と、その例外を全部削除する |

- 「これ以降すべて」の `until_date` を「前の回の日」ではなく「D の前の日」にするのは、前の回の日を探す必要がなく、展開の結果は同じだからです。
- 元の系列がすでに後ろで切られていて、`until_date` が D の前の日より早いときは、早い方を残します。**Why**: 延ばすと、前に切って消えた回が戻ってしまうからです。

「すべて」変更のときの例外の扱い:
- 「この回だけ削除」した回は、そのまま削除した状態で残します。
- 個別に変えた回には、今回変えた項目だけを上書きします（日時と終日は除く）。値が変わらない行は書き込みません。
- ただし、**開いていた回が例外の行のときは、その例外だけ、日時・終日も含めて、変更をすべて上書きします**（下の Δ ≠ 0 で例外を消す場合を除く）。
  - **Why**: 開いていた回の時刻を変えて「すべて」を選んだのに、その回だけ変わらないのは不自然だからです。
- 通知の分（`notify_offset_min`）は、終日かどうかが（変更後の）系列と違う例外には上書きしません（`notify_enabled` は上書きします）。
  - **Why**: 分の意味が、終日と時間指定で違うからです（[4.3](#43-各項目の決め方)。終日は 0:00 からの分）。上書きすると、終日の「朝6時 = `-360`」が時間指定の例外に入り、開始の 360 分後に通知してしまいます。
- 繰り返しのルールか開始日を変えた場合は、例外をすべて消します。ルールを変えたとは、現在と値が違うことです（曜日の並びだけが違うなら、変えたことになりません）。開始日を変えたとは、下の Δ が 0 でないことです。
- **Why**: 例えば「毎日 ジム」のタイトルを全部変えたときに、以前消した大晦日の回が復活するのは不自然です。ただし、ルールや開始日を変えると、どの例外がどの回に当たるのかが変わります。そのため、その場合だけは例外をリセットします。

- `until_date` は内部だけで使います。画面には「終わりの指定」の入力欄を出しません（RP-3）。

**変更の中身（`changes`）**
- ユーザーが変えた項目だけを渡します。キーがない項目は「変えていない」、`null` は「空にした」です。
  - **Why**: 例えば「すべて」でタイトルだけ変えたとき、個別に決めた回の時刻まで上書きしないために、何を変えたかを区別する必要があるからです。
- 日付と時刻は、フォームに出ていた、その回の値に対する変更後の値です。
- **`kind`（予定・タイムブロック）は、作成した後に変えられません**。`changes` に含めません。
  - **Why**: 予定とタイムブロックは、ワークスペースがあるか・終日にできるか・通知の初期値が違うので（4.1）、作成後に種類だけを変えると、列の組み合わせが合わなくなるからです。
- **「この予定のみ」では、繰り返しのルールを変えられません**（変えようとすると `InvalidChangeError`）。ルールを変えたとは、現在のルールと違うことです（「すべて」と同じ判定。変えていないルールが一緒に渡されても受け付けます）。
  - **Why**: 例外の行は 1 回だけの行で、ルールを持たないからです。ルールを変えたいときは、「これ以降すべて」か「すべて」を選びます。
- 繰り返さない予定は、範囲を無視して、その行を書き換えます。ルールを付けると、開始日を 4.4 のとおりにずらして、繰り返す予定になります。

**日付を変えたときの系列のずらし方（「これ以降すべて」「すべて」で共通）**
- 系列をずらす日数を **Δ** とします。`changes` に開始日があるときは、Δ = 変更後の開始日 − その回の日付（生成された回ならその日、例外の行なら `original_date`）です。開始日がなければ Δ = 0 です。
  - **Why 表示上の開始日から数えないのか**: 別の日に移した例外の回を開いて日付を変えたとき、移した先の日から数えると、移した日数の分だけずれた日にその回が出てしまい、ユーザーが選んだ日にならないからです。
- **日付をずらせる（Δ ≠ 0 にできる）のは、weekly・monthly・yearly だけです**。daily・weekday・holiday で Δ ≠ 0 になると、`InvalidChangeError` にします。ルールを同時に変えたときは、変更後のルールで判定します（繰り返さない予定にする場合は、ずらせます）。
  - **Why**: これらのルールは、開始日が「どの日に回があるか」を決めません。開始日をずらしても回は動かず、最初の回が消えたり、例外が黙って消えたりするだけになるからです。日付を動かしたいときは、「この予定のみ」にします（フォームの動きは [11.4](#114-フォームev-14tb-12)）。
- 系列の開始日・終了日を Δ 日ずらします。「これ以降すべて」なら、新しい系列の開始日は、回の日付 D に Δ を足した日（= 変更後の開始日）です。ずらした開始日がルールに合わなければ、4.4 のとおりにずらします。
- 「すべて」では、`until_date` があれば、それも Δ 日ずらします。
  - **Why**: ずらした後も回の数を変えないためです。ずらさないと、境目の手前に回が増えたり、最後の回が消えたりします。
- ルールを同時に変えていない weekly は、曜日も Δ だけずらします（水・金の回を 1 日後ろにしたら、木・土）。monthly・yearly は、ずらした開始日がそのまま新しい基準になります。
  - **Why**: 開始日だけが動くと、weekly の曜日が合わなくなり、水・金の回を木曜に動かしたのに、系列は水・金のままになるからです。
- 終了日は、変更後の終了日が渡されたときだけ、1 回の長さをそれに合わせます。渡されなければ、Δ だけずらして長さを保ちます。
  - **Why**: 表示中の回の長さから求めると、別の長さに変えた例外の回で、タイトルだけを直したときに、系列全体の長さが変わってしまうからです。

**「これ以降すべて」で作る新しい系列**
- 元の系列の `until_date` を引き継ぎます。日付をずらしたとき（Δ ≠ 0）は、「すべて」と同じく、引き継いだ `until_date` も Δ 日ずらします。
  - **Why**: 元の系列が、前に「これ以降すべて」で後ろを切られていたとき、新しい系列がその先まで続いてしまわないようにするためです。ずらさないと、ずらした後の回の数が変わり、Δ が大きいと回が 1 つも残らなくなります。
- 最初の回（`start_date`）を選んだときは、系列を切らず、「すべて」と同じにします（変更・削除とも）。切ると、1 回も残らない系列ができてしまうからです。

**ルールをなくす（繰り返さない予定にする）**
- 「すべて」でルールを `null` にすると、系列は繰り返さない予定になります。開始日・終了日は、系列の開始日・終了日（上のずらし方を適用した後）です。`until_date` は `NULL` にし、例外はすべて消します。「これ以降すべて」なら、D 以降が、繰り返さない予定の行 1 つになります。

**存在しない回**
- ルールにも例外の行にも当たらない日付を対象にすると、`OccurrenceNotFoundError` にします。見つからない系列・削除済みの系列を対象にしたときも同じです。
  - **Why**: 黙って受け付けると、「この予定のみ」の変更が、存在しない回の予定を新しく作ってしまうからです。「すべて」の削除だけは、回の日付を使わないので確かめません。
- 削除した回（`cancelled` の例外の行）への、「この予定のみ」の変更も、存在しない回として扱います。
  - **Why**: 削除した回は画面に出ていないので、通すと、画面に出ない行に変更が残るだけになるからです。

**エラーの種類**
- 対象が存在しない・削除されている → `OccurrenceNotFoundError`。変更の中身が受け付けられない（「この予定のみ」でルールを変える、daily・weekday・holiday で日付をずらす、など）→ `InvalidChangeError`。
  - **Why**: API（実装 #4）が、「依頼を捨てる」場合（対象がもうない）と「エラーを返す」場合（中身が悪い）を区別するためです。文面（message）では区別しません。

## 5. API 設計

画面も、将来の MCP サーバーも、同じ API を使います（NF-5）。

### 5.1 エンドポイント

| メソッドとパス | 内容 |
| --- | --- |
| `GET /api/changes?since=<rev>` | `since` より後に変わったワークスペース・予定を返す（削除も含む）。`since=0` なら全件（削除済みは除く。初回の読み込みに、削除の記録は要らないため） |
| `PUT /api/workspaces/:id` | ワークスペースの作成・更新 |
| `DELETE /api/workspaces/:id` | ワークスペースの削除（[Q6](#q6-ワークスペースを削除したときの中の予定)） |
| `PUT /api/entries/:id` | 予定・タイムブロックの作成。繰り返さない予定の更新 |
| `PATCH /api/entries/:id` | 繰り返し予定の更新。`scope`（`this` / `following` / `all`）と `occurrence_date` を指定する |
| `DELETE /api/entries/:id` | 削除。繰り返し予定なら `scope` と `occurrence_date` を指定する |
| `GET /api/occurrences?from=&to=` | 期間内の予定を、繰り返しを展開したうえで日付順に返す（祝日・記念日も含む） |

- 書き込みの API はすべて、`edited_at`（端末で編集した時刻）を受け取ります。新しく作る行の ID（「これ以降すべて」で作る新しい系列の ID を含む）も端末から送ります。
- `GET /api/occurrences` は画面では使いません。将来の MCP で「今週の予定を教えて」に答えるためのものです。MVP で一緒に作ります。
  - **Why MVP で作るのか**: 繰り返しの展開は `shared/` にあるので、画面用に作ったものを呼ぶだけで済むからです。実際に動かしておけば、MCP を作るときに API の形で悩まずに済みます。

### 5.2 なぜ「何をしたいか」を送る形にするのか

「これ以降すべて変更」は、行の書き換えとしては「元の系列を切る」「新しい系列を作る」「例外を消す」という3つの操作になります。
画面が行を3つ書き換える形にすると、将来の MCP サーバーも同じ処理を自前で書く必要が出てきます。そこで、API は「どの回を、どの範囲で、どう変えたいか」を受け取り、行の書き換えはサーバー側で行います。

- 画面も同じ処理（`shared/recurrence.ts`）を手元で実行して、すぐ表示に反映します（電波がなくても表示が変わるように）。その後、同じ依頼をサーバーに送ります。
- 端末とサーバーは同じコード・同じ入力で計算するので、同じ結果になります。
- D1 の `batch()`（まとめて実行。途中で失敗したら全部取り消される）で書き込むので、3つの操作のうち一部だけが保存されることはありません。

## 6. 同期・オフライン

### 6.1 方針

- 画面は、起動時に**全データ**をサーバーから読み込んで手元（メモリ）に持ちます。表示はすべて手元のデータから作ります。
  - **Why**: 自分1人の予定なので、何年分あっても数千件・数MB程度です。全部を手元に持てば、スクロールのたびに通信が発生しないので表示が速くなります（NF-6）。電波が切れても、見るのに困りません（SY-2）。
- 変更はまず手元に反映し、その後サーバーに送ります（楽観的更新）。

### 6.2 送る（端末 → サーバー）

```
 編集 ──▶ 手元のデータを更新（すぐ表示に反映）
       └─▶ 送信待ちの列（IndexedDB に保存）──▶ 電波があれば先頭から順に送る
                                              失敗したら、電波が戻ってから再送
```

- 送信待ちの列は IndexedDB に保存します。
  - **Why**: スマホのブラウザは、裏に回したタブを勝手に閉じることがあります。列をメモリにしか持たないと、電車の中で編集した内容が、電波が戻る前に消えてしまいます。IndexedDB に保存しておけば、次に開いたとき（電波がある状態）に送れます。
- 同じ依頼を2回送っても結果は変わりません。ID も編集時刻も端末で決めているからです。そのため、「送れたかどうかわからない」ときは、気にせず再送します。
  - サーバーは、2回目を「もう反映済み」として捨てます。今の行の `edited_at` が、依頼の行の `edited_at` と**同じ**なら捨てる、という決め方です（[6.4](#64-食い違ったときsy-3)）。
  - **Why 同じなら捨てるのか**: 同じ内容をもう一度書いても、行の中身は変わらないのに、通し番号（rev）だけが進みます。他の端末は、その行を差分でもう一度受け取ることになります。同じなら捨てることで、「2回送っても結果は変わらない」が、rev も含めて成り立ちます。
- 途中で古くなって実行できなくなった依頼（別の端末が先に削除した系列への変更など。[4.5](#45-繰り返し予定の変更削除rp-4) の `OccurrenceNotFoundError`）は、API がエラーにせず、「捨てた」として返します。端末は、その依頼を列から外して、次の依頼に進みます（実装は #4c）。
  - **Why**: エラーを返すと、端末は「電波の不調などで失敗した」と判断して、その依頼を列の先頭に残し、再送し続けます。何度送っても同じエラーになるので、列が先頭で止まり、後ろの依頼が送れなくなります。
  - 変更の中身が受け付けられないとき（`InvalidChangeError`）は、これと区別して、エラーを返します（4.5 の「エラーの種類」）。

### 6.3 受け取る（サーバー → 端末）

- `GET /api/changes?since=<最後に受け取った rev>` で、差分だけを受け取ります。
- 受け取るタイミング:
  - 起動したとき
  - 送信が終わったとき
  - 電波が戻ったとき（`online` イベント）
  - タブが前面に戻ったとき
  - 画面を開いている間、60秒ごと
- **Why 通し番号（rev）を使うのか**: サーバーの時刻で「いつ以降」と区切ると、同じミリ秒に2件保存されたときなどに取りこぼす可能性があります。通し番号は保存するたびに1ずつ増える（`meta.rev`）ので、取りこぼしがありません。
- **読み込みは、行の構造だけを確かめます**（型・必須の列・日付と時刻の形・rrule の形。`src/worker/db/rows.ts`）。長さ・年の範囲・15 分刻みのような入力のルールは、読み込みでは確かめず、書き込むときに確かめます（[4.2](#42-テーブル定義)）。
  - **Why 構造だけなのか**: 入力のルールを後で厳しくしたときに、すでに DB にある行が「壊れた行」になって、全端末の同期が止まるのを防ぐためです。
- **構造が壊れた行が 1 行でもあると、差分の読み込み全体が失敗します**（`CorruptRowError`。表名と id をログに出します）。直し方は [付録 A.3](#a3-壊れた行が見つかったとき) です。
  - **Why 壊れた行だけを飛ばさないのか**: 飛ばして返すと、端末は「全部受け取った」と思い込み、その行が永久に届かないまま、気づけなくなるからです。壊れたデータを黙って配らないために、止めて気づけるようにします。
- **Why 即時通知（WebSocket）にしないのか**: 自分1人なので、2台で同時に編集することはまずないからです。タブを前面に戻したときに取りに行けば十分で、仕組みも単純になります。

### 6.4 食い違ったとき（SY-3）

- 行ごとに `edited_at`（端末で編集した時刻）を比べます。届いた依頼の方が新しければ保存し、**同じか古ければ**捨てます（[Q4](#q4-食い違ったときにどちらを正とするか)）。同じなら捨てる理由は [6.2](#62-送る端末--サーバー) です。
- 1つの依頼で複数の行を書き換える場合（「これ以降すべて」など）は、どれか1行でも、サーバー側の方が新しいか同じなら、依頼全体を捨てます。
  - **Why**: 一部の行だけが保存されると、系列が二重になるなど、データの形が壊れるからです。
- サーバーの書き込みは、次の順で行います（`src/worker/db/store.ts`）。
  1. 依頼の行と同じ id の、今の行の `edited_at` を読む
  2. どれか1行でも、今の `edited_at` が依頼の `edited_at` **以上**なら、依頼全体を捨てる
  3. そうでなければ、D1 の `batch()` で、`meta.rev` を1つ増やし、依頼のすべての行をその rev で保存する（表ごとに 1 文の upsert。[4.2](#42-テーブル定義)）。1回の依頼の全行が、同じ rev になる
  - 3 の保存には、「依頼の `edited_at` が、今の行より大きいとき」だけ上書きする条件を付けます。**Why**: 1 と 3 の間に別の書き込みが割り込んでも、新しい行が古い行で上書きされることだけは防ぐためです。
  - **Why 1〜3 を完全に1回の処理にしないのか**: 自分1人の利用で、2台がほぼ同時に同じ行を書く確率が、ごく小さいからです。割り込まれると、依頼の一部の行だけが保存されることはありえますが、新しい行が古い行に上書きされることはありません。
    - 割り込まれて一部の行が弾かれたときは、書けた行数が書こうとした行数より少なくなります。そのときは、表名と行数を Worker のログに出します（id や内容は出しません）。結果は「保存した」のままです。**Why**: 弾かれた行には、別の端末の、より新しい編集が残っているだけで、データは壊れていないからです。失敗にはしませんが、依頼の一部だけが保存されたことは、後から気づけるようにします。
- 画面に出すデータは、「サーバーから受け取った内容」の上に、「まだ送れていない依頼を、手元でやり直した結果」を重ねて作ります（実装は #6）。
  - **Why**: 手元の編集結果をそのまま持ち続けると、サーバーが捨てた依頼の結果が、手元にだけ残り続けてしまいます。他の端末と内容が食い違ったまま、気づけなくなります。受け取った内容から作り直せば、サーバーが捨てた依頼の結果は、その依頼が送信の列から外れた時点で、画面からも消えます。

### 6.5 電波がない間の動き

- 画面の JavaScript は、起動時に**全部**読み込みます（画面ごとに分けて後から読み込む方式にはしない）。
  - **Why**: PWA（Service Worker）は作らないので（スコープ外）、電波がない間は新しいファイルを読み込めません。後から読み込む方式だと、電車の中で日表示を開いた瞬間に画面が壊れます。
- 画面の上部に「未送信 N件」を小さく表示します。
  - **Why**: 電波がない間に保存した変更がまだ他の端末に届いていないことを、知っておけるようにするためです。

### 6.6 削除の「元に戻す」（OT-1）

- 削除すると、手元ではすぐに消えて、画面下に「元に戻す」が5秒間出ます。
- サーバーへの送信は、その5秒が過ぎてから行います。「元に戻す」を押したら送信しません。
- タブを閉じる・裏に回す場合は、5秒を待たずにその時点で送ります。
- **Why 送信を遅らせるのか**: 先に送ってしまうと、「元に戻す」のために削除前の状態を再現する処理が必要になります。繰り返し予定の「これ以降すべて」削除などでは、この処理がかなり複雑になります。送信を遅らせれば、送らないだけで済みます。

## 7. 繰り返しの展開

- 展開とは、繰り返し予定から「その期間の何日に、何時から何時まで」という各回を作り出す処理です。
- 画面: 表示する週の範囲だけを展開します。結果は週ごとに覚えておき、データが変わったら作り直します。
- サーバー: 通知時刻の計算（[9章](#9-通知)）と `GET /api/occurrences` で、同じ関数を使います。
- 手順（1つの系列について）:
  1. `start_date` から期間の終わり（`until_date` があればそこまで）について、ルールに合う日を求める
  2. 例外の行がある日は、例外の内容で置き換える（`cancelled` なら出さない）
  3. 例外の行のうち、日時を別の日に移したものは、移した先の日で出す（`original_date` が期間の外でも、移した先が期間にかかれば出す）

**回が「かかる日」の決め方**
- 終日: `start_date`〜`end_date`（両端を含む）。
- 時間指定: `start_date`〜`end_date`。終了が `00:00` のときは、`end_date` の前の日まで。ただし、開始日より前にはしない（00:00〜00:00 でも、開始日には出す）。
  - **Why**: 終わりの時刻は、その瞬間を含まないからです。そうしないと、毎日の 20:00〜翌 00:00 が、翌日にもかかって見えてしまいます。
- 複数日の回や、日付をまたぐ回（TB-6）は、期間の前から始まっていても、期間にかかっていれば出します。系列は、1 回がかかる日数だけ、期間の手前から探します。
- 例外の行が、期間にかかるかどうかも、同じ決め方で、例外の行自身の日時で判定します。

**例外の行の扱い（細部）**
- 系列が削除されている、または見つからない例外の行は、出しません。
- 同じ回の例外の行が 2 行あるとき（同期の競合で起こりえます）は、`edited_at` が新しい方だけを使います（同じなら id が大きい方）。**Why**: 二重に出さないためです。

**並び順**: 開始の日時の順で、同じ日なら終日が先、それでも同じなら id の順です。**Why**: 入力の並びに依存すると、同じ内容でも結果の並びが変わってしまうからです。

**期間の端**
- `from` が `to` より後なら、空を返します。
- 系列が回を生成する日は、1900-01-01〜2199-12-31 に収めます。
  - **Why**: 祝日の計算が対応するのは 1900〜2199 年だからです（[Q2](#q2-スクロールできる範囲)）。2199 年の最後の週の行は 2200 年の 1 月にかかり、平日・休日のルールが、対応外の年で例外を投げてしまいます。

**展開した回に付ける情報**: 繰り返しの系列の回（系列の例外の回を含む）なら `recurring` が true、繰り返さない予定なら false です。**Why**: 画面（実装 #8）が、「この予定のみ／これ以降すべて／すべて」を選ぶ画面を出すかどうかを、回の中身から決めるためです。

## 8. 祝日・記念日の計算

### 8.1 方針

- 祝日は、ライブラリを使わず、**祝日法のルールを自前で実装**します。
- 春分・秋分・夏至・冬至・立春は、太陽の位置の**天文計算**で求めます。計算には **astronomia**（太陽の視黄経と ΔT）と、間引いた VSOP87 のデータを使います（理由は[2章](#2-技術の選定)の表）。
- 計算できる年は 1900〜2199 年です（[Q2](#q2-スクロールできる範囲)）。範囲外の年は例外にします。
- 正式な発表と食い違ったときのために、コード内に「上書き一覧」を持ちます（[Q8](#q8-祝日の正式発表の反映方法)）。祝日と記念日の2つがあります。
  - **Why 記念日にもあるのか**: 節分・夏至・冬至は、春分・秋分と同じく天文計算で決まる日で、国立天文台の発表と食い違うことがあるからです（HD-5）。固定日と第n曜日の記念日は、食い違いようがありません。
- **Why 祝日のルールにライブラリを使わないのか**: 既存のライブラリの多くは祝日の「一覧データ」を持つ方式で、数十年先までしか対応していません。HD-5 の「何年先でも」を満たせないのです。また、記念日（節分・夏至・冬至）と年末年始の判定は、どちらにしても自分で書く必要があります。

### 8.2 祝日の計算

1. 祝日法の各祝日を、「何年から何年まで、どのルールか」の表で持つ
   - 例: 成人の日は「1月15日（1949〜1999年）」→「1月の第2月曜（2000年〜）」
   - 例: 天皇誕生日は「4/29（〜1988年）」→「12/23（1989〜2018年）」→「2/23（2020年〜）」
   - 2020・2021年の五輪による海の日・スポーツの日・山の日の移動も、年を限った行として、この表に入れる
   - 祝日法の施行（1948-07-20）より前の年は、どの行にも当てはまらないので、祝日がない
2. 一度きりの祝日を表で持つ（1959年と1993年の結婚の儀、1989年の大喪の礼、1990年の即位礼正殿の儀、2019年の即位の日と即位礼正殿の儀）
   - 国民の祝日として扱い、国民の休日の判定でも祝日に数える
3. 振替休日（名前は「振替休日」）: 1973年4月12日以降に、祝日が日曜にあたったとき
   - 2006年まで: その翌日（月曜）
   - 2007年から: その日より後で、最も近い祝日でない日
4. 国民の休日（名前は「国民の休日」）: 1986年以降に、前の日と次の日がどちらも祝日である日。ここでの祝日は、2 までの表の祝日だけで、振替休日と国民の休日は数えない
   - 2006年まで: その日が日曜、または振替休日のときは除く
   - 2007年から: その日が祝日でないとき
   - 振替休日にも国民の休日にもあてはまる日は、振替休日にする（例: 1987-05-04。5/3 が日曜で、5/3 と 5/5 の祝日に挟まれている）
   - **Why 年が変わる境目を見ないのか**: 12/31 と 1/1 の前後を祝日が挟む並びはなく、振替休日も年内の翌日（12/24 や 1/2）に収まるため
5. 春分の日・秋分の日: 太陽の黄経が0度・180度になる瞬間を含む日（日本時間）
6. 最後に祝日の上書き一覧を適用する。追加は `{ date, name }`、削除は `{ date, name: null }`
   - **Why 上書きの後で振替休日などを計算し直さないのか**: 上書きは、内閣府が発表した結果（振替休日・国民の休日を含む）をそのまま反映するためのものだからです。計算し直すと、発表と食い違う日が出るおそれがあります

**画面に出す祝日名**: 内閣府の一覧では「休日」と書かれている日は、画面では「振替休日」か「国民の休日」に書き分けます。2019年の「休日（祝日扱い）」は、5/1 を「即位の日」、10/22 を「即位礼正殿の儀」と表示します。

### 8.3 記念日の計算（HD-3）

| 記念日 | 計算 |
| --- | --- |
| 節分 | 立春（太陽の黄経が315度）の前の日 |
| 夏至・冬至 | 太陽の黄経が90度・270度になる日 |
| 母の日・父の日 | 5月の第2日曜・6月の第3日曜 |
| その他 | 固定の日付（2/14、3/3、3/14、7/7、10/31、12/24、12/25、12/31） |

- 記念日は、日付の決め方（固定日・第n曜日・節気）の表として持ちます（HD-4）。
- 記念日の上書き一覧は、`{ year, name, date }` で、その年のその記念日の日付を差し替えます。記念日の追加・削除は、上書きではなく表を直して行います。名前が表にないものは、打ち間違いに気づけるよう例外にします。
- 同じ日に重なる記念日があります（例: 2026年は夏至と父の日が 6/21）。そのため、記念日は「日付 → 名前」ではなく、日付順の一覧で扱います。
- 休日・平日の判定（RP-5）は、要件定義書3章の定義どおりです。記念日は休日に含めません。コードでは、祝日（国民の祝日・振替休日・国民の休日）より広いので、`isDayOff`（休日）と `isWeekday`（平日）という名前にします。

### 8.4 正しさの確認

- 内閣府が公開している祝日一覧（1955年〜翌年）をテスト用の正解データとして保存し、全件一致することを自動テストで確かめます。
- **Why**: 祝日の計算は、条件の組み合わせ（振替休日と国民の休日が重なるなど）で間違えやすいからです。公式データと全件比べるのが、いちばん確実な確認方法です。
- 内閣府の一覧には夏至・冬至・立春がないので、国立天文台の暦要項（2004〜2027年の立春・春分・夏至・秋分・冬至。暦要項が公開されている年）も正解データとして保存します。計算した日付が一致し、時刻も1分以内で一致することを確かめます（暦要項は分までの表記のため）。
  - **Why**: 節分・夏至・冬至の日付は、天文計算の結果だけで決まります。内閣府の一覧では確かめられないからです。
- 間引いた VSOP87 のデータが、1900〜2199年の5つの節気すべてで、間引く前のデータと日付の判定に十分な精度で一致することも確かめます（許容する差と実測は [`src/shared/data/README.md`](../../src/shared/data/README.md)）。
- 正解データの入手元と更新の手順は [test/fixtures/README.md](../../test/fixtures/README.md) にあります。

## 9. 通知

### 9.1 仕組み

```
 予定を保存 ──▶ サーバーで「次に通知する時刻」を計算して next_notify_at に保存

 1分ごとの定期実行:
   next_notify_at が今以前の行を探す（索引を使うので、該当する行だけを読む）
   └─▶ Discord に送る ──▶ その次の回の通知時刻を計算して next_notify_at を更新
```

- **Why 次の通知時刻を先に計算して保存しておくのか**: 毎分すべての繰り返し予定を展開して「今通知すべきものがあるか」を調べると、D1 の読み取り量と CPU 時間（無料プランは1回10ms）を毎分消費します。先に計算しておけば、毎分の処理は「時刻が来た行を探す」だけで済みます。
- 繰り返し予定の次の回は、最大で9年先まで探します（毎年の繰り返しは1年ずつ、それ以外は1日ずつ進めて探す）。
  - **Why 9年なのか**: 2/29 の毎年の繰り返し（[Q9](#q9-毎年の繰り返しで229-を選んだとき)）は、次の回が最大8年後になるからです（2096年の次のうるう年は2104年）。この計算は保存したときと通知を送ったときにしか動かないので、毎分の処理は重くなりません。

### 9.2 細かい決めごと

- 送る順番: 先に `next_notify_at` を次の回に更新し、更新できたら Discord に送ります。
  - **Why**: 逆の順番だと、送った後で更新に失敗したときに、同じ通知が毎分届き続けます。この順番なら、最悪でも「1回届かない」で済みます。
- 定期実行が止まっていて大きく遅れた通知（10分以上）は、送らずに次の回へ進めます（[Q10](#q10-大きく遅れた通知)）。
- Discord への送信に失敗したら、その場で1回だけ再送します。

### 9.3 通知の文面

```
🔔 10分後: 歯医者
10/19（月）15:00〜16:00
📍 ○○歯科
https://calendar.ataraman.com/day/2026-10-19
```

- 終日予定は「🔔 今日: 帰省（10/19〜10/21）」のようにします。
- 最後の行は、その日の日表示へのリンクです。
  - **Why**: 通知から1タップで、その日の詳細を開けるようにするためです。
- `@everyone` などのメンションは無効にして送ります。
  - **Why**: タイトルに `@everyone` と書いた予定があっても、サーバー全員への通知にならないようにするためです。

## 10. 認証・セキュリティ

### 10.1 Cloudflare Access の設定

| 項目 | 設定 |
| --- | --- |
| 守る範囲 | `calendar.ataraman.com` 全体 |
| ログイン方法 | Google |
| 許可するユーザー | 自分の Gmail アドレス1つだけ |
| ログインの有効期限 | 1か月（AU-2。Access で選べる最大値） |
| 将来の MCP 用 | サービストークンを1つ発行し、それも許可する |

### 10.2 Worker 側の確認（二重の守り）

Access を通ったリクエストには、Access が署名した JWT（`Cf-Access-Jwt-Assertion` ヘッダー）が付きます。Worker は API の処理をする前に、毎回これを確認します。

1. JWT の署名が、自分の Access の公開鍵で正しく検証できるか（公開鍵は Access の証明書 URL から取得する）
2. JWT の宛先（`aud`）が、このアプリのものか
3. JWT のメールアドレスが、許可したアドレスと同じか（サービストークンの場合は、その ID が許可したものか）

どれか1つでも満たさなければ 403 を返します。

- **Why Access があるのに Worker でも確認するのか**: Cloudflare 公式が、「アプリを完全に守るには JWT を検証することが重要」としているからです。Access の設定ミスや、Access を通らない URL（下記）があっても、データは守れます。
- `workers.dev` の URL とプレビュー URL は、設定で無効にします。
  - **Why**: これらは `calendar.ataraman.com` とは別の入口なので、Access の保護がかかりません。
- 許可するメールアドレスは、コードではなく Cloudflare の Secrets に保存します。
  - **Why**: リポジトリにメールアドレスを残さないためです。

### 10.3 その他の対策

| 対策 | 内容 | Why |
| --- | --- | --- |
| 入力チェック | API で Zod を使い、型・長さ・形式を確認する | MCP など画面以外から来る入力も、DB に入る前に止めるため |
| SQL | プレースホルダ（`?`）を使い、文字列をつなげて SQL を作らない | SQL インジェクションを防ぐため |
| URL 欄 | `http://` と `https://` で始まるものだけをリンクにする | `javascript:` で始まる URL を押したときに、スクリプトが実行されるのを防ぐため |
| 他サイトからの書き込み | API は `Sec-Fetch-Site: same-origin` と JSON 形式のリクエストだけを受け付ける | 他のサイトから、ログイン状態を悪用して書き込まれるのを防ぐため |
| CSP ヘッダー | 自分のドメインのスクリプトだけを実行できるようにする | 万一 XSS があっても、被害を広げないため |

### 10.4 秘密情報（NF-3）

| 名前 | 中身 | 置き場所 |
| --- | --- | --- |
| `DISCORD_WEBHOOK_URL` | 通知先の Webhook URL | Secrets |
| `ALLOWED_EMAIL` | ログインを許可するメールアドレス | Secrets |
| `ACCESS_TEAM_DOMAIN` | Access のチーム名のドメイン | 通常の設定（秘密ではない） |
| `ACCESS_AUD` | Access アプリの宛先 ID | 通常の設定（秘密ではない） |

- 手元の開発環境（`wrangler dev`）には Access がないので、`.dev.vars`（Git に入れないファイル）で `AUTH_MODE=dev` を指定したときだけ、JWT の確認を省略します。
  - **Why**: 本番の設定にはこの値を書かないので、本番で確認が省略されることはありません。「指定しなければ厳しい側」にしておけば、設定を忘れても危険になりません。

## 11. 画面設計

### 11.1 共通

- 画面は「月表示」と「日表示」の2つです。どちらにも同じ形のフォームとサイドメニューが付きます。
- URL: 月表示は `/`、日表示は `/day/2026-10-19`
- JavaScript が無効なブラウザでは、画面が真っ白にならないよう「JavaScript を有効にしてください」と表示する（`<noscript>`）。
  - **Why**: 画面はすべて JavaScript で描くので、無効だと何も表示されず、原因がわからないため。
- **配色**（ダークモードのみ。NF-4）:

| 用途 | 色 | Why |
| --- | --- | --- |
| 背景 | `#1F1F1F` | 真っ黒（`#000`）より目が疲れにくい。Googleカレンダーのダークモードに近い |
| 文字 | `#E3E3E3` | 真っ白より、まぶしさが少ない |
| 月の境目の線 | `#8E918F`（2px） | 普通のマス目の線（`#3C4043`, 1px）より明るく、太くする（MV-3） |
| 年の境目の線 | `#E3E3E3`（3px） | 月の境目よりさらに目立たせる（MV-4） |
| 祝日の日付 | `#F28B82` | 暗い背景でも読める赤（HD-1） |
| 記念日の名前 | `#9AA0A6` | 控えめな灰色（HD-2） |
| タイムブロック | `#3D4A5C`（青みのある灰色） | 予定（ワークスペースの色）より目立たない色にする。時間割は背景の予定で、予定の方を目立たせたいため（TB-5） |
| ワークスペースの色 | 8色から選ぶ（トマト・オレンジ・バナナ・バジル・ピーコック・ブルーベリー・ラベンダー・グラファイト相当の、暗い背景向けの色） | 自由に色を選べると、暗い背景で読めない色を選んでしまうことがあるため |

- **文字のフォント**（NF-7）: Noto Sans JP（太さは 400 と 700 の2種類）を、自分のドメインから配信します。
  - **Why 自分のドメインから配信するのか**: Google Fonts の配信サーバーを使うと、CSP（10.3）で外部のサーバーを許可する必要があり、外部のサービスに閲覧のたびに通信が発生します。自分のドメインから配信すれば、Access の内側で完結します。
  - 文字の範囲ごとに分割されたファイル（`unicode-range`）を使い、画面に出ている文字を含むファイルだけを読み込みます。
    - **Why**: 日本語のフォントは全部で数MBあり、毎回全部を読み込むとスマホで表示が遅くなるからです。
  - 読み込んだフォントのファイルは、ブラウザに長期間キャッシュさせます。
  - 電波がない間に、まだ読み込んでいない文字が出てきた場合は、その文字だけ端末のフォントで表示されます（この挙動は受け入れる）。
- **絵文字**（NF-7）: 予定のタイトルなどに含まれる絵文字は、Noto Color Emoji の **SVG 画像に置き換えて**表示します。
  - **Why フォントではなく画像にするのか**: カラー絵文字のフォント形式が、ブラウザによって違うからです。Chrome・Firefox は COLRv1 形式に対応していますが、Safari（iPhone を含む）は対応しておらず、OpenType-SVG 形式しか表示できません。しかも、Safari で Noto Color Emoji のフォントを使うと、拡大したときなどに絵文字が消える不具合が報告されています。画像なら、どのブラウザでも同じ見た目になります。
  - 仕組み: 文字列から絵文字を見つけて `<img alt="😀">` に置き換えます。画像は Google の noto-emoji（Apache 2.0）の SVG を静的ファイルとして同梱します（約3,700ファイル。Workers の静的ファイルの上限2万ファイルに収まる）。
  - `alt` に元の絵文字を入れるので、文字をコピーしたときは元の絵文字になります。画像がまだ読み込まれていないとき（電波がない間など）は、端末の絵文字で表示されます。
  - できないこと:
    - **入力欄の中**（タイトルを入力している最中）の絵文字は、画像に置き換えられないので、端末の絵文字で表示されます。
    - **Discord の通知**の絵文字は、Discord 側の絵文字で表示されます。

### 11.2 月表示（MV-1〜10）

```
┌──────────────────────────────────┐
│ ≡   2026年10月           [今日]  │ ← 固定のヘッダー（MV-5・MV-7）
│ 日   月   火   水   木   金   土  │
├──────────────────────────────────┤
│ 27   28   29   30 ┃1 10月 2   3  │ ← 月の境目は階段状の線（MV-3）
│ 祝日名            ┃[帰省━━━━━━━]  │ ← 複数日の予定は横棒（MV-9）
│ 15:00 歯医者      ┃ 9:00 会議     │
│━━━━━━━━━━━━━━━━━━━┛ +2件          │ ← 入りきらない分は「+2件」（MV-6）
│ 4    5    6    7    8    9   10   │
│ ...                              │
└──────────────────────────────────┘
                              ( + )  ← 新規作成ボタン
```

- **仮想スクロール**: 「1970-01-04（日曜）から何週目か」を行の番号にします。表示できる範囲は1900年1月〜2199年12月です（[Q2](#q2-スクロールできる範囲)）。最初は、今日の週が画面の上から2行目に来るようにします。
  - **Why 2行目なのか**: 先週の予定も少し見えるようにするためです。
- **行の高さ**: 画面の高さから「だいたい6週間が見える高さ」を計算し、すべての行で同じ高さにします（MV-6）。マスに入る予定の行数も、この高さから決めます。
  - **Why**: 画面の大きさに合わせつつ、全部の行の高さを揃えるためです。高さが揃っていれば、画面上の距離が日数に比例します（成功の基準）。
- **階段状の線**: マスごとに線を引きます。各月の1日のマスには左側に、各月1〜7日のマスには上側に線を引くと、つながって階段になります。年の境目（1月1〜7日）は、もっと太い線にします。
  - **Why マスごとに引くのか**: 画面全体に1本の線を描く方式だと、スクロールのたびに線の位置を計算し直す必要があります。マスごとに線を持たせれば、ブラウザがスクロールに合わせて動かすだけで済みます。
- **固定ヘッダーの年月**: 画面のいちばん上に見えている週について、水曜日の年月を表示します。
  - **Why 水曜日なのか**: 7日のうち、真ん中の水曜日が属する月が、その週の4日以上を占める月だからです。
- **1日のラベル**: 各月の1日のマスには「10月」と付けます（MV-5）。1月1日のマスには「2027年1月」と付けます。
- **予定の並べ方**: Googleカレンダーと同じにします（MV-9）。
  1. 複数日の予定（横棒）を上に並べる
  2. 終日予定を並べる
  3. 時間指定の予定を時刻順に並べる
  4. 祝日名と記念日名は、日付の数字の横に出す
- **タップしたとき**:
  - 日付・空いているところ・「+2件」 → その日の日表示へ（MV-8）
  - 予定 → その予定の詳細（フォーム）

### 11.3 日表示（DV-1〜6）

```
┌──────────────────────────────────┐
│ ←   10月19日（月） 祝日名   →  [今日]│ ← 前後の日へ（DV-5）
│ [帰省 10/18〜10/21            ]  │ ← 終日・複数日の予定（DV-6）
├──────────────────────────────────┤
│  8:00 │                          │
│  9:00 │┌仕事──────────┐          │ ← タイムブロック（1色）
│ 10:00 ││              │┌会議───┐ │ ← 重なりは横に並べる（DV-4）
│ 11:00 ││              │└───────┘ │
│  ...  │                          │
└──────────────────────────────────┘
                              ( + )
```

- **1時間の高さ**: 60px（15分 = 15px）
  - **Why**: 15分刻み（DV-3）の予定でも、タイトルが1行読める高さを確保するためです。
- **最初に表示する位置**: 今日なら「今の時刻の1時間前」から、他の日なら「その日の最初の予定」から表示します（予定がなければ 8:00）。
  - **Why**: 開いたときに、いちばん見たいところがすぐ見えるようにするためです。
- **重なりの並べ方**（DV-4）: 時間が重なる予定をグループにまとめ、グループ内で左から順に空いている列に入れます。予定の幅は「全体の幅 ÷ 列の数」にします。Googleカレンダーと同じ方式です。
- **日付をまたぐもの**（TB-6）: 23:00〜翌7:00 なら、前の日には 23:00〜24:00、次の日には 0:00〜7:00 として表示します。
- **24時間以上の時間指定の予定**（例: 金曜18:00〜日曜20:00）は、タイムラインではなく上部の欄に出します。
  - **Why**: タイムラインに入れると、画面全体がその予定で埋まってしまうからです。Googleカレンダーと同じ扱いです。
- **左右のスワイプ**（DV-5）: 横方向に指を一定以上動かしたら、前後の日に移ります。縦のスクロールと区別するため、動き始めの向きで判定します。
- **タップしたとき**:
  - 空いている時間 → その時刻（15分単位に丸める）から1時間のタイムブロックを作るフォーム
  - 予定・タイムブロック → その詳細（フォーム）
  - **Why 空いている時間をタップするとタイムブロックになるのか**: 日表示は時間割を立てる場所だからです（TB-1）。予定は ( + ) ボタンから作ります。

### 11.4 フォーム（EV-1〜4・TB-1〜2）

```
┌──────────────────────────────────┐
│ ✕                        [保存]  │
│ ( 予定 | タイムブロック )         │ ← 種類の切り替え
│ タイトル ____________________    │
│ □ 終日                           │ ← 予定のときだけ
│ 開始 [2026/10/19] [15]:[00]      │
│ 終了 [2026/10/19] [16]:[00]      │
│ ワークスペース [仕事 ▼]          │ ← 予定のときだけ
│ 繰り返し [しない ▼]              │
│ 通知 [ON] [10分前 ▼]             │
│ 場所 ____________________        │
│ URL  ____________________        │
│ メモ ____________________        │
│                       [削除]     │
└──────────────────────────────────┘
```

- スマホでは下から出てくるシート、PC では画面中央のダイアログで表示します。
  - **Why**: スマホでは親指が届く下側に、PC では視線の中心に出すのが、それぞれ操作しやすいからです。
- ( + ) ボタンで開いたときの種類の初期値は、月表示なら「予定」、日表示なら「タイムブロック」です。
  - **Why**: 月表示は予定を並べる場所、日表示は時間割を立てる場所だからです。
- **ワークスペースの初期値**（EV-8）: 新しく作った予定を保存したときに選んでいたワークスペースを、端末の `localStorage` に覚えておき、次に予定を作るときの初期値にします。覚えたワークスペースが削除されていたら、並び順が最初のワークスペースにします。
  - **Why 新しく作ったときだけ覚えるのか**: 古い予定を編集して別のワークスペースに移しただけで、次の初期値が変わってしまうと紛らわしいからです。
  - **Why DB ではなく端末に覚えるのか**: 入力を楽にするための補助で、予定のデータそのものではないからです。端末ごとに違っても困らないので、同期の対象を増やさずに済む方を選びました。
- **時刻の入力**: 「時」と「分（00・15・30・45）」の2つの選択欄にします。
  - **Why**: ブラウザ標準の時刻入力は、iPhone では15分刻みの指定が効かず、1分単位で入力できてしまうからです（DV-3）。
- **日付の入力**: ブラウザ標準の日付入力を使います。
  - **Why**: スマホでは、OS の使い慣れた日付ピッカーが出るからです。
- 終了の初期値は、開始の1時間後です。開始を変えたら、長さを保ったまま終了も動かします。
  - **Why**: Googleカレンダーと同じ動きで、開始を変えるたびに終了を直す手間がないからです。
- 種類（予定・タイムブロック）の切り替えは、新しく作るときだけ出します。保存済みの予定では出しません。
  - **Why**: 種類は作成した後に変えられないからです（[4.5](#45-繰り返し予定の変更削除rp-4)）。
- 繰り返し予定（回の `recurring` が true）を保存・削除するときは、「この予定のみ／これ以降すべて／すべて」を選ぶ画面を出します（RP-4）。選べる範囲は、変えた内容で絞ります（[4.5](#45-繰り返し予定の変更削除rp-4)）。
  - 繰り返しのルールを変えたら、「この予定のみ」は出しません。
  - 変更後のルールが daily・weekday・holiday で、日付を変えたら、「この予定のみ」だけを出します。
  - **Why**: 例外の行はルールを持てず、これらのルールは日付をずらせないからです。
  - ルールも日付も変えたときは、どの範囲も受け付けられません。この組み合わせの扱いは、フォームを作るとき（実装 #8）に決めます。
- 削除の前に確認は出しません。代わりに「元に戻す」を出します（OT-1）。

### 11.5 サイドメニュー（WS-1〜4）

- 左上の ≡ で開きます。
- 中身:
  - ワークスペースの一覧（チェックボックスで表示 ON/OFF）
  - 祝日・記念日（チェックボックス）
  - 「ワークスペースを編集」（名前・色・並び順・追加・削除）
- 最初に開いたときは、ワークスペース「予定」を1つ自動で作ります。最後の1つは削除できないようにします。
  - **Why**: 予定はワークスペースに必ず属するので（EV-2）、ワークスペースが1つもないと予定を作れなくなるからです。

## 12. 確認事項（すべて★推奨どおりで確定）

ドラフト（v0.1）で確認した内容です。2026-10-19 に、**すべて★推奨どおり**で確定しました。各質問の選択肢と理由は、経緯をたどれるように残しています。

### Q1. 画面のフレームワーク

- a. React ★推奨
- b. 他に使いたいものがある（Vue、Svelte など）
- Why 推奨: 使っている人がいちばん多く、資料が豊富です。無限スクロールに必要な仮想スクロールのライブラリも、React 向けがいちばん成熟しています。慣れているものや、触ってみたいものがあれば教えてください。

### Q2. スクロールできる範囲

- a. 1900年1月〜2199年12月（300年分） ★推奨
- b. 本当に際限なく（スクロールした分だけ、後から行を足していく）
- Why 推奨: 範囲を決めて最初から全部の行がある前提にすると、スクロールが滑らかになり、作りも単純になります。後から行を足す方式は、スマホ（特に iPhone）で、行を足した瞬間に表示位置がずれやすいからです。300年あれば、実際に困ることはないと考えました。ただ、MV-1 の「際限なく」とは厳密には違うので確認させてください。

### Q3. ワークスペースの表示 ON/OFF を、どこに保存するか

- a. すべての端末で共通にする（DB に保存） ★推奨
- b. 端末ごとに別にする（スマホでは「仕事」を隠す、など）
- Why 推奨: 「どの端末から見ても同じ内容」（SY-1）に合わせるためです。

### Q4. 食い違ったときに、どちらを正とするか

- a. **編集した時刻**が後の方 ★推奨
- b. **サーバーに届いた**のが後の方
- 例: スマホで 10:00 に電波のない電車の中で編集し、12:00 に電波が戻って送信された。その間の 11:00 に、PC で同じ予定を編集していた。
  - a なら 11:00 の PC の編集が残る
  - b なら 10:00 のスマホの編集が残る
- Why 推奨: 「後から保存した方を正とする」（SY-3）の気持ちに近いのは a だと考えました。電車の中での古い編集が、後でした新しい編集を上書きしてしまうのは不自然だからです。

### Q5. 日曜・土曜の日付の色

- a. 日曜は赤、土曜は青 ★推奨
- b. 日曜だけ赤
- c. 色を付けない（Googleカレンダーと同じ）
- Why 推奨: 日本の紙のカレンダーで一般的な形で、休みの日（赤）がひと目でわかるからです。要件では祝日を赤にすることだけを決めていて、土日は決めていなかったので確認させてください。

### Q6. ワークスペースを削除したときの、中の予定

- a. 予定も一緒に削除する（削除する前に「中の予定 N件も削除されます」と確認する） ★推奨
- b. 別のワークスペースを選んで、予定をそちらに移す
- c. 中に予定があるワークスペースは削除できない
- Why 推奨: ワークスペースは3個くらいで、削除することはめったにないと考えました。そのため、いちばん単純な a にしています。間違えて消しても、過去7日間の時点に戻せます（OT-2）。

### Q7. デプロイ（本番への反映）の方法

- a. GitHub の main ブランチに取り込んだら、自動でデプロイする（GitHub Actions） ★推奨
- b. 自分のパソコンから手動でコマンドを打つ
- Why 推奨: PR を取り込むだけで反映されるので、手順を忘れたり、取り込んでいない古いコードをデプロイしたりする事故がないからです。a にする場合、Cloudflare の API トークンを作って、GitHub の Secrets に登録する作業が1回だけ必要です（手順は書きます）。

### Q8. 祝日の正式発表の反映方法

- a. コード内の「上書き一覧」を、必要になったときに手で直す ★推奨
- b. 内閣府の祝日一覧（CSV）を、毎日自動で取りに行く
- Why 推奨: 春分・秋分の天文計算の結果は、過去数十年、正式発表と一致してきました。上書きが必要になるのは、2020年の五輪のような法律の特例があるときだけです（数年に1回程度）。一方、b は内閣府の CSV の形式が変わると動かなくなり、文字コード（Shift_JIS）の処理も必要です。そのため、作る量と壊れる可能性の割に得るものが少ないと判断しました。

### Q9. 毎年の繰り返しで、2/29 を選んだとき

- a. うるう年だけ表示する ★推奨
- b. うるう年でない年は 2/28 に表示する
- Why 推奨: 毎月の繰り返しで「指定日がない月はスキップ」（RP-2）と決めたので、それに揃えました。

### Q10. 大きく遅れた通知

- a. 予定の時刻から10分以上遅れた通知は送らない ★推奨
- b. どれだけ遅れても送る
- Why 推奨: Cloudflare の障害などで定期実行が止まると、復旧した瞬間に過去の通知がまとめて届きます。予定の時刻を過ぎた通知は役に立たず、うるさいだけです。

1. 予定は ( + ) ボタンから作り、日表示の空いている時間をタップするとタイムブロックを作る（11.3・11.4）
2. 24時間以上の時間指定の予定は、日表示ではタイムラインでなく上部の欄に出す（11.3）

## 付録A. 運用

### A.1 データの復元（OT-2）

誤操作でデータを消したときは、D1 の Time Travel で過去7日間の任意の時点に戻します。画面は作らず、コマンドで行います。

```sh
# 1. 戻したい時刻を指定して復元する
npx wrangler d1 time-travel restore atara-calendar --timestamp=2026-10-19T12:00:00+09:00
# 2. 端末に全データの読み込み直しをさせるため、epoch を変える
npx wrangler d1 execute atara-calendar --remote --command "UPDATE meta SET epoch = lower(hex(randomblob(8)))"
```

- **Why 2の手順が必要なのか**: 復元すると、通し番号（rev）も過去に戻ります。端末は「rev 500 まで受け取った」と覚えているので、復元後の rev 450〜500 の変更を受け取れなくなります。`GET /api/changes` は毎回 epoch を返し、端末は覚えている値と違えば全データを読み込み直します。

### A.3 壊れた行が見つかったとき

`GET /api/changes` が、行の構造が壊れていて失敗するときの直し方です（[6.3](#63-受け取るサーバー--端末)）。直すまで、全端末の同期が止まります。

1. Worker のログ（`npx wrangler tail`、または Cloudflare のダッシュボード）で、`CorruptRowError` の表名と id を探す。
2. `wrangler d1 execute` で、その行を見て、直すか消す。

```sh
npx wrangler d1 execute atara-calendar --remote --command "SELECT * FROM entries WHERE id = '<ログの id>'"
# 値を直すとき
npx wrangler d1 execute atara-calendar --remote --command "UPDATE entries SET start_date = '2026-10-19' WHERE id = '<ログの id>'"
# 消すとき
npx wrangler d1 execute atara-calendar --remote --command "DELETE FROM entries WHERE id = '<ログの id>'"
```

### A.2 無料枠の見積もり（NF-1）

| 項目 | 無料枠 | 見込み |
| --- | --- | --- |
| Worker のリクエスト | 1日10万回（[公式](https://developers.cloudflare.com/workers/platform/limits)） | 定期実行 1,440回 ＋ 同期・編集 数百回 ＝ 1日2,000回程度 |
| 静的ファイルの配信 | 無料・無制限（[公式](https://developers.cloudflare.com/workers/platform/pricing/)） | 画面の HTML・JS・CSS はここに入る |
| CPU 時間 | 1回10ms（DB の待ち時間は含まない） | 通知は「時刻が来た行を探す」だけなので収まる見込み（9.1） |
| D1 の読み取り | 1日500万行 | 起動時の全件読み込み（数千行 × 1日10回程度）が中心で、数万行程度 |
| D1 の書き込み | 1日10万行 | 編集と通知の更新で、1日数百行程度 |
