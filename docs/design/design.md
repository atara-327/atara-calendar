## 1. 全体構成

```
 ブラウザ（PC・スマホ）
   │  https://calendar.ataraman.com
   ▼
 Cloudflare Access ……… Google ログイン。自分のアカウントだけ通す（AU-1・AU-2）
   │
   ▼
 Cloudflare Worker（1個）
   ├─ 静的ファイル配信 … 画面（React で作った HTML/JS/CSS）
   ├─ /api/*  ………………… データの読み書き（画面と、将来の MCP が使う）
   └─ scheduled ………… 1分ごとの定期実行。通知を探して Discord に送る（NT-5）
         │                         │
         ▼                         ▼
   Cloudflare D1（DB）        Discord Webhook
```

- **Why Worker を1個にまとめるのか**: 画面・API・定期実行で同じコード（日付の計算、繰り返しの展開、祝日の計算）を使うからです。デプロイも設定も1回で済みます。

## 2. 技術の選定

| 役割 | 使うもの | Why |
| --- | --- | --- |
| 言語 | TypeScript（画面・Worker の両方） | 同じロジック（繰り返し・祝日）を1つのコードで共有するため。型で、日付と時刻の取り違えを防げる |
| 画面 | React 19 + Vite | 使っている人が最も多く、ライブラリが揃っている。仮想スクロールのライブラリが成熟している（[Q1](#q1-画面のフレームワーク)） |
| 仮想スクロール | TanStack Virtual | 見えている週だけを描画するため（数万週を全部描画すると、スマホでカクつく。NF-6） |
| 画面の状態管理 | Zustand | 小さく、React の外（同期処理）からも更新できるため。同期のエンジン（[6章](#6-同期オフライン)）が store を持ち、React は読むだけにする |
| 画面の切り替え | History API（`pushState`・`popstate`）で手書きする。ルーターのライブラリは使わない | 2画面だけで、依存を増やすほどではないため。URL が変わるので、スマホの「戻る」がそのまま使える。細部は [11.2](#112-月表示mv-110) |
| API | Hono | Workers 向けの小さなフレームワークで、ルーティングと認証チェックを簡潔に書ける |
| 入力チェック | Zod | 画面と API で同じルールを共有でき、将来の MCP からの不正な入力も API で止められる |
| 天文計算 | astronomia（MIT）＋ 間引いた VSOP87 データ | 春分・秋分・夏至・冬至・立春を求めるため（[8章](#8-祝日記念日の計算)）。自作すると係数の書き写し間違いを見つけにくい。astronomia のデータはバンドルが重くなるので、振幅の小さい項を捨てたデータを使い、精度はテストで確かめる。作り方は [`src/shared/data/README.md`](../../src/shared/data/README.md) |
| ライセンスの表示 | Vite の `build.license`（`third-party-licenses.md` を出力） | 依存パッケージのライセンス全文を成果物に含めるため（MIT などの条件で、ソースのコメントはバンドルで消える）。画面では `/third-party-licenses.md` で読める。ビルドで作る絵文字の画像（Apache 2.0）は、ここに載らないので、全文を画像と同じ場所（`/emoji/<版>/LICENSE.txt`）に出す（[11.1](#111-共通)） |
| DB アクセス | SQL を直接書く（ORM は使わない） | テーブルが3つしかないため |
| DB の変更管理 | wrangler の D1 マイグレーション | 標準で、追加の道具がいらない |
| 認証の検証 | jose | Cloudflare 公式のサンプルが使っているライブラリ。Access が付ける JWT を検証する（[10章](#10-認証セキュリティ)） |
| オフライン中の保存 | IndexedDB（idb-keyval） | 未送信の変更を、タブが閉じられても失わないため（[6章](#6-同期オフライン)） |
| スタイル | CSS Modules + CSS 変数 | 追加の道具がいらない。色は CSS 変数にまとめて、ダークモードの配色を1か所で管理する |
| テスト | Vitest | Vite と同じ変換で動き、設定がほとんどいらない。設定ファイルは `vite.config.ts` と分ける（Cloudflare の Vite プラグインがあると、起動時にエラーになるため）。祝日・繰り返し・レイアウトの計算を重点的にテストする。DB は、Miniflare（ローカルの D1）を Node のテストから起動して、本物の D1 で確かめる。miniflare は wrangler が依存している版に固定し、wrangler を上げるときに合わせる（版がずれると、D1 の動きが変わりうるため）。`@cloudflare/vitest-pool-workers` は Vitest 5 に対応していない（Vitest 4 が必要）ので使わない。D1 や IndexedDB（`fake-indexeddb`）を自作の偽物にしないのは、実物との食い違いに気づけなくなるため。同期（[6章](#6-同期オフライン)）のテストは、端末のエンジンを Miniflare 上の本物の Worker につなぎ、時計・電波・タブの錠だけを偽物にする。React の画面のテストは、判断をエンジンのテストで確かめているので、今は置かない |
| フォント | Noto Sans JP（@fontsource/noto-sans-jp。自分のドメインから配信） | NF-7。詳細は [11.1](#111-共通) |
| 絵文字 | Noto Color Emoji の SVG 画像。`@iconify-json/noto`（Apache 2.0）から、ビルドのときに作る | NF-7。詳細は [11.1](#111-共通) |
| 静的チェック | ESLint + Prettier | 型チェックでは見つからない書き方のミスを見つけ、書式を揃えるため。my-budget と同じ道具にして、プロジェクト間で迷わないようにする |

### 日付・時刻の扱い（全体の方針）

- 日付は `"2026-10-19"`、時刻は `"15:00"` という**日本時間の文字列**で持ちます。内部の計算では、日付を「1970-01-01 から何日目か」の整数に直して扱います。
- 「今」の日付は、端末のタイムゾーンを使わず、UTC に9時間足して求めます。
- **Why**: 要件で日本時間に固定しており（ENV-3）、日本には夏時間がないので、1日は必ず24時間で、日付の足し算は整数の足し算で正しく計算できます。ブラウザの `Date` をそのまま使うと、海外に行ったときなどに、日付がずれるバグが起きます。

## 3. ディレクトリ構成

```
atara-calendar/
├─ src/
│  ├─ shared/        画面と Worker の両方で使うコード
│  ├─ worker/        Cloudflare Worker
│  └─ client/        画面（React）
├─ migrations/       D1 のテーブル定義と、最初から入れる行・その直し（[4.2](#42-テーブル定義)）
├─ public/           そのまま配信するファイル（静的ファイルのヘッダーを指定する `_headers`）
├─ scripts/          開発用のスクリプト（天文計算のデータの生成）
├─ vite-plugins/     ビルドと `vite dev` に組み込む Vite のプラグイン（絵文字の画像の生成。[11.1](#111-共通)）
├─ third_party/      配布物に含める、第三者のライセンス全文（絵文字の画像の Apache 2.0）
├─ test/fixtures/    テストの正解データ（内閣府の祝日一覧・国立天文台の暦要項）
├─ test/helpers/     テストで共通に使う道具（Miniflare 上のローカル D1、同期の端末、偽の時計・電波・錠など）
└─ wrangler.jsonc    Cloudflare の設定（毎分の定期実行のトリガ `triggers.crons` を含む）
```

- `src/shared/`: 画面と Worker の両方が使うコード。日付の計算・祝日と記念日・繰り返しの展開と変更・ワークスペースの削除・データの型と入力チェック（Zod）・項目をまたぐ確認（`entryRules.ts`。[4.2](#42-テーブル定義)）・API の本文と応答の形（`api.ts`）・日付や URL のパスの表記（`dateFormat.ts`・`paths.ts`。画面と、通知の文面・リンク（[9.4](#94-通知の文面)）が同じものを使う）。
- `src/worker/`: 入口 `index.ts`（`{ fetch, scheduled }` を出す）・認証・セキュリティ・設定の型と、次のフォルダ。
  - `api/`: エンドポイント（[5章](#5-api-設計)）。
  - `db/`: D1 の読み書き。DB の行（snake_case）と型（camelCase）の変換は `db/rows.ts`。
  - `notify/`: 通知の時刻の計算（[9.2](#92-保存したときの計算実装-11a)）と、文面・送信（[9.3](#93-定期実行で送る実装-11b)・[9.4](#94-通知の文面)）。
  - `cron.ts`: 定期実行（`scheduled`）。
- `src/client/`: 入口（`main.tsx`・`App.tsx`）と、画面ごとのフォルダ。`month/`（月表示。[11.2](#112-月表示mv-110)）・`day/`（日表示。[11.3](#113-日表示dv-16)）・`form/`（予定・タイムブロックのフォーム。[11.4](#114-フォームev-14tb-12)）・`sidebar/`（サイドメニューとワークスペースの編集。[11.5](#115-サイドメニューws-14)）・`sync/`（同期とオフライン対応。[6章](#6-同期オフライン)）・`emoji/`（絵文字の画像。[11.1](#111-共通)）。

何をどこに置くか:

- 画面と Worker の両方が必要なロジックは、必ず `shared/` に置く。片方だけが使うものは置かない（例: 通知の計算は Worker の `notify/`、ワークスペースの 8 色の値は画面の `workspaceColors.ts`）。
- 月表示と日表示など、複数の画面が使うものは、`client/` の直下に置く。
- `client/` では、判断を持つ部分（状態・計算・文言の決め方）を、React に依存しない `.ts` に置き、`.tsx` は描画とイベントの受け取りにとどめる。**Why**: React の画面のテストは置かないので（[2章](#2-技術の選定)）、判断を画面なしで確かめられるようにするためです。
- ブラウザや外部の機能（fetch・IndexedDB・履歴・時計・待つ関数など）は、環境（env）として引数で受け取る。**Why**: テストで偽物に差し替えるためです。
- 大文字小文字だけが違うファイル名は作らない（`Timeline.tsx` に対して `timelineGeometry.ts` とする、など）。**Why**: 大文字小文字を区別しないファイルシステム（macOS・Windows）で、`./Timeline` が取り違えられるからです。
- **Why `shared/` を分けるのか**: 繰り返しの展開と祝日の計算は、画面（表示）と Worker（通知）の両方が必要だからです。同じコードを使わないと、「画面には出ているのに通知が来ない」という食い違いが起きます。

## 4. データ設計

### 4.1 テーブル一覧

| テーブル | 中身 |
| --- | --- |
| `workspaces` | ワークスペース。組み込みの「祝日」「記念日」も行として持つ |
| `entries` | 予定とタイムブロック。両方を1つのテーブルに入れる |
| `meta` | 同期用の通し番号など、1行だけの管理情報 |

- **Why 予定とタイムブロックを1つのテーブルにするのか**: 違いは「ワークスペースがあるか」「終日にできるか」「通知の初期値」の3点だけで、繰り返し・通知・同期・削除の処理は同じだからです。
- 祝日と記念日は DB に入れず、コードで計算します（[8章](#8-祝日記念日の計算)）。

### 4.2 テーブル定義

```sql
-- ワークスペース
CREATE TABLE workspaces (
  id         TEXT PRIMARY KEY,         -- UUID（端末側で発行する）
  name       TEXT NOT NULL,
  color      TEXT NOT NULL,            -- '#RRGGBB'。画面は用意した8色から選ぶ。サーバーは形だけを確かめる（11.5）
  sort_order INTEGER NOT NULL,
  visible    INTEGER NOT NULL DEFAULT 1,   -- 表示 ON/OFF（WS-3, Q3）
  builtin    TEXT,                     -- 'holiday' / 'observance' / NULL（WS-4）
  edited_at  INTEGER NOT NULL,         -- 端末で編集した時刻（ms）。食い違いの判定用
  rev        INTEGER NOT NULL,         -- 保存したときの通し番号。差分同期用
  deleted_at INTEGER                   -- 削除した時刻（論理削除）
);

-- 予定とタイムブロック
CREATE TABLE entries (
  id            TEXT PRIMARY KEY,      -- UUID（端末側で発行する）
  kind          TEXT NOT NULL CHECK (kind IN ('event', 'block')),
  title         TEXT NOT NULL,
  workspace_id  TEXT REFERENCES workspaces(id),  -- block は NULL（TB-3）
  all_day       INTEGER NOT NULL DEFAULT 0,      -- block は常に 0
  start_date    TEXT NOT NULL,         -- 'YYYY-MM-DD'
  start_time    TEXT,                  -- 'HH:MM'。終日なら NULL
  end_date      TEXT NOT NULL,         -- 終日: 最終日（その日を含む）／時間指定: 終わる日
  end_time      TEXT,                  -- 'HH:MM'。終日なら NULL
  location      TEXT,                  -- 場所の名前（地図へのリンクは画面で作る）
  url           TEXT,
  memo          TEXT,
  rrule         TEXT,                  -- 繰り返しのルール（JSON）。繰り返さないなら NULL
  until_date    TEXT,                  -- 内部用。「これ以降すべて」で切った系列の最終日
  series_id     TEXT,                  -- 例外の行のとき、元の繰り返し予定の id
  original_date TEXT,                  -- 例外の行が置き換える回の日付
  cancelled     INTEGER NOT NULL DEFAULT 0,      -- 例外で「この回だけ削除」したら 1
  notify_enabled    INTEGER NOT NULL,  -- 通知 ON/OFF（NT-4）
  notify_offset_min INTEGER NOT NULL,  -- 開始の何分前に通知するか（4.3）
  next_notify_at    INTEGER,           -- 次に通知する時刻（UTC の ms）。サーバーが計算する
  edited_at     INTEGER NOT NULL,
  rev           INTEGER NOT NULL,
  deleted_at    INTEGER
);
CREATE INDEX entries_rev    ON entries(rev);
CREATE INDEX entries_series ON entries(series_id);
CREATE INDEX entries_notify ON entries(next_notify_at)
  WHERE next_notify_at IS NOT NULL AND deleted_at IS NULL;

-- 管理情報（1行だけ）
CREATE TABLE meta (
  id    INTEGER PRIMARY KEY CHECK (id = 1),
  rev   INTEGER NOT NULL,              -- 最後に払い出した通し番号
  epoch TEXT NOT NULL                  -- データを復元したら変える値（付録A.1）
);
```

- マイグレーションは、テーブルのほかに、次の行を最初から入れます。
  - `meta` の 1 行（`rev` = 0。`epoch` はランダムな値）。0002（「予定」を入れる）と 0003（その色を直す）が、それぞれ `rev` を 1 つ進めます（新しい DB では 2）。
  - 組み込みのワークスペース 2 行（`0001_init.sql`。WS-4）。固定の id は `builtin-holiday`（`builtin` = `'holiday'`）と `builtin-observance`（`'observance'`）、色は [11.1](#111-共通) の色、`sort_order` は大きな値（利用者のワークスペースの後ろに並べる）、`edited_at` と `rev` は 0 です。**Why**: 全端末で同じ id である必要があり、表示の ON/OFF も同期の対象だからです（[12章](#12-確認事項すべて推奨どおりで確定)の Q3）。`edited_at` が 0 なのは、端末からの最初の編集が必ず勝つようにするためです（[6.4](#64-食い違ったときsy-3)）。
  - 利用者の最初のワークスペース「予定」の 1 行（`0002_default_workspace.sql`）。`id` は `default-workspace`、`name` は `予定`、`sort_order` は 0、`visible` は 1、`builtin` は NULL、`edited_at` は 0、`deleted_at` は NULL、`rev` は `meta.rev` を 1 つ増やした値です。同じ `id` の行がすでにあれば、何も入れません（`rev` も進めません）。
    - **Why マイグレーションで入れるのか**: 画面が最初に開いたときに作る方式だと、2 台がほぼ同時に初めて開いたときに「予定」が 2 つできるからです。固定の `id` なら 1 行になり、画面に「最初に作る」処理も要りません（[11.5](#115-サイドメニューws-14)）。
    - **Why `rev` を 0 にしないのか**: 0 のままだと、`since` に正の値を覚えている端末が、差分の読み込み（[6.3](#63-受け取るサーバー--端末)）でこの行を受け取れないからです（組み込みの 2 行は、どの端末も `rev` を覚えていない時点で入れたので 0）。`edited_at` が 0 なのは、組み込みと同じ理由です。
  - 「予定」の色は、0002 では仮の `#039BE5` で入れ（8 色は、暗い背景での見え方を画面で見て決めるため）、`0003_default_workspace_color.sql` で `#4FC3F7`（[11.1](#111-共通)のピーコック）に直します。
    - **直すのは、未編集のときだけです**（`edited_at` が 0 で、色が `#039BE5` のまま）。**Why**: 利用者が選んだ色を上書きしないためです。1 回でも編集・削除されれば `edited_at` は 0 でなくなる（6.4）ので、削除済みかどうかは条件にしません。色も条件に入れるのは、もう一度当てても何も変えず、`rev` も進めないためです。
    - `rev` は `meta.rev` を 1 つ増やした値にし、`edited_at` は 0 のままです。**Why**: `rev` を進めないと、`since` を覚えている端末が色の変更を受け取れないからです。
- `wrangler.jsonc` の D1 の `database_id` は、本番の D1 の ID で（作り方は [docs/setup.md](../setup.md) の 1）、秘密の値ではないので、リポジトリに入れます。
- TypeScript の型は、`src/shared/schema.ts` の Zod のスキーマから導きます（camelCase。DB の snake_case との変換は `src/worker/db/rows.ts`）。`rev` と `next_notify_at` はサーバーの都合の列なので、型には入れません。DB から読んだ行は、`rows.ts` の読み込み用のスキーマで、行の構造だけを確かめます（[6.3](#63-受け取るサーバー--端末)）。
  - 時刻の分は 00・15・30・45 だけです（DV-3）。`24:00` は使わず、終わりが翌日の 0:00 なら、終了日を翌日にして `00:00` と書きます。
  - 項目をまたぐ確認は、スキーマには入れず、API で確かめます（下の「項目をまたぐ確認」）。**Why**: object に refine を付けると、下書きや変更のスキーマを `pick` / `omit` で導けなくなるためです。確かめる関数（`entryProblem`）は `src/shared/entryRules.ts` にあり、API と画面のフォーム（[11.4](#114-フォームev-14tb-12)）が同じものを使います。フォームだけに書き写すと、片方だけを直して食い違い、フォームを通った入力を、サーバーが 400 で断ります。4xx の依頼は端末が捨てる（[6.2](#62-送る端末--サーバー)）ので、保存した変更が画面から消えます。
- **入力の検証（API）**は、読み書き用のスキーマ（`entrySchema` など）とは別の、「入力用」のスキーマ（`schema.ts` の `*InputSchema`）で行います。**Why**: `entrySchema` などは、書き込み（`store.ts`）の確認にも使うので、入力のルールを足して後で厳しくすると、すでに DB にある行が、更新できなくなるからです。
  - 文字列の長さと形式、数の範囲は、次のとおりです。長さは UTF-16 の単位で数えます。

    | 項目 | 上限・形式 |
    | --- | --- |
    | `title` | 1〜200 文字 |
    | `location` | 200 文字まで |
    | `memo` | 10000 文字まで |
    | `url` | 2048 文字まで。`http://` か `https://` で始まり、URL として読める形（[10.3](#103-その他の対策)）。値は黙って整えない（空白を取り除くなど）。空にするなら `null` |
    | ワークスペースの `name` | 1〜50 文字 |
    | `id`（URL の `:id`・`workspaceId`・`newId` を含む） | `^[A-Za-z0-9-]{1,64}$`。端末が作る UUID と、固定の id の両方が通る形 |
    | 日付の年 | 1900〜2199 年（[Q2](#q2-スクロールできる範囲)） |
    | `notifyOffsetMin` | -1440〜10080 の整数。終日は 0:00 からの分なので負の値もあり（[4.3](#43-各項目の決め方)）、最大は 1 週間前 |
    | `editedAt` | 0 以上の整数。サーバーの今より 10 分より未来なら 400（[6.4](#64-食い違ったときsy-3)） |

  - **Why 上限を決めるのか**: 1 行が D1 の値の上限（約 2MB）に収まるようにするためです。年の範囲は、展開（[7章](#7-繰り返しの展開)）が回を生成するのが 1900〜2199 年だけで、範囲外の日付が通ると、回が 1 つも出ない系列ができるからです。
  - `deletedAt` は、ワークスペースの PUT では `null` だけを通します（削除は DELETE）。**Why**: PUT で論理削除できると、組み込みと最後の 1 つの保護（下）をすり抜けるからです。
  - 本文・`changes` などのオブジェクトは、知らないキーがあれば 400 にします（黙って捨てない）。**Why**: 変わったと思い込ませないためです（[4.5](#45-繰り返し予定の変更削除rp-4)）。
- **項目をまたぐ確認（API）**:
  - 終日なら開始・終了の時刻は `null`、時間指定ならどちらも時刻がある。
  - 終了は開始より後。終日は終了日が開始日以降（終了日はその日を含む）、時間指定は終了の日時が開始の日時より後（同じ日時は不可）。
  - タイムブロックは、終日にできず、`workspace_id` は `NULL`。予定は `workspace_id` が必要で、そのワークスペースが存在し、削除されていないこと。削除済みなら依頼を捨て（[5.1](#51-エンドポイント)）、存在しなければ、書く前に API で確かめて 409 にします。**Why 外部キー違反を待たないのか**: 外部キー違反は D1 の例外の文言でしか判定できず、本番の文言が Miniflare と同じか確かめられないからです（違うと 500 になり、端末が再送し続ける）。文言での判定は、確かめた後にワークスペースが消える割り込みへの予備として残します。
  - 組み込みのワークスペース（`builtin` がある行）は、名前・色・`builtin` の変更と削除ができません（400）。変えてよいのは `visible` と `sort_order` だけです。`builtin` を付けた新しいワークスペースの作成も、組み込みでない行に `builtin` を付けることも 400 です。予定は、組み込みのワークスペースを指せません（WS-4。作成も、移すのも、400 `builtin_workspace`）。
  - 最後の 1 つの（組み込みでない）ワークスペースは、削除できません（400。[11.5](#115-サイドメニューws-14)）。
  - 行の確認と、日付の年の範囲（`start_date`・`end_date`・`until_date`）は、サーバーが計算した後の、書く行にも当てます（400）。**Why**: 「すべて」の変更などで、変えていない項目との組み合わせが合わなくなったり、日付をずらす途中で年の範囲を出たりする（例: 2199-12-31 から始まる「毎週 月」は、開始日が 2200 年にずれる）ことがあり、範囲を出た行は、回が 1 つも出ない系列になって、画面から直せないからです。
  - 繰り返しのルールがあり、`until_date` がある行は、`until_date` が開始日以降であること（400）。ルールがない行は見ません（ルールをなくすと `NULL` になるため。[4.5](#45-繰り返し予定の変更削除rp-4)）。**Why**: ルールに合う最初の日が `until_date` より後になると（例: 10/19 からの毎日を 10/23 で切った系列の、10/23 の回を、毎週 日に変えると、最初の日が 10/25 にずれる）、回が 1 つもない系列になり、画面に出ないので直せないからです。開始日はルールに合う日にそろえてあるので（[4.4](#44-繰り返しのルールrrule-列)）、`until_date` が開始日以降なら、開始日の回は残ります。例外の行で消した回は見ません。
  - 削除する行（`deleted_at` を付ける行）には、当てません。**Why**: 確認が厳しくなる前に保存された行を、削除できなくなるからです。
- DB への書き込み（`src/worker/db/store.ts`）には、次の決めごとがあります。
  - すべての行を `entrySchema`・`workspaceSchema` で確かめてから書きます。合わない行が 1 つでもあれば、何も書かずに例外にします。**Why**: API の検証を通らない行（「これ以降すべて」で作る新しい系列など）も同じ書き込みで書くので、入口で確かめれば「書けた行は、必ず読める」が成り立つからです。
  - 書き込みは、表ごとの upsert 1 文に、行を JSON の配列（値 1 つ）にして渡し、UTF-8 のバイト数で約 1MB ごとのかたまりに分けて、同じ `batch()` に入れます。予定を書くときは、これに、`next_notify_at` を入れる UPDATE が、かたまり（500 行まで、かつ約 1MB まで）ごとに 1 文入ります（[9.2](#92-保存したときの計算実装-11a)）。**Why**: 1 行 1 文だと、ワークスペースの削除などで 1 回の依頼が数百文になり、D1 のクエリ数の上限に当たるおそれがあります。分けるのは、D1 が値 1 つを約 2MB までしか受け付けず、超えると `batch()` 全体が失敗するためで、余裕をもって半分にしました。バイトで数えるのは、日本語が 1 文字 3 バイトで、文字数だと上限の 3 倍近くになるからです。`batch()` は 1 つのトランザクションなので、全部か無しかは変わりません。1 行だけで上限を超える行は分けられないので、入力の長さの上限で防ぎます。
  - 更新（DO UPDATE）では `next_notify_at` を NULL に戻します（INSERT では書かないので NULL）。**Why**: 古い値を残すと、時刻を変えた予定や削除した予定の通知が、変更前の時刻に送られるからです。通知の時刻は、同じ batch の、この upsert のあとの UPDATE で入れます（9.2）。
  - 同じ id の既存の行と `kind` が違う行が届いたら、何も書かずに例外（`KindMismatchError`）にします（`edited_at` の新旧によらず）。**Why**: `kind` は作成後に変えられない（4.5）ので、届くのは呼び出し側のバグで、混ぜると、`kind` は event のまま中身は block、という壊れた行ができるからです。同じ id の行が 1 つの依頼に 2 つ入っているときも、同じ方針で例外にします（止めて気づけるようにするため）。
  - 更新では `kind` も `builtin` も書き換えません（`DO UPDATE SET` に入れません）。**Why**: 上の確認と書き込みの間に、別の書き込みが同じ id の行を作る割り込み（6.4）があっても、`kind` が変わらないようにするためです。`builtin` は、付けられると普通のワークスペースが組み込みとして扱われ、外せると組み込みの行が普通の行になって、上の禁止をすり抜けるからです。
    - 組み込みの名前・色の変更と削除、`builtin` を付けた作成を禁じるのは API で、`store.ts` では禁じません。表示の ON/OFF など、組み込みの行にも書く変更が、同じ書き込みを通るからです。

### 4.3 各項目の決め方

- **ID は端末側で発行する（UUID）**。**Why**: 電波がない間に作った予定にも、その場で ID が必要だからです（SY-2）。サーバーが決める方式だと、オフライン中に作った予定を後から編集・削除したときに、特定できません。
- **通知のタイミングは「開始の何分前か」の1つの数で持つ**
  - 時間指定の予定: そのまま「何分前か」。10分前なら `10`（NT-2）
  - 終日予定: 開始を「その日の 0:00」とみなし、それより後なら負の数にする。朝6時なら `-360`（NT-3）
  - **Why**: 時間指定と終日で別々の項目を持たずに済み、通知時刻の計算も「開始 − この数」の1つの式で済むからです。
  - **終日の通知の時刻は、画面では当日の朝6時（`-360`）に固定します**（要件 NT-3。予定ごとには設定できません）。画面は、終日の予定の通知を ON/OFF だけにして、「当日 6:00」と表示します。ただし、**データの形は、0:00 からの分のまま**にします。API や将来の MCP から、`-360` でない値が入りうるためです。そういう行は、通知も保存された値のとおりに行います（[9章](#9-通知)）。画面は、そういう終日の予定を開いたとき、その時刻を読み取り専用で表示し、利用者が終日の切り替えをしない限り、値を書き換えません（[11.4](#114-フォームev-14tb-12)）。**Why データの形を変えないのか**: 固定にするのは入力の画面だけの決まりで、形を変えると、すでに入った行や API から入る行のために、通知の計算（[9章](#9-通知)）を分けることになるからです。
- **場所は名前だけを保存し、地図へのリンクは画面で作る**（`https://www.google.com/maps/search/?api=1&query=場所の名前`）。**Why**: 地図の URL を保存すると、名前と URL の2つを入力することになるからです。
- **削除は「削除した時刻」を記録するだけにする（論理削除）**。**Why**: 削除したことを他の端末に伝えるには、削除の記録が DB に残っている必要があるからです（[6章](#6-同期オフライン)）。

### 4.4 繰り返しのルール（`rrule` 列）

| ルール | JSON | 補足 |
| --- | --- | --- |
| 毎日 | `{"freq":"daily"}` | |
| 毎週 | `{"freq":"weekly","days":[1,3,5]}` | 0=日〜6=土。複数選べる（RP-1） |
| 毎月 | `{"freq":"monthly"}` | 開始日の「日」と同じ日。その日がない月はスキップ（RP-2） |
| 毎年 | `{"freq":"yearly"}` | 開始日と同じ月日。2/29 の扱いは [Q9](#q9-毎年の繰り返しで229-を選んだとき) |
| 平日 | `{"freq":"weekday"}` | 要件定義書3章の定義で判定（RP-5） |
| 休日 | `{"freq":"holiday"}` | 同上 |

- 1回目は `start_date` です。開始日がルールに合わない場合（例: 月曜を開始日にして「毎週 水・金」）は、保存するときに、ルールに合う最初の日へ開始日をずらします。**Why**: 合わない1回目があると、それを繰り返しの回として数えるかどうかで、処理が分かれるからです。
- 各回の長さ（終了 − 開始）は、1回目と同じにします。
- 毎月の指定日がない月や、2/29 のうるう年でない年は、その日付が存在しないので、数えず、スキップになります。

### 4.5 繰り返し予定の変更・削除（RP-4）

Googleカレンダーと同じく、「元の予定（系列）」と「例外の行」で表します。

| 操作 | 何をするか |
| --- | --- |
| **この予定のみ** 変更 | 例外の行を1つ作る（`series_id` = 元の予定、`original_date` = その回の日付、中身は変更後の内容） |
| **この予定のみ** 削除 | 例外の行を作り、`cancelled = 1` にする |
| **これ以降すべて** 変更 | 選んだ回の日付を D として、元の予定の `until_date` を **D の前の日**にして系列を切り、D 以降は変更後の内容で新しい系列を作る。`original_date` が D 以降の例外は消す |
| **これ以降すべて** 削除 | `until_date` を **D の前の日**にする。`original_date` が D 以降の例外は消す。1回目を選んだ場合は「すべて」削除と同じ |
| **すべて** 変更 | 元の予定を書き換える。例外の扱いは下のとおり |
| **すべて** 削除 | 元の予定と、その例外を全部削除する |

- `until_date` を「前の回の日」ではなく「D の前の日」にするのは、前の回を探さずに済み、展開の結果が同じだからです。元の系列がすでに切られていて、`until_date` が D の前の日より早いときは、早い方を残します（延ばすと、切って消えた回が戻るため）。

「すべて」変更のときの例外の扱い:
- 「この回だけ削除」した回は、削除した状態で残します。
- 個別に変えた回には、今回変えた項目だけを上書きします（日時と終日は除く）。値が変わらない行は書き込みません。
- ただし、**開いていた回が例外の行のときは、その例外だけ、日時・終日も含めて、変更をすべて上書きします**（下の Δ ≠ 0 で例外を消す場合を除く）。**Why**: 開いた回の時刻を変えたのに、その回だけ変わらないのは不自然だからです。
- 通知の分（`notify_offset_min`）は、終日かどうかが（変更後の）系列と違う例外には上書きしません（`notify_enabled` は上書きします）。**Why**: 分の意味が終日と時間指定で違い（[4.3](#43-各項目の決め方)）、上書きすると、終日の `-360` が時間指定の例外に入って、開始の 360 分後に通知するからです。
- ルールか開始日を変えた場合は、例外をすべて消します。ルールを変えたとは、現在と値が違うこと（曜日の並びだけが違うなら、変えたことになりません）、開始日を変えたとは、下の Δ が 0 でないことです。**Why**: どの例外がどの回に当たるかが変わるからです。それ以外の変更（タイトルだけ、など）では消しません（以前消した回が復活するため）。
- `until_date` は内部だけで使い、画面に「終わりの指定」の入力欄は出しません（RP-3）。

**変更の中身（`changes`）**
- 変えた項目だけを渡します。キーがない項目は「変えていない」、`null` は「空にした」です。**Why**: 「すべて」でタイトルだけ変えたとき、個別に決めた回の時刻まで上書きしないため、何を変えたかを区別する必要があるからです。
- 日付と時刻は、フォームに出ていた、その回の値に対する変更後の値です。
- **`kind`（予定・タイムブロック）は、作成した後に変えられません**（`changes` に含めません）。**Why**: ワークスペースがあるか・終日にできるか・通知の初期値が違う（4.1）ので、変えると、列の組み合わせが合わなくなるからです。
- **「この予定のみ」では、繰り返しのルールを変えられません**（`InvalidChangeError`）。ルールを変えたとは、現在のルールと違うことです（「すべて」と同じ判定。変えていないルールが一緒に渡されても受け付けます）。**Why**: 例外の行は 1 回だけの行で、ルールを持たないからです。変えたいときは、「これ以降すべて」か「すべて」を選びます。
- 後ろを切った系列（`until_date` がある）で、「これ以降すべて」か「すべて」でルールを変え、ルールに合う最初の日（[4.4](#44-繰り返しのルールrrule-列)）が `until_date` より後にずれると、サーバーは 400 にし、フォームはその範囲を選べません（[4.2](#42-テーブル定義)の項目をまたぐ確認）。
- 繰り返さない予定は、範囲を無視して、その行を書き換えます。ルールを付けると、開始日を 4.4 のとおりにずらして、繰り返す予定になります。

**日付を変えたときの系列のずらし方（「これ以降すべて」「すべて」で共通）**
- ずらす日数を **Δ** とします。`changes` に開始日があるとき、Δ = 変更後の開始日 − その回の日付（生成された回ならその日、例外の行なら `original_date`）、なければ 0 です。**Why 表示上の開始日から数えないのか**: 別の日に移した例外の回を開いて日付を変えたとき、移した先の日から数えると、利用者が選んだ日にならないからです。
- **ずらせる（Δ ≠ 0 にできる）のは、weekly・monthly・yearly だけです**。daily・weekday・holiday で Δ ≠ 0 になると、`InvalidChangeError` にします。ルールを同時に変えたときは、変更後のルールで判定します（繰り返さない予定にする場合は、ずらせます）。**Why**: これらのルールは、開始日が「どの日に回があるか」を決めないので、ずらしても回は動かず、最初の回が消えたり例外が黙って消えたりするだけだからです。日付を動かしたいときは、「この予定のみ」にします（[11.4](#114-フォームev-14tb-12)）。
- 系列の開始日・終了日を Δ 日ずらします。「これ以降すべて」の新しい系列の開始日は、D に Δ を足した日（= 変更後の開始日）です。ずらした開始日がルールに合わなければ、4.4 のとおりにずらします。
- 「すべて」では、`until_date` があれば、それも Δ 日ずらします。**Why**: ずらした後も回の数を変えないためです。
- ルールを同時に変えていない weekly は、曜日も Δ だけずらします（水・金の回を 1 日後ろにしたら、木・土）。monthly・yearly は、ずらした開始日がそのまま新しい基準になります。**Why**: 開始日だけが動くと、weekly の曜日が合わなくなるからです。
- 終了日は、変更後の終了日が渡されたときだけ、1 回の長さをそれに合わせます。渡されなければ、Δ だけずらして長さを保ちます。**Why**: 表示中の回の長さから求めると、別の長さに変えた例外の回でタイトルだけを直したときに、系列全体の長さが変わるからです。

**「これ以降すべて」で作る新しい系列**
- 元の系列の `until_date` を引き継ぎます。日付をずらしたとき（Δ ≠ 0）は、「すべて」と同じく、引き継いだ `until_date` も Δ 日ずらします。**Why**: 元の系列が、前に後ろを切られていたとき、新しい系列がその先まで続かないようにするためです。ずらさないと、回の数が変わり、Δ が大きいと回が 1 つも残らなくなります。
- 最初の回（`start_date`）を選んだときは、系列を切らず、「すべて」と同じにします（変更・削除とも）。切ると、1 回も残らない系列ができるからです。

**ルールをなくす（繰り返さない予定にする）**
- 「すべて」でルールを `null` にすると、系列は繰り返さない予定になります。開始日・終了日は、系列の開始日・終了日（上のずらし方を適用した後）です。`until_date` は `NULL` にし、例外はすべて消します。「これ以降すべて」なら、D 以降が、繰り返さない予定の行 1 つになります。

**存在しない回**
- ルールにも例外の行にも当たらない日付を対象にすると、`OccurrenceNotFoundError` にします。見つからない系列・削除済みの系列を対象にしたときも同じです。**Why**: 黙って受け付けると、「この予定のみ」の変更が、存在しない回の予定を新しく作ってしまうからです。「すべて」の削除だけは、回の日付を使わないので確かめません。
- 削除した回（`cancelled` の例外の行）への、「この予定のみ」の変更も、存在しない回として扱います。**Why**: 削除した回は画面に出ておらず、通すと、画面に出ない行に変更が残るだけだからです。

**エラーの種類**
- 対象が存在しない・削除されている → `OccurrenceNotFoundError`。変更の中身が受け付けられない（「この予定のみ」でルールを変える、daily・weekday・holiday で日付をずらす、など）→ `InvalidChangeError`。**Why**: API（[5.1](#51-エンドポイント)）が、「依頼を捨てる」場合（対象がもうない）と「エラーを返す」場合（中身が悪い）を区別するためです。文面（message）では区別しません。

## 5. API 設計

画面も、将来の MCP サーバーも、同じ API を使います（NF-5）。

### 5.1 エンドポイント

すべて、[10章](#10-認証セキュリティ)の確認（ヘッダー → 認証 → リクエストの確認）の後ろで動きます。応答は JSON で、本文の形は `src/shared/api.ts`（Zod のスキーマ）で、画面の同期と Worker が共有します。

| メソッドとパス | 本文（JSON）またはクエリ | 内容 |
| --- | --- | --- |
| `GET /api/changes?since=<rev>` | クエリ `since`（0 以上の整数。必須） | `since` より後に変わったワークスペース・予定を返す（削除も含む）。`since=0` なら全件（削除済みは除く） |
| `PUT /api/workspaces/:id` | `{ workspace }`（全項目。`id` は URL と同じ、`deletedAt` は `null`） | ワークスペースの作成・更新 |
| `DELETE /api/workspaces/:id` | `{ editedAt }` | ワークスペースと、その中の予定（系列・例外を含む）をすべて論理削除する（[Q6](#q6-ワークスペースを削除したときの中の予定)） |
| `PUT /api/entries/:id` | `{ draft, editedAt }` | 予定・タイムブロックの作成（`createEntry`。id は URL の値） |
| `PATCH /api/entries/:id` | `{ occurrenceDate, scope, changes, newId, editedAt }` | 予定の変更（`changeEntry`）。`:id` は系列の id（繰り返さない予定なら自分の id）。`scope` は `this` / `following` / `all`。繰り返さない予定は、`scope` と `occurrenceDate` を使わない（形としては必要） |
| `DELETE /api/entries/:id` | `{ occurrenceDate, scope, newId, editedAt }` | 予定の削除（`deleteEntry`）。`:id` は PATCH と同じ |
| `GET /api/occurrences?from=&to=` | クエリ `from`・`to`（両端を含む。1900〜2199 年。最大 31 日） | 期間内の予定を、繰り返しを展開して日付順に返す（祝日・記念日も含む） |

- 書き込みの API はすべて、`editedAt`（端末で編集した時刻）を受け取ります。新しく作る行の ID（「これ以降すべて」の新しい系列を含む）は、端末から `newId` で送ります。`newId` が系列の id と同じなら 400 です（例外の行が、系列の行を上書きしてしまうため）。
- **新しい行の id（PUT の `:id`、PATCH・DELETE の `newId`）が、保存されている別の行とぶつかったとき**は、上書きせず、書きません。保存されている行（削除済みを含む）の `edited_at` が `editedAt` 以上なら `stale`（同じ依頼の 2 回目は、ここに入る）、そうでなければ 409（`conflict`）です。PATCH・DELETE では、サーバーが計算した行の中に、`id` が `newId` の行があるときに確かめます。**Why**: PUT は作成だけで、同じ id の行は、同じ依頼の 2 回目でなければ別の行とのぶつかりです。上書きすると、例外の行を残したまま系列が繰り返さなくなる、削除した行が生き返る、などの、画面から直せない壊れ方をするからです。
  - **同じ回の例外の行は、ぶつかりとしません**（`series_id` と `original_date` が同じ行）。`applyWrite` の `edited_at` の比較に任せます。**Why**: 「この予定のみ」の 2 回目は、既存の例外を `original_date` で見つけて、その id の行を計算するので、ぶつかりではないからです。
- **ワークスペースの削除で、別のワークスペースの系列の例外が、このワークスペースを指しているとき**は、その例外を論理削除せず、その回を削除した形（`cancelled`。「この予定のみ」の削除と同じ）にして、`workspace_id` を系列の行のものに戻し、`editedAt` を依頼の値にします。系列の行が見つからない、または削除済みなら、論理削除します。**Why**: 例外を論理削除すると、例外が抑えていた元の回が、また現れます。利用者の意図では、移した先のワークスペースを削除すれば、そこに移していた回も消えるのが自然です。`workspace_id` を戻すのは、削除したワークスペースを指す、削除されていない行を残さないためです（Q6 a が成り立つ）。
  - 「このワークスペースの系列」は、削除されていない系列だけです。**Why**: サーバーは、削除されていない系列の例外しか読まないので、端末とサーバーで消す範囲をそろえるためです（[5.2](#52-なぜ何をしたいかを送る形にするのか)の「同じ結果になる」）。
- JSON のキーは camelCase です（[4.2](#42-テーブル定義)）。入力の検証は 4.2、`editedAt` の上限は [6.4](#64-食い違ったときsy-3) で決めています。
- 変更・削除・作成は、サーバーが、DB から関係する行を読み、`shared/` の関数（`recurrence.ts`・`workspace.ts`）で書く行を計算し、`applyWrite`（6.4）で書きます（[5.2](#52-なぜ何をしたいかを送る形にするのか)）。

**応答の形**

| API | 応答（200） |
| --- | --- |
| `GET /api/changes` | `{ rev, epoch, workspaces, entries }`。行ごとの `rev` と `next_notify_at` は返さない |
| 書き込み（PUT・PATCH・DELETE） | `{ applied: true }` か、`{ applied: false, reason }`。`reason` は `stale` か `not_found` |
| `GET /api/occurrences` | `{ occurrences, holidays, observances }`。`occurrences` は[7章](#7-繰り返しの展開)の回の一覧、`holidays` と `observances` は、期間の祝日と記念日（`{ date, name }`。日付順） |

- **Why**: 行ごとの `rev` と `next_notify_at` は、サーバーの都合の値で、端末には要らないからです。端末が覚える `rev` は、応答の一番上の `rev` だけです（[6.3](#63-受け取るサーバー--端末)）。書き込みの応答に `rev` を返さないのは、端末が、書き込みの `rev` を受け取りの `rev` と取り違えて、他の端末の行を取りこぼさないようにするためです。

**依頼を捨てる（200 の `applied: false`）**

| `reason` | 起きるとき |
| --- | --- |
| `stale` | 依頼より新しい（または同じ）編集がある。`applyWrite` が捨てた場合、対象がもうなくて、その行の `edited_at` が `editedAt` 以上の場合、新しい行の id が別の行とぶつかり、その行の `edited_at` が `editedAt` 以上の場合。同じ依頼の 2 回目も、ここに入る |
| `not_found` | 対象の予定・回・ワークスペースがもうなく、その行が依頼より古い、または見つからない（`OccurrenceNotFoundError`、系列が見つからない・削除済み、削除済みのワークスペースへの書き込み） |

- **Why エラーにせず 200 で捨てるのか**: 途中で古くなって実行できなくなった依頼は、エラーにすると、端末の送信待ちの列が先頭で止まるからです（[6.2](#62-送る端末--サーバー)）。
- 対象がもうないときの `reason` は、対象の行（系列・ワークスペース）の `edited_at` が `editedAt` 以上なら `stale`、そうでなければ `not_found`（行が見つからなければ `not_found`）です。**Why**: 同じ依頼の 2 回目を、削除でも変更でも `stale` にそろえるためです（1 回目の削除や「これ以降すべて」の変更は、同じ `editedAt` の行を残す）。依頼より後の編集で対象がなくなったのなら、依頼が負けた（`stale`）と言えます。
- 削除済みのワークスペースを指す予定の作成・変更も、同じ決め方で捨てます（ワークスペースの行を対象の行とします）。削除済みのワークスペースの更新も、生き返らせずに捨てます。**Why**: ワークスペースの削除は中の予定もまとめて消すので、更新で生き返ると、空のワークスペースだけが戻るからです。存在しないワークスペースは、捨てずに 409 です。

**エラー**

端末は、「4xx は直らないので依頼を捨てる。5xx と通信の失敗は再送する」と扱います（[6.2](#62-送る端末--サーバー)）。本文は `{ error, message }` で、`error` は種類、`message` は固定の短い文言です。Zod のエラー文や内部の情報は入れず、詳しい内容は Worker のログにだけ出します。**Why**: どこで弾かれたかや内部の情報が、攻撃者への手がかりになるからです（[10.2](#102-worker-側の確認二重の守り)の 403 と同じ考え方です）。

| 状態 | `error` | 起きるとき |
| --- | --- | --- |
| 400 | `invalid_request` | 本文・パラメータが不正（JSON として読めない、入力の検証・項目をまたぐ確認（4.2）に合わない、本文の `id` が URL と違う、新しい行の `id` が書く他の行と重なる）。日付の計算が対応する年（1900〜2199 年）を出る。サーバーが計算した行の日付が年の範囲を出る（4.2）。`GET /api/occurrences` の期間が 31 日を超える |
| 400 | `invalid_change` | 変更の中身が受け付けられない（`InvalidChangeError`。[4.5](#45-繰り返し予定の変更削除rp-4)） |
| 400 | `builtin_workspace` | 組み込みのワークスペースの、名前・色・`builtin` の変更と削除、`builtin` を付けた作成、予定を組み込みのワークスペースに入れる（作成も、移すのも） |
| 400 | `last_workspace` | 最後の 1 つのワークスペースの削除 |
| 400 | `edited_at_in_future` | `editedAt` がサーバーの今より 10 分より未来 |
| 404 | `not_found` | `/api/*` の存在しないパスと、存在するパスへの違うメソッド |
| 409 | `conflict` | 同じ id の行と `kind` が違う（`KindMismatchError`）。存在しないワークスペースを指す（書く前に確かめる。外部キー違反は、割り込みへの備え）。新しい行の id が、保存されている別の行とぶつかり、その行の `edited_at` が `editedAt` より古い |
| 500 | `internal_error` | 上のどれでもない例外。壊れた行（`CorruptRowError`）など |

- 認証・リクエストの確認の 403・415 は、[10章](#10-認証セキュリティ)で別に決めています。404 は、その後ろで返すので、ログインしていない相手には 403 のままです（存在を教えない）。`/api/` の外のパスの扱いは変えません。**Why 404 も JSON にするのか**: 端末や MCP が、エラーを他と同じ形で読めるようにするためです。
- 日付の計算が対応する年を出る場合（例: 2199-12-31 から始まる「平日」の繰り返しは、開始日を 2200 年へずらす途中で、祝日の計算が例外を投げる）も 400 で、500 にはしません。**Why**: 依頼の値が原因で、再送しても直らないのに、5xx だと端末が再送し続けるからです。計算は成功して、結果の日付だけが範囲を出る場合は、行の確認（4.2）で 400 にします。
- `kind` の食い違い・存在しないワークスペース・id のぶつかりを 409 にするのは、依頼が、保存されているデータと合わず、再送しても直らないからです。

**`GET /api/occurrences`**

- 画面からは呼びません。将来の MCP で「今週の予定を教えて」に答えるためのもので、MVP で一緒に作ります。**Why**: 繰り返しの展開は `shared/` にあり、呼ぶだけで済み、MCP を作るときに API の形で悩まずに済むからです。
- 応答の中身は、`shared/` の関数で作ります（`occurrences` は `occurrencesInPeriod`（`shared/period.ts`）、`holidays` と `observances` は `namedDatesBetween`（`shared/holidays.ts`））。画面（月表示）も、同じ関数を手元の行に当てます。**Why**: 一覧が食い違うと、「API には出ないのに画面には出る」ことが起きるからです。
- **期間は最大 31 日**（両端を含む。超えたら 400）です。長い期間が必要なら、MCP は区切って呼びます。**Why**: 繰り返しの展開は、系列 100 件の 1 年分が約 34ms かかり、無料プランの Worker の CPU 時間（1 回 10ms。[付録 A.2](#a2-無料枠の見積もりnf-1)）に収まらないからです。31 日なら約 3ms です。
- `from` が `to` より後なら、空（`occurrences`・`holidays`・`observances` のすべて）を返します（[7章](#7-繰り返しの展開)の展開と同じ）。
- 削除済みのワークスペースの予定は、展開の後で除きます（`occurrencesInPeriod` の中で行います）。表示の ON/OFF（`visible`）は、画面の都合なので、見ません。**Why**: 削除したワークスペースを指す、削除されていない行が残るのは、書き込みが重なったとき（[6.4](#64-食い違ったときsy-3)）だけで、その行を出さないためです。展開の前に除くと、除いた例外の行が抑えていた、元の系列の回が現れます。
- DB からは、削除されていない予定の全行を読み、SQL では期間に絞りません。**Why**: 系列は、開始日より後ならいつでも期間にかかり、例外の行も、元の回の日付と移した先のどちらかがかかればよいので、条件が複雑で間違えやすいからです。31 日に絞るので、重いのは、この全件の読み込みだけです。

### 5.2 なぜ「何をしたいか」を送る形にするのか

「これ以降すべて変更」は、行の書き換えとしては「元の系列を切る」「新しい系列を作る」「例外を消す」という3つの操作になります。
画面が行を3つ書き換える形にすると、将来の MCP サーバーも同じ処理を自前で書く必要が出てきます。そこで、API は「どの回を、どの範囲で、どう変えたいか」を受け取り、行の書き換えはサーバー側で行います。

- 画面も同じ処理（`shared/recurrence.ts`・`shared/workspace.ts`）を手元で実行して、すぐ表示に反映し（電波がなくても表示が変わるように）、その後、同じ依頼をサーバーに送ります。
- 端末とサーバーは同じコード・同じ入力で計算するので、同じ結果になります。
- D1 の `batch()`（まとめて実行。途中で失敗したら全部取り消される）で書き込むので、3つの操作のうち一部だけが保存されることはありません。

## 6. 同期・オフライン

### 6.1 方針

- 画面は、起動時に**全データ**をサーバーから読み込んで手元（メモリ）に持ち、表示はすべて手元のデータから作ります。**Why**: 自分1人の予定なので、何年分あっても数千件・数MB程度です。手元に全部あれば、スクロールで通信せず速く（NF-6）、電波が切れても見られます（SY-2）。
- 変更はまず手元に反映し、その後サーバーに送ります（楽観的更新）。

### 6.2 送る（端末 → サーバー）

```
 編集 ──▶ 手元のデータを更新（すぐ表示に反映）
       └─▶ 送信待ちの列（IndexedDB に保存）──▶ 電波があれば先頭から順に送る
                                              失敗したら、電波が戻ってから再送
```

- 送信待ちの列は IndexedDB に保存します。**Why**: スマホのブラウザは裏のタブを勝手に閉じることがあり、メモリだけだと、電車の中での編集が電波の戻る前に消えます。
  - 依頼 1 つを、依頼の id 1 つのキーで保存します（列全体を配列で 1 つのキーに入れません）。並び順は `editedAt` です。**Why**: 古いタブが止まる直前に書き込みが重なったとき（[6.7](#67-同じ端末の複数のタブ)）、配列を読んで書き戻すと、後から書いた方がもう一方の依頼を消すからです。
  - 起動時に読み込んだ依頼は、サーバーと同じスキーマ（`shared/api.ts`）で確かめ、形の合わないもの（古い版の画面が保存したものなど）は、送らずに消して「保存できなかった変更」に数えます（[6.5](#65-電波がない間の動き)）。
- 列は、先頭から 1 つずつ順番に送ります。**Why**: 順番が崩れると、対象がなくて捨てられる依頼が出る（作成より先にその変更が届くなど）からです。
- 送るときは、同じオリジンの `/api/...` に、JSON の本文と `Content-Type: application/json` を付け、`fetch` に `redirect: 'manual'` を付けます。**Why**: 付けないと、ログイン切れのときの Access のログイン画面（別のオリジン）への転送を追いかけて CORS で失敗し、通信の失敗と区別できません。
- 同じ依頼を2回送っても結果は変わりません（ID も編集時刻も端末で決めるため）。「送れたか分からない」ときは、気にせず再送します。サーバーは、今の行の `edited_at` が依頼の `edited_at` と**同じ**なら、「反映済み」として捨てます（[6.4](#64-食い違ったときsy-3)）。**Why**: 書き直すと、行は変わらないのに rev だけが進み、他の端末が差分をもう一度受け取るからです。
- 途中で実行できなくなった依頼（別の端末が先に削除した系列への変更など。[4.5](#45-繰り返し予定の変更削除rp-4) の `OccurrenceNotFoundError`）は、API がエラーにせず「捨てた」（200 の `applied: false`。[5.1](#51-エンドポイント)）として返し、端末は列から外して次へ進みます。**Why**: エラーだと、端末が電波の不調と判断して再送し続け、列が先頭で止まるからです。変更の中身が受け付けられないとき（`InvalidChangeError`）は、区別してエラーを返します（4.5 の「エラーの種類」）。
- **端末は、応答の状態ごとに、次のように扱います**。

  | 応答 | 扱い |
  | --- | --- |
  | 200（`applied` が true でも false でも） | 列から外して、次へ |
  | 4xx（下の 401・403・408・429 を除く）で、本文が API のエラーの形（`apiErrorBodySchema`。5.1） | 直らないので、列から外して（捨てて）次へ。「保存できなかった変更」として知らせる（6.5） |
  | 401・403・Access のログイン画面への転送（`opaqueredirect`） | **依頼を捨てずに、送信を止める**。「ログインし直してください」と知らせ、次のきっかけで再び試す |
  | 5xx・通信の失敗（電波がない・タイムアウトなど）・408・429・エラーの形でない 4xx・書き込みの応答の形でない 200 | 外さずに止めて、次のきっかけで同じ依頼を再送する |

  - 応答が返ってきたのに再び試すとき（最後の行のうち、通信の失敗以外）は、画面の下に知らせます。**通信の失敗（応答がない）は、知らせません**。次に失敗でない応答が返れば、知らせは消えます（理由は 6.5）。
  - 「次のきっかけ」は、[6.3](#63-受け取るサーバー--端末)の受け取るタイミングと、編集したときです。送信が電波のない間に始まり、通信の失敗が分かるまで時間がかかっている間に次のきっかけが来たときは、止まった後にもう一度試します。
  - **Why 4xx は捨てるのか**: 依頼の中身が原因で、何度送っても同じ結果になり、列が先頭で止まるからです。5xx と通信の失敗は一時的なので、再送すれば通りえます。
  - **Why 401・403 は捨てないのか**: 原因は依頼の中身ではなくログインや設定（[10章](#10-認証セキュリティ)）で、捨てると送信待ちがすべて消え、ログインし直せば通るからです。
  - **Why 408・429 は 4xx でも再び試すのか**: 時間がたてば通るのに、捨てると編集が黙って消えるからです（Worker は返しませんが、前段の Cloudflare が返しえます）。試すのは次のきっかけでだけで、短い間に叩き続けません。
  - **Why API のエラーの形でない 4xx は捨てないのか**: Worker の API は 4xx を必ずこの形で返す（5.1 のエラーの表と 404）ので、それ以外は経路が原因（Cloudflare の前段の 400・配信の設定ミスの 404 など）で、捨てると送信待ちが全部消えるからです。リクエストの確認（[10.3](#103-その他の対策)）の 403・415 は別の形（`{ error: 'forbidden' }`・`{ error: 'unsupported_media_type' }`）で、403 は止める側、415 は端末が必ず `Content-Type` を付けるので起きません。
  - **Why 200 でも、応答の形が合わなければ外さないのか**: ログイン前の案内ページなどが 200 の HTML を返すことがあり、成功扱いにすると、変更が消えるからです。
  - 壊れた行（`CorruptRowError`）が原因の 500 と、書き込み用スキーマ（`entrySchema`・`workspaceSchema`）を満たさない行を書き直す依頼（削除を含む）の 500 は、サーバー側を直す（[付録 A.3](#a3-壊れた行が見つかったとき)）まで再送が続きます。

### 6.3 受け取る（サーバー → 端末）

- `GET /api/changes?since=<最後に受け取った rev>` で、差分だけを受け取ります。
- 受け取るタイミング: 起動したとき／送信が終わったとき（1 つ以上を送り、止まらずに終わったときだけ。止まったときは受け取りも失敗する見込みなので、次のきっかけにまとめて試す）／電波が戻ったとき（`online`）／タブが前面に戻ったとき／タブが前面にある間、60秒ごと。**Why 前面にある間だけなのか**: 裏にある間は、受け取っても見えず、前面に戻ったときに受け取れば足りるからです。
- **Why 通し番号（rev）を使うのか**: サーバーの時刻で「いつ以降」と区切ると、同じミリ秒の2件などを取りこぼす可能性があるからです。rev は保存のたびに1ずつ増える（`meta.rev`）ので、取りこぼしません。
- **書き込みが返す rev は、「最後に受け取った rev」として覚えません**（覚えるのは `GET /api/changes` が返す rev だけ）。**Why**: 進めると、他の端末が先に書いた行や、割り込みで弾かれて別の端末の新しい編集が残っている行を、取りこぼすからです。
- **読み込みは、行の構造だけを確かめます**（型・必須の列・日付と時刻の形・rrule の形。`src/worker/db/rows.ts`）。長さ・年の範囲・15 分刻みのような入力のルールは、書き込むときに確かめます（[4.2](#42-テーブル定義)）。**Why**: 入力のルールを後で厳しくしたとき、DB にある行が「壊れた行」になって、全端末の同期が止まるのを防ぐためです。
- **構造が壊れた行が 1 行でもあると、差分の読み込み全体が失敗します**（`CorruptRowError`。表名と id をログに出します。直し方は [付録 A.3](#a3-壊れた行が見つかったとき)）。**Why 壊れた行だけを飛ばさないのか**: 飛ばすと、端末は「全部受け取った」と思い込み、その行が永久に届かないまま気づけないからです。
- **端末は、応答を、構造だけを見るスキーマ（`src/shared/structure.ts`）で確かめてから当てます**（入力のルールでは弾きません。入力のルールを含む `shared/api.ts` の `changesResponseSchema` は、実行時には使いません）。**Why**: DB にある行のために、全端末の受け取りが止まらないようにするためです。形が合わない応答は、当てずに、同期のエラーとして知らせ（6.5）、次のきっかけで再び試します（飛ばして当てると、上と同じ理由で気づけません）。
- **`epoch` が、覚えている値と違えば**、受け取った内容を捨てて、`since=0` で全データを読み込み直します（[付録 A.1](#a1-データの復元ot-2)）。送信待ちの列は消さず、読み込み直しが終わるまで、受け取った内容も残します。**Why**: 復元の前に覚えた rev は無意味になります。送信待ちは、まだサーバーにない編集で、受け取った内容を残すのは、失敗したときに画面を空にしないためです。
- 受け取りは、同時に 1 つだけです（実行中に頼まれたら、終わった後にもう 1 回行う）。受け取った行は、削除済みも含めて id で置き換えて持ちます（`since=0` の応答は削除済みを含まないので、受け取った行だけにする）。**Why**: 同時に 2 つ受け取ると、古い応答が新しい応答の後に当たって、新しい内容を消すおそれがあるからです。削除済みの行を持つのは、他の端末の削除を画面から消すためです。
- 起動時の全データの読み込みに失敗したら（電波がない状態で開いたときなど。SY-4）、「読み込めませんでした」と再試行のボタンを出します。電波が戻ったとき（`online`）も、やり直します。受け取りが、応答が返ってきたのに失敗したとき（200 以外。認証の失敗を除く）は、画面の下に知らせます。通信の失敗は知らせません（6.5）。
- **Why 即時通知（WebSocket）にしないのか**: 自分1人で、2台で同時に編集することはまずなく、前面に戻ったときに取りに行けば足りるからです。

### 6.4 食い違ったとき（SY-3）

- 行ごとに `edited_at`（端末で編集した時刻）を比べます。届いた依頼の方が新しければ保存し、**同じか古ければ**捨てます（[Q4](#q4-食い違ったときにどちらを正とするか)）。同じなら捨てる理由は [6.2](#62-送る端末--サーバー) です。
- **`editedAt` が、サーバーの今より 10 分より未来の依頼は、400（`edited_at_in_future`）で断ります**。**Why**: 時計が大きく進んだ端末の編集が、その後のすべての編集に勝ち続けるからです。10 分は、普通のずれ（数秒〜数分）は通し、大きく進んだ端末だけを止める値です。過去の方向には上限を設けません（過去の `editedAt` は他の編集に負けるだけで、電波がない間の編集は、何時間も前の時刻で届きます）。
- **端末は、`editedAt` を `max(今の時刻, 前に決めた editedAt + 1)` にします**（端末全体で、決めるたびに必ず増える。起動時は、保存してある送信待ちの `editedAt` の最大値からも初期化する）。**Why**: サーバーは `edited_at` が同じ依頼を「2 回目の送信」として捨てる（6.2）ので、同じミリ秒の 2 回目の編集が消えるからです。起動時にも初期化するのは、再読み込みの間に時計が戻っても、先の編集を後の編集が追い越さないようにするためです。時計が戻っても、戻った分だけ先の値は作らず、今の時刻が追いつくまで 1 ずつ増やします。
  - 未来すぎて 400 になった依頼は、捨てられ、戻りません。端末の時計がずれているので、利用者に知らせます（6.5）。
  - **時計を直しても、ページを開き直すまで、編集は断られ続けます**（前に決めた `editedAt` より後の値しか作らないため）。開き直すと今の時刻から数え直されますが、時計が進んでいた間の送れていない依頼が残っているときは、それが断られて消えるまで、開き直した後の編集も未来の値の後ろになります（もう一度開き直せば直ります）。**Why 数え直す仕組みを入れないのか**: 時計のずれはまず起きないので、コードを複雑にしない方を、ユーザーが選びました（知らせの文言を直すだけにしています）。
- 複数の行を書き換える依頼（「これ以降すべて」など）は、どれか1行でも、サーバー側の方が新しいか同じなら、依頼全体を捨てます。**Why**: 一部の行だけが保存されると、系列が二重になるなど、データの形が壊れるからです。
- サーバーの書き込みは、次の順で行います（`src/worker/db/store.ts`）。
  1. 依頼の行と同じ id の、今の行の `edited_at` を読む（予定を書くときは、`next_notify_at` の計算に使う、その系列の行と例外の行も読む。[9.2](#92-保存したときの計算実装-11a)）
  2. どれか1行でも、今の `edited_at` が依頼の `edited_at` **以上**なら、依頼全体を捨てる
  3. そうでなければ、D1 の `batch()` で、`meta.rev` を1つ増やし、依頼の全行をその rev で保存する（[4.2](#42-テーブル定義)。予定を書くときは、同じ batch に `next_notify_at` の UPDATE も入れ、`rev` は変えない。9.2）
  - 3 の保存は、「依頼の `edited_at` が、今の行より大きいとき」だけ上書きします。**Why**: 1 と 3 の間に別の書き込みが割り込んでも、新しい行が古い行で上書きされることだけは防ぐためです。
  - **Why 1〜3 を完全に1回の処理にしないのか**: 自分1人の利用で、2台がほぼ同時に同じ行を書く確率が、ごく小さいからです。割り込まれると、一部の行だけが保存されることはありえますが、新しい行が古い行に上書きされることはありません。一部の行が弾かれたとき（書けた行数が、書こうとした行数より少ないとき）は、表名と行数だけを Worker のログに出し（id や内容は出さない）、結果は「保存した」のままにします（弾かれた行には、別の端末の新しい編集が残っているだけで、データは壊れていません）。
- **2 台以上でほぼ同時に操作したときの食い違い・エラーは、データが壊れない限り、恒久的な対策をしません**（ユーザーの方針）。上の割り込みを許すこと、最後の 1 つのワークスペースの保護を 2 台の同時の削除がすり抜けること（[11.5](#115-サイドメニューws-14)）、削除済みのワークスペースを指して残る予定を、利用者が直せないこと（5.1）が、これに当たります。記録は、[バックログ](../BACKLOG.md#恒久的な対策をしないもの)にあります。**Why**: 自分1人の利用で、まず起きないので、データが壊れなければ、直す仕組みよりコードの単純さを優先します。
- 画面に出すデータは、「サーバーから受け取った内容」の上に、「まだ受け取りで確かめていない依頼を、手元でやり直した結果」を重ねて作ります（`src/client/sync/replay.ts`）。受け取った内容か列が変わるたびに、作り直します。**Why**: 手元の編集結果を持ち続けると、サーバーが捨てた依頼の結果が手元にだけ残って食い違い、気づけません。作り直せば、その結果は、依頼が列から外れた時点で画面からも消えます。
  - **やり直しは、サーバーと同じ計算にします**。依頼ごとに、サーバーと同じ範囲の行（系列の行とその例外。ワークスペースの削除なら、中の行と、そこを指す例外の系列の行）から、`shared/` の関数で書く行を計算し、当てるかどうかもサーバーと同じ決め方（1 行でも、今の行の `editedAt` が依頼の `editedAt` **以上**なら、依頼全体を当てない）にします。サーバーが 200 で「捨てた」にする場合（対象がない・変更の中身が受け付けられない・日付の計算が範囲を出る・削除済みのワークスペースを指す・同じ id の行がすでにある PUT・新しい行の id が別の行とぶつかる・削除済みのワークスペースの更新）も、当てません。**Why**: 食い違うと、「画面では変わったのに、サーバーでは別の結果」になるからです。本物の Worker と D1 に同じ依頼（続けて当てたときを含む）を当てて、全行が一致することを、テストで確かめています（`replay.equivalence.test.ts`）。
  - **例外（一時的な食い違い）**: 起動時の全データの読み込み（`since=0`）は削除済みの行を含まない（[5.1](#51-エンドポイント)）ので、開き直した直後の端末は、次の 2 つの依頼だけ、サーバーと結果が食い違います。(1) 削除済みの行と同じ id の、予定の作成（サーバーは 409 で書かない）。(2) 削除済みのワークスペースの更新（サーバーは生き返らせずに捨てる）。送信が終われば、受け取り（削除済みの行を含む）で直ります。**Why 許すのか**: 開き直す前に作った、まだ送れていない依頼が、その間に別の端末で削除されたときにしか起きず、画面が一時的にずれるだけで、データは壊れないからです。
  - **サーバーの 400 の入力の検証は、真似ません**（長さ・年の範囲・項目をまたぐ確認・組み込みのワークスペースの保護・最後の 1 つのワークスペースの保護・`newId` が系列の id と同じ、など）。**Why**: その依頼は、送ったときに 4xx で列から外れて画面からも消える（6.2）ので、通る依頼だけを正しくやり直せばよく、検証まで真似ると、二重に保つ規則が増えて食い違うからです。
  - 想定していない例外が出た依頼は、再投げせず、当てずにログへ出します（再投げすると、画面全体が更新されなくなるため）。
  - **200 を受け取った依頼は、列と IndexedDB から外したあとも、次の受け取りが成功するまで、重ね続けます**（200 の後に始まった受け取りが成功したとき、外す）。4xx で外した依頼は、重ねません。**Why**: 外した時点で重ねるのをやめると、編集した予定が、送信が終わった瞬間に消え、受け取りの後で現れる（ちらつく）からです。サーバーが反映済みなら何も当てないので、重ね続けても結果は変わりません。
  - 削除済みのワークスペースを指して残った予定（書き込みが重なったとき）は、画面でも除きます。`GET /api/occurrences`（5.1）と同じ `occurrencesInPeriod`（`shared/period.ts`）を、展開した回に当てます（先に除くと、除いた例外が抑えていた元の回が現れます）。画面で呼ぶのは、期間の回の一覧を作る月表示（[11.2](#112-月表示mv-110)）です。

### 6.5 電波がない間の動き

- 画面の JavaScript は、起動時に**全部**読み込みます（画面ごとに分けて後から読み込む方式にはしない）。**Why**: PWA（Service Worker）は作らない（スコープ外）ので、電波がない間は新しいファイルを読み込めず、後から読み込む方式だと、電車の中で日表示を開いた瞬間に画面が壊れます。
- 画面の上部に「未送信 N件」を小さく表示します。**Why**: 電波がない間に保存した変更が、まだ他の端末に届いていないことを、知っておけるようにするためです。
- 画面の下に、次の知らせを出します。「未送信 N件」と、読み込みの状態の置き場所は、月表示の [11.2](#112-月表示mv-110) と、日表示の [11.3](#113-日表示dv-16) です。
  - **画面の下の知らせの置き場所**（次の知らせと、削除の「元に戻す」（[6.6](#66-削除の元に戻すot-1)・[11.4](#114-フォームev-14tb-12)）で共通）: 画面の下の左に、1 つの列にして縦に積みます（同期の知らせが上、「元に戻す」が下）。右は、( + ) ボタンのために空けます（列の右端は、画面の右から 88px の内側）。列の空いているところのクリックは、下の画面に通します。**Why**: 別々に固定すると、同じ場所に重なり、( + ) ボタンが知らせの［閉じる］に重なって閉じられなくなるからです。ワークスペースの編集のダイアログ（モーダル）が開いている間は、「元に戻す」だけ、ダイアログの中に出します（[11.5](#115-サイドメニューws-14)）。
  - **保存できなかった変更が N 件あります**: サーバーが 4xx で断った依頼（[6.2](#62-送る端末--サーバー)）と、起動時に形が合わずに消した依頼があるとき。`edited_at_in_future` で断られた依頼があれば、「端末の時計がずれています。時計を合わせてから、ページを開き直してください」を添えます。**Why**: 4xx は想定外で、黙って消えると気づけないからです。
    - **200 の `applied: false`（別の端末の新しい編集に負けた・対象がもうない）は知らせません**。**Why**: 食い違ったときは、後から編集した方を正とする（SY-3。[6.4](#64-食い違ったときsy-3)）ので、負けた編集は、正常な動きの結果だからです。
  - **ログインし直してください（ページを開き直してください）**: 401・403・Access のログイン画面への転送のとき（6.2）。送信待ちは捨てずに残っています。
  - **サーバーとのやり取りに失敗しています（HTTP 500）。続くときは、Worker のログを確かめてください**: 送信か受け取りで、最後に返ってきた応答が、失敗だったとき。送信の失敗は、5xx・408・429・API のエラーの形でない 4xx・形の合わない 200（6.2）。受け取りの失敗は、200 以外（認証の失敗を除く。[6.3](#63-受け取るサーバー--端末)）。失敗の回数や続いた時間は数えず、すぐ出します（一時的な失敗は、次の成功（最長 60 秒）で消えるので害が小さく、仕組みも単純です）。「HTTP 500」の数字は、その応答の HTTP の状態です。形の合わない 200（ログイン前の案内ページなど）のときは、「（HTTP 200）」の代わりに「（応答の形が違います）」と出します。
    - **通信の失敗（電波がない・タイムアウトなど。応答がない）では、出しも消しもしません**。**Why**: 電波がないのは電車の中などで普通に起きるので、出すと邪魔です。電波が切れただけでは、サーバーが直ったか分からないので、消しもしません。サーバーの失敗は、電波では直らず、知らないと気づけません。
    - **消える条件**: 同じ向き（送信なら送信、受け取りなら受け取り）で、次に返ってきた応答が、失敗でないとき。200・API のエラーの形の 4xx・認証の失敗・受け取りの読めない形の 200 も、失敗でない応答に含みます。
    - **送信と受け取りで、分けて持ちます**。**Why**: 片方の成功で、もう片方の止まった失敗の知らせを消さないためです。**両方が失敗しているときは、送信の状態を出します**（送信の失敗は、保存した編集がまだサーバーに届いていないことなので、より大事です）。閉じるボタンは付けません（直れば自分で消えるため）。
    - **限界（「元に戻す」で、送信の知らせが残ることがある）**: 失敗で止まった先頭の依頼を、「元に戻す」（[6.6](#66-削除の元に戻すot-1)）で取り消して列が空になると、送信の知らせは、次に編集するか、ページを開き直すまで残ります。**Why 直さないのか**: 削除から 5 秒の間に、タブを裏に回す・サーバーが 500 を返す・前面に戻る・元に戻す、が重なるときだけで、まず起きず、残っても次の編集か開き直しで消えるためです。直すと、取り消しの処理に知らせの扱いを足すことになります。
    - **限界（別のタブで開いて止めたタブ）**: 止めたタブには、止めた時点の知らせが残ります（止めた後の応答は読まないため。[6.7](#67-同じ端末の複数のタブ)）。新しいタブは、自分の応答で知らせを出します。
  - **サーバーのデータを読み取れませんでした**: 受け取りの応答の形が合わないとき（6.3）。閉じるボタンは付けません。
  - **この端末では、未送信の変更を保存できません**: IndexedDB が使えないとき（プライベートブラウズなど）。送信待ちは、メモリの上では動きますが、タブが閉じられると失われます。
  - **読み込めませんでした**（再試行のボタン）: 起動時の全データの読み込みに失敗したとき。
  - **別のタブで開いたため、このタブは止めました**: [6.7](#67-同じ端末の複数のタブ)。

### 6.6 削除の「元に戻す」（OT-1）

- 削除すると、手元ではすぐに消えて、画面下に「元に戻す」が5秒間出ます（`DELETE_UNDO_MS`）。サーバーへの送信は、その5秒が過ぎてから行い、「元に戻す」を押したら送信しません。タブを閉じる・裏に回す場合は、5秒を待たずにその時点で送ります。
- **Why 送信を遅らせるのか**: 先に送ると、「元に戻す」のために削除前の状態を再現する処理が必要になり、繰り返し予定の「これ以降すべて」削除などでは、かなり複雑になります。送信を遅らせれば、送らないだけで済みます。
- 元に戻すは、予定の削除にも、ワークスペースの削除にも付けます（ボタンは、予定の削除が [11.4](#114-フォームev-14tb-12)、ワークスペースの削除が [11.5](#115-サイドメニューws-14)）。**Why**: ワークスペースの削除は、中の予定がすべて消えるので、間違えたときの被害がいちばん大きいからです。削除の前の確認（「中の予定 N 件も削除されます」。[12章](#12-確認事項すべて推奨どおりで確定)の Q6）は、そのまま残します（確認は押す前に止めるもの、元に戻すは押した後に気づいたときに取り消すものです）。
- 仕組み:
  - 削除の依頼は、列に入れた時点で IndexedDB に保存し、「この時刻までは送らない」（`sendAfter`）は、メモリにだけ持ちます。**Why**: タブが勝手に閉じられても削除を失わず、再読み込みで開いたとき（元に戻すボタンがもうない）は、待たずに送るためです。
  - 元に戻すと、列と IndexedDB から、その依頼が消えます。画面に出すデータは、作り直しで削除前に戻ります（[6.4](#64-食い違ったときsy-3)）。送り始めた依頼は、元に戻せません。
  - 先頭の依頼が待ち中なら、後ろの依頼も待ちます。**Why**: 順番を崩すと、削除より先に、その後の編集が届くなどして、対象がなくて捨てられるからです。元に戻した依頼が先頭だったときは、取り消した後に、後ろの依頼をすぐ送り始めます（送り始めないと、次のきっかけまで送られません）。
  - タブが裏に回る・閉じるとき（`visibilitychange` の `hidden` と `pagehide`）は、待ちをやめて、すぐ送ります。そのときの送信には `keepalive: true` を付けます。**Why**: ページが閉じられても、ブラウザが送信を続けてくれるからです。両方の出来事を見るのは、`pagehide` だけだとスマホでタブを切り替えたときに、`visibilitychange` だけだと閉じるときに、来ないことがあるからです。

### 6.7 同じ端末の複数のタブ

- **最後に開いたタブだけが動きます**。新しいタブが開くと、Web Locks API の錠を奪い（`steal`）、古いタブは、錠を失ったことを知って止まります。止まったタブは、「別のタブで開いたため、このタブは止めました」と表示し、編集を受け付けず（列に入れない）、送受信とタイマーを止めます。新しいタブは、錠を取ってから、IndexedDB の送信待ちを読み込み、引き継いで送ります。
  - **Why**: 自分1人の利用で、同じ端末の複数のタブはまれなので、タブ同士の調整の仕組み（どのタブが送るかの選出など）を増やすほど、不具合の余地が増えるからです。最後に開いたタブにするのは、スマホで裏に残った古いタブに邪魔されないためです。
  - **Why 錠を取ってから、送信待ちを読むのか**: 錠を取る前に読むと、古いタブが止まる直前に書いた依頼を見落とすからです。
  - 止まったタブは、送信中だった依頼の応答を、読まずに捨てます（列にも IndexedDB にも触らない）。引き継いだタブが、同じ依頼を送り直しても、サーバーは 2 回目を捨てる（[6.2](#62-送る端末--サーバー)）ので、二重になりません。
- `navigator.locks` がないブラウザでは、調整せずに動かします（ログに警告を出す）。**Why**: 動かさないと、古いブラウザで予定が見られなくなります。同じ依頼を何度送っても結果が変わらないので、複数のタブが同時に送っても、害は小さいからです。

## 7. 繰り返しの展開

- 展開とは、繰り返し予定から「その期間の何日に、何時から何時まで」という各回を作り出す処理です。
- 画面は、表示する週の範囲だけを、`occurrencesInPeriod`（`shared/period.ts`。展開と、削除済みのワークスペースの予定を除く処理）で作り、結果は覚えておいて、データが変わったら作り直します（まとまりの大きさなどは [11.2](#112-月表示mv-110)）。サーバーは、通知時刻の計算（[9章](#9-通知)）と `GET /api/occurrences` で、画面と同じ展開（`expandOccurrences`）を使います。`GET /api/occurrences` は、画面と同じ `occurrencesInPeriod` で一覧を作ります（[5.1](#51-エンドポイント)）。
- 手順（1つの系列について）:
  1. `start_date` から期間の終わり（`until_date` があればそこまで）について、ルールに合う日を求める
  2. 例外の行がある日は、例外の内容で置き換える（`cancelled` なら出さない）
  3. 例外の行のうち、日時を別の日に移したものは、移した先の日で出す（`original_date` が期間の外でも、移した先が期間にかかれば出す）

**回が「かかる日」の決め方**
- 終日: `start_date`〜`end_date`（両端を含む）。
- 時間指定: `start_date`〜`end_date`。終了が `00:00` のときは、`end_date` の前の日まで。ただし、開始日より前にはしない（00:00〜00:00 でも、開始日には出す）。**Why**: 終わりの時刻は、その瞬間を含まないからです。そうしないと、毎日の 20:00〜翌 00:00 が、翌日にもかかって見えてしまいます。
- 複数日の回や、日付をまたぐ回（TB-6）は、期間の前から始まっていても、期間にかかっていれば出します。系列は、1 回がかかる日数だけ、期間の手前から探します。
- 例外の行が期間にかかるかどうかも、同じ決め方で、例外の行自身の日時で判定します。

**例外の行の扱い（細部）**
- 系列が削除されている、または見つからない例外の行は、出しません。
- 同じ回の例外の行が 2 行あるとき（同期の競合で起こりえます）は、`edited_at` が新しい方だけを使います（同じなら id が大きい方）。**Why**: 二重に出さないためです。

**並び順**: 開始の日時の順で、同じ日なら終日が先、それでも同じなら id の順です。**Why**: 入力の並びに依存すると、同じ内容でも結果の並びが変わってしまうからです。

**期間の端**
- `from` が `to` より後なら、空を返します。
- 系列が回を生成する日は、1900-01-01〜2199-12-31 に収めます。**Why**: 祝日の計算が対応するのは 1900〜2199 年だからです（[Q2](#q2-スクロールできる範囲)）。2199 年の最後の週の行は 2200 年の 1 月にかかり、平日・休日のルールが、対応外の年で例外を投げてしまいます。

**展開した回に付ける情報**: 繰り返しの系列の回（系列の例外の回を含む）なら `recurring` が true、繰り返さない予定なら false です。**Why**: 画面のフォームが、「この予定のみ／これ以降すべて／すべて」を選ぶ段を出すかどうかを、回の中身から決めるためです（[11.4](#114-フォームev-14tb-12)）。

## 8. 祝日・記念日の計算

### 8.1 方針

- 祝日は、ライブラリを使わず、**祝日法のルールを自前で実装**します。**Why**: 既存のライブラリの多くは祝日の「一覧データ」を持つ方式で、数十年先までしか対応せず、HD-5 の「何年先でも」を満たせません。記念日と年末年始の判定は、どちらにしても自分で書く必要があります。
- 春分・秋分・夏至・冬至・立春は、太陽の位置の**天文計算**で求めます。計算には **astronomia**（太陽の視黄経と ΔT）と、間引いた VSOP87 のデータを使います（理由は[2章](#2-技術の選定)の表）。
- 計算できる年は 1900〜2199 年です（[Q2](#q2-スクロールできる範囲)）。範囲外の年は例外にします。
- 正式な発表と食い違ったときのために、コード内に「上書き一覧」を持ちます（[Q8](#q8-祝日の正式発表の反映方法)）。祝日と記念日の2つがあります。**Why 記念日にもあるのか**: 節分・夏至・冬至は、春分・秋分と同じく天文計算で決まる日で、国立天文台の発表と食い違うことがあるからです（HD-5）。固定日と第n曜日の記念日は、食い違いようがありません。

### 8.2 祝日の計算

1. 祝日法の各祝日を、「何年から何年まで、どのルールか」の表で持つ
   - 例: 成人の日は「1月15日（1949〜1999年）」→「1月の第2月曜（2000年〜）」
   - 2020・2021年の五輪による海の日・スポーツの日・山の日の移動も、年を限った行として、この表に入れる
   - 祝日法の施行（1948-07-20）より前の年は、どの行にも当てはまらないので、祝日がない
2. 一度きりの祝日を表で持つ（1959年と1993年の結婚の儀、1989年の大喪の礼、1990年の即位礼正殿の儀、2019年の即位の日と即位礼正殿の儀）
   - 国民の祝日として扱い、国民の休日の判定でも祝日に数える
3. 振替休日（名前は「振替休日」）: 1973年4月12日以降に、祝日が日曜にあたったとき
   - 2006年まで: その翌日（月曜）
   - 2007年から: その日より後で、最も近い祝日でない日
4. 国民の休日（名前は「国民の休日」）: 1986年以降に、前の日と次の日がどちらも祝日である日。ここでの祝日は、2 までの表の祝日だけで、振替休日と国民の休日は数えない
   - 2006年まで: その日が日曜、または振替休日のときは除く
   - 2007年から: その日が祝日でないとき
   - 振替休日にも国民の休日にもあてはまる日は、振替休日にする（例: 1987-05-04。5/3 が日曜で、5/3 と 5/5 の祝日に挟まれている）
   - **Why 年が変わる境目を見ないのか**: 12/31 と 1/1 の前後を祝日が挟む並びはなく、振替休日も年内の翌日（12/24 や 1/2）に収まるため
5. 春分の日・秋分の日: 太陽の黄経が0度・180度になる瞬間を含む日（日本時間）
6. 最後に祝日の上書き一覧を適用する。追加は `{ date, name }`、削除は `{ date, name: null }`
   - **Why 上書きの後で振替休日などを計算し直さないのか**: 上書きは、内閣府が発表した結果（振替休日・国民の休日を含む）をそのまま反映するためのもので、計算し直すと、発表と食い違う日が出るおそれがあるため

**画面に出す祝日名**: 内閣府の一覧では「休日」と書かれている日は、画面では「振替休日」か「国民の休日」に書き分けます。2019年の「休日（祝日扱い）」は、5/1 を「即位の日」、10/22 を「即位礼正殿の儀」と表示します。

### 8.3 記念日の計算（HD-3）

| 記念日 | 計算 |
| --- | --- |
| 節分 | 立春（太陽の黄経が315度）の前の日 |
| 夏至・冬至 | 太陽の黄経が90度・270度になる日 |
| 母の日・父の日 | 5月の第2日曜・6月の第3日曜 |
| その他 | 固定の日付（2/14、3/3、3/14、7/7、10/31、12/24、12/25、12/31） |

- 記念日は、日付の決め方（固定日・第n曜日・節気）の表として持ちます（HD-4）。
- 記念日の上書き一覧は、`{ year, name, date }` で、その年のその記念日の日付を差し替えます。記念日の追加・削除は、上書きではなく表を直して行います。名前が表にないものは、打ち間違いに気づけるよう例外にします。
- 同じ日に重なる記念日があります（例: 2026年は夏至と父の日が 6/21）。そのため、記念日は「日付 → 名前」ではなく、日付順の一覧で扱います。
- 休日・平日の判定（RP-5）は、要件定義書3章の定義どおりです。記念日は休日に含めません。コードでは、祝日（国民の祝日・振替休日・国民の休日）より広いので、`isDayOff`（休日）と `isWeekday`（平日）という名前にします。

### 8.4 正しさの確認

- 内閣府が公開している祝日一覧（1955年〜翌年）を正解データとして保存し、全件一致することを自動テストで確かめます。**Why**: 祝日の計算は、条件の組み合わせ（振替休日と国民の休日が重なるなど）で間違えやすく、公式データと全件比べるのがいちばん確実だからです。
- 内閣府の一覧には夏至・冬至・立春がないので、国立天文台の暦要項（2004〜2027年の立春・春分・夏至・秋分・冬至）も正解データとして保存し、日付が一致し、時刻も1分以内で一致することを確かめます（暦要項は分までの表記のため）。節分・夏至・冬至の日付は天文計算の結果だけで決まるからです。
- 間引いた VSOP87 のデータが、1900〜2199年の5つの節気すべてで、間引く前のデータと日付の判定に十分な精度で一致することも確かめます（許容する差は [`src/shared/data/README.md`](../../src/shared/data/README.md)）。正解データの入手元と更新の手順は [test/fixtures/README.md](../../test/fixtures/README.md) です。

## 9. 通知

### 9.1 仕組み

```
 予定を保存 ──▶ サーバーで「次に通知する時刻」を計算して next_notify_at に保存

 1分ごとの定期実行:
   next_notify_at が今以前の行を探す（索引を使うので、該当する行だけを読む）
   └─▶ その次の回の通知時刻を計算して next_notify_at を更新 ──▶ Discord に送る
```

- **Why 次の通知時刻を先に計算して保存しておくのか**: 毎分すべての繰り返し予定を展開すると、D1 の読み取り量と CPU 時間（無料プランは1回10ms）を毎分消費します。先に計算しておけば、毎分の処理は「時刻が来た行を探す」だけで済みます。
- 保存したときの計算の決まりは [9.2](#92-保存したときの計算実装-11a)、定期実行で送る部分は [9.3](#93-定期実行で送る実装-11b) です（実装は、この 2 つの PR に分けています）。

### 9.2 保存したときの計算（実装 11a）

- **1 回の通知の時刻は、`開始 − notifyOffsetMin 分`**（UTC のミリ秒）です。開始は、時間指定なら開始日・開始時刻（日本時間）、終日なら開始日の 0:00（日本時間）です（[4.3](#43-各項目の決め方)）。`notify_enabled` が false の行は、通知しません。日本時間から UTC への変換は、日数と分の足し算だけで行います（`Date` を使わない。[2章](#日付時刻の扱い全体の方針)の方針。日本時間は夏時間がなく +9 時間で固定のため）。
- **次に通知する時刻は、削除されていない各行について、「その行が内容の元になっている回」のうち、通知の時刻が `afterMs` より後（`> afterMs`）の、いちばん早いもの**です。なければ NULL です（`src/worker/notify/nextNotifyAt.ts`）。入力は、1 つの系列の全行（系列の行と、その例外の行。削除済みを含んでよい）か、繰り返さない予定の 1 行です。
  - **繰り返さない予定**: その行の 1 回だけです（探す範囲の決まりは使いません）。遠い先の予定でも、その時刻に通知するためです。
  - **例外の行**（`series_id` がある行）: その行の開始から直接求めます。`cancelled` なら NULL です。**Why 直接求めるのか**: 別の日に移した先が、探す範囲より遠くても見つけるためです。
    - 展開が出さない例外（系列が見つからない・削除されている、同じ回に、より新しい例外の行が別にある）は、NULL です。**Why**: 画面に出ない予定を通知しないためです。この判定は書き写さず、展開（`expandOccurrences`）に、系列の行と同じ回の例外の行だけを渡して呼びます。**Why**: 画面と通知で判定が食い違わないためです。系列の全行を渡すと、例外が多い系列で、例外の数の 2 乗の時間がかかります。
  - **系列の行**: 展開した回のうち、例外でない回（回の `entryId` が系列の id の回）だけを見ます。**Why**: 例外で変えた回・削除した回は、展開が除くか、例外の行の回にするので、系列の回としては数えないためです。
- **探す範囲（系列の行）**: 探し始めは、`afterMs` の日本時間の日付の 2 日前と、系列の開始日の、遅い方です。期間を区切って先へ広げ（最初は 62 日。なければ 1 年（365 日）ずつ）、探し始めから 9 年後まで探します。見つかったら、そこで止めます。
  - **Why 2 日前なのか**: 通知の分の下限は -1440 で（[4.2](#42-テーブル定義)）、開始の 1 日後に通知する回があり、開始が昨日の回も、今日の通知が残っていることがあるからです（さらに 1 日の余裕を足しています）。
  - **Why 開始日より前から探さないのか**: 開始日より前に回はないので結果が変わらず、開始日が `afterMs` の日付から 9 年より先の系列（例: 2036 年から毎年）も探せるからです。`afterMs` の日付から 9 年だけ探すと、そういう系列は NULL になり、計算は保存したときと通知を送ったときにしか動かないので、保存し直さない限り通知されません。
  - **終わりの日（`until_date`）が探し始めより前の系列は、展開せずに NULL にします**（通知する回がもうない）。**Why**: 「これ以降すべて」で切った古い系列を、保存のたびに展開しないためです。
  - **Why 期間を区切るのか**: 毎日の系列をいきなり 9 年ぶん展開すると、CPU 時間（無料プランは 1 回 10ms。[付録 A.2](#a2-無料枠の見積もりnf-1)）を使うからです。ほとんどの系列は、最初の 62 日で見つかります。
  - **Why 9 年なのか**: 2/29 の毎年の繰り返し（[Q9](#q9-毎年の繰り返しで229-を選んだとき)）は、次の回が最大 8 年後になるからです。9 年の間に回がない系列は NULL です。
- **`afterMs` は、保存したときは「今」**です（保存する行について。書かない行は、下の「保存のとき」）。定期実行（11b）が、送った回の次を探すときは、`max(送った回の時刻, 今 − 10 分)` を渡します（[9.3](#93-定期実行で送る実装-11b)）。送った回の時刻より後だけを数えるので、同じ回を 2 回見つけません。
- **今より前の回は飛ばします（`> afterMs`）**。保存した時点で、通知の時刻が過ぎている回は、通知しません（保存する行について）。**Why**: 作った直後に、過ぎた通知が来ても役に立たないためです。
- **ワークスペースは、この計算では見ません**。**Why**: ワークスペースを変えるたびに、中の全行の通知の時刻を計算し直さずに済むためです。
  - 削除済みのワークスペースの予定は、送るときに、定期実行（11b）が除きます。
  - 表示 OFF のワークスペースの予定も、通知します（送るときも、表示の ON/OFF は見ません）。**Why**: 通知は、予定ごとの ON/OFF（NT-4）で決めるもので、表示を消しただけで通知まで止まると、気づかないうちに予定を逃すおそれがあるからです。

**保存のとき（`applyWrite`）**

- 書く行のうち、削除しない行が 1 つでもある系列（`series_id ?? id`）ごとに、DB の今の行（系列の行と、その例外の行）に、書く行を重ねた「書いたあとの状態」を作り、上の計算を当てて、その系列の、削除されていない全行の `next_notify_at` を決めます（`src/worker/notify/notifyUpdates.ts`）。
  - **書かない行も含めます**。**Why**: 「この予定のみ」で例外の行だけを書いたとき、系列の行の次の回も変わることがあるからです。
  - **書かない行は、`afterMs` を、「今」と「その行の今の `next_notify_at` − 1ms」の、早い方にして計算します**（今の値が NULL なら「今」）。書く行は「今」です。**Why**: 書かない行の、時刻が来て、まだ送っていない回（定期実行が拾う前）は、利用者が今回保存した回ではなく、定期実行が送るべきものだからです。例: 毎日 14:50 に通知する系列で、14:50:20 に、同じ系列の明日の回を「この予定のみ」で変えたとき、書かない行を「今」で計算し直すと、`next_notify_at` が明日に進み、今日の通知が届きません。
  - **upsert が NULL に戻した値と違う行だけ**を更新します（D1 の書き込みは、更新する行の数だけ数えられるため。[付録 A.2](#a2-無料枠の見積もりnf-1)）。
  - **書く行がすべて削除の系列は、計算しません**（ワークスペースの削除も、この書き込みを通るので同じです）。**Why**: 削除する行は、通知の対象になりません（`entries_notify` が `deleted_at IS NULL` の行だけを持つ。[4.2](#42-テーブル定義)）。見ようとすると、ワークスペースの削除のように削除する行が多い書き込みで、系列ごとの読み込みと検証が増えて、CPU 時間を使います。
- **決めた値は、書き込みと同じ `batch()` の中で、upsert のあとの UPDATE で入れます**。**Why**: 別の呼び出しにすると、その間に失敗したとき、`next_notify_at` が NULL（upsert が戻した値）のまま残り、予定が黙って通知されなくなるからです。
  - UPDATE は、upsert と同じく `json_each` で 1 文にまとめ、値の大きさの上限（約 1MB。[4.2](#42-テーブル定義)）も同じに守ります。`UPDATE ... FROM` は使わず、行ごとに値を引く相関サブクエリで書きます。**Why**: `UPDATE ... FROM` は SQLite 3.33 以降の構文で、本番の D1 が対応しているかを手元では確かめられず、通らないと、削除しない行を含む保存がすべて失敗するからです。
  - 相関サブクエリは、1 文の行数の 2 乗の時間がかかるので、**1 文に入る行数を 500 行までにして、超えたら文を分けます**（値の大きさの上限とは別）。**Why**: D1 の 1 回のクエリの時間には上限（30 秒）があり、超えると batch 全体が失敗して、保存がすべて失敗するからです。upsert は行数の 2 乗にならないので、行数では分けません。
  - UPDATE は、`edited_at` が一致する行にだけ入れます。**Why**: 確認と書き込みの間に、別の書き込みが同じ行を新しくした（割り込み。[6.4](#64-食い違ったときsy-3)）とき、その書き込みが決めた値を、古い内容から計算した値で上書きしないためです。
  - **`rev` は変えません**。**Why**: `next_notify_at` はサーバーだけが使う列で、端末には送らない（[5.1](#51-エンドポイント)）のに、変えると、値だけが変わった行を他の端末へ送り直すことになるからです。
- **計算が例外を投げたとき（バグ）は、その系列の、削除されていない全行の `next_notify_at` を NULL にして、書き込みは成功させます**。`console.error` に、系列の id と例外を出します（予定の題名などの中身は出しません）。**Why**: 通知の計算のバグで保存が失敗すると、端末が再送し続けるか、4xx で捨てて、予定そのものを失うからです。書かない行も NULL にするのは、古い値を残すと、変わった系列に、古い時刻で通知してしまうからです。
- **11a より前に保存した行の `next_notify_at` は、NULL のままです**。埋め直しは作りません（本番には、まだ試しの予定しか入っていないため）。通知したいときは、保存し直すと、その時点で計算されます。

### 9.3 定期実行で送る（実装 11b）

- **1 分ごとに動かします**（`wrangler.jsonc` の `triggers.crons` が `* * * * *`。`src/worker/cron.ts`）。**Why**: 通知を、指定した時刻から 1 分以内に届けるため（NT-5）。無料プランの Cron Triggers は、アカウント全体で 5 個までで、これが 1 個目です（[要件定義書 7章](../requirements/requirements.md#7-システム構成前提)）。
- 「今」は、定期実行の予定の時刻（`controller.scheduledTime`）です。**Why**: 通知の時刻は、分の単位でしか決まらない（開始は 15 分刻みで、通知の分は整数）ので、毎分ちょうどの予定の時刻と比べれば足りるためです。

**1 回の実行の手順**

1. 時刻が来た行を探します。`next_notify_at` が今以前で、削除されていない行を、**時刻が新しい順に、10 行まで**取ります（`src/worker/db/store.ts`）。
   - `WHERE` に `deleted_at IS NULL` まで書き、`ORDER BY` に `id` は足しません。**Why**: 部分索引 `entries_notify`（[4.2](#42-テーブル定義)）は、`WHERE` が索引の条件（`next_notify_at IS NOT NULL AND deleted_at IS NULL`）を含むときだけ使われ、時刻が来た行だけを読めます（D1 の読み取り行数を使いません）。`id` を足すと、一時的な並べ替えが要り、同じ時刻の行が多いとき（毎朝 6 時の終日の予定など）に、索引だけで 10 行を取れなくなります。テストで、`EXPLAIN QUERY PLAN` を確かめています。
   - **新しい順に取ります**（`DESC`）。**Why**: 古い順だと、遅れた行（定期実行が止まったあと、[付録 A.1](#a1-データの復元ot-2) の復元のあと）や、壊れて値が進まない行が、枠（10 行）を占め、時刻どおりの新しい通知が遅れたり、10 分を過ぎて送られなくなったりするためです。10 分を過ぎた古い行は、どうせ送らず進めるだけなので、後に回っても通知を逃しません。
   - **10 行まで**にして、残りは次の分の実行が拾います。**Why**: 無料プランの CPU 時間は 1 回 10ms で（[付録 A.2](#a2-無料枠の見積もりnf-1)）、普通の予定なら 10 行で収まり（Node の実測で 1 行 約 2ms 以下）、遅れも、同じ時刻に 100 行より多く重ならない限り、10 分の決まり（下）の中に収まるからです。例外が 1,000 件ほどある系列が 10 行同時に来ると 10ms を超えますが、自分 1 人の利用で起きる見込みがなく、超えても、その実行が途中で止まるだけ（更新が済んで、まだ送っていない行の通知は届かない）で、残りは次の分に拾われるので、対策していません。本番の CPU 時間は、[受け入れ確認の 3章](../acceptance.md#3-本番の-cpu-時間)で確かめます。
2. 行ごとに、その行の系列（系列の行と、その例外の行）を読み直し、送る回が、まだその行の回かを確かめます（通知の時刻がちょうど、読んだ値になる、その行の回を探す。ない場合は null）。**Why 読み直すのか**: 2 台でほぼ同時に操作した割り込み（[6.4](#64-食い違ったときsy-3)）で、もうない回の古い値が `next_notify_at` に残ることがあるためです（系列を削除する保存の途中で、同じ系列の例外が作られた場合など）。送る回の内容（題名・日時・場所）も、この読み込みから得ます。
   - 展開の判定を、そのまま使います（展開が出さない例外は、画面に出ない予定なので、通知もしません。[9.2](#92-保存したときの計算実装-11a)）。**Why**: 「通知の計算では出る回が、送る前の確認では出ない」という食い違いを防ぐためです。
   - 系列の行は、通知の時刻に通知の分を足した開始の日付を求めて、その 1 日だけを展開します（期間を広げて探さないので、CPU 時間を使いません）。
3. **送る回がもうその行の回でないとき**は、送りません。その行の値を、今の展開で計算し直した値（`afterMs` = 今）にして、5 の条件付きの UPDATE で直します。**Why**: 古い値を残すと、毎分、同じ行が見つかり続けるためです。
4. 送る回があるとき、**次の回の時刻**を求めます（9.2 の計算）。**`afterMs` は `max(読んだ値, 今 − 10 分)`** です。**Why**: 10 分以上遅れた回（下）を飛ばしたあと、次の回もまだ 10 分以上遅れていれば、続けて飛ばしたいからです。読んだ値だけだと、遅れた回を 1 つずつ、毎分、進めることになります（保存で書かない行は、まだ送っていない回を飛ばさない（9.2）ので、定期実行が止まっている間は、遅れた回が続くことがあります）。
5. **先に UPDATE してから、送ります**。UPDATE は `UPDATE entries SET next_notify_at = 次の値 WHERE id = ? AND next_notify_at = 読んだ値` です。`rev` は変えません（理由は 9.2 と同じ）。
   - **Why 先に更新するのか**: 逆の順番だと、送った後で更新に失敗したときに、同じ通知が毎分届き続けます。この順番なら、最悪でも「1 回届かない」で済みます。
   - **Why `next_notify_at = 読んだ値` を付けるのか**: 読んだ後に、別の実行か保存が先に値を変えていたら、その値を古い計算で上書きしないためです。変わった行が 0 なら、別の実行か保存が先に変えたので、送りません（二重に送らない）。
6. 次の 3 つが、すべて成り立つときだけ、送ります。成り立たなくても、5 の更新は済んでいます（値は進む）。**Why**: 進めないと、毎分、同じ行が見つかり続けるためです。
   - **今 − 読んだ値 < 10 分**。遅れは、予定の開始ではなく、通知の時刻から数えます（[Q10 の「予定の時刻」の読み方](#q10-大きく遅れた通知)）。10 分以上遅れた通知は、送らずに進めます。
   - **その回の予定のワークスペースが、削除されていない**（画面と `GET /api/occurrences` と同じ判定。`shared/workspace.ts`）。タイムブロックは、ワークスペースを持たないので、見ません。ワークスペースの行がない・削除済みなら、送りません（1 回の実行で 1 回だけ読みます）。**Why**: 削除したワークスペースの予定は、画面にも出ないためです。書き込みが重なると、削除済みのワークスペースを指す予定が残ることがあり（6.4）、9.2 の計算はワークスペースを見ないので、送るときに確かめます。
   - **`notify_enabled` が true**。2 の確認で、すでに見ています（念のための確認です）。
   - 表示の ON/OFF は見ません（理由は 9.2）。

**1 行で例外が起きても、ほかの行は続けます**（行ごとの try/catch。`console.error` に、行の id と例外を出します。予定の題名などの中身は出しません）。**Why**: 1 行の失敗で、同じ分に時刻が来たほかの通知まで止めないためです。
- 壊れた行（`CorruptRowError`。[6.3](#63-受け取るサーバー--端末)）が、系列の中（系列の行・例外の行）にあると、その系列の読み直しが失敗します。**壊れた行 1 行で、その系列の、時刻が来た行は、すべて処理できなくなり**（壊れた行そのものの時刻が来ていなくても）、値が進まないので、毎分、同じ例外のログが出ます。直し方は[付録 A.3](#a3-壊れた行が見つかったとき)です。時刻が新しい順に取る（上）ので、そうした行は、時刻どおりの新しい通知の枠を占めません。
- **定期実行の失敗（壊れた行・Discord への送信が続けて失敗する）は、新しい仕組みを作らず、ログだけのままにします**（ユーザーの回答）。ログに出ても、見に行かなければ、気づけません。
  - **Why 壊れた行**: 壊れた行（削除済みでない行）は、画面を開いたときの全データの読み込みも 500 にするので、[6.5](#65-電波がない間の動き)の知らせで気づけます。例外は、壊れた行が削除済みの行のときで（全データの読み込みは削除済みの行を読まないが、定期実行の系列の読み直しは読む）、定期実行だけが止まります。壊れた行自体がまず起きないので、その組み合わせのために、仕組みを足しません。
  - **Why Discord**: 続けて失敗する主な原因は、Webhook の削除・URL の変更（自分の操作）か、Discord の障害で、知らせても、届かなかった通知は戻らないからです。画面に出すには、失敗の記録（`meta` 表への列の追加）・API・画面の 3 か所が要り、見合いません。

**残る割り込みと、限界**

- **保存が分の境目をまたぐと、同じ回が、1 分遅れで、もう一度届くことがあります**。保存の「今」は書き込みの最初に決まり、書き込みはその少し後に行われます。通知の時刻（例: 14:50）の直前に保存が始まり、その書き込みの前に、定期実行が、その回を送って行の値を次の回に進めると、保存が、同じ回の値で、その行を上書きし、次の分の実行が、同じ回をもう一度送ります。**Why 直さないのか**: 直すには、行ごとに最後に送った通知の時刻を覚える列が要り、作りが重くなるためです。起きても、同じ通知が 1 分遅れでもう 1 回届くだけで、データは壊れません。[6.4](#64-食い違ったときsy-3) の方針（割り込みで起きる食い違いは、データが壊れない限り、恒久的な対策をしない）の範囲として扱います。
- **Discord が投稿を受け付けたあとで、応答が 10 秒を過ぎてタイムアウトすると、再送で同じ通知が 2 回届くことがあります**。**Why 直さないのか**: タイムアウトのときに再送しないと、届かない通知が増え、2 回届く方が、届かないより害が小さいためです。
- **止まっていたあとの最初の実行で、遅れた回を飛ばして進んだ先の回が、すでに時刻が来ていて、遅れが 10 分未満のとき、その回は、その実行では送られず、次の分に送られます**（1 分、余計に遅れます）。**Why 直さないのか**: 止まったあとの最初の実行でだけ起き、まれなためです。

**1 回の実行の D1 の呼び出し**は、時刻が来た行の読み込み 1 回、ワークスペースの読み込み 1 回、行ごとに、系列の読み込み 1 回と UPDATE 1 回です。Discord への送信（再送を含めて、行ごとに 2 回まで）と合わせて、最大 10 行で 42 回です。**Why 数えるのか**: 無料プランでは、1 回の実行でできるサブリクエスト（`fetch` と、D1 などの呼び出し）が 50 回までだからです（公式の Workers の制限。手元では確かめられません）。ワークスペースを行ごとに読むと、50 回を超えます。

**1 回の実行の時間に、20 秒の上限を付けます**。行を処理する前に、実行を始めてから 20 秒を過ぎていたら、残りの行は処理せず、次の分に回します（値は進めていないので、次の分の実行が拾います。ログに残りの行数を出します。10 分以上遅れていれば、送らずに進みます）。**Why**: レート制限の待ち（最大 5 秒）と Discord の待ち（10 秒）が重なると、毎分の実行が重なるためです（Cloudflare の、定期実行の時間の上限は手元では確かめられないので、毎分の周期（60 秒）より十分に短くしています）。上限は、行を始める前にだけ確かめ、1 行の途中では止めません。1 行の最悪は約 30 秒（前もって待つ 5 秒・送信 10 秒・429 の待ち 5 秒・再送 10 秒）なので、1 回の実行は最長で約 50 秒で、毎分の実行とは重なりません。

**Discord への送信**（`src/worker/notify/discord.ts`）

- Webhook の URL（Secret `DISCORD_WEBHOOK_URL`。[10.4](#104-秘密情報nf-3)）に、`POST`・`Content-Type: application/json` で、`{ "content": 文面, "allowed_mentions": { "parse": [] }, "flags": 4 }` を送ります。2xx なら成功です。`allowed_mentions` の理由は [9.4](#94-通知の文面) です。
- **`flags: 4`（SUPPRESS_EMBEDS）で、リンクの埋め込み（カード）を付けさせません**。**Why**: 文面の最後のリンク（9.4）の先は、Access の後ろにあり、Discord がリンクを読みに行くと、ログインの画面のカードが、毎回付くおそれがあるためです。
- **失敗（2xx 以外・通信の例外・待ちの上限）したら、その場で 1 回だけ再送します**。それでも失敗したら、ログに残して終わります（先に `next_notify_at` を進めているので、その回は届きません）。**Why 1 回だけなのか**: 何度も再送すると、Discord が落ちているときに、ほかの通知まで遅らせるためです。
- **レート制限（429）で、待ってから再送します**。Webhook は、短い時間に 5 回ほどしか投稿できないと報告されています（公式の文書では確かめていません）。同じ時刻の通知（毎朝 6 時の終日の予定など）が 6 件以上あると、6 件目以降が 429 で消えるおそれがあるためです。ヘッダーだけを見て、応答の本文は読みません。
  - 429 のときは、`Retry-After`（秒。なければ `X-RateLimit-Reset-After`）だけ待ってから、1 回だけ再送します（上の再送です）。どちらのヘッダーもなければ、待たずに再送します。
  - 2xx の応答で `X-RateLimit-Remaining` が `0` なら、次の投稿の前に、`X-RateLimit-Reset-After` だけ待ちます（同じ実行の次の投稿の前だけ。送り手を 1 回の実行で 1 つ作り、行をまたいで覚えます）。
  - **待つのは、どちらも最大 5 秒**（`MAX_RATE_LIMIT_WAIT_MS`）。**Why**: 返された秒数のまま待つと、1 回の実行が長くなり、毎分の実行が重なるためです。5 秒より長い待ちが要るときは、5 秒だけ待って再送し、まだ 429 なら、その通知は届きません。
- **1 回の待ちに、10 秒の上限を付けます**（`AbortSignal.timeout`）。**Why**: Discord が応答しないとき、ほかの行の通知を送れないまま待ち続けないためです。
- **ログに、Webhook の URL を出しません**。失敗の理由は、HTTP の状態（`HTTP 500`）か、例外の名前（`TimeoutError` など）だけを出し、例外のメッセージと応答の本文は出しません。**Why**: Webhook の URL を知っていれば、誰でも、そのチャンネルに投稿でき、`fetch` の例外のメッセージには、URL が入ることがあるためです。

**`DISCORD_WEBHOOK_URL` が設定されていないとき**（未登録・空・空白だけ）は、送らず、値は進めます。`console.error` で知らせます。**Why 進めるのか**: 進めないと、時刻が来た行が、毎分、同じ行として見つかり続け、枠（10 行）を占めて、時刻どおりの新しい通知が遅れるためです。ログは、送る通知がある実行で、1 回の実行につき 1 回だけです（通知がない実行や、遅れて、どうせ送らない通知だけの実行では出しません）。**Why**: 未設定のままでも、毎分のログで、ほかのログが埋もれないためです。

### 9.4 通知の文面

```
🔔 10分後: 歯医者
10/19（月）15:00〜16:00
📍 ○○歯科
https://calendar.ataraman.com/day/2026-10-19
```

- 文面は、`src/worker/notify/message.ts` が作ります。予定もタイムブロックも同じ文面です（タイムブロックは、NT-4 で通知を ON にしたものだけが届きます）。
- **1 行目は `🔔 {いつ}: {題名}`**。「いつ」は、時間指定と終日で決め方が違います。
  - **時間指定**: 通知の分 m（開始の何分前か。[4.3](#43-各項目の決め方)）で決めます。m = 0 は「今から」、1〜59 は「m分後」、60 以上は、日・時間・分のうち 0 でないものを並べて「後」を付けます（90 は「1時間30分後」、1440 は「1日後」）。m < 0（API から入る、開始の後の通知）は「開始から|m|分」で、60 以上は同じく、時間で並べます（-90 は「開始から1時間30分」）。
  - **終日**: 通知の日（日本時間）と開始日の差で決めます。同じ日なら「今日」、開始日が 1 日後なら「明日」、2 日後以上なら「N日後」、開始日の翌日に通知する（-1440）なら「昨日から」です。**Why 「何分後」で言わないのか**: 終日の通知の分は、開始日の 0:00 からの分で（4.3）、「朝 6 時 = -360」を「6時間後」と言っても伝わらないためです。入力の範囲の外の、さらに後の通知（開始日の 2 日後など）も、文面は作れるように、「N日前から」にします。
  - 複数日の終日の予定は、題名のあとに「（10/19〜10/21）」を付けます（月日は 0 を付けません）。
- **2 行目は、時間指定だけ**。「10/19（月）15:00〜16:00」です。日をまたぐときは、終わりにも日付と曜日を付けます（「10/19（月）23:00〜10/20（火）7:00」。終わりが翌日の 0:00 のときも同じ。[4.2](#42-テーブル定義)）。時刻は先頭の 0 を付けません（画面と同じ表記）。終日は、この行を出しません。**1 日だけの終日は、日付が、リンクにだけあります**（複数日の終日は、期間が 1 行目にあります）。**Why**: 画面からの終日の通知は、当日の朝 6 時に固定で（NT-3）、1 行目が「今日」になります。「明日」「N日後」「昨日から」になるのは、API から別の時刻を入れたときだけだからです。
- **場所があれば `📍 場所`**。なければ（空・空白だけを含む）、行ごと出しません。
- **最後の行は、その回の開始日の日表示へのリンク**（`{APP_ORIGIN}/day/{開始日}`）です。**Why**: 通知から 1 タップで、その日の詳細を開けるようにするためです。URL の頭（`APP_ORIGIN`）は、`wrangler.jsonc` の `vars` に書きます（本番は `https://calendar.ataraman.com`。秘密ではない。末尾の `/` があってもかまいません）。**Why**: コードに書き込むと、ドメインを変えたときに直し忘れるためです。手元の開発では、`.dev.vars` で差し替えられます。
- **Discord の上限（content は 2000 文字）を超えるときは、題名と場所を切り詰めて、最後を「…」にします**。日時とリンクは、切りません。**Why**: 超えると、Discord が 400 を返し、通知が届かないためです。日時とリンクを切ると、通知の用が足りなくなります。長い題名が場所を押し出さないよう、場所は、予算の半分までは削りません。題名は、場所が使い残した分を使います。絵文字（サロゲートペア）の途中では切りません（切れた半分が残ると、JSON にしたとき、不正な文字になるため）。文字数は UTF-16 の単位（`string.length`）で数えます（Discord の数え方と同じか多いので、超えない側に倒れます）。
- `@everyone` などのメンションは無効にして送ります（`allowed_mentions: { parse: [] }`）。**Why**: タイトルに `@everyone` と書いた予定があっても、サーバー全員への通知にならないようにするためです。

### 10.2 Worker 側の確認（二重の守り）

Access を通ったリクエストには、Access が署名した JWT（`Cf-Access-Jwt-Assertion` ヘッダー）が付きます。Worker は `/api/*` のすべてのリクエスト（ヘルスチェックを含む）で、API の処理をする前に、毎回これを確認します。

1. JWT の署名が、自分の Access の公開鍵で正しく検証できるか（公開鍵は Access の証明書 URL から取得する。署名の方式は RS256 だけを受け付ける。期限（`exp`）のない JWT も受け付けない）
2. JWT の発行元（`iss`）と宛先（`aud`）が、このアプリのものか
3. JWT のメールアドレスが、許可したアドレスと同じか（大文字小文字は区別しない）。サービストークンの場合は、JWT の `common_name`（サービストークンの Client ID）が、許可した ID と同じか

どれか1つでも満たさなければ 403 を返します。本文には理由を入れません。

- **Why 理由を入れないのか**: どこで弾かれたかが、攻撃者への手がかりになるからです。理由は Worker のログにだけ残します。
- **Why サービストークンは `common_name` で判定するのか**: サービストークンの JWT には `email` が付かず、`common_name` に Client ID が入るからです。許可する ID が設定されていないときは、サービストークンを一切通しません。
- 設定（`ACCESS_TEAM_DOMAIN`・`ACCESS_AUD`・`ALLOWED_EMAIL`）のどれかが空のとき、または `ACCESS_TEAM_DOMAIN` の書式が違うとき（[10.4](#104-秘密情報nf-3)）は、403 ではなく 500 を返して拒否します。理由はログに残します。**Why**: 設定漏れのまま、確認が素通りしないようにするためです。こちらの設定の問題なので、403 とは分けます。書式が違う値は、公開鍵の URL と `iss` が壊れて、どの JWT も 403 になり原因が分かりにくくなるため、設定の誤りとして気づけるようにします。
- JWT の検証に失敗した理由は、ログに残します。jose のエラー（`JOSEError`）はエラーコードを、それ以外（公開鍵の取得の失敗など）はエラーのメッセージも残します。項目の確認（`iss`・`aud`・`exp` など）で失敗したときは、食い違った項目の名前（`claim`）と理由（`reason`）も残します。値（JWT の中身や設定の値）は出しません。**Why**: コードだけでは `iss` と `aud` のどちらが食い違ったか分からず、設定の誤りをログから切り分けられないからです。値まで出すと JWT の中身がログに残るので、名前だけにします。
- **Why Access があるのに Worker でも確認するのか**: Cloudflare 公式が、「アプリを完全に守るには JWT を検証することが重要」としているからです。Access の設定ミスや、Access を通らない URL があっても、データは守れます。
- `workers.dev` の URL とプレビュー URL は、設定で無効にします。入口は Custom Domain（`calendar.ataraman.com`。`wrangler.jsonc` の `routes`）の1つだけにします。**Why**: これらは別の入口なので、Access の保護がかかりません。入口が1つなら、守る対象も1つで済み、守り漏れが起きにくくなります。
- 許可するメールアドレスは、コードではなく Cloudflare の Secrets に保存します。**Why**: リポジトリにメールアドレスを残さないためです。

### 10.3 その他の対策

| 対策 | 内容 | Why |
| --- | --- | --- |
| 入力チェック | API で Zod を使い、型・長さ・形式を確認する | MCP など画面以外から来る入力も、DB に入る前に止めるため |
| SQL | プレースホルダ（`?`）を使い、文字列をつなげて SQL を作らない | SQL インジェクションを防ぐため |
| URL 欄 | `http://` と `https://` で始まるものだけをリンクにする | `javascript:` で始まる URL を押したときに、スクリプトが実行されるのを防ぐため |
| 他サイトからのリクエスト | API は `Sec-Fetch-Site: same-origin` と JSON 形式のリクエストだけを受け付ける。すべてのメソッド（`GET`・`HEAD` を含む）で、`Sec-Fetch-Site` ヘッダーが `same-origin` でなければ（ヘッダーがないときも）403 にする。`GET`・`HEAD` 以外は、本文の有無に関係なく `Content-Type: application/json` でなければ 415 にする。認証のあとに確認する | 他のサイトから、ログイン状態を悪用して書き込まれたり、読み取られたりするのを防ぐため |
| API の応答のヘッダー | `X-Content-Type-Options: nosniff`、`Cache-Control: no-store`、`Referrer-Policy: no-referrer` を付ける（403 などのエラーにも付ける） | 応答を別の種類として解釈されたり、予定のデータが共有のキャッシュや履歴に残ったりするのを防ぐため |
| CSP ヘッダー | 自分のドメインのスクリプト・スタイル・画像・フォント・通信だけを許す（画像は `img-src 'self'` だけで、`data:` は許さない）。`object-src 'none'`、`base-uri` とフォームの送り先（`form-action`）は自分のドメインに限り、外から枠で囲まれること（`frame-ancestors 'none'`）を禁じる。`X-Content-Type-Options` と `Referrer-Policy` も一緒に付ける | 万一 XSS があっても、被害を広げないため |

- **`Sec-Fetch-Site` がないとき（ブラウザ以外。将来の MCP など）も 403 にする**。**Why**: 緩めるのはセキュリティの設計の変更で、ユーザーの確認が要るためです。厳しい形なら判定も単純になります。画面は、今のブラウザが必ず `same-origin` を付けるので通ります。MCP（サービストークン）から API を呼ぶときは、このヘッダーが付かないので、MCP を作るときに扱いを決めます（[バックログ](../BACKLOG.md#claude-連携mcp-サーバー)）。アドレス欄に直接入力した `GET`（`Sec-Fetch-Site: none`）も 403 になりますが、API は画面から呼ぶものなので、困りません。
- **`Content-Type` は、本文の有無に関係なく必須にする**。**Why**: 書き込みの API はすべて、`edited_at` を含む JSON の本文を持つ（[5.1](#51-エンドポイント)）ので、正しいリクエストは必ず満たします。本文があるときだけ確かめる形にしないのは、環境で結果が変わるためです（ブラウザは本文のない `PUT` にも `Content-Length: 0` を付け、workerd ではそのとき `body` が `null` になりません）。
- **`img-src` に `data:` を入れない**。**Why**: 今の画面も、絵文字の SVG（[11.1](#111-共通)）も、自分のドメインのファイルとして配信するので、`data:` は要らないためです。必要になったら、理由とともに足します。
- **画面の zod は jitless にし、`'unsafe-eval'` は CSP に足さない**（`src/client/zodConfig.ts`。`main.tsx` の最初の import にする）。**Why**: zod は、スキーマを作るときに `new Function` で eval を試し、その前に CSP（`script-src 'self'`）の違反がブラウザに記録されます。`'unsafe-eval'` を足して黙らせると XSS の被害を広げるので、jitless にして、試すこと自体をやめます（検証が少し遅くなっても、画面で検証するのは 1 回の依頼と受け取った行だけなので問題ありません）。Worker には CSP がないので入れません。import の順番を並べ替えたり、画面の入口を増やしたりしたときは、`zodConfig.ts` が最初に読み込まれるようにします（確認は、`vite preview` で開き、`securitypolicyviolation` が 0 件であること）。
- 画面（静的ファイル）のヘッダーは、`public/_headers` で付けます。**Why**: 画面は Workers の静的ファイルがそのまま返すので、Worker のコードを通りません（`run_worker_first` は `/api/*` だけ）。CSP は `vite dev` では付かないので、画面の PR では、`vite preview`（`_headers` も含めて動かす）で、CSP の違反がないことを確かめます。
  - 絵文字の画像（`/emoji/*`）には、`Cache-Control: public, max-age=31536000, immutable` を付けます（`/*` のヘッダーと重ねて付きます）。**Why**: 画像の URL にはパッケージの版が入っていて、中身が変わらないので、長く覚えさせられ、一度読み込んだ画像を、電波がない間も出せるからです（11.1）。

### 10.4 秘密情報（NF-3）

| 名前 | 中身 | 置き場所 |
| --- | --- | --- |
| `DISCORD_WEBHOOK_URL` | 通知先の Webhook URL。知っていれば、誰でもそのチャンネルに投稿できるので、ログに出さない（登録の手順は [docs/setup.md](../setup.md) の 9。未設定なら、通知は送らない。[9.3](#93-定期実行で送る実装-11b)） | Secrets |
| `ALLOWED_EMAIL` | ログインを許可するメールアドレス | Secrets |
| `ALLOWED_SERVICE_TOKEN_ID` | 許可するサービストークンの Client ID | Secrets（MCP を作るまでは空） |
| `ACCESS_TEAM_DOMAIN` | Access のチーム名のドメイン。`<チーム名>.cloudflareaccess.com` の形で書く（`https://` は付けない。付けると Worker は 500 を返す） | 通常の設定（`wrangler.jsonc` の `vars`。秘密ではない。値の出どころは [docs/setup.md](../setup.md) の 2.1・3） |
| `ACCESS_AUD` | Access アプリの宛先 ID | 通常の設定（同上） |
| `APP_ORIGIN` | 通知の文面の、日表示へのリンクの頭（`https://calendar.ataraman.com`。[9.4](#94-通知の文面)） | 通常の設定（同上。手元の開発では、`.dev.vars` で差し替えられる） |

- 手元の開発環境（`npm run dev`・`wrangler dev`）には Access がないので、`.dev.vars`（Git に入れないファイル。書き方の例は `.dev.vars.example`）で `AUTH_MODE=dev` を指定し、かつリクエストのホスト名が `localhost` か `127.0.0.1` のときだけ、JWT の確認を省略します。それ以外のホストでは、`AUTH_MODE=dev` でも JWT を確認します。**Why**: 本番の設定にはこの値を書かず、「指定しなければ厳しい側」なので、設定を忘れても危険になりません。ホスト名でも絞るのは、誤って本番に `AUTH_MODE` が入っても、本番のドメインでは効かないようにするためです。
- Secrets と `.dev.vars` の値の型は、`wrangler types` では作られないので、`src/worker/env.ts` に手で書きます。`npm run cf-typegen` は、`wrangler types` に `--strict-vars=false`（`vars` を `string` にして、テストで値を差し替えても型エラーにしない）と `--env-file /dev/null`（手元の `.dev.vars` を型定義に混ぜない）を付けて実行します。

### 11.1 共通

- JavaScript が無効なブラウザでは、「JavaScript を有効にしてください」と表示する（`<noscript>`）。**Why**: 画面はすべて JavaScript で描くので、無効だと真っ白になり、原因がわからないため。
- **配色**（ダークモードのみ。NF-4）:

| 用途 | 色 | Why |

| 月の境目の線 | `#8E918F`（2px） | 普通のマス目の線（`#3C4043`, 1px）より明るく、太くする（MV-3） |

| 今の時刻の線 | `#F28B82` | 日表示で今の時刻を見分けるため（[11.3](#113-日表示dv-16)） |
| タイムブロック | `#3D4A5C`（青みのある灰色） | 時間割は背景の予定なので、予定（ワークスペースの色）より目立たなくする（TB-5） |
| ワークスペースの色 | 8色から選ぶ。トマト `#E57373`・オレンジ `#FF8A65`・バナナ `#FFD54F`・バジル `#81C784`・ピーコック `#4FC3F7`・ブルーベリー `#7986CB`・ラベンダー `#B39DDB`・グラファイト `#BDBDBD` | 自由に選べると、暗い背景で読めない色を選ぶことがあるため。Google カレンダーの 8 色を、暗い背景向けに明るくした値で、ユーザーが月表示のマスでの見本（3 案）を見て選んだ。画面の色の選択は、この 8 色からだけ（[11.5](#115-サイドメニューws-14)） |

- **ブラウザが描く部品**（プルダウンの一覧・日付の選択画面・スクロールバー）も、暗い配色で描かせます（`src/client/global.css`）。**Why**: プルダウンの一覧はブラウザが別に描くので、暗い背景が透けず、白地に灰色の文字になるため（PC の Vivaldi で確認。`<meta name="color-scheme">` だけでは直らなかった）。
- **文字のフォント**（NF-7）: Noto Sans JP（太さは 400 と 700 の2種類）を、自分のドメインから、文字の範囲ごとに分割したファイル（`unicode-range`）で配信し、画面に出ている文字を含むファイルだけを読み込みます。電波がない間に、まだ読み込んでいない文字が出てきたときは、その文字だけ端末のフォントで表示されます（受け入れる）。**Why**: Google Fonts だと、CSP（10.3）で外部のサーバーを許可する必要があり、閲覧のたびに外部へ通信が発生するため。分割するのは、日本語のフォントが数MBあり、全部読み込むとスマホで表示が遅くなるため。
- **絵文字**（NF-7）: 予定のタイトルなどの絵文字は、Noto Color Emoji の **SVG 画像に置き換えて**表示します（`src/client/emoji/`）。
  - **Why フォントではなく画像か**: ブラウザごとにカラー絵文字のフォント形式が違い（Chrome・Firefox は COLRv1、Safari は OpenType-SVG だけ）、Safari では拡大時に消える不具合もあるため。画像なら、どのブラウザでも同じ見た目になります。iPhone は対象から外れましたが、作り直す得がないので、画像のまま残します（PC のブラウザは[受け入れ確認の 2.4](../acceptance.md#24-絵文字)）。
  - **画像の作り方と配信**: npm の `@iconify-json/noto`（Apache 2.0）から、ビルドのときに SVG を作り（`vite-plugins/notoEmoji.ts`）、`/emoji/<パッケージの版>/<key>.svg` で、画面の成果物にだけ入れます。画像はリポジトリに入れません（生成物）。**Why**: リポジトリが大きくならず、版が `package-lock.json` で固定され、ビルドで外部と通信しないため（ユーザーの回答）。URL に版を入れるのは、`/emoji/*` を 1 年間（immutable）覚えさせて（[10.3](#103-その他の対策)）、電波がない間も出せるようにしつつ、パッケージを上げたとき、古い画像が残らないようにするためです。Iconify 公式の `@iconify/utils` は使いません（要る変換が「`<svg>` で包む」だけで、依存を増やす理由がないため）。
  - **ライセンス**: Apache 2.0 の条件（4(a)(b)）のため、公式の全文（`third_party/noto-emoji/LICENSE.txt`）に、元の著作権表示・出どころ・作り直した旨の見出しを付けて（`vite-plugins/notoEmoji.ts`）、画像と同じ場所（`/emoji/<版>/LICENSE.txt`）に出します。
  - **ない画像の URL**は、SPA のフォールバックで `index.html` が返り、`<img>` が失敗して、端末の絵文字になります（パッケージを古い版へ戻すと、その絵文字だけ、最長 1 年そうなる。受け入れる。**Why**: ない URL にだけ長いキャッシュを付けない安い手がなく、起きるのがまれなため）。
  - **画像のある key の一覧**は、画面の JS に入れます（gzip で約 12KB 増える）。**Why 遅延読み込みにしないか**: 題名を描くたびに同期で引くため、遅延だと題名がちらつく。
  - **絵文字の見つけ方**（`splitEmoji.ts`）: `Intl.Segmenter` で書記素に分け、絵文字として表示されるまとまりのうち、画像のある key のものだけを画像にします。ふつうは文字の記号（「#」「1」「©」「™」「↔」。`❤` は文字、`❤️` は絵文字）は、「会議 #1」が崩れるので、画像にしません。`Intl.Segmenter` がないブラウザ（Firefox 114〜124）では、端末の絵文字のまま出します（調整せずに動かす。[6.7](#67-同じ端末の複数のタブ) と同じ考え方。**Why**: 例外を投げると、アプリ全体が真っ白になるため）。
  - **表示**: `<img alt="元の絵文字">` にするので、コピーすると元の絵文字になります。読み込めなかったとき（電波がなく、まだ覚えていない画像）は、端末の絵文字に切り替えます。大きさは文字に合わせた 1.2em の正方形で、行の高さは変わりません。使うのは、予定とワークスペースの題名・名前を出すところです（祝日名・記念日名は使わない）。iPhone の画像長押しのメニューは出しません（予定を押す操作の邪魔になるため。Android に効くかは、[受け入れ確認の 2.6](../acceptance.md#26-日表示の操作感)で確かめる）。
  - **できないこと**: 入力欄の中の絵文字、Discord の通知の絵文字、国旗（`@iconify-json/noto` に画像がない。ユーザーが了承）は、端末や Discord 側の絵文字で表示されます。
- **はみ出た予定名は、「…」ではなく、右端を薄くして切ります**（月表示・日表示。ユーザーの要望）。文字の右の端（1em ぶん）が、透明に向かって薄くなります（`src/client/global.css` の `--fade-end`）。**Why**: 「…」が 1 文字ぶんの幅を取り、狭いマス（スマホで約 55px）では、見える文字がさらに減るため。
  - 対象は、月表示の時間指定の予定・横棒（祝日・記念日を含む）と、日表示の上部の欄（祝日・記念日を含む）・タイムラインの題名です。タイムラインの時刻と日表示の見出しの日付は、予定名ではないので、はみ出したら「…」のままです。
  - 薄くなるのは右の 1em だけなので、短い名前は薄くなりません。そこまで文字が届く名前は、はみ出していなくても、末尾が少し薄くなります（CSS だけでは、はみ出したかどうか分からないため）。背景（予定の色）まで薄くならないよう、`<button>` ではなく、中の `<span>` にかけます。

### 11.2 月表示（MV-1〜10）

```
┌──────────────────────────────────┐
│ ≡   2026年10月           [今日]  │ ← 固定のヘッダー（MV-5・MV-7）
│ 日   月   火   水   木   金   土  │
├──────────────────────────────────┤
│ 27   28   29   30 ┃1 10月 2   3  │ ← 月の境目は階段状の線（MV-3）
│ [祝日名]          ┃[帰省━━━━━━━]  │ ← 祝日・記念日と複数日の予定は横棒（HD-1・MV-9）
│ 15:00 歯医者      ┃ 9:00 会議     │
│━━━━━━━━━━━━━━━━━━━┛ +2件          │ ← 入りきらない分は「+2件」（MV-6）
│ 4    5    6    7    8    9   10   │
│ ...                              │
└──────────────────────────────────┘
                              ( + )  ← 新規作成ボタン
```

- **仮想スクロール**: 表示できる範囲は1900年1月〜2199年12月です（[Q2](#q2-スクロールできる範囲)）。最初は、今日の週が画面の上から2行目に来るようにします。**Why**: 先週の予定も少し見えるようにするため。
- **行の高さ**: 「だいたい6週間が見える高さ」を画面の高さから計算し、すべての行で同じにします（MV-6）。マスに入る予定の行数も、この高さから決めます。**Why**: 高さが揃っていれば、画面上の距離が日数に比例するため（成功の基準）。
- **階段状の線**: マスごとに線を引いて、つなげます（`src/client/month/boundaries.ts`）。年の境目（1月1〜7日）は、もっと太い線にします。日曜日の 1 日だけは、左側の線を引きません。**Why**: 日曜は行の左端で、引くと、画面の端に、その行だけ孤立した縦線が出るため。
- **固定ヘッダー**: ≡（サイドメニューを開く。[11.5](#115-サイドメニューws-14)）、年月、「今日」ボタン、曜日の見出しです。年月は、いちばん上に見えている週の水曜日の年月です（**Why**: 真ん中の水曜日が属する月が、その週の4日以上を占めるため）。「今日」ボタンは、今日の週を、上から 2 行目に戻します。日表示から戻ったときは、「今日」ではなく、出ていく前の位置を開きます（画面の大きさが変わって作り直すときも同じ）。**Why**: 遠い日付の日表示を見たあとで今日に戻ると、前の位置を探し直すことになるため。
- **1日のラベル**: 各月の1日のマスには「10月」、1月1日のマスには「2027年1月」と付けます（MV-5）。
- **予定の並べ方**: Googleカレンダーと同じです（MV-9）。(1) 複数日の予定と、祝日・記念日（横棒）、(2) 終日予定、(3) 時間指定の予定（時刻順）の順です。
- **タップしたとき**: 日付・空いているところ・「+2件」・祝日・記念日の横棒 → その日の日表示へ（MV-8）。予定（横棒・終日・時間指定。どれも `<button>`） → その回のフォーム（[11.4](#114-フォームev-14tb-12)）。祝日・記念日は、編集も削除もできないので、フォームは開かない。( + ) ボタン（画面の右下に浮かせる） → 新しい予定のフォーム。

細部:

- **週ごとの情報は、描く週の分だけ、4 週間のまとまりで計算して覚えます**（NF-6。全期間の 300 年分は計算しない）。`occurrencesInPeriod` と `namedDatesBetween`（`GET /api/occurrences` と同じ関数。[5.1](#51-エンドポイント)）で計算し、画面に出すデータ（`view`）の行か、マスに入る予定の行数が変わったときだけ捨てます（`src/client/stableRows.ts`）。**Why 変わったときだけか**: 同期のエンジンは、変更がなくても 60 秒ごとに `view` の参照を作り直すので、そのたびに計算し直すと、1 分ごとにスクロールが引っかかるため。送信待ちの依頼があるあいだは、やり直し（[6.4](#64-食い違ったときsy-3)）が行を新しく作るので、覚えが捨てられます（性能だけの話で、正しさは変わらない）。
- **タイムブロックは、展開の前に除きます**（MV-10）。**Why**: 毎日・平日の時間割は系列の数が多くなりやすく、展開して捨てるのが無駄なため（系列と例外の行の `kind` が同じなので、除いてよい。[4.5](#45-繰り返し予定の変更削除rp-4)）。表示が OFF のワークスペースの予定（WS-3）は、展開した回から除きます。**Why**: 別のワークスペースへ移した例外の行を先に除くと、その例外が抑えていた、元の系列の回が現れるため（[5.1](#51-エンドポイント)）。
- **予定の並べ方の細部**（MV-9）
  - 複数日の予定と、時間指定でも**日付をまたぐ予定**（23:00〜翌 1:00 など）は、横棒にします（回がかかる最後の日は `lastCoveredDate`。[7章](#7-繰り返しの展開)）。**Why**: 時間指定の 1 行にすると、どの日にかかっているかが分からないため。
  - 横棒は、週の行の中で、ほかの日と重ならない、いちばん上の行（レーン）に詰めます。順は、祝日 → 記念日 → 複数日の予定（先に始まる順。同じ日なら長い順）、そのあとに 1 日だけの終日の予定です。棒の行は、かかる日のすべてで同じで、動かしません。**Why**: 途中で動くと、1 本の棒に見えないため。祝日・記念日を、1 日だけの終日の予定より上にするのは、休みかどうかを先に知りたいためです（ユーザーの回答）。**前の日から続く複数日の横棒は、動かしません**。**Why not 祝日・記念日を、すべての横棒の先頭にする**: 棒の行は週の中で 1 つなので、祝日の日のために棒ごと 1 行下がり、ほかの日の上に空き行ができるため。
  - 時間指定の予定は、その日の横棒の下に、時刻順に並べます。**Why**: 横棒が通っていない上の行に入れると、「横棒、終日、時間指定」の並びが崩れるため。
  - 入りきらない日は、いちばん下の行を「+N件」にします。**N は、その日にかかる予定のうち、出せなかった数**です（横棒も、祝日・記念日の横棒も数える）。横棒が途中の日で出せないときは、棒がその日で切れ（切れた側の角は四角）、その日の N に数えます。
  - 色: 横棒と終日の予定は、ワークスペースの色の背景で、文字は、背景とのコントラスト比が大きい方（白か `#1F1F1F`）にします。時間指定の予定は、ワークスペースの色の小さな丸と、通常の文字色です。
- **祝日・記念日**は、終日の予定と同じ横棒で出します（HD-1・HD-2。ユーザーの要望と回答。「削除不可能にして」）。
  - **その日 1 マスの横棒**で、色は、組み込みのワークスペースの行の色です（行がまだ読み込まれていないときは、出さない）。**Why 色の既定値をコードに持たないか**: 色の決め場所を、ワークスペースの行の 1 か所にするため。祝日・記念日は、`namedDatesBetween` で計算して出し、行としては保存しません（[8章](#8-祝日記念日の計算)）。
  - 日付の横の名前は、出しません（同じことを 2 か所に出さないため）。**祝日の日付の数字の色は、残します**（祝日は祝日の色、日曜は赤、土曜は青。[Q5](#q5-日曜土曜の日付の色)。今日は丸）。**Why**: 横棒が「+N件」に隠れた日でも、休みだと一目で分かるため。組み込みの「祝日」が OFF なら、日付の色も付けません。
  - 表示の ON/OFF（WS-3・WS-4）は、組み込みのワークスペース「祝日」「記念日」ごとです。出せなかった分は、「+N件」の N に数えます。
  - 押すと、日付を押したのと同じで、日表示へ移ります（フォームは開かない）。`<button>` にせず、クリックは、下にある日付のマスのリンクに通します。**Why not `<Link>`**: フォーカスと読み上げが二重になる。**Why not 押しても何もしない `<button>`**: Tab で止まり、ボタンとして読み上げられるのに、何も起きない。
- **範囲（1900〜2199 年）の外の日**（最初の週の 1899-12-31 と、最後の週の 2200-01-01〜04）は、リンクにせず、1 日のラベルも、月と年の境目の線も付けません。日付の数字は、薄く出します。**Why**: 日表示へ移る先がなく、祝日の計算も対応していないため。範囲の中の日に始まる複数日の横棒は、外のマスまで伸びてよいですが、外の日には「+N件」を出しません（行き先がないため）。
- **読み上げ**: 日付のマスのリンクは「10月22日（木） 祝日名」、「+N件」は「10月22日（木）の予定、ほか 2 件」、予定のボタンは「10月22日（木） 15:00 歯医者」（複数日は開始日〜最後の日。`src/client/month/eventLabel.ts`）です。**Why**: 画面ではマスの位置で日付が分かるが、読み上げでは、それだけでは、いつの予定か分からないため。今日のマスには `aria-current="date"` を付けます。祝日・記念日の横棒と、曜日の見出しは、読み上げません（`aria-hidden`。**Why**: マスのリンクの読み上げと重複するため）。
- **スクロールバーは隠します**。**Why**: 数百年分の長さでは、つまみが位置の目安にならず、バーの幅のぶん、マスの幅が曜日の見出しとずれるため。
- **左右の外枠と、予定の文字の大きさ**（ユーザーの要望）。**左端（日曜）のマスにも、1px の左の線を引き、左右の外枠をそろえます**（外側の余白は付けない。左右とも、画面の端に 1px の枠線があるだけ。**Why**: 右端にだけ外枠があり、余白が右にだけあるように見えたため）。**予定の文字（時間指定の予定・横棒の題名。祝日・記念日を含む）は 10px** にします。日付の数字（12px）・月のラベル（11px）・「+N件」（12px）と、行の高さ（18px）は、変えません。**Why**: マスが 7 分の 1 の幅（スマホで約 55px）しかなく、12px では、予定名が数文字しか見えないため。10px は、12・11・10px の見比べから、ユーザーが選びました（11px では、3 文字の名前でも、最後の文字が右端の薄くなる部分にかかる）。
- **同期の状態の置き場所**（[6.5](#65-電波がない間の動き)）: 「未送信 N件」は、ヘッダーの「今日」ボタンの隣に置きます。読み込み中・読み込めませんでした（再試行のボタン）・別のタブで止めた、は、月表示の上端に重ねて出します（読み込めているときは、何も出さない）。ほかの知らせは、画面の下の列に出します。日表示にも、「未送信 N件」と、読み込みの状態を出します（[11.3](#113-日表示dv-16)）。**Why**: 月表示は、マスを隠さないことが大事で、状態は、問題があるときだけ小さく出すため。日表示にも出すのは、`/day/...` を直接開いて読み込みに失敗したとき、再試行のボタンがないと行き止まりになるため。
- **幅の狭い画面（約 640px 以下。スマホ）では、時間指定の予定の時刻と、1 月 1 日のラベルの年（「1月」だけになる）を省きます**（MV-9。ユーザーの回答）。**Why**: マスが約 55px しかなく、時刻や年で幅が埋まると、題名やラベルが読めないため。時刻は日表示で、年は固定ヘッダーで見られます。
- **画面の切り替え（URL）は、History API で手書きします**（[2章](#2-技術の選定)）。`/` が月表示、`/day/YYYY-MM-DD` が日表示です。日付の形が正しくない・存在しない日付・範囲の外・そのほかのパスは、月表示にして、URL も `/` に置き換えます。日付のマスは普通のリンク（`<a href>`）で、ふつうのクリックだけ、ページを読み込み直さずに移ります。日表示の［月表示］（`goToMonth`）は、この画面から移ってきたなら、ブラウザの「戻る」と同じにし、アドレスを直接開いたときは、月表示へ移ります。**Why**: 画面が 2 つだけで、ライブラリを足すほどの仕組みが要らず、依存とバンドルを増やさないため。
- **CSP の下での書き方**（日表示・サイドメニューも同じ。[10.3](#103-その他の対策)）: HTML の `style` 属性や `<style>` 要素は使いません。位置や高さ、ワークスペースの色のように、値が実行時に決まるものだけを、React の `style` プロパティ（CSP の対象外）で与え、それ以外は CSS Modules です。
- **スクロールの重さ**（NF-6）: `scrollTop` や `clientHeight` を、スクロールや描画のたびには読みません（読むたびにレイアウトをやり直す強制リフローで、フレームの時間を食うため）。位置は、仮想スクロールのライブラリが持っている値を、見える行が変わったとき・スクロールが始まった／止まったとき・画面が消えるときに覚えます（`src/client/month/scrollMemory.ts`）。画面が消えるときにも覚えるのは、スクロールの途中で日表示へ移ると、ずれるためです。

### 11.3 日表示（DV-1〜6）

```
┌──────────────────────────────────┐
│ ≡ [月表示] ‹ 2026年10月19日（月） › [今日]│ ← 前後の日へ（DV-5）
│                         未送信 N件 │ ← 中身がなければ、この行は高さ 0
│ [文化の日                     ]  │ ← 祝日・記念日（押せない。DV-6）
│ [帰省 10/18〜10/21            ]  │ ← 終日・複数日の予定（DV-6）
├──────────────────────────────────┤
│  8:00 │                          │
│  9:00 │┌仕事──────────┐          │ ← タイムブロック（1色）
│ 10:00 ││              │┌会議───┐ │ ← 重なりは横に並べる（DV-4）
│ 11:00 ││              │└───────┘ │
│  ...  │                          │
└──────────────────────────────────┘
                              ( + )
```

- **横の幅**: 上部の欄とタイムラインは、いちばん広くて 720px にし、それより広い画面では中央に置きます（ヘッダーは画面の幅いっぱいのまま）。**Why**: PC の広い画面で、予定が横に伸びすぎて見づらかったため（ユーザーの回答）。
- **1時間の高さ**: 60px（15分 = 15px）。**Why**: 15分刻み（DV-3）の予定でも、タイトルが1行読める高さを確保するため。
- **ヘッダーは 2 行**です。
  - 1 行目: 左端に ≡（[11.5](#115-サイドメニューws-14)）、［月表示］（ユーザーの回答）、‹（前の日）、日付、›（次の日）、右端に［今日］。日付は、年も出します（「2026年10月19日（月）」）。**Why**: 範囲が 300 年あり、年をまたいで動くと、年が分からなくなるため。幅の狭い画面（約 640px 以下。月表示の MV-9 と同じ境目）では、年を省きます（ユーザーの回答）。**Why**: スマホの幅 412px の 1 行目に、≡ が増えた分、年まで収まらないため。範囲（1900-01-01〜2199-12-31）の端では、‹ か › を押せなくします。日付の文字の色は、月表示と同じです（祝日と日曜は赤、土曜は青。祝日が土曜なら赤。組み込みの「祝日」が OFF なら赤を付けない。[11.2](#112-月表示mv-110)）。
  - 2 行目: 右端に、未送信の件数です。件数がないときは、この行は高さを持ちません。**Why**: スマホの幅では、1 行目に収まらないため。祝日名・記念日名は、ここには出しません（上部の欄に出す。同じことを 2 か所に出さないため）。読み込みの状態（`SyncOverview`）は、月表示と同じく、タイムラインの領域の上端に重ねます（[11.2](#112-月表示mv-110)）。
- **上部の欄**（DV-6）に出すのは、祝日・記念日と、終日の予定と、**長さが 24 時間以上**（ちょうど 24 時間も含む）の時間指定の予定（例: 金曜18:00〜日曜20:00）です。**Why**: タイムラインに入れると、画面全体がその予定で埋まるため（Googleカレンダーと同じ）。**タイムブロックは、長さによらず、ここに出しません**（タイムラインに出す。**Why**: 要件 TB-6 が、日付をまたぐタイムブロックを、前の日と次の日に分けて表示するとしているため）。
  - 予定は、1 件 1 行のボタンで、押すと、その回の編集フォームが開きます。色は、ワークスペースの色です（文字は、背景とのコントラスト比が大きい方）。中身は、題名（絵文字は画像。[11.1](#111-共通)）と、複数日なら期間（終日は「10/18〜10/21」、時間指定は「10/16 18:00〜10/18 20:00」。1 日だけの終日は、期間なし）です。
  - **祝日・記念日**（HD-1・HD-2。月表示と同じ。[11.2](#112-月表示mv-110)）は、欄の先頭に、祝日 → 記念日 → 予定の順で出します。**Why**: 休みかどうかを先に知りたいため。終日の予定と同じ形（題名・組み込みのワークスペースの色）で、期間は出しません。組み込みのワークスペースが OFF なら、出しません。押せない項目で（ボタンにしない。カーソルも、押したときの色の変化も付けない）、フォームは開きません。**Why not 押しても何もしない `<button>`**: Tab で止まり、ボタンとして読み上げられるのに、何も起きないため。
  - 高さは、約 3.5 行（94px）までで、超えたら、欄の中でスクロールします。日を動いたら、スクロール位置は、先頭に戻します。1 件もなければ、欄ごと出しません。**Why**: スマホで、上部の欄が長くなって、タイムラインが見えなくならないようにするため。4 行目を半分だけ見せるのは、続きがあることが分かるようにするため。
- **タイムライン**は、縦にスクロールする領域の中に、0:00〜24:00 を出します。左に、時刻の目盛り（「0:00」〜「24:00」）、各正時に線（`#3C4043`・1px）を引きます。末尾に余白を足して、( + ) ボタンの下に、23:00〜24:00 の項目が隠れないようにします。
  - 24:00 の線と目盛りも出します。**Why**: 23 時台の項目の終わりが、23:30 なのか 24:00 なのか、見て分からないため（ユーザーの要望）。目盛りの文字は、線の中央ではなく、線のすぐ下に置きます。**Why**: 中央だと、最初に表示する位置が正時のとき、その目盛りが、上端で半分切れるため。
  - 右に余白は付けません（項目は、画面の右端まで届く。ユーザーの回答）。スクロールバーは、細く出します（月表示は隠す。[11.2](#112-月表示mv-110)）。**Why**: 日表示は 1 日の長さなので、PC で、バーが位置の目安と操作に使えるため。
- **出す項目**は、同期のエンジンの行から、月表示と同じ関数（`occurrencesInPeriod`。[5.1](#51-エンドポイント)）で、その日にかかる回を求めます。祝日・記念日は、`namedDatesBetween` で計算して、上部の欄の先頭に足します。ヘッダーの日付を赤にするかは、その日が、表示が ON の祝日かどうか（`isHolidayShown`）で決めます。
  - タイムブロックは、ワークスペースの表示 ON/OFF によらず、常に出します（TB-3・TB-5・DV-2）。予定は、表示が ON で、削除されていないワークスペースのものだけで（WS-3）、展開した回から除きます（月表示と同じ Why。[11.2](#112-月表示mv-110)）。
  - 日をまたぐものは、その日の範囲（0:00〜24:00）に切り取ります（TB-6。23:00〜翌7:00 なら、前の日には 23:00〜24:00、次の日には 0:00〜7:00。3 日にわたるタイムブロックの真ん中の日は、0:00〜24:00）。終了が翌日の 0:00 ちょうどのものは、翌日には出ません（`lastCoveredDate`。[7章](#7-繰り返しの展開)）。
- **重なりの並べ方**（DV-4）: 時間が重なる予定をグループにまとめ、グループ内で左から順に空いている列に入れます。幅は「全体の幅 ÷ そのグループの列の数」です。Googleカレンダーと同じ方式で、予定とタイムブロックは同じ並べ方に入れます。終了と開始がちょうど接する項目は、重ならない扱いです（`src/client/day/layout.ts`）。**Why 列の数をグループごとに決めるか**: 全体を最大の重なりで割ると、離れた時間の項目まで細くなるため。
- **項目**は `<button>` で、押すと、その回の編集フォームが開きます。位置と高さは、時刻から決まる値のまま（1 分 = 1px）で、最小の高さは 15px（15 分）です。
  - 色は、予定がワークスペースの色、タイムブロックが `#3D4A5C`（文字は `#E3E3E3`）です。隣の項目と区別できるよう、右に 2px、下に 1px の隙間を空けます。
  - 中身は、題名（絵文字は画像。[11.1](#111-共通)）です。高さが 30px 以上なら、2 行目に時刻「9:00〜10:00」を出します。15 分（15px）の項目は、題名 1 行だけで、文字を小さくします。日をまたいで切り取った項目も、元の開始と終了の時刻を出します（前の日からの続きは「23:00〜7:00」）。長さが 24 時間以上の項目（タイムブロックだけ）は、日付も出します（「10/19 9:00〜10/21 18:00」）。**Why**: 時刻だけだと、「9:00〜9:00」が長さ 0 に、真ん中の日の「18:00〜20:00」が、その日の 18:00〜20:00 に見えるため。
  - 読み上げの名前は、時刻（日付）と題名です（「9:00〜10:00 題名」。タイムブロックは先頭に「タイムブロック」。上部の欄は「10/18〜10/21 終日 帰省」）。
- **今の時刻の線**は、**今日の日表示にだけ**出します（今日以外には「今」がないため。ユーザーの回答）。`#F28B82`（[11.1](#111-共通)）の 2px の横線で、左端に小さな丸を付けます。分が変わる瞬間に合わせて 1 分ごとと、タブが前面に戻ったときに、位置を更新します。**Why**: `setInterval` だと、動き出した時刻の端数のぶん、動きが最大 1 分遅れ、裏に回ったタブのタイマーは、ブラウザが遅らせるため。今日かどうかも、線と同じ時刻（分）で判定します（`useToday` のように 60 秒ごとに見る別の時刻だと、0:00 を迎えたとき、線が出るのが最大 1 分遅れるため）。
- **最初に表示する位置**: 今日なら「今の時刻の1時間前」から、他の日なら「その日のタイムラインの最初の項目」から表示します（項目がなければ 8:00）。上部の欄の項目は数えず、前の日から続く項目は、0:00 から始まるものとして数えます。**Why**: 開いたときに、いちばん見たいところがすぐ見えるようにするため。
  - 位置を決めるのは、日付が変わったとき（‹ ›・スワイプ・［今日］）と、`/day/...` を直接開いて、最初の読み込みが終わったとき（1 回だけ）です。読み込みが終わる前は、今日なら今の 1 時間前、他の日なら 8:00 に置き、終わったときに置き直します。同期でデータが変わっても、動かしません（見ている位置が、勝手に動くため）。描く前に決めます（描いたあとに動かすと、一瞬、0:00 が見えるため）。
  - ［今日］は、今日でなければ今日へ移り、今日を見ているなら、位置だけを今の 1 時間前へ動かします。
- **タップしたとき**:
  - 空いている時間 → その時刻（15分単位に切り下げ）から1時間のタイムブロックを作るフォーム。23:30 なら、翌日の 0:30 までです（TB-6）。時間軸（左の目盛り）は、押しても何も起きません。最初の読み込みが終わるまでは、何もしません（( + ) と同じ。[11.4](#114-フォームev-14tb-12)）。**Why タイムブロックか**: 日表示は時間割を立てる場所だから（TB-1。予定は ( + ) から作る）。**Why not キーボードで押せるようにする**: タイムライン全面を覆う 1 つのボタンにすると、読み上げで何のボタンか言えず、Tab で項目の間にも挟まるため。キーボードと読み上げからは、( + ) で、同じタイムブロックを作れます。
  - 予定・タイムブロック → その詳細（フォーム）
- **( + ) ボタン**は、タイムブロックのフォームを、**見ている日**の、今の時刻の次の正時から 1 時間で開きます（ちょうど正時のときも、その 1 時間後）。23 時台は、見ている日の 23:00 です。**Why 見ている日のままか**: 日表示は、その日の時間割を立てる場所なので（ユーザーに報告した決定）。**Why 23 時台を 23:00 にするか**: 0:00 にすると、今日を見ていて 23:20 に押したとき、タイムラインの反対の端（23 時間以上前）に作ってしまうため。
- **左右のスワイプ**（DV-5）: 横に指を動かすと、前後の日に移ります。**今は、アニメーションしません**（ユーザーの回答。後で、画面が指についてくる動きの演出を加える。[バックログ](../BACKLOG.md#画面の使い心地の改善)）。
  - 動き始め（8px 以上）の向きで、横か縦かを決め（同じ大きさなら縦）、途中で変えません。横に 60px 以上動いて指を離したら、左へ → 次の日、右へ → 前の日です（範囲の端では動かない）。マウスは対象にしません（PC は ‹ › のボタン）。**Why**: 斜めの指で、縦にスクロールしながら日が動いてしまわないため。縦のスクロールと拡大は、ブラウザに任せます。
  - 2 本目の指が触れたら、その操作は、スワイプにしません（拡大などの 2 本指の操作と取り違えるため。`src/client/day/swipe.ts`）。スワイプの直後の `click` は、空いているところのタップにしません（指を離した位置のものが、押されたことになるため）。ただし、キーボードから来た `click` は捨てません。
- **日から日へ動くときは、履歴を積みません**。‹ ›・スワイプ・［今日］は、`replaceDay`（`replaceState`）で今の履歴を置き換えます。［月表示］（`goToMonth`）は、何日動いたあとでも、月表示に戻ります。**Why**: 日ごとに履歴を積むと、［月表示］も、スマホの「戻る」も、月表示ではなく、前の日に戻ってしまうため。

### 11.4 フォーム（EV-1〜4・TB-1〜2）

```
┌──────────────────────────────────┐
│ ✕                        [保存]  │
│ ( 予定 | タイムブロック )         │ ← 種類の切り替え
│ タイトル ____________________    │
│ □ 終日                           │ ← 予定のときだけ
│ 開始 [2026/10/19] [15]:[00]      │
│ 終了 [2026/10/19] [16]:[00]      │
│ ワークスペース [仕事 ▼]          │ ← 予定のときだけ
│ 繰り返し [しない ▼]              │ ← 毎週のときは、下に曜日（日〜土）のトグル
│ 通知 [✓] [ 10 ] 分前             │ ← 終日は「当日 6:00」の表示だけ
│ 場所 ____________________        │
│ URL  ____________________        │
│ メモ ____________________        │
│                       [削除]     │
└──────────────────────────────────┘
```

画面に出す誤りなどの文言は、ここで決めたもののほかは `src/client/form/messages.ts` にあります。

- スマホでは下から出てくるシート、PC では画面中央のダイアログで表示します（幅の境目は月表示と同じ約 640px）。**Why**: スマホでは親指が届く下側に、PC では視線の中心に出すのが、操作しやすいため。
- **種類の初期値**（( + ) ボタンで開いたとき）: 月表示なら「予定」、日表示なら「タイムブロック」です。**Why**: 月表示は予定を並べる場所、日表示は時間割を立てる場所だから。種類の切り替えは、新しく作るときだけ出します（**Why**: 種類は作成した後に変えられないため。[4.5](#45-繰り返し予定の変更削除rp-4)）。切り替えたら、通知は、その種類の初期値（予定は ON・タイムブロックは OFF。NT-4）に戻し、タイムブロックでは終日を外します（**Why**: 戻さないと、切り替える順番で、初期値が変わるため）。
- **開始の初期値は、今日（日本時間）の次の正時、終了は 1 時間後**です（14:20 なら 15:00〜16:00、ちょうど 14:00 でも 15:00〜16:00、23 時台なら翌日の 0:00〜1:00）。**Why**: Google カレンダーと同じ動きで、開いてすぐ、これから使う時間帯になっているため。日表示から開くときは、日表示が開始を渡し（[11.3](#113-日表示dv-16)）、そこから 1 時間が初期値です。
- **ワークスペースの初期値**（EV-8）: 新しく作った予定を保存したときに選んでいたワークスペースを、端末の `localStorage` に覚え、次に予定を作るときの初期値にします。覚えたものが削除されていたら、並び順が最初のワークスペースにします（`localStorage` は、プライベートブラウズなどで例外を投げることがあるので、握りつぶす。覚えられなくても、予定は作れます）。**Why**: 新しく作ったときだけ覚えるのは、古い予定を編集して別のワークスペースに移しただけで、次の初期値が変わると紛らわしいため。DB ではなく端末に覚えるのは、入力を楽にする補助で、予定のデータそのものではなく、端末ごとに違っても困らないため。
  - 選択肢は、削除されていない利用者のワークスペース（組み込みの「祝日」「記念日」は、予定を入れられないので除く。WS-4）を、並び順で並べます。表示が OFF のものも選べます。
- **時刻の入力**: 「時」と「分（00・15・30・45）」の2つの選択欄にします。**Why**: ブラウザ標準の時刻入力は、iPhone では15分刻みの指定が効かないため（DV-3）。iPhone は対象から外れましたが、ほかの端末でも害がないので残します。**日付の入力**は、ブラウザ標準の日付入力に、`min`（1900-01-01）と `max`（2199-12-31）を付けます（[Q2](#q2-スクロールできる範囲)）。**Why**: スマホでは、OS の使い慣れた日付ピッカーが出るため。
- 終了の初期値は開始の1時間後で、開始を変えたら、長さを保ったまま終了も動かします。**Why**: Googleカレンダーと同じ動きで、開始を変えるたびに終了を直す手間がないため。開始の日付をキーボードで打つ途中は、終了を動かさず、打ち終わったときに動かします（途中の値が範囲の外になるため。途中で利用者が終了を直していたら、その直しを尊重する）。
- **終日 ⇔ 時間指定を切り替えたら、通知のタイミングは、その形の初期値（終日は当日の朝 6 時、時間指定は 10 分前）に戻します**（ON/OFF は変えません）。**Why**: 数の意味が違う（時間指定は「開始の何分前」、終日は「当日の 0:00 からの分」。[4.3](#43-各項目の決め方)）ので、そのままだと、終日の「朝 6 時 = -360」が、時間指定の「開始の 360 分後」になるため。時間指定にするとき、終了が開始より後にならなければ、開始の 1 時間後にします。終日にするとき、終了が翌日の 0:00 の時間指定（23:00〜翌 0:00 など）は、開始と同じ日の 1 日だけにします（終日の終了日は、その日を含むため。[7章](#7-繰り返しの展開)）。
- **通知のタイミング**:
  - **時間指定の予定とタイムブロック**は、「[ 10 ] 分前」の数の入力欄で、利用者が分を入力します。整数の 0〜10080 分で、0 は開始時刻です（上限は、サーバーの検証と同じ。[4.2](#42-テーブル定義)）。範囲の外のときは、入力欄の近くに誤りを出して、保存できません（入力の途中でも、すぐ出す。ユーザーの回答）。通知が OFF のときも、入力欄は出して、編集できます（薄く出す）。**Why**: 隠すと、入力欄の誤りが、見えないまま、保存を止めるため。
  - **終日の予定**は、入力欄を出さず、通知の ON/OFF だけにして、「当日 6:00」と表示します。保存する `notifyOffsetMin` は `-360` です（NT-3。[4.3](#43-各項目の決め方)）。
  - API から入った、通常は作れない値（`-360` でない終日の予定の時刻。時間指定の、開始より後の通知＝負の値。API は -1440 から通す）は、利用者が変えない限り、書き換えず、範囲の確認も通します。**Why**: 題名だけ直したいのに通知を直させる理由がなく、黙って書き換えると、フォームを開いて保存しただけで、通知の時刻が変わるため。「変えていない」は、分の数と、終日かどうかの両方が同じことです（終日と時間指定では、同じ数でも意味が違うため）。
- **繰り返しの欄**（RP-1・RP-3・RP-6。予定にもタイムブロックにも）: 選択欄は「しない／毎日／毎週／毎月／毎年／平日／休日」です。終わりの指定は出しません（RP-3）。
  - 毎週は、曜日（日〜土）を、トグルで複数選びます（1 つも選ばないと、保存できない誤り）。初期値は開始日の曜日で、選ぶまでは、開始日を変えたら曜日もついてきます。**Why**: 曜日が前の開始日のままだと、「最初の回は…」が意図しない日になるため。保存する曜日は、昇順にそろえます。**Why**: 並びの違いを「ルールを変えた」と見なさないため（[4.5](#45-繰り返し予定の変更削除rp-4)）。
  - 毎月は「毎月 N 日」、毎年は「毎年 M 月 D 日」と、基準の日付から作った説明を出します（[4.4](#44-繰り返しのルールrrule-列)）。N が 29〜31 なら「その日がない月は飛ばします」（RP-2）、2/29 の毎年なら「うるう年だけ」（[Q9](#q9-毎年の繰り返しで229-を選んだとき)）を添えます。平日・休日には、判定の決まり（土曜・日曜・祝日・年末年始は休日。記念日は休日ではない。RP-5）を添えます。基準の日付は、新しく作るときと、繰り返さない予定にルールを付けるときは開始日、すでに繰り返している予定でルールも開始日も変えていないときは、今のルールの基準の日（別の日に移した例外の回は、元の日付）です。
  - 開いた予定の欄には、**系列の行のルール**を出します（例外の回も）。送るのは、系列のルールと値が違うときだけです（曜日の並びだけの違いは、変えたことにしない）。**Why**: 変えていないルールまで送ると、開いてから送るまでの間に別の端末が変えたルールを、上書きするため。
  - 開始日がルールに合わないときは、保存するときに、ルールに合う最初の日へ、開始日がずれます（4.4）。**保存の前に**、「最初の回は 10月21日（水）になります」と出します（求めるのは shared の `normalizeStart`）。**Why**: ずらす計算を画面に書き写すと、片方だけを直して食い違い、画面が言った日と保存された日がずれるため。
  - ずらす途中で、日付が 1900〜2199 年を出るとき（例: 2199-12-31 の「平日」）は、サーバーも 400 にする（[4.2](#42-テーブル定義)・[5.1](#51-エンドポイント)）ので、繰り返しの欄に誤りを出して、保存しません。**Why**: 4xx の依頼は端末が捨てるので、保存した変更が、画面から消えるため（[6.2](#62-送る端末--サーバー)）。
  - **すでに繰り返している予定の、ルールか開始日を変えたとき**は、入力の段では、日付を含む説明（毎月 N 日など）と「最初の回は…」を出しません（平日・休日の判定は出す）。**Why**: 保存したあとの基準の日が、範囲によって違い、範囲を選ぶまで決まらないため。範囲ごとの説明は、範囲を聞く段で出します（下）。
- **繰り返し予定を保存・削除するときは、「この予定のみ／これ以降すべて／すべて」を選ぶ段を出します**（RP-4）。繰り返さない予定（ルールを付けて繰り返す予定にする場合も含む。[4.5](#45-繰り返し予定の変更削除rp-4)）と、何も変えずに保存したときは、聞きません。
  - **選べる範囲は、画面に決まりを書き写さず、shared の `changeEntry`（削除なら `deleteEntry`）を、手元の行に、範囲ごとに実際に当てて決めます**（`src/client/form/scope.ts`）。投げた範囲と、項目をまたぐ確認に合わない範囲は、選べません。**Why**: サーバーも、同じ関数と同じ確認で受け付けるかを決めるので、フォームで選べた範囲が、サーバーで 4xx になることはない（4xx は、保存した変更が画面から消える。6.2）。決まりを書き写すと、片方だけを直して食い違うため。
  - 結果として、ルールを変えたら、「この予定のみ」は出しません。変更後のルールが毎日・平日・休日で、日付を変えたら、「この予定のみ」だけを出します。**Why**: 例外の行はルールを持てず、これらのルールは日付をずらせないため。最初の回の「これ以降すべて」は、「すべて」と同じ（系列を切らない）なので、選べます。範囲は、「この予定のみ／これ以降すべて／すべて」の順に出し、1 つだけでも、聞きます（**Why**: 何が起きるかを、利用者が確かめられるようにするため）。初期の選択は、出したもののうち最初です。
  - 開いている回が、もうない（ほかの端末で変更・削除された）ときは、その旨を出して、保存しません。繰り返さない予定にも、同じ関数を予定全体で当てて、もうないことを見つけます（聞かずに送ると、サーバーが黙って捨てるため）。
  - ルールを毎日・平日・休日に変えて、日付も同時に変えたときは、どの範囲も受け付けられないので、「繰り返しを毎日・平日・休日に変えるときは、日付を同時に変えられません。片方ずつ保存してください」と出して、保存しません（ユーザーの回答）。**Why**: 選べる範囲が 1 つもない画面を出すより、理由と直し方を伝えて止める方が、行き止まりにならないため。この理由にするのは、日付の変更を外すと選べる範囲があるときだけです（ほかの理由で選べないとき、「同時の変更」のせいにしないため）。ほかの理由で、どの範囲も選べないときは、「この組み合わせの変更は保存できません」と出します（まれなので、専用の文言は出さない）。
- **範囲を聞く段**は、フォームのダイアログの中身を差し替えて出します（ラジオボタンと［保存］［戻る］。削除なら［削除］［戻る］）。ダイアログを入れ子にはしません。**Why**: 入れ子にすると、下の、履歴を積む仕組み（スマホの「戻る」で閉じる）や、Esc・「戻る」の扱いが増えるため。
  - ［戻る］は、入力した値を保ったまま、フォームに戻ります（フォーカスは、段を出したボタンへ）。Esc と、スマホの「戻る」は、この段でも、フォームごと閉じます（保存しない。**Why**: 段ごとに履歴を積まないため）。
  - 範囲の名前の下に、何が起きるかを 1 行で添えます。ルールか開始日を変えたときは、さらに、**範囲ごとに、保存したあとの系列の説明**（例: 「保存後: 毎月 5 日（最初の回は 1月5日（月））」。「すべて」と「これ以降すべて」だけ）を、その範囲で実際に当てた結果から作って出します。**Why**: 範囲ごとの基準の日とずらし方を、画面に書き写すと、サーバーの結果と食い違うため。
  - 範囲を選んで［保存］［削除］を押したとき、もう一度、手元の行で選べる範囲を決め、選んだ範囲が、まだ選べるときだけ送ります。**Why**: 範囲を聞く段を開いている間に、ほかの端末の変更が届くことがあり、そのまま送ると、サーバーが「捨てた」にするか、400 にするため（[6.2](#62-送る端末--サーバー)）。選べなくなったときは、入力の段に戻り（入力は残る）、理由を出します。
- **入力の確認**は、サーバーと同じ決まり（`shared` の入力のスキーマと、項目をまたぐ確認。[4.2](#42-テーブル定義)）で、保存の前に行い、日本語の誤りを欄の近くに出します。**Why**: 通らない本文は、エンジンが例外を投げ、通ってもサーバーが 400 で断ると、保存した変更が画面から消える（[6.2](#62-送る端末--サーバー)）ため。開始・終了の誤りと、通知の分の誤りは、入力の途中でも、すぐ出します。**ほかの誤りは、保存を押したあと**に出します（開いた直後の空のタイトルに、誤りを出さないため）。誤りがあれば、いちばん上の誤りの欄にフォーカスを移します。空白だけのタイトルは、空と同じ誤りにします（**Why**: サーバーは通すが、月表示で、何も書いていない予定になるため）。
- **保存**は、新しく作るときは下書きを、編集は、変えた項目だけを送ります（[4.5](#45-繰り返し予定の変更削除rp-4)）。ただし、通知の分は、終日を切り替えたときも、元と同じ数でも、終了日は、開始日を変えたときも、送ります。**Why**: 分の意味が違う（4.3）ので、フォームの値をはっきり送るため。終了日は、開始日だけだと、サーバーが終了日を同じ日数だけずらして長さを保ち（4.5）、フォームで終了を別の長さに直していたとき、その直しが消えるため。
  - 何も変えていないなら、何も送らずに閉じます。**Why**: 送ると、行の編集時刻と rev だけが進み、他の端末が受け取り直すため。
  - エンジンが受け付けないとき（読み込み前・別のタブで止めたとき）や、想定外の例外が起きたときは、フォームを閉じずに、理由を出します。**Why**: 閉じると、入力が失われ、例外を握りつぶして閉じると、保存したつもりで保存されないため。
  - 場所・URL・メモは、空なら `null`、入力があれば、前後の空白も含めて、そのまま保存します。URL の欄は `type="url"` にしません。**Why**: ブラウザが、前後の空白を黙って取り除き、入力した値と保存する値が食い違うため。
- **場所**があれば、横に地図へのリンク（[4.3](#43-各項目の決め方)）を、**URL** が http(s) で、サーバーの検証を通るなら、開くリンクを出します。どちらも、新しいタブ（`rel="noopener noreferrer"`）で開きます。
- **削除**: 確認は出さず（繰り返しの予定は、範囲を聞く段のあと）、フォームを閉じて、画面の下の列（[6.5](#65-電波がない間の動き)）に「削除しました［元に戻す］」を、`DELETE_UNDO_MS`（5 秒）の間、出します（OT-1。[6.6](#66-削除の元に戻すot-1)）。続けて削除したときは、知らせを並べて、それぞれ 5 秒を数えます（**Why**: 1 つに置き換えると、前の削除を、元に戻せなくなるため）。すでに送り始めていて戻せなかったときは、「元に戻せませんでした」に変えて、少しして消します。
- **( + ) ボタン**（月表示の右下。[11.2](#112-月表示mv-110)）は、最初の読み込みが終わるまでは、押せません。**Why**: 終わる前に開くと、ワークスペースの選択肢がなく、保存してもエンジンが受け付けないので、入力してから失敗するより、先に押せなくするため。
- **フォームを開いたら、ブラウザの履歴を 1 つ積み、スマホの「戻る」で閉じます**（URL は変えません）。✕・保存・削除・Esc・背景を押して閉じたときも、積んだ履歴を戻します。**Why**: 積まないと、フォームを開いたまま「戻る」を押したとき、月表示から出てしまい（[2章](#2-技術の選定)）、閉じるときに戻さないと、開閉のたびに履歴が残るため。URL を変えないのは、入力の途中を URL にしても、開き直したときに復元できず、共有もしないため。再読み込みなどで履歴の印だけが残ったときも、履歴を 1 つ戻します。履歴の出し入れは、サイドメニューと共通の部品（`src/client/historyMark.ts`）です（[11.5](#115-サイドメニューws-14)）。
- **ネイティブの `<dialog>`（`showModal()`）**を使います。**Why**: フォーカスの閉じ込め・Esc で閉じる・背景を操作できなくする、が、追加の部品なしで手に入るため。Esc は、✕ と同じ閉じ方です（保存しない。確認も出さない）。新しく作るときは、タイトルの欄にフォーカスを置き、閉じたときは、開く前にフォーカスがあった要素に戻ります。
  - **背景（外側の暗いところ。スマホではシートの上、PC では中央のダイアログの外側）を押したときも、✕ と同じ閉じ方にします**（保存しない。確認も出さない）。フォームのどの段（範囲を聞く段を含む）でも同じです。**Why**: ユーザーの要望（2026-10-29）。背景を押すと、入力の途中でも、入力は失われます（✕ を押したときと同じ）。
    - 押し始めた位置も、背景のときだけ閉じます。**Why**: 入力欄で文字を選ぶ途中に、指（マウス）が背景にはみ出して離したとき、閉じて入力を失わないため。続けて押した 2 回目以降の click（`event.detail` が 2 以上）では、閉じません。**Why**: ( + ) や予定をダブルクリックすると、1 回目で開いたフォームの背景に、2 回目が当たって、すぐ閉じるため。
    - PC で、時刻の一覧（`<select>`）や日付の選択画面を開いたまま背景を押したとき、フォームまで閉じるかは、手元では確かめきれませんでした。ユーザーの実機（PC の Vivaldi）で確かめます（[受け入れ確認 2.15](../acceptance.md#215-フォームの外側を押して閉じるpcスマホ)）。判定は、サイドメニュー・予定のフォーム・ワークスペースの編集の 3 つで同じなので、共通の部品（`src/client/backdropClose.ts`）です。
- **予定をタップ**（横棒・終日・時間指定）すると、その回のフォームが開きます。タイムブロックは、月表示に出ないので、日表示（[11.3](#113-日表示dv-16)）から開きます。

### 11.5 サイドメニュー（WS-1〜4）

```
┌──────────────┐
│ メニュー   ✕ │ ← 左から重ねて出す。幅は 300px まで
│ ワークスペース│
│ ☑ ● 予定     │ ← チェックボックス（表示 ON/OFF）・色の丸・名前
│ ☑ ● 仕事     │
│ ☑ ● 趣味     │
│ 祝日・記念日  │
│ ☑ ● 祝日     │
│ ☑ ● 記念日   │
│ [ワークスペースを編集] │
└──────────────┘
```

- ヘッダーの左端の ≡ で開きます（月表示・日表示のどちらにも付く。[11.2](#112-月表示mv-110)・[11.3](#113-日表示dv-16)）。中身は、ワークスペースの一覧（チェックボックスで表示 ON/OFF）、祝日・記念日（チェックボックス）、「ワークスペースを編集」（名前・色・並び順・追加・削除）です。
- 最初のワークスペース「予定」は、画面が作らず、マイグレーションで固定の id の行として最初から入れます（[4.2](#42-テーブル定義)の「Why マイグレーションで入れるのか」）。
- 最後の1つは削除できないようにします。**Why**: 予定はワークスペースに必ず属する（EV-2）ので、1つもないと予定を作れなくなるため。

ユーザーの回答で決めたこと（いずれも推奨どおり）:

- サイドメニューは、PC もスマホも、≡ を押すと左から重ねて出す（ドロワー）。背景を押す・スマホの「戻る」・Esc で閉じる。**Why**: PC だけ常に出すと、月表示のマスが狭くなり、画面の作りも 2 通りになるため。
- ワークスペースの編集は、［ワークスペースを編集］で、編集用のダイアログ（予定のフォームと同じ形）を開く。中身は、利用者のワークスペースの一覧、並び順を変える［↑］［↓］、［＋ ワークスペースを追加］。行を押すと、同じダイアログの中身が、名前・色・削除の欄に切り替わる（入れ子のダイアログにしない）。削除の前に「中の予定 N 件も削除されます」と確認し（[Q6](#q6-ワークスペースを削除したときの中の予定)）、削除したら、予定と同じく「元に戻す」を 5 秒出す（[6.6](#66-削除の元に戻すot-1)）。**Why ドラッグにしないか**: 3 個くらいなら ↑↓ で足り、タッチの処理を作らずに済むため。
- 画面では、色を、[11.1](#111-共通) の 8 色からだけ選べる。サーバー（API）は、'#RRGGBB' の形だけを確かめる（API とスキーマは変えない）。API から 8 色以外の色が入ったワークスペースは、編集画面で、その色を「今の色」として 9 つ目の見本に出し、選び直さなければ、そのまま保存する。**Why**: API はユーザー専用で、サーバーで絞る必要が小さく、組み込みの「祝日」「記念日」が 8 色以外の色を持つので、絞ると例外が要るため。API から入った値は、表示だけして、勝手に書き換えない（[11.4](#114-フォームev-14tb-12) の、通知の時刻と同じ）。

*サイドメニュー*

- **ネイティブの `<dialog>`（`showModal()`）**で、左から重ねて出します（幅は 300px まで）。背景は暗くし、押すと閉じます（押し始めた位置も、背景のときだけ。予定のフォーム・ワークスペースの編集も同じ。[11.4](#114-フォームev-14tb-12)）。**✕ のボタンも置きます**。**Why**: フォーカスの閉じ込め・Esc・背景の操作の禁止が、追加の部品なしで手に入るため。✕ は、Esc のないタッチ操作や読み上げで、閉じる方法を、目に見える形で示すため。
- **2 つの節**に分けます。「ワークスペース」は、削除されていない、組み込みでないワークスペースを、予定のフォームの選択肢（[11.4](#114-フォームev-14tb-12)）と同じ並び（`sortOrder`。同じなら id の順）で出します。「祝日・記念日」は、組み込みの 2 行（祝日・記念日の順）です。各行は、チェックボックス・色の丸・名前（絵文字は画像。長い名前は、後ろを「…」で省く。[11.1](#111-共通)）です。**Why 並びを同じ関数で決めるか**: メニューとフォームで並びが食い違うと、同じワークスペースを別の順に探すことになるため。
- **表示の ON/OFF は、チェックを変えたら、すぐ保存します**（[Q3](#q3-ワークスペースの表示-onoff-をどこに保存するか)。DB に保存して、全端末で共通）。組み込みの「祝日」「記念日」も同じです（API は、組み込みの行の `visible` の変更を許す。[4.2](#42-テーブル定義)）。
- **最初の読み込みが終わるまでは、チェックボックスと［ワークスペースを編集］を押せません**（一覧がなく、エンジンも受け付けない。≡ は押せる）。読み込み中・読み込めなかった・別のタブで止めた、のときは、一覧の上に、その理由を出します（月表示・日表示の上端の読み込みの表示 `SyncOverview` と同じ文言。`src/client/sync/phaseNotice.ts` の 1 か所から取る。[6.5](#65-電波がない間の動き)）。**Why**: 理由を出さないと、読み込みの前に止まったとき「読み込み中…」のままに見え、押せない理由が分からないため。読み込みの前は、見出しだけの節は出しません（読み込めていて 0 個なら、「ワークスペースがありません」）。

*履歴（スマホの「戻る」）*

- サイドメニューを開いたら、ブラウザの履歴を 1 つ積み、スマホの「戻る」で閉じます。✕・Esc・背景を押して閉じたときも、積んだ履歴を戻します。再読み込みなどで印だけが残ったときも、履歴を 1 つ戻します（予定のフォームと同じ。URL は変えない。[11.4](#114-フォームev-14tb-12)）。
- 仕組みは、予定のフォームと共通の部品（`src/client/historyMark.ts`）で、**印の名前を分けます**（フォームは `form`、サイドメニューは `sidebar`）。**Why**: 同じ印にすると、フォームが閉じるとき、サイドメニューが積んだ履歴を戻してしまうため（逆も同じ）。
- **メニューから編集へ移るときは、履歴を積み直さず、メニューの履歴を、そのまま引き継ぎます**。**Why**: `history.back()` は非同期で、戻りきる前に履歴を積むと、履歴と画面の状態が食い違うため。
- **どの段にいても、Esc・✕・背景を押す・スマホの「戻る」は、全部を閉じます**。段の中の［戻る］は、一つ前の段に戻ります。**Why**: 段ごとに履歴を積まないため（予定のフォームの、範囲を聞く段と同じ）。

*ワークスペースの編集*（詳しい判定は `src/client/sidebar/workspaceEdit.ts`）

- 見た目の枠は、予定のフォームと同じです（スマホは下から出るシート、PC は中央のダイアログ）。Esc と、背景を押したときも、✕ と同じ閉じ方です（どの段でも、全部を閉じる。保存しない。[11.4](#114-フォームev-14tb-12)）。**Why**: 枠が同じなので、片方だけ背景を押しても閉じないと、迷うため（ユーザーの回答。2026-10-29）。
- **段 1（一覧）**: 利用者のワークスペースを、サイドメニューと同じ並びで出します。各行は、色の丸・名前（押すと段 2）・［↑］［↓］です（いちばん上の［↑］と、いちばん下の［↓］は押せない）。下に［＋ ワークスペースを追加］（押すと、空の段 2）があります。
  - **並べ替え**は、並びを入れ替えたあと、利用者のワークスペースの `sortOrder` を、並びの順に 0, 1, 2… に振り直し、値が変わった行だけを保存します（組み込みの行は変えない）。**Why**: 2 行の値を入れ替えるだけだと、同じ値の行があるとき（API から入れたときなど）、並びが変わらないため。動かしたあとは、同じ行の同じボタン（端で押せなくなったら、反対のボタン）にフォーカスを戻します。
- **段 2（名前と色）**: 名前の入力欄、色の見本（ラジオボタン）、［削除］（新しく作るときは出さない）・［戻る］（入力を捨てて段 1 へ）・［保存］（保存して段 1 へ）です。
  - **名前**は必須です。前後の空白を除いて空なら「名前を入れてください」、上限（`INPUT_LIMITS.workspaceName`。[4.2](#42-テーブル定義)）を超えたら、その文字数を添えて、誤りにします（保存を押したあとに出す）。保存する値は、前後の空白を除いたものです。同じ名前のワークスペースは、作れます（サーバーも許し、色で見分けるため。WS-2）。
  - **色**は、[11.1](#111-共通) の 8 色の見本です（読み上げの名前は色の名前）。選んでいる色は、色に頼らず、見本のまわりの輪で示します。「今の色」（開いたときの色）が 8 色にない場合は、上のとおりです（選び直したあとも、その色に戻せる）。16 進の大文字・小文字は区別せず、8 色の同じ色と見なします（サーバーは小文字の `#e57373` も通すため）。
  - **既存の行を［保存］するときは、同期のエンジンの view の最新の行を土台にして、開いたときの値から変えた項目（名前・色）だけを、入力した値で上書きして送ります**（`workspaceToSave`）。**Why**: ワークスペースは行全体を put するので、開いたときの行を土台にすると、段 2 を開いている間に、ほかの端末が変えた、触っていない項目（表示の ON/OFF・並び順など）まで、戻してしまうため（予定のフォームは、変えた項目だけを `changes` で送る。[11.4](#114-フォームev-14tb-12)）。
    - 名前も色も変えていなければ、何も送らず、段 1 に戻ります（**Why**: 送ると、行の編集時刻と rev だけが進み、他の端末が受け取り直すため）。最新の行がない（ほかの端末で削除された）ときも、何も送らず、段 1 に戻って、その旨を出します（**Why**: サーバーは、削除済みのワークスペースの更新を、生き返らせずに黙って捨てる（[5.1](#51-エンドポイント)）ので、保存したつもりで保存されないため）。
  - **新しく作るとき**: 色の初期値は、8 色のうち、削除されていない利用者のワークスペースが、まだ使っていない、最初の色です（全部使っていれば、トマト）。**Why**: 色でワークスペースを見分けるため（WS-2）。`sortOrder` は、今のいちばん大きい値 + 1（いちばん下）、`visible` は ON、`builtin` は `NULL`、id は端末で作る UUID（[4.3](#43-各項目の決め方)）です。名前の欄にフォーカスを置きます（既存の行を開いたときは、スマホでキーボードが出ないよう、見出しに置く）。
  - エンジンが受け付けないとき（読み込み前・別のタブで止めたとき）は、段を変えずに、理由を出します（予定のフォームと同じ）。
- **段 3（削除の確認）**: 「『仕事』を削除します。中の予定 N 件も削除されます。」と、［削除］［戻る］です（N が 0 なら、「中の予定」の文は出さない。［戻る］は段 2 へ、入力は保つ）。
  - **N の数え方**: 削除されていない行のうち、`seriesId` が `NULL`（繰り返さない予定と、繰り返しの系列。例外の行は数えない）で、そのワークスペースのものです。**Why**: 利用者が作った予定の数（繰り返しは 1 件）に合わせるため。別の系列から「この予定のみ」で移した回は数えませんが、まれなので、正確さより、単純さを取ります。
  - **最後の 1 つ**（削除されていない、組み込みでない行が 1 つだけ）は、段 2 の［削除］を押せなくし、「最後の 1 つは削除できません」と添えます。確認の段を開いている間に、ほかの端末の変更で最後の 1 つになったときは、送る前に、もう一度確かめて、段 2 に戻します。**Why**: サーバーは 400 にし、端末は 4xx の依頼を捨てる（保存した変更が画面から消える。[6.2](#62-送る端末--サーバー)）ため。
  - 削除したら、段 1 に戻り、「削除しました［元に戻す］」を、`DELETE_UNDO_MS`（5 秒）の間、**ダイアログの中に**出します（[6.6](#66-削除の元に戻すot-1)）。**Why**: 画面の下の列（[6.5](#65-電波がない間の動き)）は、モーダルが開いている間、押せないため。同じ知らせが、背景の下に押せない形で重ならないよう、編集のダイアログが開いている間は、列の側は出さず、閉じたら、残りの時間のぶん、列の側に出します。

## 付録A. 運用

### A.1 データの復元（OT-2）

誤操作でデータを消したときは、D1 の Time Travel で過去7日間の任意の時点に戻します。画面は作らず、コマンドで行います。

```sh
# 1. 戻したい時刻を指定して復元する
npx wrangler d1 time-travel restore atara-calendar --timestamp=2026-10-19T12:00:00+09:00
# 2. 端末に全データの読み込み直しをさせるため、epoch を変える
npx wrangler d1 execute atara-calendar --remote --command "UPDATE meta SET epoch = lower(hex(randomblob(8)))"
```

- **Why 2の手順が必要なのか**: 復元すると、通し番号（rev）も過去に戻り、端末が「rev 500 まで受け取った」と覚えていると、復元後の rev 450〜500 の変更を受け取れないため。`GET /api/changes` は毎回 epoch を返し、端末は覚えている値と違えば全データを読み込み直します。

### A.2 無料枠の見積もり（NF-1）

| 項目 | 無料枠 | 見込み |
| --- | --- | --- |
| Worker のリクエスト | 1日10万回（[公式](https://developers.cloudflare.com/workers/platform/limits)） | 定期実行 1,440回 ＋ 同期・編集 数百回 ＝ 1日2,000回程度 |
| 静的ファイルの配信 | 無料・無制限（[公式](https://developers.cloudflare.com/workers/platform/pricing/)） | 画面の HTML・JS・CSS はここに入る |
| CPU 時間 | 1回10ms（DB の待ち時間は含まない） | 定期実行は、時刻が来た行を、1 回に最大 10 行処理する（実測は [9.3](#93-定期実行で送る実装-11b)）。保存のときの通知の時刻の計算も、系列を展開する（実測は [9.2](#92-保存したときの計算実装-11a)） |
| D1 の読み取り | 1日500万行 | 起動時の全件読み込み（数千行 × 1日10回程度）が中心で、数万行程度 |
| D1 の書き込み | 1日10万行 | 編集と通知の更新で、1日数百行程度 |

### A.3 壊れた行が見つかったとき

`GET /api/changes` が、行の構造が壊れていて失敗するときの直し方です（[6.3](#63-受け取るサーバー--端末)）。直すまで、全端末の同期が止まり、画面の下に、[6.5](#65-電波がない間の動き)の知らせ（「サーバーとのやり取りに失敗しています（HTTP 500）」）が出ます。

1. Worker のログ（`npx wrangler tail`、または Cloudflare のダッシュボード）で、`CorruptRowError` の表名と id を探す。
2. `wrangler d1 execute` で、その行を見て、直すか消す。

```sh
npx wrangler d1 execute atara-calendar --remote --command "SELECT * FROM entries WHERE id = '<ログの id>'"
# 値を直すとき
npx wrangler d1 execute atara-calendar --remote --command "UPDATE entries SET start_date = '2026-10-19' WHERE id = '<ログの id>'"
# 消すとき
npx wrangler d1 execute atara-calendar --remote --command "DELETE FROM entries WHERE id = '<ログの id>'"
```

- 直す値は、`entrySchema`・`workspaceSchema` を満たすこと（時刻は 15 分刻み、色は `#RRGGBB` など）。**Why**: 読み込みは行の構造だけを確かめる（[6.3](#63-受け取るサーバー--端末)）ので、満たさない値でも読めますが、その行を書き直す依頼（削除を含む）は、書き込みの確認（[4.2](#42-テーブル定義)）で毎回 500 になり、端末の送信待ちが止まるためです。
- 定期実行（[9.3](#93-定期実行で送る実装-11b)）も、壊れた行を読むと例外になります。その行の `next_notify_at` が進まないので、毎分、ログに `通知の処理に失敗しました（行の id: …）` が出ます（壊れた行そのものの表名と id は、同じ時刻の `entries の行が壊れています（id: …）` に出ます）。直し方は上の手順 2 と同じです。**Why**: 毎分のログで、壊れた行に気づけるようにするため。直すまで、その行（と、その系列の行）の通知は届きません。

### A.4 デプロイ（本番への反映）

main に取り込まれると、GitHub Actions（`.github/workflows/ci.yml` の `deploy`）が本番に反映します（[12章](#12-確認事項すべて推奨どおりで確定)の Q7）。

1. 確認（`check`: 型・Lint・書式・テスト・ビルド）が通ったときだけ動く。
2. main の最新のコミットでなければ、エラーにして止める。
   - **Why**: `deploy` が concurrency のグループに入るのは `check` が終わった時点なので、順番が「`check` が終わった順」になり、古いコミットが後から本番を上書きすることがあるため（古い実行の Re-run も同じ）。
3. `wrangler d1 migrations apply --remote` で、テーブルの変更（マイグレーション）を先に当てる。
   - **Why 先に当てるのか**: 新しいコードが、新しいテーブルの形を前提にできるようにするためです。
4. `wrangler deploy` で、画面と Worker を入れ替える。

- デプロイは1つずつ動かします（`concurrency`。同時に2つ動かないようにするため。順番は上の2で守ります）。
- リポジトリの変数 `DEPLOY_ENABLED` が `true` のときだけ動きます。本番の下準備（[docs/setup.md](../setup.md)）が終わるまでは動かさないためです。
- 手で動かすときは、GitHub の **Actions → CI → Run workflow**（main を選ぶ）。
- main の最新の実行の `deploy` が cancelled か失敗になっていたら、Run workflow で main を動かします。
  - **Why**: デプロイ中に、古いコミットの実行が待ちに入ると、GitHub は待っていた最新の実行を取り消し、その古い実行は、上の2の確認で止まるので、本番が最新にならないまま残ることがあるため。
- 本番のデータを元に戻せない形で変えるマイグレーションは、マージの前にユーザーに確認します（CLAUDE.md の「PR とコミット」）。

#### 認証情報とログの扱い

このリポジトリは public で、Actions のログは誰でも読めます。そのため、次のようにします（手順は [docs/setup.md](../setup.md) の 4.2）。

- デプロイ用の Secret（`CLOUDFLARE_API_TOKEN`・`CLOUDFLARE_ACCOUNT_ID`）は、リポジトリの Secret ではなく、GitHub の環境 `production`（Deployment branches を `main` だけにする）に置きます。
  - **Why**: リポジトリの Secret は、PR の CI でも読め、PR の側でワークフローを書き換えれば、レビュー前のコードがトークンを使えてしまうため。main だけが使える環境なら、main に入ったコードからしか読めません。
- Secret は、`wrangler d1 migrations apply` と `wrangler deploy` のステップにだけ渡します（ジョブ全体の `env` にしない）。
  - **Why**: `npm ci`（依存パッケージのインストールスクリプト）や build にトークンを渡さず、依存パッケージが乗っ取られたときに盗まれる範囲を狭めるためです。
- ログのメールアドレスは、`deploy` の最初のステップで伏せ字にします。伏せ字の元には、環境の Secret `CLOUDFLARE_ACCOUNT_EMAIL`（Cloudflare にログインするメールアドレス。トークンの持ち主）を使います。Worker の Secret `ALLOWED_EMAIL`（Access で許可する Gmail）とは別のもので、Cloudflare の表記と同じ大文字小文字で登録します。
  - **Why**: wrangler は、認証エラーのとき、自動で `whoami` を実行して、トークンの持ち主のメールアドレスをログに出し、誰でもログを読めるため。Access で許可する Gmail とは限らないので、`ALLOWED_EMAIL` では代わりになりません。

#### マイグレーションの書き方と、戻し方

- マイグレーションは、**1つ前のコードでも動く形**にします。列を消す・名前を変えるときは、PR を2回に分けます（1回目で、コードを新しい形に移す。名前を変えるなら、新しい名前の列を足す。2回目で、使わなくなった列を消す）。
  - **Why**: マイグレーションを当ててからコードを入れ替えるまでの間と、デプロイが失敗したときは、古いコードが新しいテーブルで動くためです。
- 戻すときは、Squash したコミットを revert します。次のデプロイで、コードが戻ります。
  - ふつうは、コードの revert だけでよいです。マイグレーションを1つ前のコードでも動く形にしているので、テーブルが新しい形のままでも、戻した古いコードが動きます。
  - テーブルの変更そのものを戻す必要があるときだけ、[A.1](#a1-データの復元ot-2) の Time Travel を使います（マイグレーションは前に進めるだけで、revert ではテーブルは戻らないため）。Time Travel はデータベース全体を戻すので、その時刻より後の編集はすべて消えます。
  - 順番は、次のとおりです。
    1. revert をデプロイする（マイグレーションのファイルもなくなる）
    2. Time Travel で戻す
    3. A.1 の手順を行う（epoch の更新など。内容は A.1 を見る）
  - **Why この順番なのか**: 新しいコードが動いたまま Time Travel をすると、古いテーブルで壊れ、Time Travel の後にデプロイすると、マイグレーションの記録も戻っているので、ファイルが残っていれば、戻したはずのマイグレーションがもう一度当たるため。

#### ログ

- Workers Logs を有効にしています（`wrangler.jsonc` の `observability`）。
  - **Why**: [A.3](#a3-壊れた行が見つかったとき) の「ダッシュボードで探す」を成り立たせるため。
