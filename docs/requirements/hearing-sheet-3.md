## K. 構成と認証（L1・L2 の続き） ★★

- **K1. アプリ全体を Cloudflare に載せる（Vercel は使わない）** ★★
  - a. 画面も API も DB も Cloudflare（Workers ＋ D1）にまとめる ★推奨
  - b. 画面と API は Vercel、DB だけ Cloudflare D1
  - Why 推奨:
    1. D1 にいちばん素直にアクセスできるのは、Cloudflare Workers の中からです。Vercel から使う場合は Cloudflare の REST API を経由することになり、通信が1回増えて遅くなります。さらに、強い権限を持つ API トークンを Vercel に置く必要があります。
    2. 通知の定期実行（Cron Triggers）も Cloudflare Workers でやる予定なので、全部を1か所にまとめると管理する場所が1つで済みます。
    3. 無料枠の範囲で収まる見込みです（下の「無料枠の確認」を参照）。
- **K2. ログインは Cloudflare Access（Zero Trust）＋ Googleアカウント** ★★
  - a. Cloudflare Access で `ataraman.com` のカレンダー用サブドメイン全体を守る。ログインは Google。許可するのは自分の Google アカウントだけ ★推奨
  - b. アプリ自体にログイン機能を作る（Googleログインを自前で実装する）
  - Why 推奨:
    1. 2次ヒアリングで Zero Trust をおすすめしなかったのは、「Supabase の API がインターネットに直接公開されていて、Zero Trust では守れない」ことが理由でした。DB が D1 になると、DB には Workers の中からしかアクセスできなくなります。なので、入口（ドメイン）を Access で守れば全部を守れます。つまり、最初に考えていた案がいちばん簡単になります。
    2. ログインのコードを自分で書かずに済むので、セキュリティの穴を作りにくくなります。
    3. 後で作る MCP サーバー（Claude Code / Desktop から使う）は、Access の「サービストークン」（機械用の ID とパスワード）で通せます。ローカルで動くので OAuth もいりません（[Cloudflare公式](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/)）。
    4. 通知の定期実行は Cloudflare の内部で動くので、Access に邪魔されません。
  - 注意: Access のログイン状態の有効期限（例: 1週間、1か月）は設定で選べます。切れると Google でログインし直しになります。どのくらいがいいですか？（★推奨: 1か月。Why: 自分専用なので頻繁にログインし直すのは面倒だからです。Google アカウント自体の2段階認証で十分守れます）

### 無料枠の確認（K1・K2 の根拠）

| サービス | 無料枠 | このアプリでの見込み |
| --- | --- | --- |
| D1（DB） | 1つのDBにつき500MB、1日に500万行の読み取り・10万行の書き込み（[公式](https://developers.cloudflare.com/d1/platform/limits)） | 予定データは数MB程度の見込み。1分ごとの通知チェックを入れても、1日の読み取りは数万行程度 |
| D1 の復元（Time Travel） | 過去7日間の任意の時点に戻せる（同上） | D4「自動バックアップ」の代わりになる（K6 で確認） |
| Workers の定期実行（Cron Triggers） | **アカウント全体で5個まで**（[公式](https://developers.cloudflare.com/workers/platform/limits)） | このアプリでは1個使う（K4 で確認） |
| Cloudflare Access | 50ユーザーまで無料（[Cloudflare blog](https://blog.cloudflare.com/teams-plans)） | 自分1人 |

- 月額はドメイン代を除いて **0円** の見込みです。
- ※ Access の無料枠（50ユーザー）は2020年の発表が根拠です。Google ログインとサービストークンが無料プランで使えるかは、公式資料では確認しきれませんでした。セットアップのときに管理画面で確かめます。

- **K3. `ataraman.com` の DNS は Cloudflare で管理している？**
  - a. している
  - b. していない（他社で管理している）
  - Why 聞くか: Cloudflare Access で守ったり、Workers を独自ドメインで公開したりするには、そのドメインの DNS が Cloudflare で管理されている必要があるからです。
- **K4. Cloudflare アカウントで、すでに使っている Cron Triggers（定期実行）はいくつ？**
  - Why 聞くか: 無料プランではアカウント全体で5個までです。すでに5個使っていると、通知を送る仕組みを考え直す必要があります。わからなければ「わからない」で大丈夫です（ダッシュボードの Workers の各設定で確認できます）。
- **K5. ドメインの綴り**: 回答では `calender.ataraman.com` でした。英語の正しい綴りは **calendar**（ar で終わる）です。
  - a. `calendar.ataraman.com` に直す ★推奨
  - b. `calender` のままでいい（わざとそうしている）
  - Why 推奨: 綴りを間違えたURLは、打つたびに迷う原因になるからです。
- **K6. バックアップ（D4）**
  - a. D1 の Time Travel（過去7日間の時点に戻せる）で十分 ★推奨
  - b. それとは別に、定期的に外部へバックアップを取りたい
  - Why 推奨: 自分専用のアプリで心配なのは「操作ミスで消してしまった」ことで、7日あれば気づいて戻せます。b にすると Cron Triggers をもう1個使い、保存先も必要になります。

## R. 繰り返し（R2 の続き）

- **R3. 「平日」「休日」の定義**
  - 平日 = 月〜金のうち、祝日（振替休日・国民の休日を含む）ではない日
  - 休日 = 土・日・祝日（振替休日・国民の休日を含む）
  - 記念日・行事（H1 の母の日など）は休日に**含めない**
  - a. この定義でいい ★推奨
  - b. 違う（どこが違うか教えてください）
  - Why 推奨: 「休日（祝日を含む）」という回答から、平日はその反対だと考えました。
- **R4. 年末年始やお盆を休日として扱う？**
  - a. 扱わない（法律で決まった休日だけ） ★推奨
  - b. 年末年始（12/29〜1/3）は休日にする
  - c. 自分で休日を追加できるようにしたい
  - Why 推奨: 年末年始やお盆の休みは職場によって違います。一律に決めると、かえってズレる可能性があるからです。必要になったら c を後から追加できます。

> 技術メモ: 「平日」「休日」で繰り返すには、何年先でも祝日がわかっている必要があります。ところが春分の日・秋分の日は、前年の2月にならないと正式に決まりません。そこで、遠い未来の祝日は法律のルールと計算式で求めておき、正式に発表されたら置き換える方針にします。

## H. 記念日・行事（H1 の続き）

- **H2. 表示する記念日・行事の一覧**（いらないものを消して、足したいものがあれば足してください）
  - 節分 / バレンタインデー / ひな祭り / ホワイトデー / 母の日 / 父の日 / 七夕 / ハロウィン / クリスマスイブ / クリスマス / 大晦日
  - ★推奨: この一覧で始めて、後から足したり消したりできるようにする
- **H3. 祝日と記念日の見分け方**
  - a. 祝日は日付を赤くして名前も出す。記念日は名前だけを控えめな色で出す ★推奨
  - b. その他（希望があれば教えてください）
  - Why 推奨: 休みかどうかが一目でわかることがいちばん大事です。そのため、赤い日付で区別するという、日本のカレンダーで一般的な表し方に合わせました。
- **H4. 記念日も、祝日とは別のワークスペースとして ON/OFF したい？**
  - a. したい（祝日と記念日を別々に ON/OFF） ★推奨
  - b. 祝日と記念日はまとめて ON/OFF でいい
  - Why 推奨: 祝日は常に表示しておき、記念日だけ消したい、という使い方ができるようにするためです。

## G. タイムブロック（G の続き）

- **G9. タイムブロックもワークスペースに属する？**
  - a. 属する（色やワークスペースごとの表示 ON/OFF が予定と同じように効く） ★推奨
  - b. 属さない（タイムブロックは別扱い）
  - Why 推奨: 「仕事の時間割だけ表示する」といった切り替えが予定と同じ操作でできて、色のルールも1つで済むからです。

## E. その他

- **E13. 削除の取り消し**
  - a. 削除した直後に数秒間「元に戻す」ボタンを出す ★推奨
  - b. 不要（削除前に確認ダイアログを出すだけ）
  - Why 推奨: 毎回確認ダイアログが出ると操作のテンポが悪くなります。それでいて、確認を流れ作業で押してしまうので、誤操作は防げません。「元に戻す」なら操作は速いまま、ミスにも対応できます。
- **E14. 今の Googleカレンダーの予定を移す？**
  - a. 移さない（新しく入れ直す）
  - b. MCP サーバーができたら、Claude に移してもらう（Googleカレンダーの MCP で読んで、こちらの MCP で書き込む） ★推奨
  - c. 最初のバージョンから、移す仕組みが欲しい
  - Why 推奨: 外部連携（X）は全部「不要」だったので、移すためだけに読み込み機能を作るのは割に合いません。後で作る MCP を使えば、追加のコードなしで移せます。

## 前提（違っていたら教えてください）

2次ヒアリングの前提に加えて、以下のように進めます。

1. 月表示のマス目の表示は Googleカレンダーと同じにする
   - 時間を指定した予定は「15:00 歯医者」のように表示する
   - 複数日にまたがる予定は、マスをまたぐ横棒で表示する
2. 日表示では、左右にスワイプ（PCでは矢印ボタン）で前後の日に移動する
3. 朝6時の通知時刻（N7）は、設定画面で全体の時刻を1つ変えられるようにする（予定ごとには変えない）
4. Discord の Webhook URL は、コードに書かずに Cloudflare の秘密の設定（Secrets）に保存する
5. MCP で削除を許可しても（M3）、Claude Code / Desktop 側でツールを実行する前に確認が出るので、それを誤操作の防止策とする
6. O2 で「開き直したときの表示は不要」としたので、電波がない状態でタブが読み込み直されると表示できない（この挙動は受け入れる）
